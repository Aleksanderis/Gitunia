# Testing

## Principles

- Test where the risk is: parsing git output, graph layout, destructive operations, worktree handling, key handling, and rendering regressions. Plain wiring gets no tests.
- Real `git` against real temporary repos for the Git layer. No mocking the process runner except for timeout/cancellation/error-path tests.
- State and keymap logic is pure and tested without a terminal.
- No test touches the user's repos, global git config or network. Isolation recipe, naming, waiting rules and fixture shapes are in the `testing` skill. A runner for production code under test comes from `IsolatedGit.CreateRunner()` (or `TestRepository.CreateIsolatedRunner()`), never `new GitRunner()`: the machine's global git config (e.g. `core.autocrlf=true` on Windows CI) must not leak in (#608).
- Process spawns dominate test time on Windows (#624): the suite starts ~6,200 git processes in `Git.Tests` and ~11,700 in `Tui.Tests` (counted once on one Windows 11 machine, not a budget). Test runners therefore get `TestGitSpeed`: the real `mingw64\bin\git.exe` instead of the `cmd\git.exe` shim (which starts it as a second process), and `gc.auto=0`, `maintenance.auto=false` and `core.fsync=none` (without them every commit starts a `git maintenance run --auto` child). New fixtures that build a runner use it; keep the number of git calls per fixture low.
- Tests run in parallel and git children inherit the process environment: never change process-wide environment variables in a test, except in the `AmbientEnvironmentGroup` collection (runs alone), or concurrent git runs flake (#299).
- Parallelism: `tests/xunit.runner.json` (copied into every test project by `tests/Directory.Build.props`) caps xUnit at 8 threads per assembly, parallel across test classes (collections). xUnit has no method-level parallelism: split a slow class instead. `dotnet test` on the root solution also runs the test assemblies concurrently; on a single csproj or dll it cannot. On a CPU-bound machine that concurrency buys no wall time and only lengthens every git call: with the CPU limited to 2 logical CPUs (`start /affinity 3`), the suite took 402 s concurrent and 432 s one project at a time, but `Git.Tests` alone dropped from 6 m 27 s to 2 m 43 s (#634). The Windows CI leg therefore runs the projects one after another and stops at the first failing one. Capping xUnit threads (2 instead of 8) changed nothing measurable. Test git runners get a 2-minute default timeout (`TestGitSpeed.Timeout`; production keeps 30 s) and waits for background events are generous (30-60 s: a passing test never waits that long); do not write a test whose pass depends on a timeout below ~1 s.
- No unbounded waits: a blocking wait or gate in a test or fake carries a timeout (30 s), because `TestContext.Current.CancellationToken` only fires when the run ends. `Gitunia.Tui.Tests` also has a 10-minute run watchdog (`RunWatchdog`) that aborts a hung testhost (it cannot help if the stuck process is the `dotnet test` driver; #384)). The Linux CI test step adds `--blame-hang-timeout 10m` (names a hung test) and a 10-minute step timeout (covers a host that died with no test running; #666). A callback that signals a test from a background thread uses `TestSignal`, not a disposed `SemaphoreSlim`: a late `Release` on a disposed semaphore throws on a pool thread and can end the host.
- A failing test blocks merge. No coverage percentage gate.

## Layers

| Layer | Tools | Covers |
|---|---|---|
| Git parsers | xUnit, captured output fixtures | Every parser incl. odd cases (renames, unicode, detached, unborn, in-progress ops) |
| Git integration | xUnit, temp repos (see `testing` skill) | Commands end to end: branches, worktrees, stash, merge/rebase, partial staging |
| Tui loading and effects | xUnit; fakes of the reader interfaces (`tests/Gitunia.Tui.Tests/Fakes`, wired by `FakeGitServices`) where git is not the subject, real temp repos (`TestGit.Services`) where it is (watchers, refresh, effect runner; each test class says which tests stay real and why) | Stores, pollers and loaders without a process per test; the wiring against real git |
| Graph layout | xUnit, property tests | Lane assignment invariants, determinism, incremental == full |
| State/keymap | xUnit | Command -> state transitions, modal behaviour, no binding conflicts (test reads the keymap table) |
| Rendering | snapshot tests of frames as text (`ScreenComposer`; `gitunia <repo> --print-frame WxH [--diff] [--zoom <pane>] [--tab details\|changes\|files] [--colors truecolor\|16\|none [--light]]` prints the same frame, with ANSI colours when asked) | Layout at several terminal sizes, wide chars, ASCII fallback; `MainViewTests` builds the Terminal.Gui `MainView` without a terminal and checks view-level settings the text frames cannot show (the detail list's panel scheme, which colours its blank cells) |
| Startup smoke | `StartupSmokeTests` runs `TuiApplication.Run` on Terminal.Gui's headless `ansi` driver (`DriverName`, `ExitAfterFirstIteration`, `FrameCaptured`, `HomeDirectory`) with temp config/state dirs, once with a repository and once with none (picker) | The whole shell is constructed the way `Program.Main` does and its first frame is drawn (forced inside the first loop iteration, then the loop stops; the test asserts the screen text has the `NORMAL` status bar and the history pane, or the empty-picker text), so a draw-time fault fails the test; a constructor-order crash (null field, `_keys` used before it exists: #519, #401) fails `dotnet test`. It cannot see rendering or key handling: UI issues also get a tmux run of the real binary |
| AOT smoke | CI script | AOT publish succeeds with no `IL*` warnings; binary starts and renders a frame against a fixture repo |
| Manual | checklist | Real terminals (kitty, alacritty, Windows Terminal, tmux), credential prompts, huge repos; mouse: the Terminal.Gui views (`PaneListView`, `PickerView`) have no headless test, so check click, double-click and wheel in tmux by sending SGR sequences (`tmux send-keys -l $'\e[<0;X;YM\e[<0;X;Ym'`, wheel is button 64/65; a drag is the press `0;X;Y` + `M`, one or more moves `32;X;Y` + `M`, then the release `0;X;Y` + `m`) or with a real mouse; the pure parts (`DragTracker`, `PaneResizer`, the button layouts, `VisualRangeController`) are unit-tested |

Windows interactive runs: tmux does not exist natively, so drive the real `gitunia.exe` with psmux, which accepts the same `new-session`/`send-keys`/`capture-pane` commands (evaluated in #65; syntax differences and caveats in the `testing` skill, "Driving the real binary"). Snapshot and smoke tests stay the gate; psmux is for ad-hoc checks of Windows-only bugs.

Windows runs only the OS-sensitive tests (#637): every test class marked `[Trait("Os", "Independent")]` (pure logic on in-memory data, proven by Linux) is excluded there with `--filter "Os!=Independent"`, and Linux runs all. The default is the safe side: an unmarked test runs on Windows, so a forgotten mark costs minutes, never coverage. `OsTraitGuardTests` (Core.Tests) fails if a marked file uses real git, paths, the file system, processes or the environment, and if Git.Tests or Platform.Tests carry the mark. Counted with `--list-tests` (theory rows counted), Windows selects 4,080 of 5,028 tests (Core 1,102 of 1,552, Platform 49 of 49, Git 809 of 809, Tui 2,120 of 2,618). The 85 marked classes were picked by a conservative source scan, so more can be marked later; the saving is mostly in test count, the slow real-git tests stay. The count drifts as tests are added: recount with `dotnet test <project> --no-build --list-tests --filter "Os!=Independent"`. Author rules: `testing` skill, "Mark OS-independent tests".

CI (`.github/workflows/ci.yml`) runs build, test, AOT publish and the smoke run on linux-x64 and windows-x64 on release tags (`v*`) and manual dispatch (`gh workflow run ci.yml`): never on PRs or branch pushes. Local `dotnet build` and `dotnet test` are the gate; dispatch CI before closing a milestone or cutting a release. Tests that need Linux-only file names (`*`, `:` or a tab) or shell-script fakes skip themselves on Windows. The macOS leg is a separate M5 issue. Why (free-plan minutes): `decisions.md` and `docs/history/testing.md`.

Agents verify locally first (`dotnet build`, `dotnet test`, AOT publish when dependencies or projects changed, `scripts/inspect.sh --changed`), open the PR ready and push once. Code-only PRs rely on the build-time AOT analyzers until the pre-release run. After merging, if another PR merged since the last push, run `dotnet build && dotnet test` on updated `main`.

A change to `ci.yml` that moves build or output paths (e.g. `ArtifactsPath` on the Windows leg) is tried locally first with the same environment variables (`UseArtifactsOutput=true`, `ArtifactsPath=<dir outside the repo>`, then `dotnet test`); tests must not assume the binaries sit inside the repo (#663).

## Performance checks

A benchmark (BenchmarkDotNet, not part of the normal test run) for graph load and layout on a generated 100k-commit repo. Record numbers in `docs/performance.md` when targets are verified.

### Big repo

`scripts/gen-big-repo.sh [dir] [commits]` builds a deterministic repo with `git fast-import` (default 100000 commits, ~5-10 s, linear `main` with a merged 4-commit feature branch every 40 commits, 24 kept branches, a tag per 5000 commits, commit-graph written). Default location `${GITUNIA_BIG_REPO:-${XDG_CACHE_HOME:-~/.cache}/gitunia/big-<commits>}`; it is generated on demand, never committed, and re-running is a no-op. Subjects are `Commit #<n>: ...` / `Merge feature f<k>`, so the newest and oldest commit are recognizable on screen. Linux/macOS only (bash, awk).

### Measurement harness

`scripts/measure.sh <binary> <repo> [--runs N] [--keys N] [--marker T] [--oldest T] [--size WxH] [--only-start]` runs the binary as `<binary> <repo>` in a private tmux server and prints `key=value` lines. Requires bash >= 5 and tmux on Linux/macOS. On Windows use `scripts/measure.ps1 <binary> <repo> [-Runs N] [-Keys N] [-Marker T] [-Oldest T] [-Size WxH] [-OnlyStart]` (PowerShell 7 and psmux, same metrics and output; each poll costs ~50 ms, so its numbers are comparable only with other `measure.ps1` runs). The binary runs with a private `XDG_STATE_HOME`/`XDG_CONFIG_HOME` (on Linux and, in the `.ps1` twins, Windows), so a restored session of the real user (extra tabs, saved scroll position) cannot change the frame or the RSS; macOS state under `~/Library` is not isolated. Timings are wall-clock ms from polling `capture-pane`, so they carry a 1-3 ms polling floor; compare binaries with the same harness rather than reading them as absolute.

`scripts/measure-tabs.sh <binary> [--tabs N] [--commits N] [--runs N] [--size WxH]` measures a session restore: it builds N throwaway repos and a `session.json` under a temp `XDG_STATE_HOME`/`HOME` (nothing real is touched), runs the binary without arguments and prints cold start, RSS (active tab only, all tabs visited) and tab-switch times. Same tmux requirements and polling floor; `scripts/measure-tabs.ps1 <binary> [-Tabs N] [-Commits N] [-Runs N] [-Size WxH]` is the psmux twin for Windows; its RSS is the Windows working set, only loosely comparable with Linux RSS. `screenshot.sh` has no Windows port yet (#606).

What the harness expects of the binary:

- Invoked as `<binary> <repo-path>`; renders in the alternate screen, fills the terminal.
- First frame shows the commit list with the newest commit subject (HEAD's subject, from `git log -1 --format=%s`) as text. "Cold start" = tmux `new-session` until that text is on screen.
- Keys: `j`/`k` move the selection, `Ctrl-d` half page down, `G` last commit, `gg` first commit. Each must change the rendered frame (a moved highlight counts, since captures keep escape sequences). Jumping to the end must show the oldest commit's subject; `gg` the newest.
- It must re-render on terminal resize (the harness resizes and expects the marker again).
- Binaries that can't do all of this still work with `--only-start --marker <text>`.

Metrics: `binary_bytes`, `cold_start_ms_{median,p95,max}`, `key_latency_ms_{median,p95,max}` (`j` to changed frame), `page_scroll_ms_*` (`Ctrl-d`), `details_step_ms_{median,p95,max}` and `details_burst_10j_ms` (#215: `j` until the details pane header shows another commit and no "Loading..." is left, with 300 ms between steps / 10 `j` in one burst; needs the details pane in its default layout), `diff_step_ms_{median,p95,max}` (#225: `j` until the diff pane beside the Changes file list shows another commit: its title hash changed, no "Loading..." and a hunk header is on screen; 300 ms between steps), `burst_200j_settle_ms` (200 queued `j` until the frame stops changing), `jump_to_end_ms` (`G` after the log finished streaming; the harness waits for the `+` in `n/total+` to vanish, because `G` goes to the last loaded commit), `jump_to_start_ms`, `resize_ms` (frame changes after a window shrink and still shows the newest subject), `rss_kib`. `nan` means the expected frame never appeared within `--timeout`. Each poll costs a tmux round trip, so expect a few ms of floor on every latency figure; run a trivial reference program to calibrate on your machine. `cold_start_samples` and `key_samples` report how many samples produced numbers.
