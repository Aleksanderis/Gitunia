# Decisions

Log of settled choices that cut across docs. Agents follow these without asking. Open questions live in `roadmap.md`. Format: `decision. Why.` Entries are grouped under a date heading, newest date last. The 2026-10-10 entries are the baseline and may be reworded in place. Once the M0 decision (#7) is closed the log is append-only: when a decision changes, add a new entry that supersedes the old one and don't edit history.

## 2026-10-10

- C# on .NET with Native AOT (Rust is the runner-up). Why: the owner is a .NET developer doing heavy agentic development, so the code must stay reviewable by them. Revisit only if the M0 spike shows the rendering layer is a time sink.
- Git access via the `git` CLI, not libgit2. Why: matches the user's real config, hooks, credentials and new git features such as worktrees.
- Standalone multi-repo client (tabs, picker, session restore), not bound to the current directory. Why: retrofitting multi-repo later is expensive, so the Git API is repo-scoped from the start.
- Cross-platform from day one (Linux first; Windows and macOS later, macOS lowest priority and droppable). Platform-specific code only behind a platform abstraction.
- Minimum git 2.43, `net10.0`, JSON config with source generation, MIT licence, product/binary name `gitunia`, config under the platform config dir `gitunia`. Why: LTS on current distros; AOT-safe; defaults accepted by the owner.
- Fourth project `Gitunia.Platform` (config/state dirs, console capability detection) referenced by Git and Tui; Core stays free of OS code. Why: issue #1 requires the platform abstraction in one place and Core must not touch the console or process. SDK pinned to 10.0.400 with `rollForward: latestFeature`; test projects use xUnit v3; test method names may contain underscores (CA1707 off under `tests/`).
- External tools: hand the terminal to `$EDITOR`/difftool/mergetool by suspending and resuming the TUI; clipboard via OSC 52. No built-in text editor (staging works on hunks and lines in the diff view).
- Other open-source Git clients are sources of ideas, never of copied code. Why: licence hygiene.
- Spikes live on unmerged `spike/` branches and close with findings. Issues labeled `destructive` or `needs-review` are merged by the owner; agents continue with other unblocked issues meanwhile.
- PRs are merged with a merge commit (never squash or rebase) and the branch is deleted afterwards. Why: the owner wants the full branch history and topology visible in the graph.
- Renderer: Terminal.Gui v2 (2.5.0), not a custom renderer (decision #7, owner chose after reviewing the spikes). Why: the custom renderer code was judged far harder to read and maintain than toolkit widgets, and Terminal.Gui is fast enough. Accepted costs: startup near the 100 ms budget, larger binary and memory, a native library beside the binary, modal keys/chords hand-rolled at the application level (no modal keymap in the toolkit), custom drawing for the commit graph. Spike data (Linux x64, 100k-commit repo, `scripts/measure.sh` medians incl. 1-3 ms tmux polling):
  - List-only spike, Terminal.Gui vs custom: binary 9.47 MB + 564 KB native lib vs 2.56 MB; cold start ~97 ms vs ~28 ms; `j` latency ~34 ms vs ~4.8 ms; RSS ~50 MB vs ~33 MB.
  - Heavier M1-like screen (sidebar, graph, details, status) at 120x40: Terminal.Gui cold start ~107 ms, `j` ~34 ms, RSS ~71 MB; custom 24 ms, 7.4 ms, 35 MB.
  - Both AOT-clean on Linux and Windows (win-x64 smoke under ConPTY in CI passed 8/8 for Terminal.Gui, 10/10 for custom).
- Terminal.Gui settings and pitfalls: set `Application.MaximumIterationsPerSecond` to ~100 (default 25 gave ~34 ms key latency; 100 gives ~13 ms and cold start ~85 ms at ~2.6% idle CPU; higher values busy-spin a core). Use an append-only `IListDataSource` for streamed commits (`SetSource(ObservableCollection)` rescans per add and freezes input). The focused `ListView` swallows keys, so handle keys at the application level (`app.Keyboard.KeyDown`). `TextView` is obsolete in 2.5.0 (a separate package replaces it); check its AOT status before M2 commit-message input.
- Standalone launch (spike #3) findings for M1: resolve paths with `git -C <path> rev-parse`; check `--is-bare-repository` before `--show-toplevel`; a linked worktree has `--git-dir` != `--git-common-dir`; dedupe tabs by the resolved toplevel; a path inside a `.git` directory needs its own case. Resolving costs 0-2 ms.
- The renderer stays swappable, but only Terminal.Gui is built and maintained. The custom renderer lives in `src/Gitunia.CustomRenderTui` (cell buffer with diff flush, VT input parser, raw terminal for Linux/macOS/Windows) with a runnable demo in `samples/Gitunia.CustomRenderTui.Demo`, tests, and a manual-only Windows ConPTY smoke workflow. It is not actively maintained: not referenced by the app, features are not mirrored into it, and it is only kept building and tested in CI as a future option. It may rot; a revival starts with its README's 'missing' list. The spike branches were deleted once this landed; spike numbers stay in the issue comments and the renderer entry above. What this requires of the main code: Terminal.Gui types stay in the rendering project, the state layer exposes renderer-agnostic view models and key events as data, keymap handling is our own engine, and no renderer abstraction interface is added until a second renderer is revived. If the boundary starts to cost features, tell the owner.

## 2026-10-11

- The Terminal.Gui spike (#4 heavy screen) is preserved as a reference sample in `samples/Gitunia.TerminalGuiSpike` (also tagged `archive/spike-4-terminal-gui-heavy`); not referenced by the app and not maintained. Use it as a starting point for the M1 UI, rewritten against the state layer.
- Terminal.Gui look experiment (merged into that sample): the custom demo's look (header bar, tab row, dimmed hashes, lane colours, status hints) is achievable in Terminal.Gui with ~160 extra lines and no hard limits found. Minor limits: border title glyphs are fixed (workaround: overlay view), `ListView` has no per-row styling (custom `IListDataSource.Render`), colour-depth fallback unverified, wide chars and mouse untested. Measured on the 100k repo at 100 iterations/s: 120x40 cold start ~58 ms, `j` ~8-10 ms, RSS ~75 MB; 200x60 cold start ~98 ms, `j` ~20 ms (custom demo: 16 ms, ~4 ms, ~31-36 MB, flat with screen size). The renderer choice (Terminal.Gui vs CustomRenderTui) is still open for the owner to reconsider; M1 does not start UI work until it is settled.
- Code conventions (from the PR #60 review), recorded in `CLAUDE.md`: no truncated names (`platform`, not `p`; `selection`, not `sel`), one type per file (models and logic in separate files, unless related or inherited), scripts live in `scripts/` for both bash and PowerShell, tmux-based interactive testing is Linux/macOS only.
- Renderer confirmed by the owner: Terminal.Gui. This supersedes the 'still open for the owner to reconsider' note and the 'M1 does not start UI work until it is settled' gate above; UI work in M1 may start. Key style for M1 (#8): agents draft the first iteration following common vim, yazi and lazygit patterns; the owner reviews it in use and adjusts later, so keep the keymap data-driven.
- M1 key design (#8, first iteration, owner adjusts after use): both `Tab` cycling and `Ctrl-w` + direction move pane focus; frequent actions are per-view single keys with a `<space>` leader for global ones; chords show a which-key popup after 500 ms and never time out; Insert mode swallows printable keys so chords cannot fire while typing. Patterns followed: vim (motions, counts, `gt`/`gT`, `]c`/`[c`, `Ctrl-w`), lazygit (per-pane focus, `/` filter, `Enter` drills in), yazi (`h`/`l` collapse/enter, `Alt-` combos in inputs). Closes the pane focus and key style open questions.
- Commit ids are a fixed 40-byte `ObjectId` struct (SHA-1 or SHA-256) instead of interned hash strings (#13). Why: no intern table or string per parent link, equality and hashing without allocation. Cost: 40 bytes per id even for SHA-1 (about 12 bytes padding); per-commit memory is still dominated by `CommitInfo`, its subject string and decorations. Author names and emails are interned. The default log excludes `refs/stash` so stash commits do not appear as graph nodes; callers that pass revisions get exactly those.
- Diff parser (#15): `DiffParser` is incremental (feed byte chunks; a file is emitted when the next `diff --git` starts, so memory is bounded by the largest single file) and keeps every header and `@@` line verbatim, so `DiffPatchWriter.WriteFile` reproduces git's text exactly. `DiffReader` fixes the options that make output predictable (`--no-color --no-ext-diff --no-textconv --src-prefix=a/ --dst-prefix=b/ --find-renames --find-copies`); callers add the rest (`--cached`, `--binary`, `-U<n>`, `--format=` for `show`). Partial staging uses `DiffPatchWriter.WriteSelection` (hunk and line index addressing, counts and offsets recomputed; `Forward` to stage, `Reverse` to unstage or discard with `apply -R`). Known limits: combined diffs (`diff --cc`, merge commits) are skipped with a warning; invalid UTF-8 is replaced and a warning says the text is no longer exact, so such patches must not be applied; partial patches are not meaningful for binary, added or deleted files (stage whole) and hunks with zero context are not re-anchored; `GitRunner` has no stdin support, so applying a patch needs a temp file or a runner extension (follow-up for the staging issue).
- Graph lane layout (#16) lives in `Gitunia.Core/Graph`: `GraphLayoutBuilder` appends commits (children before parents) and yields immutable `GraphRow`s (node lane, lane count, `Through`/`Incoming`/`Outgoing` edges); `GraphLayout.Compute` is the batch form and gives the identical result for any chunking. A lane waits for exactly one commit id, so several children of one commit share a single incoming lane (the later children draw an outgoing edge into it); lanes are not shifted left, freed lanes are reused leftmost-first, and a parent missing from the stream keeps its lane open. Why: stable columns while scrolling and loading, O(open lanes) per commit.
- Keymap engine (#19) lives in `Gitunia.Core.Keymap`: bindings are `KeyBinding(mode, view, key sequence, action id)` rows in a `KeyBindingTable` with a view hierarchy (`Graph`/`Detail`/`Sidebar`/`Diff` inherit `Lists`, everything inherits `Global`; a more specific view shadows an equal sequence). `KeymapEngine.Process(state, key, view)` is pure, takes a renderer-agnostic `KeyEvent` and returns the next `KeymapState` plus an outcome; the app switches mode with `state.WithMode`. A binding that is a strict prefix of a longer one in the same view is reported as a conflict (no chord timeout, so it could never fire); when it happens anyway the longer chord wins. Key notation in code and docs is the `docs/ux.md` one (`Ctrl-w c`, `<space>o`); the `docs/ux.md` keymap row for `Ctrl-w h j k l` was split into four explicit chords so the doc test can parse it, and a `v` row (Visual mode toggle) was added. Arrow and PageUp/PageDown keys are bound in lists. Confirm mode deliberately has no `Enter` binding.
- Workspace state (#17) lives in `Gitunia.Core.Workspaces`: immutable records, `WorkspaceReducer.Reduce(Workspace, WorkspaceCommand) -> WorkspaceUpdate(Workspace, Effects)`, tab ids allocated from a counter in the workspace and never reused, commands for a closed tab are dropped (late git results). Tabs are deduped by `RepositoryLocation.RootPath` with a trailing-separator-insensitive comparer that ignores case on Windows and macOS. Closing the active tab activates its right neighbour (left if it was last); recents are capped at 50.
- Graph view (#22) is the first real Tui shell. Everything Terminal.Gui-specific is in `Views` (`GraphListSource`, an append-only `IListDataSource` that draws only the visible rows; `MainView`, `LineView`, `Palette`) and `Input` (`KeyTranslator`, `KeyController`: every key goes through `app.Keyboard.KeyDown` into the keymap engine, and a completed binding becomes an action id handled by `ActionRouter`). `Rendering` has no Terminal.Gui types: a row is a `StyledLine` of `StyledSegment`s with a `SegmentRole`, so `ScreenComposer` renders a whole frame as text for snapshot tests and for `gitunia <repo> --print-frame WxH` (a small diagnostic flag that prints one frame and exits; the CI smoke run uses it). `LoadRepositoryEffect` is executed by `EffectRunner`; results come back as `TabCommand`s on the UI thread through `WorkspaceHost`. A new effect (clipboard, file watching) adds a case to `EffectRunner.Run`, a new action a branch in `ActionRouter.Execute`. The streamed rows of a tab live in a `TabSession` beside the immutable `RepoState`, which still records the selected commit and scroll offset.
- Graph rows keep a compact `GraphEntry` (id, subject, author, time, decorations, lane row) instead of the whole `CommitInfo`. Lanes are laid out on the loader thread; batches (the first 150 commits, then 2000 or 40 ms worth) are appended on the UI thread. The lane area is as wide on every row as the widest row seen so far (at most 40% of the terminal), so columns do not jump while scrolling or loading. Each lane takes two columns, with box-drawing connectors and an ASCII fallback for terminals without Unicode. The slot for the working-tree pseudo-row is `ScreenLayout.ReservedLeadingRows` (0 until the staging view exists). Without a path argument the app still prints the banner and exits (no session restore or repo picker yet); `gitunia <path>` opens one tab. Numbers are in `docs/architecture.md`.
- Terminal.Gui findings for #22: a `ListView` over a custom source with `MaxItemLength` 0 and one `Reset` change event per appended batch keeps its selection and viewport while 100k rows stream in; an Esc followed by a key within a few milliseconds arrives as `Alt-<key>` (a terminal limitation, not a bug; people type slower than that, scripts must send them separately).
- File watching (#27) lives in `Gitunia.Git` (no Core types): one `RepositoryWatcher` per tab, one shared `WatchBudget`, `RepositoryRefresher` for incremental refresh; details in `docs/git-layer.md`. The Platform abstraction is not involved: `FileSystemWatcher` is cross-platform and its failures (inotify limit, buffer overflow, unsupported file systems) fall back to polling, which is the per-OS escape hatch. Wiring into tab state and effects (calling `SetActive` on tab switch, running the refresh effect, applying the changed sections) is left to the UI work. Known limit: the recursive working tree watcher also sees `.git/objects`; the classifier filters those events but they still cost inotify watches.
- Session persistence (#18) lives in `Gitunia.Core.Persistence`: `SessionStore` reads and writes `session.json` in `IPlatform.StateDirectory` (tabs with their repository location and view state, active tab index, recents, pins), schema `version` 1, System.Text.Json source generation (`SessionJsonContext`), saves via `AtomicFileWriter` (temp file in the same directory, flush to disk, rename over the target). Loading never throws: a missing file gives an empty workspace; an unreadable, oversized, malformed or other-version file is renamed to `session.json.corrupt` and an empty workspace is used (the result carries a message for the status line). Bad entries inside a valid file (relative paths, duplicates, unknown pane, bad commit id) are skipped or defaulted. Tabs whose directory vanished are restored flagged `IsMissing`; the others get a `LoadRepositoryEffect`. Per-tab data beyond the view state (head, refs) is not stored; it reloads. The user config file (`ConfigDirectory`: keymap and theme overrides) is not part of this change since no setting exists yet; it gets its own versioned file when the first setting lands. The app wires load at startup and save on change (debounced) when the Tui workspace host exists.
- Clipboard (#52): `Gitunia.Core.Clipboard` has `CopyToClipboardEffect(Text, Description)` (a `WorkspaceEffect`), `Osc52Environment.Detect(lookup)` (injected env lookup, never the process env: `TERM` `dumb`/`linux` -> unsupported, `TMUX` -> tmux passthrough, `STY` -> screen DCS chunks of 76 chars, else direct) and the pure `Osc52Encoder.Encode(text, options)` (UTF-8 base64, ST terminator, refuses empty text and payloads over 100000 base64 bytes, the xterm limit). `Gitunia.Tui.ClipboardWriter` is the only code that writes the sequence to the terminal and returns the status-bar message. OSC 52 gives no acknowledgement, so "supported" is a best guess: the success message says what to enable if the clipboard stays unchanged. Terminals and multiplexers: tmux needs `set -g set-clipboard on` or `set -g allow-passthrough on` (tmux 3.3+); GNU screen may need its own setup; some terminals ask permission or disable OSC 52 by default (e.g. xterm `allowWindowOps`, Alacritty `osc52`, Windows Terminal supports it). The key binding and status-bar display are wired once the Terminal.Gui shell exists (follow-up issue); `y` and `graph.copy-hash` already exist in the keymap.
- Sidebar (#23): the pure part is `Gitunia.Core.Sidebar` (`SidebarBuilder` turns a tab's refs, worktrees and stashes plus `SidebarState` (folded sections, filter, cursor) into `SidebarRow`s; `SidebarReducer` handles `SidebarCommand`s through `RepoReducer`, so cursor, folding and filter live in `RepoState` per tab). `PaneNavigator` (Core) does `Tab`/`Ctrl-w` focus movement over the open panes (sidebar and graph for now; detail and diff plug in by joining the available list). Stashes come from `StashReader` (`stash list --format=%gd%x00%H%x00%gs%x1e`; note `%x00`, the stash list command does not expand `%00`), worktrees from the existing `RefReader`; both load beside the refs in `SidebarDataLoader`. In the Tui, `SidebarActionHandler` takes pane-focus and sidebar actions before the graph router, `SidebarPresenter` keeps the `ListView` selection in step with the state cursor (a click goes back as a command), and `ScreenComposer` takes an optional `SidebarModel`. The sidebar is a quarter of the screen (20-36 columns) and hidden under 60 columns. `KeyController` gained `SetMode` plus `TextTyped`/`Erased` events for Insert-mode text entry (the sidebar filter is the first user). Loader tests post through a serializing `InlineUi` because the workspace host is single-threaded and several loaders now dispatch.
- Help, palette and which-key (#20): overlay state is pure (`Gitunia.Core.Overlays`: `OverlayState`, `PaletteState`, `FuzzyMatcher`, `HelpBuilder`, `PaletteEntryBuilder`, `WhichKeyBuilder`); action titles live in `ActionCatalog` (a test fails when a default action has none) and key text comes from `KeyFormatter`, so nothing is hand-listed. Rendering is renderer-agnostic frames (`Gitunia.Tui.Rendering.Overlays`: `OverlayFrame` of `StyledLine`s, snapshot-tested at several sizes) drawn by one `OverlayView` added last to the window. `OverlayController` (Tui/App) sits in front of the `ActionRouter`: while an overlay is open it consumes actions, in Command mode (palette) typed text reaches it through `KeyController.TextKeyPressed` and every key is swallowed so graph keys never fire. The overlays have their own keymap views, `Palette` (Up/Down, Command mode) and `Help` (inherits `Lists` so scrolling reuses the list motions). The which-key popup appears 500 ms after a chord prefix via `WhichKeyTimer` (a `System.Threading.Timer` that posts to the UI thread; stale callbacks are dropped by a generation counter). Overlays are not part of `--print-frame`: the frames are tested directly. The status-bar key hints are unchanged (they would conflict with other shell work in flight); add `? :` there when the status bar is next reworked.
- Palette scope (#20 review): the palette lists every registered action (the acceptance line), including modal-internal ones; actions without behaviour yet show "<title>: not implemented yet" in the status bar. Hiding modal-only actions is left to the owner.
- Commit details (#24): `CommitDetailsReader` (`Gitunia.Git`) runs `git log -1 -z` (parsed by `CommitDetailsParser`: full raw message, author and committer with their UTC offsets via `%aI`/`%cI`, parents) and then `git diff-tree --raw -z -M -C` against the explicitly named first parent (or `--root`), because `diff-tree` shows merges against every parent and ignores `--first-parent` (parsed by `CommitFileChangeParser`, statuses reuse `FileChangeKind`). In the Tui, `CommitDetailsStore` (one per tab, owned by `TabSession`) is fed by every graph selection change: it shows the loading state at once, debounces 80 ms, cancels the load of the previous selection (its git processes are killed), ignores stale results and caches the last 64 commits. Pane rows are width-independent (`DetailContentBuilder`; long lines are cut with an ellipsis, not wrapped) and drawn by `DetailPaneRenderer`, shared by the Terminal.Gui list source and `ScreenComposer`, so `--print-frame` shows the pane for the newest commit. Pane focus is `FocusedPane` of the tab's view state; `ActionRouter.ViewName` picks the keymap view (`Graph` or `Detail`) from it.
