# Decisions

Log of settled choices that cut across docs. Agents follow these without asking. Open questions live in `roadmap.md`. Format: `date, decision. Why.` The entries dated 2026-10-10 are the baseline and may be reworded in place. Once the M0 decision (#7) is closed the log is append-only: when a decision changes, add a new entry that supersedes the old one and don't edit history.

- 2026-10-10, C# on .NET with Native AOT (Rust is the runner-up). Why: the owner is a .NET developer doing heavy agentic development, so the code must stay reviewable by them. Revisit only if the M0 spike shows the rendering layer is a time sink.
- 2026-10-10, Git access via the `git` CLI, not libgit2. Why: matches the user's real config, hooks, credentials and new git features such as worktrees.
- 2026-10-10, Standalone multi-repo client (tabs, picker, session restore), not bound to the current directory. Why: retrofitting multi-repo later is expensive, so the Git API is repo-scoped from the start.
- 2026-10-10, Other open-source Git clients are sources of ideas, never of copied code. Why: licence hygiene.
- 2026-10-10, Spikes live on unmerged `spike/` branches and close with findings. Issues labeled `destructive` or `needs-review` are merged by the owner; agents continue with other unblocked issues meanwhile.
- 2026-10-10, Cross-platform from day one (Linux first; Windows and macOS later, macOS lowest priority and droppable). Platform-specific code only behind a platform abstraction.
- 2026-10-10, Minimum git 2.43, `net10.0`, JSON config with source generation, MIT licence, product/binary name `gitunia`, config under the platform config dir `gitunia`. Why: LTS on current distros; AOT-safe; defaults accepted by the owner.
- 2026-10-10, External tools: hand the terminal to `$EDITOR`/difftool/mergetool by suspending and resuming the TUI; clipboard via OSC 52. No built-in editor.
- 2026-10-10, PRs are merged with a merge commit (never squash or rebase) and the branch is deleted afterwards. Why: the owner wants the full branch history and topology visible in the graph.
- 2026-10-10, added a fourth project `Gitunia.Platform` (config/state dirs, console capability detection) referenced by Git and Tui; Core stays free of OS code. Why: issue #1 requires the platform abstraction in one place and Core must not touch the console or process. SDK pinned to 10.0.400 with `rollForward: latestFeature`; test projects use xUnit v3; test method names may contain underscores (CA1707 off under `tests/`).
- 2026-10-10, renderer: Terminal.Gui v2 (2.5.0), not a custom renderer (decision #7, owner chose after reviewing the spikes). Why: the owner judged the custom renderer code far harder to read and maintain than toolkit widgets, and Terminal.Gui is fast enough. Spike data (Linux x64, 100k-commit repo, `scripts/measure.sh` medians incl. 1-3 ms tmux polling): list-only spike, Terminal.Gui vs custom: binary 9.47 MB + 564 KB native lib vs 2.56 MB, cold start ~97 ms vs ~28 ms, `j` latency ~34 ms vs ~4.8 ms, RSS ~50 MB vs ~33 MB. Heavier M1-like screen (sidebar, graph, details, status), 120x40: Terminal.Gui cold start ~107 ms, `j` ~34 ms, RSS ~71 MB; custom 24 ms, 7.4 ms, 35 MB. Both AOT-clean on Linux and Windows (win-x64 smoke under ConPTY in CI passed 8/8 for Terminal.Gui, 10/10 for custom). Accepted costs: startup near the 100 ms budget, larger binary and memory, a native library shipped beside the binary, modal keys/chords hand-rolled at the application level (the toolkit has no modal keymap), the commit graph still needs custom drawing.
- 2026-10-10, Terminal.Gui settings and pitfalls from the spikes: set `Application.MaximumIterationsPerSecond` to ~100 (default 25 gave ~34 ms key latency; 100 gives ~13 ms and cold start ~85 ms at ~2.6% idle CPU; higher values busy-spin a core). Use an append-only `IListDataSource` for streamed commits (`SetSource(ObservableCollection)` rescans per add and freezes input). The focused `ListView` swallows keys, so handle keys at the application level (`app.Keyboard.KeyDown`). `TextView` is obsolete in 2.5.0 (a separate package replaces it); check its AOT status before M2 commit-message input. Revisit the renderer only if a measured target fails; the custom renderer in `src/Gitunia.CustomRenderTui` is the fallback reference.
- 2026-10-10, spike #3 (standalone launch) findings for M1: resolve paths with `git -C <path> rev-parse`; check `--is-bare-repository` before `--show-toplevel`; a linked worktree has `--git-dir` != `--git-common-dir`; dedupe tabs by the resolved toplevel; a path inside a `.git` directory needs its own case. Resolving costs 0-2 ms.
- 2026-10-10, renderer stays swappable, but only Terminal.Gui is built. A custom renderer may return later as a separate project (e.g. `Gitunia.Tui.Custom`); no custom renderer code lives in the repo now, and the spike branches (`spike/5-custom-renderer`, `spike/5-heavy`, `spike/5-windows`) are the reference. Why: the owner wants the option open without paying for two renderers now. What this requires of the code: everything Terminal.Gui-specific stays in the rendering project; the state layer exposes renderer-agnostic view models (rows, spans, styles, key events as data) and never references Terminal.Gui types; keymap handling is our own engine fed by key events, not Terminal.Gui bindings. We do not add a renderer abstraction interface until a second renderer actually exists. If the boundary is cheap to keep it stays; if it starts to cost features, tell the owner.
- 2026-10-11, the Terminal.Gui spike (#4 heavy screen) is preserved as a reference sample in `samples/Gitunia.TerminalGuiSpike` (also tagged `archive/spike-4-terminal-gui-heavy`); not referenced by the app and not maintained. Use it as a starting point for the M1 UI, rewritten against the state layer.
- 2026-10-10, renderer stays swappable, but only Terminal.Gui is built and maintained. The custom renderer lives in `src/Gitunia.CustomRenderTui` (library: cell buffer with diff flush, VT input parser, raw terminal for Linux/macOS/Windows), with a runnable demo in `samples/Gitunia.CustomRenderTui.Demo`, tests, and a manual-only Windows ConPTY smoke workflow. It is NOT actively maintained for now: it is not referenced by the app, features are not mirrored into it, and it is kept building and tested in CI only as a future option. Why: the owner wants the option open without paying for two renderers. If the main app's needs change it, the custom project may rot; that is accepted, and a revival starts with its README's 'missing' list. The spike branches were deleted once this landed; spike numbers stay in the issue comments and in the renderer decision entry above. What this requires of the main code: Terminal.Gui types stay in the rendering project, the state layer exposes renderer-agnostic view models and key events as data, keymap handling is our own engine, and no renderer abstraction interface is added until a second renderer is actually revived.
