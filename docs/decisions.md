# Decisions

Log of settled choices that cut across docs. Agents follow these without asking. Open questions live in `roadmap.md`. Format: `decision. Why.` Entries are grouped under a date heading, newest date last. The 2026-10-10 entries are the baseline and may be reworded in place. Once the M0 decision (#7) is closed the log is append-only: when a decision changes, add a new entry that supersedes the old one and don't edit history.

## 2026-10-10

- C# on .NET with Native AOT (Rust is the runner-up). Why: the owner is a .NET developer doing heavy agentic development, so the code must stay reviewable by them. Revisit only if the M0 spike shows the rendering layer is a time sink.
- Git access via the `git` CLI, not libgit2. Why: matches the user's real config, hooks, credentials and new git features such as worktrees.
- Standalone multi-repo client (tabs, picker, session restore), not bound to the current directory. Why: retrofitting multi-repo later is expensive, so the Git API is repo-scoped from the start.
- Cross-platform from day one (Linux first; Windows and macOS later, macOS lowest priority and droppable). Platform-specific code only behind a platform abstraction.
- Minimum git 2.43, `net10.0`, JSON config with source generation, MIT licence, product/binary name `gitunia`, config under the platform config dir `gitunia`. Why: LTS on current distros; AOT-safe; defaults accepted by the owner.
- Fourth project `Gitunia.Platform` (config/state dirs, console capability detection) referenced by Git and Tui; Core stays free of OS code. Why: issue #1 requires the platform abstraction in one place and Core must not touch the console or process. SDK pinned to 10.0.400 with `rollForward: latestFeature`; test projects use xUnit v3; test method names may contain underscores (CA1707 off under `tests/`).
- External tools: hand the terminal to `$EDITOR`/difftool/mergetool by suspending and resuming the TUI; clipboard via OSC 52. No built-in text editor (staging works on hunks and lines in the diff view).
- Other open-source Git clients are sources of ideas, never of copied code. Why: licence hygiene.
- Spikes live on unmerged `spike/` branches and close with findings. Issues labeled `destructive` or `needs-review` are merged by the owner; agents continue with other unblocked issues meanwhile.
- PRs are merged with a merge commit (never squash or rebase) and the branch is deleted afterwards. Why: the owner wants the full branch history and topology visible in the graph.
- Renderer: Terminal.Gui v2 (2.5.0), not a custom renderer (decision #7, owner chose after reviewing the spikes). Why: the custom renderer code was judged far harder to read and maintain than toolkit widgets, and Terminal.Gui is fast enough. Accepted costs: startup near the 100 ms budget, larger binary and memory, a native library beside the binary, modal keys/chords hand-rolled at the application level (no modal keymap in the toolkit), custom drawing for the commit graph. Spike data (Linux x64, 100k-commit repo, `scripts/measure.sh` medians incl. 1-3 ms tmux polling):
  - List-only spike, Terminal.Gui vs custom: binary 9.47 MB + 564 KB native lib vs 2.56 MB; cold start ~97 ms vs ~28 ms; `j` latency ~34 ms vs ~4.8 ms; RSS ~50 MB vs ~33 MB.
  - Heavier M1-like screen (sidebar, graph, details, status) at 120x40: Terminal.Gui cold start ~107 ms, `j` ~34 ms, RSS ~71 MB; custom 24 ms, 7.4 ms, 35 MB.
  - Both AOT-clean on Linux and Windows (win-x64 smoke under ConPTY in CI passed 8/8 for Terminal.Gui, 10/10 for custom).
- Terminal.Gui settings and pitfalls: set `Application.MaximumIterationsPerSecond` to ~100 (default 25 gave ~34 ms key latency; 100 gives ~13 ms and cold start ~85 ms at ~2.6% idle CPU; higher values busy-spin a core). Use an append-only `IListDataSource` for streamed commits (`SetSource(ObservableCollection)` rescans per add and freezes input). The focused `ListView` swallows keys, so handle keys at the application level (`app.Keyboard.KeyDown`). `TextView` is obsolete in 2.5.0 (a separate package replaces it); check its AOT status before M2 commit-message input.
- Standalone launch (spike #3) findings for M1: resolve paths with `git -C <path> rev-parse`; check `--is-bare-repository` before `--show-toplevel`; a linked worktree has `--git-dir` != `--git-common-dir`; dedupe tabs by the resolved toplevel; a path inside a `.git` directory needs its own case. Resolving costs 0-2 ms.
- The renderer stays swappable, but only Terminal.Gui is built and maintained. The custom renderer lives in `src/Gitunia.CustomRenderTui` (cell buffer with diff flush, VT input parser, raw terminal for Linux/macOS/Windows) with a runnable demo in `samples/Gitunia.CustomRenderTui.Demo`, tests, and a manual-only Windows ConPTY smoke workflow. It is not actively maintained: not referenced by the app, features are not mirrored into it, and it is only kept building and tested in CI as a future option. It may rot; a revival starts with its README's 'missing' list. The spike branches were deleted once this landed; spike numbers stay in the issue comments and the renderer entry above. What this requires of the main code: Terminal.Gui types stay in the rendering project, the state layer exposes renderer-agnostic view models and key events as data, keymap handling is our own engine, and no renderer abstraction interface is added until a second renderer is revived. If the boundary starts to cost features, tell the owner.

## 2026-10-11

- The Terminal.Gui spike (#4 heavy screen) is preserved as a reference sample in `samples/Gitunia.TerminalGuiSpike` (also tagged `archive/spike-4-terminal-gui-heavy`); not referenced by the app and not maintained. Use it as a starting point for the M1 UI, rewritten against the state layer.
- Terminal.Gui look experiment (merged into that sample): the custom demo's look (header bar, tab row, dimmed hashes, lane colours, status hints) is achievable in Terminal.Gui with ~160 extra lines and no hard limits found. Minor limits: border title glyphs are fixed (workaround: overlay view), `ListView` has no per-row styling (custom `IListDataSource.Render`), colour-depth fallback unverified, wide chars and mouse untested. Measured on the 100k repo at 100 iterations/s: 120x40 cold start ~58 ms, `j` ~8-10 ms, RSS ~75 MB; 200x60 cold start ~98 ms, `j` ~20 ms (custom demo: 16 ms, ~4 ms, ~31-36 MB, flat with screen size). The renderer choice (Terminal.Gui vs CustomRenderTui) is still open for the owner to reconsider; M1 does not start UI work until it is settled.
- Code conventions (from the PR #60 review), recorded in `CLAUDE.md`: no truncated names (`platform`, not `p`; `selection`, not `sel`), one type per file (models and logic in separate files, unless related or inherited), scripts live in `scripts/` for both bash and PowerShell, tmux-based interactive testing is Linux/macOS only.
- Renderer confirmed by the owner: Terminal.Gui. This supersedes the 'still open for the owner to reconsider' note and the 'M1 does not start UI work until it is settled' gate above; UI work in M1 may start. Key style for M1 (#8): agents draft the first iteration following common vim, yazi and lazygit patterns; the owner reviews it in use and adjusts later, so keep the keymap data-driven.
- M1 key design (#8, first iteration, owner adjusts after use): both `Tab` cycling and `Ctrl-w` + direction move pane focus; frequent actions are per-view single keys with a `<space>` leader for global ones; chords show a which-key popup after 500 ms and never time out; Insert mode swallows printable keys so chords cannot fire while typing. Patterns followed: vim (motions, counts, `gt`/`gT`, `]c`/`[c`, `Ctrl-w`), lazygit (per-pane focus, `/` filter, `Enter` drills in), yazi (`h`/`l` collapse/enter, `Alt-` combos in inputs). Closes the pane focus and key style open questions.
- Commit ids are a fixed 40-byte `ObjectId` struct (SHA-1 or SHA-256) instead of interned hash strings (#13). Why: no intern table or string per parent link, equality and hashing without allocation. Cost: 40 bytes per id even for SHA-1 (about 12 bytes padding); per-commit memory is still dominated by `CommitInfo`, its subject string and decorations. Author names and emails are interned. The default log excludes `refs/stash` so stash commits do not appear as graph nodes; callers that pass revisions get exactly those.
- Diff parser (#15): `DiffParser` is incremental (feed byte chunks; a file is emitted when the next `diff --git` starts, so memory is bounded by the largest single file) and keeps every header and `@@` line verbatim, so `DiffPatchWriter.WriteFile` reproduces git's text exactly. `DiffReader` fixes the options that make output predictable (`--no-color --no-ext-diff --no-textconv --src-prefix=a/ --dst-prefix=b/ --find-renames --find-copies`); callers add the rest (`--cached`, `--binary`, `-U<n>`, `--format=` for `show`). Partial staging uses `DiffPatchWriter.WriteSelection` (hunk and line index addressing, counts and offsets recomputed; `Forward` to stage, `Reverse` to unstage or discard with `apply -R`). Known limits: combined diffs (`diff --cc`, merge commits) are skipped with a warning; invalid UTF-8 is replaced and a warning says the text is no longer exact, so such patches must not be applied; partial patches are not meaningful for binary, added or deleted files (stage whole) and hunks with zero context are not re-anchored; `GitRunner` has no stdin support, so applying a patch needs a temp file or a runner extension (follow-up for the staging issue).
- Graph lane layout (#16) lives in `Gitunia.Core/Graph`: `GraphLayoutBuilder` appends commits (children before parents) and yields immutable `GraphRow`s (node lane, lane count, `Through`/`Incoming`/`Outgoing` edges); `GraphLayout.Compute` is the batch form and gives the identical result for any chunking. A lane waits for exactly one commit id, so several children of one commit share a single incoming lane (the later children draw an outgoing edge into it); lanes are not shifted left, freed lanes are reused leftmost-first, and a parent missing from the stream keeps its lane open. Why: stable columns while scrolling and loading, O(open lanes) per commit.
- Keymap engine (#19) lives in `Gitunia.Core.Keymap`: bindings are `KeyBinding(mode, view, key sequence, action id)` rows in a `KeyBindingTable` with a view hierarchy (`Graph`/`Detail`/`Sidebar`/`Diff` inherit `Lists`, everything inherits `Global`; a more specific view shadows an equal sequence). `KeymapEngine.Process(state, key, view)` is pure, takes a renderer-agnostic `KeyEvent` and returns the next `KeymapState` plus an outcome; the app switches mode with `state.WithMode`. A binding that is a strict prefix of a longer one in the same view is reported as a conflict (no chord timeout, so it could never fire); when it happens anyway the longer chord wins. Key notation in code and docs is the `docs/ux.md` one (`Ctrl-w c`, `<space>o`); the `docs/ux.md` keymap row for `Ctrl-w h j k l` was split into four explicit chords so the doc test can parse it, and a `v` row (Visual mode toggle) was added. Arrow and PageUp/PageDown keys are bound in lists. Confirm mode deliberately has no `Enter` binding.
- Workspace state (#17) lives in `Gitunia.Core.Workspaces`: immutable records, `WorkspaceReducer.Reduce(Workspace, WorkspaceCommand) -> WorkspaceUpdate(Workspace, Effects)`, tab ids allocated from a counter in the workspace and never reused, commands for a closed tab are dropped (late git results). Tabs are deduped by `RepositoryLocation.RootPath` with a trailing-separator-insensitive comparer that ignores case on Windows and macOS. Closing the active tab activates its right neighbour (left if it was last); recents are capped at 50.
- Graph view (#22) is the first real Tui shell. Everything Terminal.Gui-specific is in `Views` (`GraphListSource`, an append-only `IListDataSource` that draws only the visible rows; `MainView`, `LineView`, `Palette`) and `Input` (`KeyTranslator`, `KeyController`: every key goes through `app.Keyboard.KeyDown` into the keymap engine, and a completed binding becomes an action id handled by `ActionRouter`). `Rendering` has no Terminal.Gui types: a row is a `StyledLine` of `StyledSegment`s with a `SegmentRole`, so `ScreenComposer` renders a whole frame as text for snapshot tests and for `gitunia <repo> --print-frame WxH` (a small diagnostic flag that prints one frame and exits; the CI smoke run uses it). `LoadRepositoryEffect` is executed by `EffectRunner`; results come back as `TabCommand`s on the UI thread through `WorkspaceHost`. A new effect (clipboard, file watching) adds a case to `EffectRunner.Run`, a new action a branch in `ActionRouter.Execute`. The streamed rows of a tab live in a `TabSession` beside the immutable `RepoState`, which still records the selected commit and scroll offset.
- Graph rows keep a compact `GraphEntry` (id, subject, author, time, decorations, lane row) instead of the whole `CommitInfo`. Lanes are laid out on the loader thread; batches (the first 150 commits, then 2000 or 40 ms worth) are appended on the UI thread. The lane area is as wide on every row as the widest row seen so far (at most 40% of the terminal), so columns do not jump while scrolling or loading. Each lane takes two columns, with box-drawing connectors and an ASCII fallback for terminals without Unicode. The slot for the working-tree pseudo-row is `ScreenLayout.ReservedLeadingRows` (0 until the staging view exists). Without a path argument the app still prints the banner and exits (no session restore or repo picker yet); `gitunia <path>` opens one tab. Numbers are in `docs/architecture.md`.
- Terminal.Gui findings for #22: a `ListView` over a custom source with `MaxItemLength` 0 and one `Reset` change event per appended batch keeps its selection and viewport while 100k rows stream in; an Esc followed by a key within a few milliseconds arrives as `Alt-<key>` (a terminal limitation, not a bug; people type slower than that, scripts must send them separately).
- File watching (#27) lives in `Gitunia.Git` (no Core types): one `RepositoryWatcher` per tab, one shared `WatchBudget`, `RepositoryRefresher` for incremental refresh; details in `docs/git-layer.md`. The Platform abstraction is not involved: `FileSystemWatcher` is cross-platform and its failures (inotify limit, buffer overflow, unsupported file systems) fall back to polling, which is the per-OS escape hatch. Wiring into tab state and effects (calling `SetActive` on tab switch, running the refresh effect, applying the changed sections) is left to the UI work. Known limit: the recursive working tree watcher also sees `.git/objects`; the classifier filters those events but they still cost inotify watches.
- Session persistence (#18) lives in `Gitunia.Core.Persistence`: `SessionStore` reads and writes `session.json` in `IPlatform.StateDirectory` (tabs with their repository location and view state, active tab index, recents, pins), schema `version` 1, System.Text.Json source generation (`SessionJsonContext`), saves via `AtomicFileWriter` (temp file in the same directory, flush to disk, rename over the target). Loading never throws: a missing file gives an empty workspace; an unreadable, oversized, malformed or other-version file is renamed to `session.json.corrupt` and an empty workspace is used (the result carries a message for the status line). Bad entries inside a valid file (relative paths, duplicates, unknown pane, bad commit id) are skipped or defaulted. Tabs whose directory vanished are restored flagged `IsMissing`; the others get a `LoadRepositoryEffect`. Per-tab data beyond the view state (head, refs) is not stored; it reloads. The user config file (`ConfigDirectory`: keymap and theme overrides) is not part of this change since no setting exists yet; it gets its own versioned file when the first setting lands. The app wires load at startup and save on change (debounced) when the Tui workspace host exists.
- Graph search and jump to ref (#26): the pure parts live in `Gitunia.Core.Search` (`SearchQueryParser`, `GraphSearchMatcher`, `GraphSearchScanner`, `GraphSearchReducer` with `GraphSearchState`/`Command`/`Effect`, `RefJumpResolver`, `FuzzyMatcher`, `PromptTextEditor`); the Tui side is `SearchController` and `RefJumpController` behind `IPromptHandler` (the router offers every action to them first, Insert-mode keys reach them through `KeyController.TextKeyHandler`). Search state is per tab and lives in `TabSession.Search` (not persisted). Scanning runs on the UI thread in slices of 5000 rows queued one by one (a full 100k scan takes ~70 ms), so no other thread touches the non-thread-safe `CommitGraph`; a newer query bumps a generation counter and the older slices stop; because the whole log streams in anyway, "load on demand" is the scan following the stream (`GraphGrewCommand`) rather than a second process. Plain text matches the subject only: `GraphEntry` keeps no body, and a `--grep` log call would need a second process for little gain (follow-up if wanted). `gr` is a status-bar prompt, not a popup list (no overlay exists yet); the palette/help overlay work may replace it with a shared list overlay. Ref candidates skip symbolic refs such as `origin/HEAD`.
- Clipboard (#52): `Gitunia.Core.Clipboard` has `CopyToClipboardEffect(Text, Description)` (a `WorkspaceEffect`), `Osc52Environment.Detect(lookup)` (injected env lookup, never the process env: `TERM` `dumb`/`linux` -> unsupported, `TMUX` -> tmux passthrough, `STY` -> screen DCS chunks of 76 chars, else direct) and the pure `Osc52Encoder.Encode(text, options)` (UTF-8 base64, ST terminator, refuses empty text and payloads over 100000 base64 bytes, the xterm limit). `Gitunia.Tui.ClipboardWriter` is the only code that writes the sequence to the terminal and returns the status-bar message. OSC 52 gives no acknowledgement, so "supported" is a best guess: the success message says what to enable if the clipboard stays unchanged. Terminals and multiplexers: tmux needs `set -g set-clipboard on` or `set -g allow-passthrough on` (tmux 3.3+); GNU screen may need its own setup; some terminals ask permission or disable OSC 52 by default (e.g. xterm `allowWindowOps`, Alacritty `osc52`, Windows Terminal supports it). Wired in #78: `y` (`graph.copy-hash`) in the graph pane goes through `Gitunia.Tui.App.ClipboardCopier` on the UI thread (so the write cannot interleave with Terminal.Gui output), which posts the message on the `StatusChannel` (warning on failure, the status bar clips it to the screen width); when the console is not interactive no writer exists and the copier only posts a warning.

## 2026-10-12

- Tab bar and repo picker (#21) and session wiring (#81). Core (`Gitunia.Core.Picker`) holds the pure parts: `PickerReducer.Reduce(PickerState, PickerCommand, PickerContext)`, the palette's `FuzzyMatcher` (name matches count double, ties go to the shorter name), `PathQuery`/`PathCompleter` (a typed path starts with `/`, `~`, `./`, `../` or a drive; relative paths resolve against the active repository or the home directory, never the process working directory), `PickerRowBuilder` (open, pinned, recent, discovered; one row per repository with all its tags) and `RepositoryScanner`. The file system reaches the picker only through `PickerContext` (injected functions), so tests use a fake. `PickerController` (Tui) owns the open picker, runs the scan and `RepositoryDiscovery` on the thread pool and posts results to the UI thread. Discovered repositories come from the conventional folders below the home directory (`Projects`, `src`, `code`, `dev`, `repos`, `git`, `work`, ... depth 3, at most 2000, hidden/dependency/symlinked folders skipped, found repositories not descended into), rescanned at most every 30 s when the picker opens; configurable scan roots wait for the config file (M4).
- Lazy tab loading (#91): `EffectRunner` creates every restored tab's `TabSession` (empty, `IsPending`) but starts the load (log, refs, status, sidebar data) only for the active tab; a background tab's load starts the first time it becomes active (it runs off the UI thread, so input is not blocked). Until first activation a background tab also has no HEAD, refs or dirty/ahead/behind markers in the tab bar, and a missing or broken repository is only reported then; a cheap status-only refresh of background tabs is tracked in #129. Decision (#111): background tabs are not loaded when idle (measured: ~37 ms first visit, ~0.5-1 MB per loaded tab, see architecture.md; a tab opened through the picker is always active, so it loads at once).
- The picker query is plain state edited by the keymap (printable keys arrive as `TextInput`; `Backspace` is handled by the app because the keymap leaves it unbound by design); while it is open the keymap runs in Insert mode with the `Picker` view. A repository that is already open is focused instead of opened twice (the reducer dedupes by root path). A missing tab is located through the picker (`LocatingTabId`): the chosen repository replaces it. Esc with no tab open quits.
- Terminal key facts (Terminal.Gui 2.5.0, tmux): `Ctrl-j` arrives as `Ctrl+Enter`, `Ctrl-^` as `Ctrl+6`, `Ctrl-h` as `Ctrl+Backspace`; `KeyTranslator` maps the first two to `Ctrl-j` and `Ctrl-^` so the documented bindings work.
- Session wiring (#81): `gitunia` restores the session at startup (`SessionStore.LoadAsync`; a discard shows its detail in the status bar until the first key), `gitunia <path>` opens or focuses that repository on top of the restored tabs, no tabs means the picker opens; `SessionPersistence` saves 500 ms after the last workspace change on a timer thread (skipping unchanged workspaces) and flushes on exit. A start without a path from a non-interactive terminal still prints the banner (the CI smoke run relies on it). Background tabs load lazily (#91, below). Tab bar markers (`RepoStatusSummary`: dirty, ahead, behind) are read when a tab loads and kept current by `TabRefresher` (#90): the first refresh after the load is a baseline that re-applies every section and reloads the graph if a change was seen meanwhile or the loaded graph's ref decorations differ from the baseline refs (`GraphRefCheck`, #161; a commit made between the load and the baseline read leaves no event to diff); later refreshes apply only differing sections and reload the graph only when HEAD or refs changed (or on `r`). Each tab keeps its selection and scroll: `GraphTabBinder` swaps the list source on tab change and restores them once the commit has streamed in.
- Sidebar (#23): the pure part is `Gitunia.Core.Sidebar` (`SidebarBuilder` turns a tab's refs, worktrees and stashes plus `SidebarState` (folded sections, filter, cursor) into `SidebarRow`s; `SidebarReducer` handles `SidebarCommand`s through `RepoReducer`, so cursor, folding and filter live in `RepoState` per tab). `PaneNavigator` (Core) does `Tab`/`Ctrl-w` focus movement over the open panes (sidebar and graph for now; detail and diff plug in by joining the available list). Stashes come from `StashReader` (`stash list --format=%gd%x00%H%x00%gs%x1e`; note `%x00`, the stash list command does not expand `%00`), worktrees from the existing `RefReader`; both load beside the refs in `SidebarDataLoader`. In the Tui, `SidebarActionHandler` takes pane-focus and sidebar actions before the graph router, `SidebarPresenter` keeps the `ListView` selection in step with the state cursor (a click goes back as a command), and `ScreenComposer` takes an optional `SidebarModel`. The sidebar is a quarter of the screen (20-36 columns) and hidden under 60 columns. `KeyController` gained `SetMode` plus `TextTyped`/`Erased` events for Insert-mode text entry (the sidebar filter is the first user). Loader tests post through a serializing `InlineUi` because the workspace host is single-threaded and several loaders now dispatch.
- Help, palette and which-key (#20): overlay state is pure (`Gitunia.Core.Overlays`: `OverlayState`, `PaletteState`, `FuzzyMatcher`, `HelpBuilder`, `PaletteEntryBuilder`, `WhichKeyBuilder`); action titles live in `ActionCatalog` (a test fails when a default action has none) and key text comes from `KeyFormatter`, so nothing is hand-listed. Rendering is renderer-agnostic frames (`Gitunia.Tui.Rendering.Overlays`: `OverlayFrame` of `StyledLine`s, snapshot-tested at several sizes) drawn by one `OverlayView` added last to the window. `OverlayController` (Tui/App) sits in front of the `ActionRouter`: while an overlay is open it consumes actions, in Command mode (palette) typed text reaches it through `KeyController.TextKeyPressed` and every key is swallowed so graph keys never fire. The overlays have their own keymap views, `Palette` (Up/Down, Command mode) and `Help` (inherits `Lists` so scrolling reuses the list motions). The which-key popup appears 500 ms after a chord prefix via `WhichKeyTimer` (a `System.Threading.Timer` that posts to the UI thread; stale callbacks are dropped by a generation counter). Overlays are not part of `--print-frame`: the frames are tested directly. The status-bar key hints gained `? :` with #93.
- Palette scope (#20 review): the palette lists every registered action (the acceptance line), including modal-internal ones; actions without behaviour yet show "<title>: not implemented yet" in the status bar. Hiding modal-only actions is left to the owner.
- Session save failures (read-only or full state directory) post one status error per failing streak (#93): `SessionStore.SaveAsync` returns false, the next change or the exit flush retries silently, and a later success re-arms the message. Replacing a missing tab opens the new repository first and closes the missing tab second, so a failed open never loses the entry.
- Commit details (#24): `CommitDetailsReader` (`Gitunia.Git`) runs `git log -1 -z` (parsed by `CommitDetailsParser`: full raw message, author and committer with their UTC offsets via `%aI`/`%cI`, parents) and then `git diff-tree --raw -z -M -C` against the explicitly named first parent (or `--root`), because `diff-tree` shows merges against every parent and ignores `--first-parent` (parsed by `CommitFileChangeParser`, statuses reuse `FileChangeKind`). In the Tui, `CommitDetailsStore` (one per tab, owned by `TabSession`) is fed by every graph selection change: it shows the loading state at once, debounces 80 ms, cancels the load of the previous selection (its git processes are killed), ignores stale results and caches the last 64 commits. Pane rows are width-independent (`DetailContentBuilder`; long lines are cut with an ellipsis, not wrapped) and drawn by `DetailPaneRenderer`, shared by the Terminal.Gui list source and `ScreenComposer`, so `--print-frame` shows the pane for the newest commit. Pane focus is `FocusedPane` of the tab's view state; `ActionRouter.ViewName` picks the keymap view (`Graph` or `Detail`) from it.
- Mouse (readiness M1): if Terminal.Gui's mouse handling is limited over tmux/ssh, document the limits here and keep the keyboard complete; mouse stays optional (revisit later). The "Large-repo graph layout" open question is closed: incremental lanes (#16), numbers in `docs/architecture.md`. #64 is split into (a) and #100 (b).
- Diff viewer (#25): the pure part is `Gitunia.Core.Diff` (`DiffDocumentBuilder` flattens the parser's `DiffFile`s into `DiffRow`s plus hunk and file anchors, `DiffNavigator` does `]c`/`[c`/`]f`/`[f`, `DiffSearch`/`DiffSearchState` the search, `PaneZoom` the zoom rule). `DiffStore` (Tui/Loading, one per tab inside `DiffSession`) streams the diff of the commit against its first parent (`diff <first-parent> <commit>`, or `show --format= <commit>` for a root commit) through `DiffReader` off the UI thread, cancels the load of a previous commit and caps the rows at 400,000. It always loads the whole commit, not one file, because `]f`/`[f` walk the files of the commit and a rename needs both paths to be detected; `Enter` on a file just puts the cursor at its header. `DiffPaneController` (Tui/App) is the diff's action handler and search prompt; `ActionRouter` hands it actions after the sidebar and before the graph/detail lists (`ActionRouter.Diff`, and `ViewName` knows the `Diff` view). Layout is data: `PaneLayout.Compute(width, height, isDiffOpen, zoomed)` returns every pane's rectangle and `MainView` binds its views to it, so the layout is unit-tested without a terminal. The diff sits beside a compact detail pane (file list, a third of the width, 24-60 columns) from 70 columns up and replaces it only below that (#108: SourceGit shows that a narrow file list next to the diff works; at 70 columns the diff still has 45). `Ctrl-w j`/`Ctrl-w k` move focus between the top row (sidebar, graph) and the bottom row (detail, diff) via `PaneNavigator.StepVertically` (#105). `<space>z` on the sidebar stays a no-op with a notice: the sidebar is a narrow strip, zooming it has no use (#105, dropped). Focus `Diff` is saved as `Detail` in the session file because the pane is not open after a restart. `ScreenComposer` takes an optional `DiffPaneModel` and `PaneArrangement` and draws its panes from `PaneLayout.Compute`, so side-by-side, replaced and zoomed layouts are frame-tested (`DiffFrameTests`); `--print-frame WxH --diff` opens the diff of the newest commit and `--zoom graph|detail|diff` zooms a pane (#118; `--zoom diff` implies `--diff`), so every layout can be inspected from the command line.
- Status messages (#93): one global `StatusChannel` per window (not per tab) holds an immutable `StatusLog` of the last 50 messages; messages are single-line (newlines collapse), the newest shows until dismissed or replaced, and background code posts through the UI-thread dispatcher it already uses. Key-action notices (`ActionRouter.Message`) stay transient and are not logged, so the history does not fill with `not implemented yet`. Dismiss is `<space>x` (plus `Esc` in the graph), history `<space>m`, retry of failed commit details `r` in the Detail view.
- Incremental graph reload (#126): measured on the 100k-commit repo (`scripts/gen-big-repo.sh`): a full re-read after a refresh takes ~840 ms, of which ~780 ms is git producing the full log format (C# parse and layout cost ~35 ms; a hashes-only log takes 40 ms thanks to the commit-graph file). That is above the issue's 200 ms limit, so the reload is incremental: after one new commit it takes ~105 ms including the guard commands. The join needs the same commit, lane, edges and an equal `GraphRow.LaneFingerprint` (hash of the commits the open lanes wait for), because lanes depend on the topology above. Guards: `rev-list --count` must equal the spliced length (catches deleted or moved refs whose commits sit below the join), and new rows may not appear in the old graph in a different order. Refs below the join come from a `--no-walk --all` log since refs move without commits changing. Accepted limit: history below the join rewritten with the same commit count is not noticed until a manual refresh (`r` always reads everything). Limit accepted (#148): below the join every commit has the same id, and ids are content hashes, so its ancestors cannot differ; the cases that can still differ (a moved or deleted side-branch tip, a changed count, unshallowing) are caught by the count guard and the lost-tip check in `GraphSplicer.Splice`. What remains unguarded is a `git replace` ref (it changes the parents `git log` reports without changing ids) that keeps the commit count; no extra hash of rows below the join is worth its cost, and `r` resynchronizes. The issue's "retry" path is not a full read: a failed automatic refresh keeps the previous snapshot and reruns incrementally, which is correct since nothing was applied; only a failed manual refresh stays forced. The per-refresh copy of the old rows (`TabRefresher`, ~0.8 MB at 100k rows, needed so the background read does not see the UI list change) and the splicer's result list are accepted too. `TabRefresher` takes an optional `graphReloaded` callback that the wiring tests use to tell incremental from full reloads. Not taken: a topology-only two-pass reload (~120 ms of git alone plus parsing, little gain) and a stored parent list per row (memory).
- Diff viewer extras (#106): word wrap is real wrapping, not horizontal scroll. `DiffListSource` maps diff rows to screen lines through `DiffWrapMap` (rebuilt when the document changes, only while wrap is on, so the cost is paid on demand; a width change calls `DiffWrapMap.Resize` (#162): row text widths are measured once per document (+4 bytes per row), and a resize is arithmetic for rows whose characters are all one column wide after tab expansion (#174: ASCII, tab-indented, accented text; the measured width is stored, the bitwise complement marks rows with wide or zero-width characters), and also for those marked rows while they fit one line; only wider-than-the-pane rows with wide characters still use `SegmentCount`; 400k rows: ~300-400 ms full build, 4-8 ms resize, Debug; tab-indented or accented rows 3.6-4.2 ms against 220-540 ms per-row `SegmentCount`); `ListView` items are then screen lines and the controller converts to and from diff rows for search, hunk/file jumps and the remembered cursor. Highlight is applied per screen line, so a search match that spans a wrap point is only highlighted on the part inside each line. The frame composer (`--print-frame`, `DiffFrameTests`) draws unwrapped. "Load anyway" (`L`) lifts the 400,000-row cap and a new 100,000-lines-per-file cap (`DiffParser` keeps the first lines of a longer file and sets `DiffFile.IsTruncated`, so one huge file no longer needs memory for all of it). Dropped: progressive display while the diff streams (the commit is read in one go and the pane shows "Loading..."; closing the pane cancels git; `L` on a huge commit is the only case where it can be slow) and loading binary content (nothing readable to show in a terminal). The diff follows the graph selection (decided over a "stale" marker): once the selected commit's details have arrived (the same settle delay as the detail pane, so fast `j`/`k` does not start git per row) `DiffPaneController.FollowSelection` loads that commit and keeps the cursor on the same file path. A live refresh needs nothing more: a commit's diff never changes, and when a refresh moves the selection to another commit the same follow rule applies. The diff arguments moved to `DiffReader.ReadCommitAsync` in `Gitunia.Git`. Status bar hints come from `PaneHints.For(focusedPane)`.
- Mouse (#64 part a): the mouse follows the key path. `Gitunia.Core.Mouse` holds `MouseGesture` (click, double-click, wheel up/down), `MouseMap` and `DefaultMouseMap` (view, gesture -> action id and count, same view inheritance as the keymap); `docs/ux.md` has the matching table, checked by a test. In the Tui, `PaneListView` (the four list panes) and the picker view translate Terminal.Gui flags (`MouseFlagTranslator`) into gestures; `MouseController` resolves them and calls the same `RouteAction` as keys, so a wheel notch is `list.down` with count 3, a graph double-click is `graph.open-details`, a tab click is `tab.next` with the tab number (`3gt`). Decisions: the toolkit's own wheel scrolling is replaced (it moved only the viewport and left the selection behind, and bypassed the keymap path); a gesture first focuses the pane under the pointer; the toolkit still selects the clicked row (a position, not an action); a sidebar single click is `Enter` (it toggles sections, so double-click is deliberately unbound there: Terminal.Gui reports click then double-click); while an overlay is open, pane gestures are ignored; a sideways wheel is ignored. Terminal.Gui 2.5.0 names: `MouseFlags.WheeledUp/WheeledDown/LeftButtonClicked/LeftButtonDoubleClicked`, a sideways wheel is vertical wheel plus Ctrl.
- Mouse (#100 part b): drag, resize, buttons and overlays follow the same rule (mouse map to action ids, then the key handlers). Drag in Terminal.Gui 2.5.0 arrives as `LeftButtonPressed`, then position reports with `LeftButtonPressed | PositionReport` while the button is held, then `LeftButtonReleased` and a `LeftButtonClicked` at the release position, even after a drag and routed to the view under the pointer. `DragTracker` (pure) tells click from drag and marks that trailing click for swallowing; `DragGrab` grabs the mouse on the press (`View.App.Mouse.GrabMouse`) so a drag goes on outside the view and keeps the grab until the trailing click has reached the dragging view (300 ms fallback timeout), otherwise the click would land on the pane under the pointer and end the selection. Drag-select: the first move off the pressed row focuses the pane, selects the pressed row and raises `DragStart` (`visual.toggle`), then each move raises `DragUp`/`DragDown` with the row distance (`list.up`/`list.down` with that count), so the range is the existing Visual mode (`VisualRangeController`: graph, detail and diff, drawn as selected rows through `IRangeSource.Range`, ended by `v`, `Esc`, `q`, a click, or focus moving). Decisions: `v` is implemented for keys too (it was bound but did nothing); `y` in Visual mode copies the range (#140: `visual.copy`, text builders in `RangeTextBuilder`, diff rows not screen lines, notes skipped), staging will act on it too (#31); auto-scroll while the pointer rests outside the pane (#137): `PaneListView` runs an 80 ms UI-loop timer, step `1 + (distance-1)/2` rows capped at 6 (pure `DragAutoScroll.Step`), stopped when the pointer is back inside, at the list end, on release or when an overlay opens. Resize: `PaneSizes` (sidebar width, bottom strip height, detail width; null is automatic) live in the tab's `RepoViewState` (saved with the session per tab as `sidebarWidth`, `bottomHeight`, `detailWidth`, absent or negative means automatic, no version bump: #138; set through `SetPaneSizesCommand`), are clamped by `PaneLayout` on every layout (`PaneResizer` is the pure rule shared by the drag and the keys `Ctrl-w > < + - =`, because nothing may be mouse-only). A zoomed pane has nothing to resize. Buttons: the diff title row (`[<f] [f>] [<h] [h>] [w] [z] [x]`) and the highlighted picker row (`[pin]`/`[unpin]`, `[remove]`) are drawn by the pure renderers (`DiffTitleButtons`, `PickerRowButtons`) and each button is a mouse-map view of its own, so a click runs the action of its key; buttons are dropped on narrow rows, the keys stay. The "menu" is the command palette: a click on the header bar opens it and a click on an entry runs it. While an overlay is open the wheel scrolls it (or moves the palette highlight) wherever the pointer is, and a click outside closes it (view `Backdrop`, action `cancel`); panes ignore everything else, including the toolkit's own focus-on-click. Clicking a pane title row focuses the pane; dividers and the detail/diff title rows are the resize handles.
- Background status polling (#135): `StatusReader` takes an `UntrackedFilesMode`; `BackgroundStatusPoller` uses `Normal` (`--untracked-files=normal`: an untracked directory is one entry), because the tab bar only needs to know the tree is dirty. Measured on a throwaway repo with 20,000 untracked files in 100 directories: `all` 9 ms and 288 KB of output, `normal` 1 ms and 80 bytes (cold, large real trees will show a bigger gap). The active tab keeps `All`. `RepoStatusSummary.From(StatusSnapshot)` replaces the hand-built summaries (`TabRefresher` still builds its own, #144).

## 2026-10-13

- Bottom pane tabs (#169): the detail pane has three tabs, `BottomTab` (`Details`, `Changes`, `Files`, in `Gitunia.Core.Workspaces`), stored in `RepoViewState.BottomTab` (changed by `SetBottomTabCommand`, saved in the session file as the name `BottomTab`; a missing or unknown value, as in older files, is `Changes`). `DetailContentBuilder.Build(entry, state, tab)` builds the rows of one tab (`DetailContent.Tab`; `Files` is filled on every tab so the title can count them, `FirstFileRow` only points at file rows on Changes, so the copy-path and open-diff code needs no tab special case beyond a notice). The title row starts with `DetailTabStrip`, whose layout also resolves clicks (views `DetailTab.Details|Changes|Files`, like the diff buttons). `DetailTabController` handles `detail.next-tab`, `detail.previous-tab` and `detail.tab-*`; `TuiApplication` rebuilds the rows when the tab in the state differs from the shown one and keeps one cursor row per tab while the commit stays selected (`TabSession.DetailSelections`). Keys `]` `[` `gd` `gc` `gf` live in both the Graph and Detail views (the bottom pane follows the graph selection); digits are counts and `gt` belongs to repo tabs, so they were not used. `--print-frame` takes `--tab details|changes|files`. Defaults taken without asking the owner (change them here if wrong): a fresh tab opens on Changes (keeps `Enter`, `j`, `Enter` as the way to a diff; Details is one key away), a diff opens only from Changes (so "opening a diff switches to Changes" holds trivially), Details or Files can be selected while a diff is open (the compact pane beside the diff shows that tab), and the Files tab is a placeholder until its own issue.
- Graph columns (#168): a graph row is a table, `GraphColumnLayout.Compute(width, laneColumns)` (pure, returns `GraphColumns`, like `PaneLayout`) and `GraphRowRenderer` draws it: lanes, message (ref decorations and subject), author, date, short hash, each after one space. The message flexes up to 100 columns (`MaximumMessageWidth`), so on wide terminals the other columns stay beside it and the rest of the row is blank. Author is 16 columns (longer names end with an ellipsis, wide characters are never split), date is `yyyy-MM-dd` as the author's local date (#183: the log uses `--date=raw` (`%ad`, "seconds offset") and the parser keeps the author's UTC offset in `AuthorTime`, so a late-evening commit shows the day the author saw; a bare number without offset counts as UTC; compact absolute, not relative: it needs no clock, so rows and snapshots are deterministic and the date does not change while the list is on screen; the commit details pane has the full time), the hash is the 7-digit short hash in the dim hash colour (the date is faint too). Columns are added in the order author, date, hash only while the message keeps at least 30 columns, so a narrowing terminal drops hash, then date, then author, and they come back on widening. Below about 50 columns only lanes and message remain. A search match on `author:` or `hash:` marks the whole column text; when that column is dropped nothing is marked. The widths are fixed constants rather than content-based so the columns do not shift while commits stream in. The 100k-commit key latency is unchanged (`measure.sh`: `j` median 7.4 ms).
- Look and feel (#171, owner review pending): the default look is decided by `PaletteTable` (colours of a scheme: accents, muted, selection tints, bars, lanes) and `Palette` (role to colour), documented in `docs/ux.md` ("Look and colours"). Open design questions settled with the recommended default: (1) framing keeps the existing layout (one-column dividers and title rows, no boxes around panes: a box costs two rows and columns per pane and the issue excludes layout changes); focus is shown by the filled accent chip on the focused bottom pane's title, the accent divider beside the focused sidebar or bottom pane, and the selection tint; (2) the selected row is a background tint (focused: blue; unfocused: grey) instead of reverse video, and the unfocused detail and diff panes now show their cursor row too (before, nothing marked it); (3) the palette is a GitHub-like set (dark and light variants) in 24-bit colour, with `NO_COLOR`/`TERM=dumb` falling back to styles only; the 256-colour terminal gets the 24-bit scheme because Terminal.Gui writes either 24-bit or 16-colour sequences, and the 16-colour scheme (used when `TERM` has no `256color`, or the driver reports no 24-bit support, in which case we also force the driver to 16 colours) uses only the 16 named colours so the terminal's theme decides; (4) the background is dark unless `COLORFGBG` says light (`ConsoleCapabilities.IsLightBackground`; querying the terminal with OSC 11 would cost start-up time and is not done); (5) overlays use the accent frame, the status mode, active tab and overlay title are one accent chip. `Palette` holds the configured table in a static (set once at start-up, UI thread only; the pure overload `Palette.For(segment, isSelected, isFocused, table)` is what tests use). The contrast of every role on a typical dark and light background (and on the selection tints) is a test (`PaletteTests`, ratio 4.5, dividers 3.0); 16-colour readability depends on the terminal's own theme and was not measured. `--print-frame ... --colors truecolor|16|none [--light]` prints a frame with ANSI colours (`AnsiFrameWriter`; `StyledSegment.Selection` lets a frame made of several panes mark each pane's selection, focused or dim, on its own). The start-up time is unchanged (200x60 on the 100k repository, median of 10 cold starts: ~78 ms before and after).
