# Git layer

Contract between `Gitunia.Git` and everything above it: the rules every caller and reader follows. How each feature works inside (classes, edge cases, limits) is in the code and its XML docs, and the history of decisions in `docs/internal/history/git-layer.md`.


## Running git


- **Version.** Minimum git is 2.43 (older releases lack worktree and ref-listing behaviour we rely on). `Program.Main` runs `GitVersionDetector` at startup (concurrently with repository discovery) and exits with git's "too old" or "not found" message on stderr below it; feature-detect newer capabilities (for example relative worktree paths, 2.48) instead of raising the floor.
- **Locating git.** `GitExecutableLocator` resolves git once at startup from `PATH` only and passes the absolute path in `GitRunnerOptions.Executable` and, through `TuiApplication.GitExecutable`, to `ExternalToolRunner` (difftool, mergetool, terminal retry of a remote call); the current directory is never searched (relative and empty `PATH` entries are skipped), because on Windows a bare name would run a `git.exe` from the folder Gitunia was started in. On Windows `PATHEXT` is applied, and a hit at `<Git>\cmd\git.exe` becomes `<Git>\mingw64\bin\git.exe` when that exists (one process start per call instead of two). The bare name `git` stays only as the fallback when `PATH` holds none, so the not-found error still comes from the version check.
- **Discovery.** `RepositoryDiscovery.DiscoverAsync` validates paths the user opens: bare repos, linked worktrees (kept as their own location, flagged `IsLinkedWorktree`, with the shared `CommonDirectory`), and non-repos (`NotARepositoryException`). A path inside a git directory resolves its working tree from the `gitdir` pointer, the `.git` directory name or `core.worktree`, and fails clearly otherwise.
- **Spawning, environment, machine formats, parsers.** The rules are in `.claude/rules/git-layer.md` (no shell, per-call `-c` flags, only `LC_ALL=C`, `GIT_TERMINAL_PROMPT=0` and `GIT_OPTIONAL_LOCKS=0` through `ReadOnly: true`, NUL-separated machine formats, one pure parser per command). Remote calls also set `GIT_SSH_COMMAND` and `GCM_INTERACTIVE=never` ("Remote calls"). Nothing else is set.
- **Reads without a runner call of their own.** Commit trees (`ls-tree -r -z --long`, whole tree at once, `TreeEntry`) and blobs (`cat-file blob <id>`, 1 MiB cap, NUL in the first 8000 bytes means binary) are described in their classes; detail in `docs/internal/history/git-layer.md`.
- **Every call** takes a `CancellationToken` and a timeout, captures stderr and maps the exit code to a typed error. Long operations (fetch, pull, push, clone) stream progress (`--progress`) to the caller.
- **Conflicts** (`IConflictReader`, `ConflictReader`, `ConflictParser`, `IConflictWriter`, `ConflictWriter`, `IConflictRecreator`, `ConflictRecreator`; #696, feeds the conflict editor of #689 and #690): the reader is read-only (`ReadOnly: true`, no serialisation needed). `ls-files -u -z -- :(literal)<path>` names the stages that exist; a missing ours or theirs stage (delete/modify), a symlink or submodule, a binary file (NUL in the first 8000 bytes), a file over 1 MiB, text that is not valid UTF-8 and a file with no markers left are `ConflictReadKind.Unsupported` with a reason that ends in "use the mergetool". A missing base stage alone is add/add: it reads like any text file, with an empty base (`Base = ""`, no `merge-file` base merge). Otherwise the hunks are parsed from the working-tree file, because its markers hold each side's conflicting text (and the base for `diff3`/`zdiff3`) and show what the user already edited by hand. A merge-style hunk (no `|||||||` section) gets its base from `ConflictBaseFinder`: `cat-file blob :1:`, `:2:` and `:3:<path>` go to a private temp directory and `merge-file -p --diff3` merges them (exit code = number of conflicts, 1 to 127 accepted; the working tree and index are untouched); a file hunk takes the base of the next merge hunk whose ours and theirs match (line terminators ignored), else stays without base, and any git or IO failure leaves the hunks as parsed. `ConflictParser` is pure: `merge`, `diff3` and `zdiff3` markers, a marker size other than 7 (`conflict-marker-size`), line terminators kept exactly (CRLF stays), a `=======` line outside a hunk stays text, and unbalanced markers (a second opening inside a hunk, a missing close) are a reported problem, never guessed at; so is any line of seven or more `<` in a file that merely documents conflicts. `ConflictWriter` runs no git: it overwrites the working-tree file in place (UTF-8, no BOM added; not atomic, so the caller keeps the resolved text in memory until the write succeeds) and refuses a path outside the working tree or inside `.git`; it never touches the index (marking resolved is an `add`). `ConflictRecreator` (#690) runs `checkout --merge -- :(literal)<path>` (a write call, 1 minute timeout): the file gets its markers back in the user's `merge.conflictStyle` and a file already marked resolved gets its stages back from the resolve-undo record; git's refusal (no recorded conflict) is the thrown `GitCommandFailedException`.
- **User environment.** Credentials, hooks, signing and identity come from the user's real config. Prompts cannot reach a redirected git (stdin is closed), so a call that may prompt either fails with git's message or goes through `ExternalToolRunner` (`architecture.md`); a failed fetch, pull or push offers the terminal (#45, "Remote calls").

### Runner (`GitRunner`)

- `RunAsync` collects output; `StreamAsync` yields stdout chunks (idle timeout that pauses while the consumer works, errors surface after the last chunk, disposing early kills git). A chunk is a view of one pooled 64 KiB buffer, valid only until the next chunk is requested: parse or copy it first. Errors are `GitCommandFailedException` (exit code not in `AcceptedExitCodes`), `GitTimeoutException`, `GitNotFoundException` (only "file not found"/"path not found": ENOENT, `ERROR_FILE_NOT_FOUND`, `ERROR_PATH_NOT_FOUND`), `GitStartFailedException` (any other start failure, with the native message: command line too long, access denied), `GitVersionTooOldException`; a missing repository folder is not a start failure (the runner passes `-C` and never sets the process working directory, so git itself exits 128 and it surfaces as `GitCommandFailedException`); cancellation raises `OperationCanceledException`; timeout or cancel kills the whole process tree (`ProcessKiller` ignores kill errors, including an `AggregateException` for a part of the tree that cannot be stopped, so they never replace the real result). Git exiting ends the call: a background child of a hook that keeps stdout or stderr open gets a 1.5 s drain grace, then the readers are cut (only a read that stays pending that long after the exit, so output already in the pipe is always read first and a busy consumer never loses data; `RunAsync` also stops reading 5 s after the exit for a child that keeps writing) and the exit code and what was read count (no pipe-EOF hang).
- Stdin is closed at once unless the call sets `GitRunOptions.StandardInput` (patches, `commit -F -`, paths; `RunAsync` only). Read-only polling passes `ReadOnly: true`; mutating calls never do. `GitRunnerOptions.EnvironmentOverrides` is for tests only. `OnStandardErrorLine` reports stderr segments (split at LF and CR) and makes the timeout an idle limit.

### Remote calls (`RemoteRunner`, `IRemoteWriter`)

- Fetch, pull and push run through `RemoteRunner` with `IProgress<RemoteProgress>` parsed from stderr and an idle timeout of 2 minutes of silence. A pull is `fetch --progress` then `merge --ff-only @{upstream}` (the user's `pull.rebase` never applies; a diverged pull throws `PullDivergedException` after the fetch). The merge step is never killed: a cancel is honoured between fetch and merge only. A plain force push does not exist: `PushRequest.Lease` (`--force-with-lease=refs/heads/<b>:<expected>`, the tip of our remote-tracking branch) is the only way to overwrite. A cancelled fetch leaves the repository consistent.
- `BranchWriter.FastForwardAsync` fetches `<upstream>:refs/heads/<b>` from the repository itself (no `+`), so git checks fast-forward and the checked-out refusal atomically. `RemoteManager` runs `remote add|remove|rename|set-url -- <args>` as plain config writes (remove is always behind a Confirm).
- **No prompts.** `SshCommandPolicy` sets `GIT_SSH_COMMAND` to the effective ssh command plus `-o BatchMode=yes`, only when that command is plain `ssh` (its first word, or a leading quoted path with spaces; a `GIT_SSH` program or another client is left alone); without it ssh opens `/dev/tty` even with stdin closed. `GCM_INTERACTIVE=never` stops Git Credential Manager from opening its sign-in window, which ignores `GIT_TERMINAL_PROMPT`, opens behind the terminal and would hold the call until the idle timeout (#1313); the call fails with `terminal prompts disabled` instead. `RemoteAuthFailure.Matches(stderr)` recognises auth failures (not a missing repository, a refused push or a network error); the UI then offers the same command in the terminal. `RemoteCommands` builds the arguments for both paths (background with `--progress`/`--no-progress`, terminal retry without; a pull there is `pull --no-rebase --ff-only`); the retry sets no environment.

### Clone and init (`IRepositoryCreator`)

- They run outside any `-C` (`RunGlobalAsync`) with absolute paths; `CloneSource.Resolve` makes a typed local path absolute against an explicit base directory and leaves URLs alone. The clone target must be missing or an empty directory (`CloneTargetException` before git runs). A failed or cancelled clone removes what it created; init keeps a non-empty directory's files and returns an existing repository root as is (`InitResult.WasRepository`). No prompts, as in "Remote calls".

### Paths that are not valid UTF-8

- Status output is decoded with `GitPathText.Decode`: valid UTF-8 as is, every invalid byte becomes the lone surrogate `U+DC00 + byte`. `StatusEntry.Path` therefore round-trips byte-exactly through `GitPathText.Encode`. Display code must treat lone surrogates as replacement characters.
- Such a string cannot be a process argument (the runtime would replace the surrogates). Stage, unstage and discard pass paths on stdin with `GitOptions.PathspecFromStandardInput` + `PathspecFileNul` and `GitPathText.EncodePathspecFile`.
- Diffs are decoded lossily. `DiffFile.HasInvalidText` marks a file with invalid UTF-8 in a path or line, and `DiffPatchWriter` throws `InexactPatchException` for it, so line and hunk staging is refused and the file is staged whole by path.
- Deleting an untracked file by raw bytes goes through `IByteExactFileSystem` (Linux only; elsewhere an explicit "unsupported" result, `architecture.md`).


## Mutating operations

All take the repository location, are never `ReadOnly`, and run one at a time per tab (the caller enforces it). Each class's XML docs hold the edge cases; the rules below are contracts callers rely on.

| Operation | Class | Git command | Contract |
|---|---|---|---|
| Index | `IIndexWriter` | `add`, `restore --staged`, `apply --cached [-R] -` | Paths on stdin with `--literal-pathspecs`. |
| Partial staging | `PatchStager` | `apply --cached` with a rebuilt patch | Never builds a patch from the rows on screen: re-reads the diff, matches lines by kind, number and text, falls back to the whole file for what a partial patch cannot represent. Typed `PatchStagingResult`. |
| Reflog | `IReflogReader` | `reflog show --format=... -n` | Read-only. |
| Line history | `IFileHistoryReader.ReadRangeAsync` | `log --format=... -n <limit> -L<start>,<end>:<path> <revision> --` | Read-only. `-L` takes no pathspec and follows moved lines and renames itself, so the line numbers are those of the file at `<revision>` (`HEAD` for the Changes view, the shown commit otherwise), not of the working tree. The patch of each commit stays on its `FileHistoryEntry.Patch` and is parsed by `DiffParser` when the entry is highlighted. A range beyond the file or a missing path is git's own fatal error, shown as the failure text. |
| Blame | `IBlameReader` | `blame --incremental [-w] [-M] [-C] [<rev>] -- <path>` (`BlameOptions`; `<rev>` may be `<id>^`); `config --get blame.ignoreRevsFile` (git blame reads that file itself, the reader only reports it); lines from `cat-file blob <rev>:<path>` or the working tree file | Read-only. The lines (`ReadContentAsync`: UTF-8, else Latin-1; CRLF and a BOM dropped; a NUL in the first 8000 bytes means binary) and the blame (`BlameAsync`, streamed) are two reads, so a view shows the lines before the history is walked. `BlameParser` is incremental: a chunk of output may end inside a line, a commit's headers appear only the first time it is named, a record ends at `filename`. Chunks arrive in the order found, not file order; renames are followed (default behaviour); the zero id is an uncommitted line; `boundary` marks a boundary commit. |
| File history | `IFileHistoryReader` | `log --follow --find-renames --name-status -z --format=... -n <limit> <revision> -- :(literal)<path>` | Read-only. The parser tracks the file's name across renames; a commit without a status line (a merge) takes the followed name. The diff of one entry is `FileHistoryDiffCommand` (`show --format= -m --first-parent <hash> -- <path> [<old path>]`) run by `IDiffReader.ReadAsync`. |
| Message search | `ICommitMessageSearcher` | `log -z --grep=<text> --fixed-strings --all` | Only for `body:` queries; read-only, 60 s timeout. |
| Reset | `IResetWriter` | `reset --soft\|--mixed\|--hard <commit>^{commit}` | Returns the previous HEAD hash for the undo hint; the UI does the checks and the Confirm. |
| Ancestry | `IAncestryReader` | `merge-base --is-ancestor` | Exit 0 yes, 1 no, else throws; decides whether a force push is offered. |
| Worktrees | `IWorktreeWriter` | `worktree add\|remove\|lock\|unlock\|prune` | A locked worktree is refused even with force; the branch is kept. `ListChangesAsync` names what a forced remove would lose. Reads stay in `RefReader`. |
| Discard | `IWorkingTreeDiscarder` | `restore --worktree`, `clean -f -d`, `apply -R` | Cannot be undone, callers confirm first; `clean` never touches tracked or ignored paths; hunks and lines touch the working tree only. |
| Stash | `IStashWriter` | `stash push\|apply\|pop\|drop` | Push compares `refs/stash` before and after (git exits 0 on "nothing to save"); apply, pop and drop find the entry by commit hash, not `stash@{n}`; a conflicting apply or pop is `Conflicted` and the stash is kept; undo of a drop is `stash store`. `CheckRestoreAsync`/`RestoreFileAsync` copy one file from the stash (`--literal-pathspecs restore --source=<hash> --worktree`, untracked files from `<hash>^3`); the state (missing, not in stash, identical, creates, overwrites) is decided by comparing `rev-parse <src>:<path>` with `hash-object <path>`, and an overwritten file is first saved with `hash-object -w` (its id is the undo). |
| Stash details | `IStashDetailsReader` | `diff-tree --raw`, `DiffReader` | Read-only, addressed by hash; tracked and untracked parts are separate; the files read returns null when the hash is gone. |
| Config | `IGitConfigReader` | `config --type=bool --get rebase.autoStash` | Read with the refs of a refresh; `RebaseGuard` skips the dirty-tree refusal when set. |
| Rebase | `IRebaseWriter` | `-c core.editor=true rebase <onto>^{commit}` | Through `OperationRunner`; non-interactive; a target starting with `-` is refused. |
| Quick rebase | `IQuickRebaseWriter` | the interactive engine | Fixup, reword, drop of one commit; `PlanAsync` then `RunAsync` re-reads the range and refuses a different one. |
| Interactive rebase | `IInteractiveRebaseWriter` | `rebase --interactive --no-update-refs --empty=drop` with `sequence.editor` | Validates one entry per commit in replay order (`RebaseTodoValidator`); the editor is `gitunia --sequence-editor` (no new environment variable; a set `GIT_SEQUENCE_EDITOR` is refused with `RebaseEnvironmentException`; needs the published binary). `--rebase-merges` ranges are read by letting git write the todo and failing the editor. The read creates and removes `.git/rebase-merge`, so it is refused while an operation runs. `OriginalHead` is the undo hint. | Commit | `ICommitWriter` | `commit -F - [-s] [--no-verify] [--amend]` | Message on stdin as typed, 10 minute timeout for hooks, returns the new HEAD plus the previous one for an amend. `$EDITOR` commits are not a runner call. |

- **Merge** (`IMergeWriter`, `MergeWriter`; #38): `merge --no-edit [--no-ff|--squash] <target> --`, result `MergeResult` with `MergeKind` (`UpToDate`, `FastForward`, `MergeCommit`, `Squashed`, `Conflicted`) and the old and new HEAD. A normal merge goes through `OperationRunner`, so a stop on conflicts is a `Conflicted` result with the operation in progress; a squash writes no `MERGE_HEAD`, so its conflicts are recognised from a changed unmerged set and no operation is in progress. A branch arrives as its full ref (`refs/heads/x`, `refs/remotes/o/x`); the writer passes the short name when it resolves to the same commit, so git writes its own message (`into <branch>`, `merge.log`, `merge.suppressDest`), and keeps the full ref with `-m "Merge branch 'x'"` only when a tag of the same name would win (that message has no `into` part). A commit is passed by hash.
- **Operations** (`IOperationWriter`, `OperationWriter`, `OperationRunner`, `IOperationInfoReader`): continue, abort and skip of a stopped merge, rebase, cherry-pick or revert run `git -c core.editor=true <op> --continue|--abort|--skip`, so no editor opens for the prepared message (an editor named by the user's `GIT_EDITOR` still wins; that variable is not touched). Every call that starts or advances an operation returns the one `OperationResult(Outcome, Head)` with `OperationOutcome.Completed`, `Conflicted` or `Emptied` (a continue of a cherry-pick or revert whose index equals HEAD with nothing unmerged would be refused by git as "now empty", so the writer runs `--skip` instead and reports `Emptied`; #1284); #38-#40 (start a merge, rebase, pick or revert) reuse it through `OperationRunner.RunAsync(location, arguments)` and pass `-c core.editor=true` or `--no-edit` themselves. A failed call is `Conflicted` only when the operation is still in progress and the set of unmerged files changed (a rebase that stops on the next commit); a continue with nothing resolved, a dirty tree or a refusing hook still throws `GitCommandFailedException` with git's message. Abort runs through `RunToCompletionAsync`, which never reports `Conflicted`. A merge cannot be skipped. `OperationInfoReader` reads the banner details from the state files without spawning git (`OperationInfo`: target branch, rebase step and total, commits left in a pick range, the stopped commit with its subject, the original tip when the files name it).
- **Cherry-pick and revert** (`IPickWriter`, `PickWriter`; `IPickCommitReader`, `PickCommitReader`): `git cherry-pick --no-edit --empty=drop [-m n] <commits> --` or `git revert --no-edit [-m n] <commits> --` through `OperationRunner`, so a stop on conflicts is `PickOutcome.Conflicted` (the sequencer state then drives continue, abort and skip) and a pick whose commits HEAD already has is `NothingToApply` (a git that does not know `--empty` answers with a usage error before anything ran and the call is repeated without it; an empty pick then stops like git's default). A revert that would be empty fails with git's message. A call that fails without a conflict stop but leaves its own pick or revert in progress (a range whose later commit turns empty) is aborted with `--abort`, so the tip returns to where it was and git's message is thrown; a cancel or timeout midway of a multi-commit sequence is aborted the same way (the earlier commits are undone, with a `reset --merge` to the old tip when a kill during a commit made the abort skip the rewind; the undone commits stay in the reflog; a single-commit pick that was already committed is not rolled back; an abort that itself fails leaves the sequence in progress); an operation that was already in progress is never aborted. A list over `PickWriter.MaxCommits` (500, keeps the command line under the Windows limit) is refused with a clear message before anything runs. The caller fixes the order of the commits. `PickCommitReader` reads subjects and, for merge commits, their parents with subjects (`log --no-walk=unsorted`, one call, a second only when a merge is among them) for the mainline prompt.

## Parsers

Rules: `.claude/rules/git-layer.md`.

- **Diffs.** `DiffReader.ReadAsync(location, ["diff", ...])` streams `DiffFile` > `DiffHunk` > `DiffLine`, addressed by file, hunk and line index with old/new line numbers. Headers and hunk lines are kept verbatim so patches reproduce git's text. Binary files carry no hunks, only header lines. `IDiffReader.ReadWorkingFileAsync` reads one file of the Changes view (unstaged, staged, untracked via `--no-index`, conflicted via `DiffParser(readsCombined: true)`); paths go as `:(literal)` pathspecs after `--`. Limits, combined diffs and non-UTF-8 handling: `docs/internal/history/git-layer.md`.

## Models

- **Repository:** path, git dir, common dir, HEAD state (branch, detached, unborn; `RefReader.ReadHeadAsync`), operation in progress (merge, rebase, cherry-pick, revert, bisect).
- **Worktree:** path, HEAD, branch, locked, prunable, bare, per-worktree dirty summary. Worktrees are first-class: every view that shows a branch also shows which worktree has it checked out.
- **Branch/ref:** local, remote, tag, upstream, ahead/behind, last commit, checked-out-in (worktree).
- **Status:** staged/unstaged/untracked/conflicted per path. The Unstaged list holds worktree changes, untracked and conflicted paths; ignored entries are in no list.
- **Commit graph:** hash (`ObjectId`, a fixed 40-byte struct), parents, author, date, subject, refs. Lane assignment is a pure function computed incrementally from `rev-list --parents` order, so it can be tested and cached.
  - A lane waits for exactly one commit id; lanes are not shifted left, so columns do not jump while scrolling or loading.
  - **Lane order (#757).** A branch tip takes the leftmost free lane, so the newest tip is leftmost; the layout never reads HEAD.
  - **One lane per branch (#759).** A first parent continues its commit's lane even when another lane waits for it, so every lane runs to its fork commit, where lanes join (several `Incoming` edges).
  - **Merge from the left (#1234).** A later parent of a merge joins the leftmost open lane already waiting for it (the edge runs from the node to that lane, whichever side it lies on); only a parent no lane waits for opens a new lane. The layout never looks ahead, so a merged-in commit that a lane reaches only further down still gets its own lane until the two join there.
  - **Colours (#761, #807, #849).** A lane takes the colour slot of its branch name (`BranchColors`, from a separate `log --no-walk` read started with the log; lanes fall back to their first commit when it fails), moved on to a slot no open lane and no tip of the last 50 rows uses. `GraphRow.LabelSlots` colours the chips. Behaviour: `docs/internal/ux-workflows.md`, graph.
  - `GraphRow.LaneFingerprint` hashes the commits the open lanes wait for, so an incremental reload only joins old rows where the layout below is the same.


## Refresh

- **Polling (default, #543).** No file watchers unless `watchFiles` is set. `TabPoller` polls the active tab only: every 2 s `RepositoryFingerprint` (name, size, time of files in the git directory, `refs/`, `reftable/` (reftable repositories, git 2.45+, where `HEAD` and `refs/heads` are stubs), the identity files of other worktrees; off the UI thread), hashed per group (HEAD, refs, index, worktrees, operation files; other worktrees' `index` and `logs` are left out, as the classifier does). A changed group requests only its kinds: HEAD or refs `Head|Refs`, index `Index|WorkingTree`, worktree identity `Worktrees`, operation files `Operation` plus the status kinds. After a refresh Gitunia ran itself (stage, commit, manual) the poller takes a new fingerprint for the groups that refresh covered (`TabPoller.AcceptRefresh`), so its own writes are not read as outside changes. Otherwise a status refresh every 5 s. A refresh that took t postpones the next status refresh to at least 5 t (at most 60 s); a failed or timed-out one counts the same (its elapsed time) and the wait doubles for each failure in a row until a refresh succeeds (`RefreshBackoff`, #1307). A tick is skipped while the tab is busy and never overlaps a running read; a hidden tab does not poll and checks at once when shown. Own actions refresh right after they finish. Terminal focus-in triggers `TabPoller.CheckNow` (at most one check per 1.5 s, `PollOptions.FocusThrottle`; a check also ignores the status back-off, since the user came back): `TerminalFocusReporting` enables DECSET 1004 and registers `ESC [ I`/`ESC [ O` on the driver's ANSI parser (Linux, macOS, Windows; elsewhere explicitly unsupported, focus just does not refresh; a process killed by a signal may leave the shell echoing `^[[I` until `reset`). `<space>or` is the manual refresh. Costs: `docs/internal/performance.md`.
- **Processes per refresh (#1310).** `RepositoryRefresher` takes HEAD from the `# branch.head` / `# branch.oid` header of the status it reads anyway (`RefReader.ReadHeadAsync` stays for the first load and the frame printer), so a refresh that reads refs starts three processes (refs, worktrees, status) and a status-only one starts one. `TabRefresher` copies the graph rows only for a refresh that reads refs or is the baseline. The diff prefetch reads a neighbour with one `show --first-parent` (`IDiffReader.ReadCommitAgainstFirstParentAsync`) instead of a first-parent lookup plus the diff. Counts are tested with `GitRunner.StartedCount`.
- **Watching (opt-in).** `"watchFiles": true` gives each tab a `RepositoryWatcher` instead of the poller (git directory, common directory, `refs/`, `reftable/`, `worktrees/`, working tree). `RepositoryChangeClassifier` maps paths to `RepositoryChangeKinds`; events are merged and debounced (200 ms quiet, at most 2 s). A background tab keeps pending kinds and reports them on activation. `WatchBudget` caps watchers across tabs (64); a tab that cannot get slots, or whose watcher fails (inotify limit), polls every 5 s instead (a one-shot timer, so polls never overlap, and no status refresh is asked for again until the last one finished; a hidden tab skips its polls and polls at once when shown; the interval backs off like `TabPoller`'s after a slow, failed or timed-out refresh, via `RepositoryWatcher.RecordRefresh`). On Linux working-tree watching is ignore-aware: a non-recursive root watcher plus one per directory listed by `WorkingTreeDirectoryLister` (a single `ls-files -z --cached --others --exclude-standard`), capped per tab at a quarter of `max_user_instances` (`InotifyLimit.DirectoryCap`, 16 to 2048), then polling; Windows and macOS use one recursive watcher (64 KiB buffer; the git-directory watchers use 16 KiB) that drops events under the working tree's own `.git` and under ignored directories (one `ls-files --others --ignored --exclude-standard --directory` read after `Start`, repeated when a `.gitignore` in the working tree or `info/exclude` changes (its `info/` directory is one more watcher when it exists), and every 5 minutes (`IgnoredReloadInterval`; a hidden tab reads when shown) for `core.excludesFile`, whose path is not known without the git config, with bursts of edits collapsed into one more read; events before it arrives pass; a directory holding only ignored files counts as ignored). A buffer overflow (`InternalBufferOverflowException`, routine during an install or build) reports everything once and keeps watching; any other watcher error makes the tab poll and try to watch again after 60 s (`WatcherRetryInterval`). The first fallback fingerprint is read on a thread pool thread outside the lock, so `Start` does not wait for it; `StartAsync` also creates the watchers on a pool thread, and neither it nor the retry holds the watcher lock while planning or creating them (only taking the slots and publishing happen under it; a watcher disposed or fallen back to polling meanwhile retires what it made, #1351). Each watcher is one `WatchBudget` slot (counted per handle, not by size; only the buffers differ). Only a `FileSystemWatcher` error arms the retry; the inotify limit and the directory cap keep polling. Files inside `.git/rebase-merge` and similar are not watched on Windows and macOS (as on Linux); HEAD and index events follow them. Limits: files written between `Start` and the first listing, directories holding only ignored files, and submodule contents are not watched.
- **Incremental refresh.** `RepositoryRefresher.RefreshAsync(location, previous, kinds)` re-reads only the sections the kinds can affect (head and refs together, worktrees, status; operation files are always checked) and returns the new `RepositorySnapshot` plus the `RepositorySections` that actually differ. Unchanged sections keep the previous object, so views compare by reference and a refresh never resets scroll or selection.
- **Background status.** `BackgroundStatusPoller` runs `git status` for every non-active, non-missing tab, sequentially, at start and every 30 s, and dispatches only when the summary changed. A repository whose read failed or timed out is skipped for a growing period (doubling per failure in a row, at most 5 min) and one that read slower than about two fifths of a pass waits five times its read time (`ReadBackoff`, #1307). It loads nothing else, so unvisited tabs stay cheap; tab bar markers lag by up to the interval. Status polling uses `--untracked-files=normal` (the tab bar only needs to know the tree is dirty).
- **Worktree overview.** `WorktreeOverviewPoller` runs `git status` in every other worktree of the active tab, one at a time, when the tab or its worktree list changes and every 30 s (bare and prunable skipped, an unreadable one keeps its last value and is skipped on the timer for a growing period like background tabs, `ReadBackoff`; a change of the tab or its worktree list reads every worktree again). It only reads and posts `WorktreeStatusesRead`; whether the tab still takes the result (it moved, was closed, nothing changed) is decided in `WorktreeReducer`. `SwitchWorktreeCommand` replaces the tab's location and runs the load effect again; view state, refs and sidebar stay.
- **Working-tree state.** Every loaded tab keeps the full `StatusSnapshot` in `RepositoryState.WorkingTree` (snapshot plus the selected file by section and path). A new snapshot replaces it and re-finds the selection (same path and list, else the same path in the other list after a stage or unstage, else the row near the old index); a snapshot with the same content returns the same state, so a refresh never repaints or loops. The background poller updates only the summary, so a background tab's snapshot may be older than its markers until the tab is activated. After stage or unstage the cursor stays at the same index of its list. List order is git's order; any display ordering is applied in the state layer so indexes stay the row indexes.
- **Wiring.** `TabRefresher` (`Gitunia.App/Tabs`) is created by the effect runner when a tab's load starts and owns that tab's `TabPoller` (or, with `watchFiles`, its watcher). After the initial load it records a baseline snapshot (and reloads the graph when a change was seen meanwhile or the loaded graph's decorations differ from the baseline refs). Each change then runs `RefreshAsync` off the UI thread (one at a time; changes arriving meanwhile are merged) and dispatches commands only for the sections that differ (stashes are re-read when HEAD or refs changed). Failures are reported once through `StatusChannel`; a manual refresh (`<space>or`) always reports its outcome.
- **Graph reload.** The graph is swapped in only when HEAD or refs changed, or on manual refresh. An automatic reload is incremental (`IncrementalGraphLoader`): it streams the new log and stops at the first row equal to the old graph (`GraphSplicer` via `LaneFingerprint`), re-reads the refs of the few ref-carrying commits and reuses the old rows below. A branch change on a reused commit only replaces refs; the full read is the fallback when the primary branch name of a commit that chose a lane colour (`GraphRow.ColorChosenByName`) changed, or on any mismatch. A manual refresh always reads everything. After either, the selected commit stays on the same screen row, except that a cursor that was on HEAD follows HEAD to its new row and the list scrolls to show it (#1182).
- **Soft row limit (#515).** A log longer than `GraphLoader.SoftRowLimit` (100,000) loads only its newest rows (`StreamCappedAsync`, then `rev-list --count`). `RepositoryLoader.ExpandAsync` streams the log again on demand and appends the rows below the cut; a replaced graph makes a running expansion stale. A refresh of a cut tab reads the newest rows again instead of splicing. Numbers: `docs/internal/performance.md`.
- **Limits.** A branch name added by an incremental reload on a reused commit has no `LabelSlots` entry and its chip takes the hash colour; a local and a remote branch of one name on different commits share one slot until the next full read (cosmetic). History rewritten below the join without changing the commit count (a `git replace` ref) is only picked up by a manual refresh. A selected commit that disappeared keeps its row position (unless the cursor was on HEAD, which it follows).
