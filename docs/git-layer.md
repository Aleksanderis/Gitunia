# Git layer

Contract between Gitunia.Git and everything above it.

## Running git

- Minimum supported git is 2.43 (older releases lack worktree and ref-listing behaviour we rely on and are out of mainstream support). Detect the version at startup with a clear error below it; feature-detect newer capabilities (for example relative worktree paths, 2.48) instead of raising the floor.
- Repository-scoped API. Every reader is an instance that holds a `GitRunner` and takes the `RepositoryLocation` it reads as an argument on every call (no handle, no static "current repo"); git is run with that path as working directory (`-C`), never relying on the app's cwd. Repository discovery (`RepositoryDiscovery.DiscoverAsync`, `rev-parse --show-toplevel/--git-common-dir`) validates paths the user opens, including bare repos, linked worktrees (kept as their own location, flagged `IsLinkedWorktree`, with the shared `CommonDirectory` for grouping them under their main repo) and non-repos (`NotARepositoryException`). A path inside a git directory resolves its working tree from the `gitdir` pointer, the `.git` directory name or `core.worktree`, and fails clearly otherwise.
- Spawn `git` with `ProcessStartInfo` (no shell), arguments as a list, `-c core.quotepath=off` and similar per-call `-c` flags rather than mutating user config.
- Environment: `LC_ALL=C` for parsed output, `GIT_TERMINAL_PROMPT=0` for background calls, `GIT_OPTIONAL_LOCKS=0` for read-only status polling (avoids fighting the user's other git processes over `index.lock`). Nothing else is set.
- Prefer machine formats: `status --porcelain=v2 -z`, `for-each-ref --format=...`, `log --format=... -z`, `worktree list --porcelain -z`, `rev-list --parents`, `diff --raw -z`, `cat-file --batch` for bulk object reads.
- Runner API (`GitRunner`): `RunAsync` collects output, `StreamAsync` yields stdout chunks (its timeout is an idle timeout that does not run while the consumer handles a chunk; errors surface after the last chunk; disposing early kills git). Errors are `GitCommandFailedException` (exit code not in `GitRunOptions.AcceptedExitCodes`), `GitTimeoutException`, `GitNotFoundException`, `GitVersionTooOldException`; cancellation raises `OperationCanceledException`. On timeout or cancel the whole process tree is killed. Read-only polling must pass `ReadOnly: true` (sets `GIT_OPTIONAL_LOCKS=0`); stdin is closed so git never waits for input. `GitRunnerOptions.EnvironmentOverrides` exists for test isolation; production code must not use it.
- Every call: `CancellationToken`, timeout, captured stderr, exit code mapped to a typed error. Long operations (fetch, pull, push, clone) stream progress (`--progress`) to the caller.
- Credentials and hooks run in the user's real environment. Interactive prompts (ssh passphrase, credential helper UI) need a defined story (open question in `roadmap.md`).

## Parsers

- One parser per command, pure functions over `ReadOnlySpan<byte>`/string, with fixture-based tests (captured real output including odd cases: renames, copies, unicode paths, spaces, detached HEAD, unborn branch, merge in progress).
- Parsers never throw on unknown fields; they ignore them and surface a warning.
- Diffs: `DiffReader.ReadAsync(location, ["diff", ...])` streams `DiffFile` > `DiffHunk` > `DiffLine` (addressed by file, hunk and line index, with old/new line numbers). `DiffPatchWriter` writes files and hunks back verbatim, and `WriteSelection` builds a patch of chosen lines for `git apply --cached` (`-R` for `PatchDirection.Reverse`). Binary files carry no hunks, only header lines. Details and limits: "Design notes" below (#15).

## Models

- Repository: path, git dir, common dir, HEAD state (branch, detached, unborn; `RefReader.ReadHeadAsync`), operation in progress (merge, rebase, cherry-pick, revert, bisect).
- Worktree: path, HEAD, branch, locked, prunable, bare, per-worktree dirty summary. Worktrees are first-class: every view that shows a branch also shows which worktree has it checked out.
- Branch/ref: local, remote, tag, upstream, ahead/behind, last commit, checked-out-in (worktree).
- Commit graph: hash, parents, author, date, subject, refs; lane assignment computed incrementally from `rev-list --parents` order. Graph layout is a pure function so it can be tested and cached.
- Status: staged/unstaged/untracked/conflicted per path, with hunk/line addressing for partial staging (`git apply --cached` with generated patches).

## Refresh

- One watcher set per open tab, debounced; background tabs mark themselves stale and refresh on activation. Cap total watchers and fall back to polling.
- Watch `.git` (and each worktree's gitdir) with `FileSystemWatcher`, debounced, plus manual refresh. Fall back to polling where watching is unreliable.
- A refresh recomputes only what changed (refs, status, worktrees) and never resets scroll or selection.
- Implementation (`Gitunia.Git`): `RepositoryWatcher` is the watcher set of one tab. It watches the git directory, the common directory (linked worktrees), `refs/`, `worktrees/` (each linked worktree's gitdir, added when the directory appears later) and the working tree with `FileSystemWatcher`. `RepositoryChangeClassifier` maps a path to `RepositoryChangeKinds` (head, refs, index, working tree, worktrees, operation; lock files, objects and logs are ignored). Events are merged and debounced (200 ms quiet, at most 2 s under a continuous stream); the callback gets the merged kinds on a thread pool thread.
- `SetActive(false)` marks a background tab: it keeps the pending kinds, reports nothing and `IsStale` is true and `BecameStale` is raised once (thread pool) when the first change arrives or when a tab with unreported changes is hidden; `SetActive(true)` reports them at once and re-arms `BecameStale`. The notification goes through an optional `queueNotification` constructor parameter (thread pool by default) and `ReportChange(kinds)` feeds a change in without a file event, so tests assert once/re-arm without sleeps (#170).
- `WatchBudget` caps watchers across all tabs (64 by default; a tab needs 3 to 6). A tab that cannot get its slots, or whose watcher fails to start or raises an error (for example the inotify limit), polls every 5 s instead: a cheap fingerprint of the git directory, refs and worktrees files, plus a working-tree status refresh on every tick. The working tree watcher is recursive, which on Linux costs one inotify watch per directory.
- `RepositoryRefresher.RefreshAsync(location, previous, kinds)` re-reads only the sections the kinds can affect (head and refs together, worktrees, status; operation files are always checked) and returns the new `RepositorySnapshot` plus the `RepositorySections` that actually differ. Unchanged sections keep the previous object, so views can compare by reference and leave scroll and selection alone.
- Background tabs: `BackgroundStatusPoller` (`Gitunia.Tui/App`) runs `git status` for every non-active, non-missing tab, sequentially, at start and every 30 s, and dispatches `StatusLoadedCommand` only when the summary changed. It loads nothing else, so unvisited tabs stay cheap while the tab bar markers stay right (#129). Limit: markers lag by up to the interval.
- Wiring (`Gitunia.Tui/App/TabRefresher`): `EffectRunner` creates one `TabRefresher` per tab when the tab's load starts; it owns the tab's `RepositoryWatcher` (`SetActive` follows the active tab, so background tabs refresh on activation). After the initial load it records a baseline snapshot (and reloads the graph when a change was seen meanwhile or when `GraphRefCheck` finds the loaded graph's branch, tag and detached-HEAD decorations differ from the baseline refs, which covers a change made between the load and the baseline read), then each change runs `RefreshAsync` off the UI thread (one at a time, changes arriving meanwhile are merged) and dispatches commands only for the sections that differ (HEAD, refs, worktrees, status summary; stashes are re-read when HEAD or refs changed). The graph is swapped in (`TabSession.ReplaceGraph`) only when HEAD or refs changed or on manual refresh (`r`); an automatic reload is incremental (`IncrementalGraphLoader`, #126): it streams the new log from the top and stops at the first row that equals the old graph (same commit, lane, edges and open lanes below it, `GraphRow.LaneFingerprint`, found by `GraphSplicer`), checks the total with `rev-list --count`, re-reads the refs of the few ref-carrying commits (`--no-walk`) and reuses the old rows below; any mismatch or no join falls back to the full read, and a manual refresh always reads everything; `GraphTabBinder` keeps the selected commit selected and on the same screen row, and the graph search restarts its scan. Failures are reported once through `StatusChannel`; a manual refresh always reports its outcome ("<repo>: refreshed" or the failure). Limits: a selected commit that disappeared keeps the old row position; an incremental reload trusts the old rows below the join, so history rewritten below it without changing the commit count is only picked up by a manual refresh (`r`).


## Design notes

Details moved out of `decisions.md` (#253). Notes are historical: where a later note contradicts an earlier one, the later one wins.

- Standalone launch (spike #3) findings for M1: resolve paths with `git -C <path> rev-parse`; check `--is-bare-repository` before `--show-toplevel`; a linked worktree has `--git-dir` != `--git-common-dir`; dedupe tabs by the resolved toplevel; a path inside a `.git` directory needs its own case. Resolving costs 0-2 ms.

- Commit ids are a fixed 40-byte `ObjectId` struct (SHA-1 or SHA-256) instead of interned hash strings (#13). Why: no intern table or string per parent link, equality and hashing without allocation. Cost: 40 bytes per id even for SHA-1 (about 12 bytes padding); per-commit memory is still dominated by `CommitInfo`, its subject string and decorations. Author names and emails are interned. The default log excludes `refs/stash` so stash commits do not appear as graph nodes; callers that pass revisions get exactly those.

- Diff parser (#15): `DiffParser` is incremental (feed byte chunks; a file is emitted when the next `diff --git` starts, so memory is bounded by the largest single file) and keeps every header and `@@` line verbatim, so `DiffPatchWriter.WriteFile` reproduces git's text exactly. `DiffReader` fixes the options that make output predictable (`--no-color --no-ext-diff --no-textconv --src-prefix=a/ --dst-prefix=b/ --find-renames --find-copies`); callers add the rest (`--cached`, `--binary`, `-U<n>`, `--format=` for `show`). Partial staging uses `DiffPatchWriter.WriteSelection` (hunk and line index addressing, counts and offsets recomputed; `Forward` to stage, `Reverse` to unstage or discard with `apply -R`). Known limits: combined diffs (`diff --cc`, merge commits) are skipped with a warning; invalid UTF-8 is replaced and a warning says the text is no longer exact, so such patches must not be applied; partial patches are not meaningful for binary, added or deleted files (stage whole) and hunks with zero context are not re-anchored; `GitRunner` has no stdin support, so applying a patch needs a temp file or a runner extension (follow-up for the staging issue).

- File watching (#27) lives in `Gitunia.Git` (no Core types): one `RepositoryWatcher` per tab, one shared `WatchBudget`, `RepositoryRefresher` for incremental refresh; details in the Refresh section above. The Platform abstraction is not involved: `FileSystemWatcher` is cross-platform and its failures (inotify limit, buffer overflow, unsupported file systems) fall back to polling, which is the per-OS escape hatch. Wiring into tab state and effects (calling `SetActive` on tab switch, running the refresh effect, applying the changed sections) is left to the UI work. Known limit: the recursive working tree watcher also sees `.git/objects`; the classifier filters those events but they still cost inotify watches.

- Commit details (#24; the debounce on every move and the FIFO cache described here were changed in #215, see "Faster commit details" in architecture.md): `CommitDetailsReader` (`Gitunia.Git`) runs `git log -1 -z` (parsed by `CommitDetailsParser`: full raw message, author and committer with their UTC offsets via `%aI`/`%cI`, parents) and then `git diff-tree --raw -z -M -C` against the explicitly named first parent (or `--root`), because `diff-tree` shows merges against every parent and ignores `--first-parent` (parsed by `CommitFileChangeParser`, statuses reuse `FileChangeKind`). In the Tui, `CommitDetailsStore` (one per tab, owned by `TabSession`) is fed by every graph selection change: it shows the loading state at once, debounces 80 ms, cancels the load of the previous selection (its git processes are killed), ignores stale results and caches the last 64 commits. Pane rows are width-independent (`DetailContentBuilder`; long lines are cut with an ellipsis, not wrapped) and drawn by `DetailPaneRenderer`, shared by the Terminal.Gui list source and `ScreenComposer`, so `--print-frame` shows the pane for the newest commit. Pane focus is `FocusedPane` of the tab's view state; `ActionRouter.ViewName` picks the keymap view (`Graph` or `Detail`) from it.

- Background status polling (#135): `StatusReader` takes an `UntrackedFilesMode`; `BackgroundStatusPoller` uses `Normal` (`--untracked-files=normal`: an untracked directory is one entry), because the tab bar only needs to know the tree is dirty. Measured on a throwaway repo with 20,000 untracked files in 100 directories: `all` 9 ms and 288 KB of output, `normal` 1 ms and 80 bytes (cold, large real trees will show a bigger gap). The active tab keeps `All`. `RepoStatusSummary.From(StatusSnapshot)` replaces the hand-built summaries (`TabRefresher` still builds its own, #144).
