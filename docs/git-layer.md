# Git layer

Contract between `Gitunia.Git` and everything above it: the rules every caller and reader follows. How each feature works inside (classes, edge cases, limits) is in the code and its XML docs, and the history of decisions in `docs/history/git-layer.md`.

## Running git

- **Version.** Minimum git is 2.43 (older releases lack worktree and ref-listing behaviour we rely on). Detect the version at startup with a clear error below it; feature-detect newer capabilities (for example relative worktree paths, 2.48) instead of raising the floor.
- **Repository-scoped API.** Every reader is an instance that holds a `GitRunner` and takes the `RepositoryLocation` it reads as an argument on every call: no handle, no static "current repo". Git runs with that path as working directory (`-C`), never relying on the app's cwd.
- **Discovery.** `RepositoryDiscovery.DiscoverAsync` validates paths the user opens: bare repos, linked worktrees (kept as their own location, flagged `IsLinkedWorktree`, with the shared `CommonDirectory` for grouping under their main repo), and non-repos (`NotARepositoryException`). A path inside a git directory resolves its working tree from the `gitdir` pointer, the `.git` directory name or `core.worktree`, and fails clearly otherwise.
- **Spawning.** `ProcessStartInfo`, no shell, arguments as a list, per-call `-c` flags (`-c core.quotepath=off` and similar) rather than mutating user config.
- **Environment.** `LC_ALL=C` for parsed output, `GIT_TERMINAL_PROMPT=0` for background calls, `GIT_OPTIONAL_LOCKS=0` for read-only status polling (avoids fighting the user's other git processes over `index.lock`). Remote calls also set `GIT_SSH_COMMAND` (see "Remote calls"). Nothing else is set.
- **Machine formats.** `status --porcelain=v2 -z`, `for-each-ref --format=...`, `log --format=... -z`, `worktree list --porcelain -z`, `rev-list --parents`, `diff --raw -z`, `cat-file --batch` for bulk object reads.
- **Commit trees** (`ICommitTreeReader`, `CommitTreeReader`, `CommitTreeParser`; #173): `ls-tree -r -z --long <commit> --` lists every file of a commit in one read-only call, parsed into `TreeEntry(Path, Kind, Id, Size)` (`TreeEntryKind`: file, executable, symlink, submodule from the mode `100755`/`120000`/`160000`; a submodule has no size). Directories are not listed by git; the Core `FileTreeModel` derives them from the paths. Paths that are not UTF-8 survive through `GitPathText`. The whole tree is read at once (not per directory): see the measured timings in `architecture.md`.
- **Blobs** (`IBlobReader`, `BlobReader`; #511): `cat-file blob <id>` reads the content of one file for the Files tab's content view, by the blob id from the tree listing (so odd paths and non-UTF-8 names need no quoting). The cap is `BlobReader.MaximumBytes` (1 MiB): a blob whose size is known to be larger is not read at all, an unknown size is checked on the output; a NUL byte in the first 8000 bytes (git's own check) makes it binary. Result: `BlobContent(Kind: Text | Binary | TooLarge, Text, Size)`; no text conversion or filters.
- **Every call** takes a `CancellationToken` and a timeout, captures stderr and maps the exit code to a typed error. Long operations (fetch, pull, push, clone) stream progress (`--progress`) to the caller.
- **User environment.** Credentials, hooks, signing and identity come from the user's real config. Prompts cannot reach a redirected git (stdin is closed), so a call that may prompt either fails with git's message or goes through `ExternalToolRunner` (`architecture.md`); a failed fetch, pull or push offers the terminal (#45, "Remote calls").

### Runner (`GitRunner`)

- `RunAsync` collects output. `StreamAsync` yields stdout chunks: its timeout is an idle timeout that does not run while the consumer handles a chunk, errors surface after the last chunk, disposing early kills git.
- Errors: `GitCommandFailedException` (exit code not in `GitRunOptions.AcceptedExitCodes`; carries `StandardError` and, from `RunAsync`, `StandardOutput`), `GitTimeoutException`, `GitNotFoundException`, `GitVersionTooOldException`. Cancellation raises `OperationCanceledException`. On timeout or cancel the whole process tree is killed.
- Stdin is closed at once so git never waits for input, unless the call sets `GitRunOptions.StandardInput` (bytes written then closed; `RunAsync` only). That is how patches (`apply --cached -`, built with `DiffPatchWriter`), commit messages (`commit -F -`) and paths reach mutating calls.
- Read-only polling passes `ReadOnly: true` (sets `GIT_OPTIONAL_LOCKS=0`); mutating calls never do.
- `GitRunnerOptions.EnvironmentOverrides` exists for test isolation; production code must not use it.
- `GitRunOptions.OnStandardErrorLine` reports stderr segments (split at line feed and carriage return, which git uses to redraw progress) while the run is going and makes the timeout an idle limit; `GitRunOptions.Environment` adds variables for one call.

### Remote calls (`RemoteRunner`, `IRemoteWriter`; #44)

- `RemoteWriter` runs `fetch --progress [--prune] [--all | -- <remote>]`, `pull` as `fetch --progress` then `merge --ff-only @{upstream}` (so the user's `pull.rebase` never applies) and `push --progress [--set-upstream] [--force-with-lease=refs/heads/<b>:<expected>] [-- <remote> [<local>[:refs/heads/<b>]]]` (a plain force never exists: `PushRequest.Lease` is the only way to overwrite, and it expects the tip of our remote-tracking branch; `--set-upstream` is the first push) and `DeleteRemoteBranchAsync` as `push --no-progress --delete -- <remote> refs/heads/<b>` through `RemoteRunner`, with `IProgress<RemoteProgress>` (`Stage`, `Percent` or null for count-only stages, parsed by `RemoteProgressParser` from stderr, `remote: ` prefix stripped). The idle timeout is 2 minutes of silence on stderr (a quiet hook or credential helper counts against it); a cancel kills the process tree, and refs are updated by git only after the objects arrived, so a cancelled fetch leaves the repository consistent (tested with fsck and a lock-file check). The merge step of a pull rewrites the index and working tree, so it is never killed: a cancel is honoured between the fetch and the merge only. A diverged pull throws `PullDivergedException` after the fetch, with no merge or checkout done; `PullOutcome` is `UpToDate` or `FastForwarded`.
- `BranchWriter.FastForwardAsync` (#572) runs `fetch --no-tags --no-write-fetch-head --no-recurse-submodules . <upstream>:refs/heads/<b>` (no leading `+`): a fetch from the repository itself, so no network; git accepts only a fast-forward and refuses a branch checked out in any worktree, and writes the reflog entry. Chosen over `merge-base --is-ancestor` plus `update-ref` because git does both checks atomically.
- `TagWriter` push and remote delete use the same runner (still `--no-progress`, no progress callback).
- `RemoteManager` (`IRemoteManager`; #400) lists remotes (`remote` for names, `config --get-regexp` for the raw URLs, so `insteadOf` aliases survive) and runs `remote add|remove|rename|set-url -- <args>` as plain config writes (no runner, no network, `--` before the names). Git itself removes or renames the remote-tracking branches and moves `branch.*.remote` and `merge` settings; the caller reads the refs again afterwards. Remove is destructive and always behind a Confirm in the UI.
- **No prompts.** stdin is closed and `GIT_TERMINAL_PROMPT=0`, but ssh asks on the controlling terminal. `SshCommandPolicy` sets `GIT_SSH_COMMAND` to the effective command (`GIT_SSH_COMMAND`, else `core.sshCommand`, else a `GIT_SSH` program (left alone), else `ssh`) plus `-o BatchMode=yes`, only when that command is plain `ssh`; a `GIT_SSH` program or another client (plink) is left alone. A call that needs a passphrase fails with git's message (ssh answers `Permission denied (publickey...)`; checked against a real sshd: without `BatchMode` ssh opens `/dev/tty` and prompts even with stdin closed). `RemoteAuthFailure.Matches(stderr)` recognises these failures (`Permission denied (publickey`/`password`/`keyboard-interactive`, `could not read Username`/`Password`, `terminal prompts disabled`, `Authentication failed`, `Host key verification failed`, HTTP 401), and not a missing repository, a refused push or a network error. The UI then offers the same command in the terminal (#45): `RemoteCommands` builds the arguments for both the background writer (with `--progress`; the remote branch delete and the tag push and delete (#512) are built there too, with `--no-progress` in the background only) and the terminal retry (without; a pull is the single process `pull --no-rebase --ff-only`, so `pull.rebase` never applies, and a diverged branch fails as in the background). The retry sets no environment, so ssh, askpass and the credential helper behave as in the user's shell.
- Status bar: `RemoteProgressText.Format` (Core) renders the single progress line (`Fetching: Receiving objects 45%`); the keys, chips and `Esc` cancel are #456, which also wires `GitServices.Remote` to it.

### Clone and init (`IRepositoryCreator`, `RepositoryCreator`; #401)

- Neither needs an open repository, so they run outside any `-C`: `RemoteRunner.RunGlobalAsync` (the same idle timeout, progress parsing and `SshCommandPolicy`, with `core.sshCommand` read from the global config) for `git clone --progress -- <source> <absolute target>` and `GitRunner.RunGlobalAsync` for `git init -- <absolute directory>`. All paths are absolute; `CloneSource.Resolve` (pure) makes a typed local path absolute against an explicit base directory and `~`, and leaves URLs (`scheme://`, scp-like `host:path`) alone, so the process working directory never matters.
- The target must be missing or an empty directory (`CloneTargetException` otherwise, before git runs). A failed or cancelled clone leaves nothing behind: killing git cannot run its own cleanup, so the creator removes the topmost directory it created (the target and the parents git makes), or empties a target that already existed empty. Init keeps the files of a non-empty directory and returns a folder that already is a repository root as it is (`InitResult.WasRepository`).
- No prompts: stdin is closed, `GIT_TERMINAL_PROMPT=0` and ssh runs in batch mode, so a clone that needs credentials fails with git's message. #45's terminal hand-off plugs in at the clone call (`RepositoryCreationActions.RunCloneAsync` in the UI).

### Paths that are not valid UTF-8

- Status output is decoded with `GitPathText.Decode`: valid UTF-8 as is, every invalid byte becomes the lone surrogate `U+DC00 + byte`. `StatusEntry.Path` therefore round-trips byte-exactly through `GitPathText.Encode`. Display code must treat lone surrogates as replacement characters.
- Such a string cannot be a process argument (the runtime would replace the surrogates). Stage, unstage and discard pass paths on stdin with `GitOptions.PathspecFromStandardInput` + `PathspecFileNul` and `GitPathText.EncodePathspecFile`.
- Diffs are decoded lossily. `DiffFile.HasInvalidText` marks a file with invalid UTF-8 in a path or line, and `DiffPatchWriter` throws `InexactPatchException` for it, so line and hunk staging is refused and the file is staged whole by path.
- Deleting an untracked file by raw bytes goes through `IByteExactFileSystem` (Linux only; elsewhere an explicit "unsupported" result, `architecture.md`).

## Mutating operations

All take the repository location, are never `ReadOnly`, and run one at a time per tab (the caller enforces it).

- **Index** (`IIndexWriter`): add, `restore --staged` (`rm --cached` on an unborn branch), `--intent-to-add`, and `ApplyPatchAsync` (`git apply --cached [-R] --whitespace=nowarn -`). Paths on stdin with `--literal-pathspecs`.
- **Partial staging** (`PatchStager`): never builds a patch from the rows on screen. It re-reads the file's diff with git's default context, finds the chosen lines by kind, line number and text (`DiffLineMatcher`), writes a patch with `DiffPatchWriter.WriteSelection` (`Forward` to stage, `Reverse` to unstage) and applies it. Git rejects a patch that does not apply and leaves the index alone. Whole-file fallback for what a partial patch cannot represent: binary, added, deleted and copied files, untracked binary files and symlinks, truncated diffs, `HasInvalidText`, names that are not valid UTF-8. Results are typed (`PatchStagingResult`: `Applied`, `WholeFile`, `FileChanged`, `NothingSelected`). Lines of an untracked text file go through `add --intent-to-add` first; the empty entry is removed again on every outcome that stages nothing.
- **Reflog** (`IReflogReader`, `ReflogReader`, `ReflogParser`): `reflog show --format=<hash, %gd, %gs> --date=relative -n <limit> <ref> --`; the selector carries the relative time, the position is the `n` of `ref@{n}`, the subject splits at the first `: ` into action and message. Read-only.
- **Message search** (`ICommitMessageSearcher`, `CommitMessageSearcher`, #97): `log -z --format=%H --regexp-ignore-case --fixed-strings --grep=<text> --exclude=refs/stash --all --`; returns the set of matching commit ids (subject and body). Run only when the graph search gets a `body:` query; read-only, 60 s timeout.
- **Merge** (`IMergeWriter`, `MergeWriter`; #38): `merge --no-edit [--no-ff|--squash] <target> --`, result `MergeResult` with `MergeKind` (`UpToDate`, `FastForward`, `MergeCommit`, `Squashed`, `Conflicted`) and the old and new HEAD. A normal merge goes through `OperationRunner`, so a stop on conflicts is a `Conflicted` result with the operation in progress; a squash writes no `MERGE_HEAD`, so its conflicts are recognised from a changed unmerged set and no operation is in progress. A branch arrives as its full ref (`refs/heads/x`, `refs/remotes/o/x`); the writer passes the short name when it resolves to the same commit, so git writes its own message (`into <branch>`, `merge.log`, `merge.suppressDest`), and keeps the full ref with `-m "Merge branch 'x'"` only when a tag of the same name would win (that message has no `into` part). A commit is passed by hash.
- **Reset** (`IResetWriter`, `ResetWriter`): `reset --soft|--mixed|--hard <commit>^{commit} --`; returns the HEAD hash read right before, which the status and the Confirm print as the undo. It checks nothing else: the UI refuses a detached HEAD or a running operation and names the lost files from a status read.
- **Worktrees** (`IWorktreeWriter`, `WorktreeWriter`): `worktree add [-b <new> --] <path> [<start>]`, `remove [--force] -- <path>` (a locked worktree is refused even with force; the branch is kept), `lock [--reason]`, `unlock` and `prune --verbose` (the removed entries come from stderr). `ListChangesAsync` runs `status --porcelain -z --no-renames` inside the worktree so the UI can name what a forced remove would lose (untracked count, ignored do not). Reads stay in `RefReader.ReadWorktreesAsync`.
- **Discard** (`IWorkingTreeDiscarder`, `PatchDiscarder`): nothing here can be undone, so callers confirm first. `--literal-pathspecs restore --worktree` for tracked files (staged changes stay), `clean -f -d -q --` for untracked ones (never touches a tracked or an ignored path; batches of 64 arguments), and `apply -R` for hunks and lines (working tree only, the index is never touched), cut from the same pickable diff staging uses (`PickableDiffReader`).
- **Stash** (`IStashWriter`): `PushAsync(location, message, includeUntracked)` runs `git stash push --quiet [--include-untracked] [-m msg]` and compares `refs/stash` before and after, because git exits 0 on "No local changes to save" (`NothingToStash`). Apply, pop and drop take a `StashEntry` and find its current `stash@{n}` by commit hash first (`Missing` when gone), so a changed stack hardly ever redirects them (a push by another process between the lookup and the call still could); pop needs the `stash@{n}` form anyway. An apply or pop that fails and changed the `git ls-files --unmerged` set is `Conflicted` (the stash is kept); other failures, including a refusal while files were already unmerged, throw. The undo of a drop is `git stash store -m "<subject>" <hash>`.
- **Rebase** (`IRebaseWriter`, `RebaseWriter`): `git -c core.editor=true rebase <onto>^{commit}` through `OperationRunner.RunAsync`, so a stop on conflicts is `OperationOutcome.Conflicted`; non-interactive only. A target starting with `-` is refused.
- **Quick rebase** (`IQuickRebaseWriter`, `QuickRebaseWriter`; #459): fixup, reword and drop of one commit on top of the interactive engine. `PlanAsync(location, kind, commit)` reads the parents (`rev-list --parents -n 1`, twice for a fixup), picks the base (the parent, two back for a fixup, `RebaseBase.Root` at the root), reads the range through the engine and the full message (`log -n 1 --format=%B`); it throws `RebaseRangeException` for a merge commit, a merge in the range, a commit outside the history of HEAD, or a fixup with nothing before it. `RunAsync(location, plan, newSubject)` re-reads the range (a different one throws, nothing is rebased) and starts the engine with every other commit picked; a reword replaces only the first line of the message.
- **Interactive rebase** (`IInteractiveRebaseWriter`, `InteractiveRebaseWriter`; #399 the engine, #458 the todo editor on top of it, ux.md workflow 3): `ReadRangeAsync(location, RebaseBase)` lists the commits of `<onto>..HEAD` (or all of HEAD for `RebaseBase.Root`) oldest first with `log --topo-order --reverse -z`; a merge commit in the range, or an empty range, throws `RebaseRangeException` (`--rebase-merges` is post-MVP). `RebaseAsync` takes one `RebaseTodoEntry(Commit, Action, Message)` per commit in replay order (`Pick`, `Reword`, `Squash`, `Fixup`, `Drop`), validates it against the range (every commit exactly once by full hash, nothing omitted, the first kept entry is not a squash or fixup, a reword has text; `RebaseTodoValidator`) and runs `git -c core.editor=true -c sequence.editor=<cmd> rebase --interactive --no-update-refs --empty=drop <onto>^{commit}|--root` through `OperationRunner`, so a stop on conflicts is `OperationOutcome.Conflicted` and the banner and continue, skip and abort of the operation flow take over. The sequence editor is the `SequenceEditorCommand` (in production `gitunia --sequence-editor`, handled first in `Program.Main`, no UI and no repository discovery) followed by the prepared todo; it copies that file over git's todo (`SequenceEditor.Copy`), so no new environment variable is set. A set `GIT_SEQUENCE_EDITOR` would win over the config and is refused with `RebaseEnvironmentException` (not a range error). The command must be the published binary: under `dotnet run` the process path is the `dotnet` host, which is not supported as an editor. A reword is `pick` plus `exec git commit --amend --allow-empty -F '<file>'`; the message and todo files live in `<git dir>/gitunia-rebase/` (per worktree) and are deleted once no operation is in progress after the call (completed, or git refused to start), and kept while any rebase is stopped (a conflict, a hook rejecting an exec line, a cancel: the later exec lines run on continue), and a stale directory is removed by the next start when no operation is in progress. A squash keeps git's combined message (`core.editor=true`). `InteractiveRebaseResult.OriginalHead` is the undo hint (`git reset --hard <OriginalHead>`; `ORIG_HEAD` and the reflog hold it too); abort returns there. Redundant commits that become empty are dropped (`--empty=drop`, as the plain rebase does).
- **Operations** (`IOperationWriter`, `OperationWriter`, `OperationRunner`, `IOperationInfoReader`): continue, abort and skip of a stopped merge, rebase, cherry-pick or revert run `git -c core.editor=true <op> --continue|--abort|--skip`, so no editor opens for the prepared message (an editor named by the user's `GIT_EDITOR` still wins; that variable is not touched). Every call that starts or advances an operation returns the one `OperationResult(Outcome, Head)` with `OperationOutcome.Completed` or `Conflicted`; #38-#40 (start a merge, rebase, pick or revert) reuse it through `OperationRunner.RunAsync(location, arguments)` and pass `-c core.editor=true` or `--no-edit` themselves. A failed call is `Conflicted` only when the operation is still in progress and the set of unmerged files changed (a rebase that stops on the next commit); a continue with nothing resolved, a dirty tree or a refusing hook still throws `GitCommandFailedException` with git's message. Abort runs through `RunToCompletionAsync`, which never reports `Conflicted`. A merge cannot be skipped. `OperationInfoReader` reads the banner details from the state files without spawning git (`OperationInfo`: target branch, rebase step and total, commits left in a pick range, the stopped commit with its subject, the original tip when the files name it).
- **Cherry-pick and revert** (`IPickWriter`, `PickWriter`; `IPickCommitReader`, `PickCommitReader`): `git cherry-pick --no-edit --empty=drop [-m n] <commits> --` or `git revert --no-edit [-m n] <commits> --` through `OperationRunner`, so a stop on conflicts is `PickOutcome.Conflicted` (the sequencer state then drives continue, abort and skip) and a pick whose commits HEAD already has is `NothingToApply` (a git that does not know `--empty` answers with a usage error before anything ran and the call is repeated without it; an empty pick then stops like git's default). A revert that would be empty fails with git's message. A call that fails without a conflict stop but leaves its own pick or revert in progress (a range whose later commit turns empty) is aborted with `--abort`, so the tip returns to where it was and git's message is thrown; a cancel or timeout midway of a multi-commit sequence is aborted the same way (the earlier commits are undone, with a `reset --merge` to the old tip when a kill during a commit made the abort skip the rewind; the undone commits stay in the reflog; a single-commit pick that was already committed is not rolled back; an abort that itself fails leaves the sequence in progress); an operation that was already in progress is never aborted. The caller fixes the order of the commits. `PickCommitReader` reads subjects and, for merge commits, their parents with subjects (`log --no-walk=unsorted`, one call, a second only when a merge is among them) for the mainline prompt.
- **Commit** (`ICommitWriter`): `CommitAsync(location, CommitRequest(Message, SignOff, NoVerify, Amend))` runs `git commit -F - [-s] [--no-verify] [--amend]` with the message on stdin kept as typed (the `-F` default cleanup is `whitespace`, so `#` lines stay) and a 10 minute timeout for hooks. It returns the new HEAD plus the previous hash for an amend. `ReadHeadMessageAsync` reads HEAD's message for Amend. Hook and signing output comes back in `GitCommandFailedException`. Commits through `$EDITOR` are not a runner call.

## Parsers

- One parser per command: pure functions over `ReadOnlySpan<byte>`/string with fixture-based tests, using captured real output including odd cases (renames, copies, unicode paths, spaces, detached HEAD, unborn branch, merge in progress).
- Parsers never throw on unknown fields; they ignore them and surface a warning.
- **Diffs.** `DiffReader.ReadAsync(location, ["diff", ...])` streams `DiffFile` > `DiffHunk` > `DiffLine`, addressed by file, hunk and line index with old/new line numbers. Headers and hunk lines are kept verbatim so patches reproduce git's text. Binary files carry no hunks, only header lines. `IDiffReader.ReadWorkingFileAsync` reads one file of the working-tree view (unstaged, staged, untracked via `--no-index`, conflicted via `DiffParser(readsCombined: true)`); paths go as `:(literal)` pathspecs after `--`. Limits, combined diffs and non-UTF-8 handling: `docs/history/git-layer.md`.

## Models

- **Repository:** path, git dir, common dir, HEAD state (branch, detached, unborn; `RefReader.ReadHeadAsync`), operation in progress (merge, rebase, cherry-pick, revert, bisect).
- **Worktree:** path, HEAD, branch, locked, prunable, bare, per-worktree dirty summary. Worktrees are first-class: every view that shows a branch also shows which worktree has it checked out.
- **Branch/ref:** local, remote, tag, upstream, ahead/behind, last commit, checked-out-in (worktree).
- **Status:** staged/unstaged/untracked/conflicted per path. The Unstaged list holds worktree changes, untracked and conflicted paths; ignored entries are in no list.
- **Commit graph:** hash (`ObjectId`, a fixed 40-byte struct), parents, author, date, subject, refs. Lane assignment is a pure function computed incrementally from `rev-list --parents` order, so it can be tested and cached.
  - A lane waits for exactly one commit id; lanes are not shifted left, so columns do not jump while scrolling or loading.
  - **Lane 0** is reserved for the first-parent chain of the checked-out branch's tip (`GraphLayoutBuilder(headCommit)`; the tip comes from `ICommitLogReader.ReadCurrentBranchTipAsync`, read concurrently with the log). Commits above HEAD whose first-parent chain reaches it (a branch ahead of HEAD such as `origin/main`) continue the shaft upwards and take lane 0 while it is free; `ICommitLogReader.ReadHeadLayoutAsync` returns them as a set, computed from the history and the tip only, never from which refs reach a commit. A detached or unborn HEAD, or a failed tip read, gives no head commit and the leftmost free lane is used.
  - The reservation is part of `GraphRow.LaneFingerprint`, so an incremental reload after HEAD moved cannot join rows laid out for another HEAD and falls back to reading further or fully.
  - Known limit: the tip is read by a separate git process, so a commit made between the two reads can leave lane 0 reserved but empty until the next refresh.

## Refresh

- **Watching.** One `RepositoryWatcher` per open tab watches the git directory, the common directory (linked worktrees), `refs/`, `worktrees/` and the working tree with `FileSystemWatcher`. `RepositoryChangeClassifier` maps a path to `RepositoryChangeKinds` (head, refs, index, working tree, worktrees, operation; lock files, objects and logs are ignored). Events are merged and debounced (200 ms quiet, at most 2 s under a continuous stream); the callback gets the merged kinds on a thread pool thread.
- **Background tabs.** `SetActive(false)` marks a tab as background: it keeps pending kinds, reports nothing, and `IsStale` is true (`BecameStale` fires once). `SetActive(true)` reports them at once. Background tabs refresh on activation.
- **Budget and fallback.** `WatchBudget` caps watchers across all tabs (64 by default; a tab needs 3 to 6). A tab that cannot get its slots, or whose watcher fails to start or errors (for example the inotify limit), polls every 5 s instead: a cheap fingerprint of the git directory, refs and worktrees files, plus a working-tree status refresh on every tick. Working-tree watching is ignore-aware (#83): a recursive `FileSystemWatcher` costs one inotify watch per directory on Linux, ignored ones (`node_modules`, `bin/obj`) included, so the root gets a non-recursive watcher plus one per directory that `WorkingTreeDirectoryLister` finds with a single `ls-files -z --cached --others --exclude-standard` (directories holding tracked or non-ignored files, and their parents). These directory watchers do not use `WatchBudget` slots; they are capped per tab (`MaximumWorkingTreeDirectories`, 2048) and a larger tree polls; the cap is not the binding limit, see the instance limit below. The listing runs off-thread after `Start`. A created directory (with its subdirectories) is watched at once, because it may be empty and unknown to git, and triggers a rescan (serialised, coalesced) that adds listed directories and drops watched ones that git does not list and that are gone or hold files (ignored); an empty one stays. Changes to ignored files inside a watched directory still report `WorkingTree` (the status refresh finds nothing). If the listing fails, the working tree is watched recursively as before. Only Linux uses this mode (`EffectRunner` passes the lister there); Windows and macOS keep one cheap recursive watcher. A new directory is watched with at most 64 subdirectories before the rescan, and a rescan that fails after the first one keeps the current set. Limits: files written between `Start` and the first listing (~330 ms measured on a 10k-directory tree, off-thread) are missed; directories that hold only ignored files or are empty at start (for example `logs/` with `*.log` ignored) are not watched, so a new non-ignored file there is noticed at the next refresh or any other event, not at once; submodule contents are not watched. Per-directory watchers (up to thousands) are created outside the watcher's lock (plan under the lock, create, install under the lock); `Start`, the recursive root fallback and the `worktrees` directory still create their one to six watchers under it. Measured numbers are in `docs/performance.md` ("Working tree watching"). Each .NET `FileSystemWatcher` takes one inotify instance, so the per-user `max_user_instances` limit (128 on many systems, 1024 here) binds before the 2048 cap; hitting it falls back to polling (#543).
- **Incremental refresh.** `RepositoryRefresher.RefreshAsync(location, previous, kinds)` re-reads only the sections the kinds can affect (head and refs together, worktrees, status; operation files are always checked) and returns the new `RepositorySnapshot` plus the `RepositorySections` that actually differ. Unchanged sections keep the previous object, so views compare by reference and a refresh never resets scroll or selection.
- **Background status.** `BackgroundStatusPoller` runs `git status` for every non-active, non-missing tab, sequentially, at start and every 30 s, and dispatches only when the summary changed. It loads nothing else, so unvisited tabs stay cheap; tab bar markers lag by up to the interval. Status polling uses `--untracked-files=normal` (the tab bar only needs to know the tree is dirty).
- **Worktree overview.** `WorktreeOverviewPoller` runs `git status` (untracked files listed individually, like the tab's own read) in every other worktree of the active tab, one at a time, when the tab or its worktree list changes and every 30 s, because changes there raise no event for this tab. Bare and prunable entries are skipped, an unreadable worktree keeps its last value. The tab's own worktree is counted from its live `WorkingTree` snapshot. Switching a tab to another worktree (`SwitchWorktreeCommand`) replaces its location and runs the load effect again (new session, refresher and watcher); the view state, refs and sidebar stay.
- **Working-tree state.** Every loaded tab keeps the full `StatusSnapshot` in `RepositoryState.WorkingTree` (snapshot plus the selected file by section and path). A new snapshot replaces it and re-finds the selection (same path and list, else the same path in the other list after a stage or unstage, else the row near the old index); a snapshot with the same content returns the same state, so a refresh never repaints or loops. The background poller updates only the summary, so a background tab's snapshot may be older than its markers until the tab is activated. After stage or unstage the cursor stays at the same index of its list. List order is git's order; any display ordering is applied in the state layer so indexes stay the row indexes.
- **Wiring.** `TabRefresher` (`Gitunia.Tui/App`) is created by the effect runner when a tab's load starts and owns that tab's watcher. After the initial load it records a baseline snapshot (and reloads the graph when a change was seen meanwhile or the loaded graph's decorations differ from the baseline refs). Each change then runs `RefreshAsync` off the UI thread (one at a time; changes arriving meanwhile are merged) and dispatches commands only for the sections that differ (stashes are re-read when HEAD or refs changed). Failures are reported once through `StatusChannel`; a manual refresh (`<space>r`) always reports its outcome.
- **Graph reload.** The graph is swapped in only when HEAD or refs changed, or on manual refresh. An automatic reload is incremental (`IncrementalGraphLoader`): it streams the new log from the top and stops at the first row equal to the old graph (same commit, lane, edges and open lanes below it, found by `GraphSplicer` via `GraphRow.LaneFingerprint`), checks the total with `rev-list --count`, re-reads the refs of the few ref-carrying commits (`--no-walk`) and reuses the old rows below. Any mismatch falls back to the full read; a manual refresh always reads everything. The selected commit stays selected and on the same screen row.
- **Soft row limit (#515).** A log longer than `GraphLoader.SoftRowLimit` (100,000) loads only its newest rows (`StreamCappedAsync` reads one row more to know, then `rev-list --count` for the total). `RepositoryLoader.ExpandAsync` streams the whole log again later and appends the rows below the cut (skipping the shown ones, checking the last shown id); a replaced graph (refresh) makes a running expansion stale. A refresh of a cut tab reads the newest rows again instead of splicing. Numbers: `performance.md`.
- **Limits.** A selected commit that disappeared keeps the old row position. An incremental reload trusts the old rows below the join, so history rewritten below it without changing the commit count (for example a `git replace` ref) is only picked up by a manual refresh.
