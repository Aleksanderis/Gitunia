# UX

Spec for workflows and keys; the flows are written before the views. Keyboard and mouse are both fully supported: every action is reachable with either.

## Principles

- Modal and discoverable: Normal mode navigates, actions are short mnemonic chords, `?` shows keys for the current view, `:` or `Ctrl-p` opens a command palette that lists every action with its binding.
- Key bindings are the defaults, and users can remap them or add extra bindings in the config file (planned for M4; the keymap engine is data-driven from M1 so remapping needs no redesign). Vim-like motions everywhere: `h j k l`, `gg`/`G`, `Ctrl-d`/`Ctrl-u`, `/` search, `n`/`N`, counts (`5j`). Arrow keys and PageUp/Down also work.
- History layout: left sidebar (branches, remotes, tags, stashes, worktrees), center commit graph, right/bottom detail (commit info, files, diff). Working tree status is a pseudo-row at the top of the graph.
- Working-tree layout (staging): selecting the status row (or a key from anywhere) switches the center and detail panes to unstaged files, staged files and a diff/hunk view. Whole files, hunks or selected lines are staged and unstaged from the diff itself, then the commit message is written and committed from the same screen. Details of this flow are specified as workflow 2 below, before M2.
- Branches and worktrees are first-class, not a submenu: they are always visible in the sidebar and every branch shows which worktree holds it.
- Destructive actions confirm and say what they will do and how to undo it.
- Mouse is optional but complete: everything doable by keyboard is doable with the mouse (click to focus/select, double-click to open, wheel to scroll, clickable tabs, buttons and menus for actions, drag to select ranges and resize panes). Nothing is keyboard-only or mouse-only; mouse paths are listed in the Mouse section below.

## Workspace and tabs

- The app opens with or without a repo: `gitunia` (restore last session, or repo picker if none), `gitunia <path>` (open that repo as a tab, also from outside any repo; a subdirectory resolves to its repo root).
- Tab bar shows repo name (path on disambiguation), branch and a dirty/ahead/behind marker, and background-activity state.
- Repository picker: fuzzy search over recent, pinned and discovered repos (configurable scan roots), open by typing a path, close/pin entries. Pinning (#218) keeps a repository at the top of the picker, right after the open tabs and above recents and discovered repositories, however long ago it was opened; pins are saved in the session file and never expire (recents are limited to the last 50). Opening an already-open repo focuses its tab.
- Each tab keeps its own selection, scroll, filters and focused pane.  Closing the active tab activates its right neighbour (left if it was last).

## Modes

Normal (navigate, act), Visual (select a range of lines/commits), Insert (text input: commit message, filters), Command (`:` palette), Confirm (y/n dialogs).

## Focus model and key style

- Panes: sidebar (left), graph (center), detail pane with Details, Changes and Files tabs (right/bottom) and diff (the diff belongs to the Changes tab and sits beside its file list; on screens too narrow for both it opens on demand and replaces the detail pane, see 1c). `Tab` cycles in the order sidebar, graph, detail, diff (skipping panes that are closed); `Shift-Tab` reverses. Directions follow that layout (sidebar and graph on top, detail and diff below them). `Ctrl-w` + `h` `j` `k` `l` moves focus by direction (`j` from the sidebar or graph goes to the detail pane, or the diff when the detail pane is hidden; `k` from a bottom pane goes to the graph), `Ctrl-w w` cycles, `Ctrl-w c` closes the tab. Both exist; the focused pane has a highlighted border and its own status hints.
- Frequent actions are single keys per view (`Enter`, `y`, `/`); global actions use the `<space>` leader (`<space>o` open repo, `<space>p` pin, `<space>z` zoom pane). `g` and `]`/`[` start chords; counts prefix motions (`5j`, `3gt`).
- Chord engine: a pending prefix shows in the status bar and, after 500 ms, a which-key popup listing the continuations; `Esc` cancels; there is no chord timeout. Bindings are data (mode, view, key sequence, action id), so remapping in M4 needs no redesign.
- Help and palette (#20): `?` opens a help overlay with the keys of the focused view (its own bindings, then the inherited `Lists` and `Global` ones), generated from the keymap table and the action titles in `ActionCatalog`, never hand-written; `j`/`k`/`Ctrl-d`/`gg` scroll it and `Esc`, `q` or `?` close it (every other action is ignored while it is open). `:` or `Ctrl-p` opens the command palette in Command mode: typing filters every action fuzzily (title or action id), `Up`/`Down` move, `Enter` runs the highlighted action and `Esc` closes; each row shows its bindings, and the focused view's own actions come first. The which-key popup is the same kind of overlay, docked above the status bar.
- Status messages (#93): background work that fails (worktree, stash or status reads of a tab, a failed session save, a session file that was reset at start-up) reports through one `StatusChannel` in `Gitunia.Core.Status`; later features post to it the same way. The newest message shows in the status bar between the position and the key hints (errors in the error colour) and stays until dismissed with `<space>x`, or `Esc` in the graph when nothing else claims it, or until a newer one replaces it. `<space>m` opens the history (the last 50, newest first; long messages wrap) as an overlay; a failed graph load is posted there too; it updates live: a message posted while it is open appears at the top without reopening. Tab-scoped messages start with the repository name, and a message equal to the one showing is not posted again. A key action's own one-off notice (`HEAD is not loaded yet`) still takes the place of the message while it lasts. The status bar hints end with `? :` (help and palette).
- `Esc` precedence: cancel a pending chord, then leave Insert mode, then clear a filter or search highlight, then go back one pane level (diff to detail to graph); in the graph, when nothing else claims it, `Esc` dismisses the status message. `q` goes back one level the same way and quits only from the graph with nothing pending; `h` is back in Detail and Diff and collapse in Sidebar, `l` is forward (Detail to the diff, Sidebar expand; Diff has no horizontal scroll).
- In Insert mode (search box, picker input) printable keys are text; only `Esc`, `Enter`, `Ctrl-` and `Alt-` combinations act, so the leader and chords never fire while typing.

## Workflows

Each later workflow (2-7 at the end of this section) needs a written step-by-step key flow here before it is implemented. Flows 0 and 1 are specified now.

### 0. Open a repo, switch tabs, reopen the session

1. `gitunia` restores the last session (tabs, active tab, per-tab selection/focus). With no session it opens the repo picker. `gitunia <path>` opens that path as a tab (subdirectory resolves to the repo root; a repo already open just gets focused) and keeps the other restored tabs.
2. `Ctrl-t` or `<space>o` opens the repo picker (Insert mode, input focused). It lists open, pinned, recent and discovered repos, fuzzy-filtered as you type; `Up`/`Down` and `Ctrl-j`/`Ctrl-k` move; `Enter` opens in a new tab (or focuses the existing tab); `Backspace` deletes a character; `Tab` or `Right` accepts the suggestion (#232: the highlighted repository's path is filled in and its subfolders are listed; in a typed path it completes the folder name); typing and matching ignore case (a suggestion is only matched case-insensitively, the accepted path keeps the folder's real case, so on a case-sensitive file system the directory part of a typed path must still be spelled exactly); `Esc` cancels (with no tab open it quits instead, since there is nothing to go back to). Discovered repositories come from a scan of the conventional source folders below the home directory (`Projects`, `src`, `code`, `dev`, `repos`, `git`, `work`, ... up to three levels deep, hidden and dependency folders skipped); configurable scan roots arrive with the config file in M4. A typed path is listed off the UI thread: the previous rows stay until the new listing arrives (`scanning...` appears after about 150 ms when there are none), a newer keystroke cancels the older listing, and a listing slower than 5 s ends with a "timed out" notice. Rows show tags (`open`, `pinned`, `recent`, `found`); a click highlights a row and a double-click opens it.
3. Typing something that starts with `/`, `~/`, `./`, `../` or `C:\` is treated as a path (a drive letter needs `C:\` or `C:/`; others need `/`, `~/`, `./` or `../`; anything else is a fuzzy query): the list shows the matching directories (repositories marked), `Tab` completes to the common prefix and then to the highlighted directory, `Enter` opens the resolved path (relative paths are taken from the active repository, or the home directory, never from the process working directory); a non-repo path shows an inline "not a git repository" message and stays open.
4. In the picker `Alt-p` (or the `[pin]` / `[unpin]` button on the highlighted row) pins the highlighted entry to the top of the list or unpins it (a pinned row is tagged `pinned`; `<space>p` does the same for the repository of the active tab) and `Alt-d` removes it from recents (never deletes anything on disk).
5. Switch tabs with `gt` / `gT` (or `3gt`), `Alt-1`..`Alt-9`, or `Ctrl-^` or `<space><Tab>` for the previously active tab. Mouse: click a tab. Tab bar (#219, #220, #221): one row on the bar background (the status bar's, so the screen is bracketed by the two bars), a margin, then every tab as a chip with two columns of padding on each side, ` N name markers `, one blank column between tabs and a ` + ` button after the last tab that opens the picker (#232; `Ctrl-t`). The active tab is the filled accent chip, the others are buttons (#240, `SegmentRole.RepositoryTab`): the same padded chip on a subtle tinted background (the dim selection tint), so they read as clickable; without background colours they are underlined, in ASCII bracketed `[ 2 name ]` (same width). The active one stays clear without colour (it is the only chip in the accent colour; with `NO_COLOR` the chip is reverse video). The name is the repository name, or the name you gave the tab with `Ctrl-w r` (a status bar prompt that starts with the current name; `Enter` saves it, an empty name restores the repository name, `Esc` cancels; the name is saved with the tab in the session file). The branch is not part of the tab (it made tabs very long; the sidebar marks the current branch with `*`); `TabLabelFactory` has a switch for showing it that a future config option can set (#46). Tabs that do not fit are left out of the row (the active one always shows), names are cut at 40 characters. Markers: `*` for a dirty working tree, `↑n` ahead, `↓n` behind (`+n`/`-n` without Unicode) and an ellipsis while the tab loads; two tabs with the same name show their parent directory; when the tabs do not fit the row scrolls to keep the active one visible (`<` marks hidden tabs on the left). Markers follow external git activity (file watching; `r` refreshes manually). `Ctrl-w c` closes the tab; closing the last tab shows the picker.
6. A tab whose repo disappeared (moved or deleted) stays in the bar marked `! name (missing)`; `Enter` on it opens the picker (Locate repository, starting in the folder that held it) and the chosen repository replaces that tab, `Ctrl-w c` closes it.
7. Terminal key caveats, verified against Terminal.Gui 2.5.0 under tmux: `Ctrl-j` (0x0A) arrives as `Ctrl+Enter`, distinct from `Enter` (0x0D), so it works as a picker alias for `Down` (the translator maps it to `Ctrl-j`; a terminal that sends the same byte for both would break the alias, `Down` still works); `Ctrl-^` (0x1E) arrives as `Ctrl+6` and is mapped to `Ctrl-^`, so it works, and `<space><Tab>` remains the fallback for terminals that swallow it; some terminals send `Backspace` as `Ctrl-h`, which the picker treats as `Backspace`.

### 1. Browse the graph, jump, search

1. A repo tab opens with focus on the graph, the newest commit selected and HEAD marked. Commits stream in; the list is usable immediately and the status bar shows loading progress.
   A graph row is a table (#168, #217): branch lanes (the message starts two columns after the last line of the row's own lanes, so with many branches open the rows that only use the first lanes keep their message close to the line; author, date and hash stay in fixed columns and the message takes the room the lanes left free), message (ref decorations then subject), author, date (`yyyy-MM-dd`, the author's local date) and short hash (dimmed). The message column is the flexible one and takes all the width the other columns leave (no cap, #198), so a wide terminal is used in full and nothing else is squeezed; author is 16 columns (ellipsis when longer), 20 when the row has 140 or more columns left after the lanes, date 10, hash 7. Narrow terminals drop columns instead of squeezing the message below 30 columns: hash first, then date, then author; they return when the terminal widens (`gitunia <repo> --print-frame WxH` shows any width). Ref labels (#214): the symbolic `origin/HEAD` is hidden; a local branch and its remote-tracking branch (same name) on the same commit are one label, `main ↔` (ASCII: `main (r)`); the branch HEAD is on gets a `◆` before it (ASCII: `HEAD -> main`). A remote branch with no local branch of that name, or on another commit, keeps its own `origin/x` label. Example at 120 columns (without the sidebar):
   ```
   ●  Fix parser crash on empty input                      Ada Lovelace     2026-10-13 7a21f84
   ●  (◆ main ↔) Merge branch 'topic'                      Alexander the G… 2026-10-12 ee3f455
   ```
2. Move with `j`/`k`, `Ctrl-d`/`Ctrl-u`, `gg`/`G`, counts and the mouse wheel. `@` jumps to HEAD; `gr` opens a prompt in the status bar (Insert mode) that fuzzy-filters refs (branches, tags, remotes) and also accepts a hash prefix of at least 4 hex digits; the best candidate is shown, `Up`/`Down`/`Tab` cycle through the others, `Enter` selects that commit and `Esc` cancels.
3. `Enter` on a commit moves focus to the detail pane; `Esc` or `h` returns to the graph. The detail pane follows the graph selection while the graph is focused. The pane sits below the graph (hidden on screens under 14 rows) and has three tabs, shown as buttons on its title row (#169, #198): **Details** (hash, author, committer only when different, parents, refs and the full message), **Changes** (the changed files with their status `A` `M` `D` `T`, `R<score> old -> new`, `C<score> old -> new`; merges show the changes against the first parent) and **Files** (the file tree of the commit; only a placeholder, "not implemented yet", for now). A fresh tab opens on Changes. `]` / `[` switch to the next / previous tab (wrapping) and `gd` `gc` `gf` jump to Details, Changes, Files, from the graph or the detail pane; a click on a tab label does the same. The selected tab is part of the repo tab's view: it is kept while the graph selection moves, is saved with the session and each tab remembers its own cursor row for the selected commit. While focused, `j`/`k` scroll through the rows of the tab; on Changes, focusing lands on the first file row, the diff of that file is already shown beside the list and `j`/`k` show the diff of each file as the cursor reaches it, with no `Enter` (1c); `Enter` or `l` moves focus into the diff (on the other tabs they only say to open Changes). When the details fail to load the pane says so and `r` in the detail pane (or the palette) retries. The title row shows the file count (`.. files` until the details of the commit have arrived, instead of a `0 files` that flickers, #223); the rows of the tabs start at the same left edge (the summary line, the labels, the file marks and the placeholder; only the commit message is indented).
4. `/` opens the search box (Insert mode). Plain text matches the commit subject (the message body is not searched yet: graph rows keep only the subject), `author:` matches the author name and `hash:` the start of the hash, all case-insensitive. Matches are highlighted in the rows while typing and the status bar shows the count (`/fix_  3/17`). `Enter` jumps to the first match at or after the selection and returns to Normal mode, `n`/`N` step through matches (counts work, the search wraps), `Esc` in the box cancels, `Esc` in Normal mode clears the highlight. The search scans the loaded commits in small slices between key presses and keeps scanning as the log streams in, so matches beyond the loaded range appear as they load and the status bar shows `searching N%` meanwhile. In the box `Backspace`, `Ctrl-u` and `Ctrl-w` edit the text.
5. `y` copies the selected commit hash (OSC 52); `r` refreshes the repo now.

### 1b. Sidebar navigation

1. `Ctrl-w h` (or `Tab` cycling) focuses the sidebar (sections: branches, remotes, tags, worktrees, stashes). `j`/`k` move, `l`/`Enter` expand a section, `h` collapses it (or moves to the parent).
2. `Enter` on a branch, remote branch or tag selects its commit in the graph and keeps focus in the sidebar; `l` on a leaf moves focus to the graph. Each branch shows the worktree that holds it.
3. `/` filters the sidebar entries by name (Insert mode: type, `Backspace` erases, `Enter` keeps the filter and returns to Normal mode, `Esc` drops it). The filter also matches the worktree shown beside a branch and unfolds every section with a match; in Normal mode `Esc` clears an active filter, and otherwise (like `q`) returns focus to the graph.
4. A section header shows its entry count; Remotes and Tags are folded by default. A branch shows `wt:<directory>` for the worktree that has it checked out (`*` marks the current branch and the current worktree) and `↑n↓m` against its upstream. A stash is not a graph node, so `Enter` on it only says so. The sidebar is hidden below 60 columns.

### 1c. Diff viewing

1. The diff is part of the Changes tab, not a mode of its own (owner decision of 2026-10-13, see "Design notes" below). While Changes is the selected tab the diff pane is shown beside the file list: it holds the whole commit's unified diff (against the first parent, so merge commits match the file list) with the header of the file under the file cursor at the top. It is there as soon as the tab is, for the first file; moving the file cursor with `j`/`k` (or the mouse, a click on a row) shows that file's diff at once, no `Enter` needed, and selecting another commit in the graph loads that commit's diff at its first file (a load in flight is cancelled when another commit is asked for). `Enter` or `l` on the file list moves focus into the diff to scroll, search and copy; `h` (or `q`, `Esc`) comes back to the file list and the diff stays. On the Details and Files tabs the pane is not shown. Narrow or short screens (below the side-by-side width of 72 columns, or without the bottom strip) keep the on-demand behaviour: the diff opens with `Enter` or `l` on a file row, takes focus and replaces the detail pane (screens under 14 rows zoom it), and `q`, `Esc` or `h` closes it. The diff pane sits beside the compact file list (a third of the width, 24-60 columns) on screens of 72 columns or more, so both are visible together at 80 columns (a diff opened on demand on a narrow screen that is then widened stays open and also keeps showing a Details or Files tab beside it, following the graph selection). `<space>z` zooms the focused graph, detail or diff pane to the full area between the tab row and the status bar and back (the sidebar does not zoom; moving focus to another pane ends the zoom). While zoomed, `Tab` only reaches panes that are shown.
2. `j`/`k`, `Ctrl-d`/`Ctrl-u`, `gg`/`G` scroll; `]c` / `[c` jump to the next / previous hunk and `]f` / `[f` to the next / previous file of the commit (counts work; at the last one the status bar says so). The title shows the commit, the file under the cursor and `file n/m  hunk n/m`. `/` opens a search box (Insert mode, case-insensitive substring over every row including headers; matches are highlighted while typing); `Enter` jumps to the first match at or after the cursor, `n`/`N` step through matches and wrap, `Esc` in the box cancels. Mouse: the buttons at the right of the title row (`[<f] [f>] [<h] [h>] [w] [z] [x]`) are `[f` `]f` `[c` `]c` `w` `<space>z` and `q`; a drag selects a range of rows (Mouse section).
3. Rows are `old new` line numbers, a `+`/`-`/space marker and the text; text is cut with an ellipsis while word wrap is off (the default); `w` turns wrap on, and a long row then continues on the following screen lines under a blank gutter (`j`/`k` move by screen line, the title shows `[wrap]`; there is no horizontal scroll), tabs expand to 4-column stops and wide characters are never split. Binary files, renames without edits, mode changes and "no newline" markers get a note row; parser warnings (such as invalid UTF-8 in the patch) show as a red `!` row above the first file.
4. `q`, `Esc` or `h` goes back: first it clears an active search, then returns focus to the file list (beside the file list the diff stays; an on-demand diff closes). If the tab is changed away from Changes while the diff has focus, focus returns to the detail pane. A diff is capped at 400,000 rows and 100,000 lines per file (the last row, or the file's note row, says it was cut short); `L` loads the same commit again without the caps (the cursor stays on the same file; with nothing cut it only says so). Binary files have no content to load, so `L` leaves them as a note. The diff follows the graph selection: while the pane is shown, moving the graph (or a refresh that moves the selection) loads the newly selected commit once its details have arrived; beside the file list it shows the file under the file cursor (the first one for a new commit), an on-demand diff keeps the cursor on the same file if the new commit touches it; the old diff stays until then. A resize that makes room for the diff loads it at once; one that takes the room away returns focus from the diff to the file list. The status bar shows the keys of the focused pane (sidebar, graph, detail, diff).

Still to design before their milestones:

2. Working-tree layout: review unstaged changes, stage whole files, hunks or selected lines in the built-in diff view, unstage, write the message, commit, amend.
3. Create/switch/rename/delete branch; set upstream; see ahead/behind.
4. Worktrees: add (new branch or existing), switch the app's active worktree, remove, prune, lock; see dirty state across all worktrees at a glance.
5. Merge, rebase onto, cherry-pick, revert from the graph.
6. Stash push/apply/pop/drop.
7. Fetch/pull/push with visible progress and cancel.

## Look and colours

Colours are decided in one place: `PaletteTable` (`Gitunia.Tui.Views`) holds the colours of a scheme and `Palette` says which role uses which colour, so a theme (#46, #47, #61) later swaps the table and nothing else. There is no config file yet.

**Frame (#197).** Every pane is a box and neighbouring boxes share their edges, so the whole screen is one frame split into panes (`FrameGrid`, drawn the same way by the UI and by `--print-frame`):

```
 1 repo                                                       <- tab row
╭─ repo ───────────────┬─ History ──────────────────────────────╮
│  ▾ Branches 2        │ ○─╮  (main) Merge feature x    Ada ... │
│     feature/x        │ ●  │  Fix parser                       │
├─ Details ─ Changes ─ Files ─ 64d72f2 ─ 3 files ┬─ Diff ... ──┤
│ commit  64d72f2...                             │ @@ -1 +1 @@  │
╰────────────────────────────────────────────────┴─────────────╯
 NORMAL  1/4  j/k gg G ^d ^u @ ? : q                          <- status bar
```

- Rounded outer corners and plain T and cross junctions; the ASCII tier uses `+`, `-` and `|`. Where two boxes meet there is one line, not two.
- Titles sit in the top edge of each box as chips after one stretch of line: the sidebar shows the repository name, the graph `History`, the bottom pane its tabs, the commit and the file count, the diff its title and buttons. The title row of the bottom pane is the line between the graph and the bottom panes (so it costs no extra row).
- Text is padded by one column inside each box (rows keep their selection tint over the padding); the first and last column and the top and bottom edge row belong to the frame, so the frame costs two columns and one row more than the old divider layout (the old header row is gone, #221).
- Focus: the focused pane's whole box is drawn in the accent colour (bold), every other line in the quiet border colour, and its title chip is the filled accent chip (the other titles are dim chips). Focus never relies on colour alone: the chips differ in text style, and with `NO_COLOR` the focused box is bold.
- Layout numbers: the sidebar (clamped 20-36 columns, shown from 60 columns) and the detail/diff split are widths including the padding; drag and the `Ctrl-w` size keys move the shared line.

**Selection and focus.** The selected row is a background tint, never inverse video, so the row keeps its own colours (branch, hash, diff colours stay readable). The focused pane's selection uses the full tint (blue), a pane without focus keeps a quieter grey tint, so the cursor stays findable. This holds for the graph, sidebar, detail, diff, picker rows, overlay rows and the Visual range. Focus is also shown by the frame (above): the focused pane's box is accent, its title is a filled accent chip and the other titles are dim chips. The active tab, the status mode (`NORMAL`, `INSERT`...) and an overlay's title bar are the same accent chip; the tab row and the status bar sit on a slightly lighter bar. An overlay's frame is drawn in the accent colour.

**Roles to colours** (accent blue, green, red, yellow, cyan, purple, muted grey):

| Role | Colour |
|---|---|
| Section titles, buttons, diff file header, the focused pane's frame | accent, bold |
| Graph lanes | a cycle of 12 colours (6 in 16-colour mode) |
| Local branch / current branch (HEAD) / remote branch / tag | green / cyan / purple / yellow, bold (remote branches are not red: red means an error or a deletion, #222; blue on a light terminal in the 16-colour scheme, where yellow and purple are taken) |
| Hash, date, line numbers, hints, counts, punctuation | muted |
| Added line or file / removed / modified | green / red / yellow; hunk header cyan |
| Errors | red, bold (in the status bar on its own bar) |
| Search match | dark text on yellow (kept on a selected row) |
| Overlay key column | yellow, bold |

**Colour depth.** The scheme follows the terminal. 24-bit (`COLORTERM=truecolor`, also used for 256-colour terminals because Terminal.Gui has no 256-colour output of its own): the Catppuccin palette (Mocha on a dark terminal, Latte on a light one; #216), checked by a test for a contrast ratio of at least 4.5 on a typical dark and light terminal background (3.0 for dividers), also on selected rows. 16-colour (`TERM` without `256color`, or a Terminal.Gui driver that cannot do 24-bit; the driver is then forced to 16 colours): only the 16 named colours, so the terminal's own theme decides the exact look; the focused selection is bright black (bold), the unfocused one underlined. `NO_COLOR` or `TERM=dumb`: text styles only (reverse video for the selection, underline when unfocused, bold underline for search matches, underline for the current branch). Light backgrounds are recognised from `COLORFGBG` (background 7 or 15) and get darker accents and light tints; a terminal that does not set it is assumed dark. A terminal whose `TERM` has no `256color` and that sets no `COLORTERM` (for example over ssh without `COLORTERM` forwarded) gets the 16-colour scheme; set `COLORTERM=truecolor` to force the 24-bit one.

**Looking at it without the UI.** `gitunia <repo> --print-frame WxH [--diff] --colors truecolor|16|none [--light]` writes the frame with ANSI colours (the graph is focused, the sidebar cursor shows the dim tint). The overlays and the picker are not part of the printed frame; open them with `?`, `:` and `Ctrl-t`.

## Keymap

The single source of truth for bindings. Add a row in the same change that adds a binding; no conflicts within a mode/view. A test parses this table (columns `Mode/View | Key | Action`; keys in backticks, `Picker` rows are Insert mode, `Palette` rows Command mode, the rest Normal) and checks every key is a registered default in `DefaultKeymap` with no conflicts. Notation: `Ctrl-w c` is a chord, `<space>o` a leader chord, `<lt>` a literal `<`, `:name` is an ex command and not a key. Modes: rows apply to Normal, except those whose view says `(Visual)` (Visual mode only); Visual repeats the Lists motions; global `Ctrl-`/`Alt-` rows also work in Insert; `Esc` is bound in every mode; Insert/Command `Enter` accept the input; Confirm mode has only `y` (yes), `n` (no) and `Esc` (no), so a stray `Enter` never confirms a destructive action.

| Mode/View | Key | Action |
|---|---|---|
| Global | `?` | Show keys for current view |
| Global | `:` / `Ctrl-p` | Command palette |
| Global | `q` | Back / quit from root view |
| Global | `Tab` / `Shift-Tab` | Next / previous pane |
| Lists | `j` `k` / `gg` `G` | Move / top / bottom |
| Lists | `/` `n` `N` | Search, next, previous (graph search prefixes: `author:`, `hash:`) |
| Global | `gt` / `gT` | Next / previous tab (counts: `3gt` goes to tab 3) |
| Global | `Alt-1`..`Alt-9` | Jump to tab N |

Pointer-position behaviour that has no action of its own: a click on a pane focuses it, a click on a list row selects it (graph, detail, sidebar, diff; the details pane follows the graph selection as with keys), a click on a picker row highlights it. A click on empty space does nothing. The wheel moves the selection, not just the view (the keyboard has no pure scroll either), so the details pane follows it as it does for `j`/`k`. A mouse action does not touch a pending count or chord typed before it. While the help, palette or status history is open, panes and the picker ignore every mouse gesture (no focus change, no selection), except that the wheel scrolls the help or history (or moves the palette highlight) when the pointer is over a pane or the overlay, and a click on a pane, the tab row or the header closes it (`Backdrop` row), like `Esc`; the which-key popup does not block the mouse.

Drag to select: press a row of the graph, detail or diff pane and move the pointer; the pane takes focus, the pressed row becomes the anchor, Visual mode starts (status bar `VISUAL`) and the cursor follows the pointer, also above or below the pane while the button is held: while the pointer rests outside the pane the cursor keeps moving every 80 ms, 1 row just outside, 1 more per 2 rows of distance, at most 6, until the pointer is back inside, the list ends or the button is released (#137). The range is drawn like the selected row. The release leaves the range active; a click on a row, `Esc`, `q`, `v` or moving focus to another pane or tab ends it. `y` copies the range (the drag plus `y`, or `visual.copy` from the palette) and ends it; staging lines (#31) will act on it too. The sidebar has no ranges (a drag there only moves its selection); a drag also does not start a range while a prompt (search, filter, ref jump) or the picker is open.

Drag to resize: the line between the sidebar and the graph, the line between the detail and diff panes, and the title rows of the detail and diff panes (the line between the graph and the bottom panes) follow the pointer while the button is held. Sizes are clamped to what fits (at least 12 columns for the sidebar and detail, 20 for the graph and diff, 3 rows for the bottom panes, 4 for the graph), belong to the tab and are saved with the session (#138); `Ctrl-w =` (or `:`, then "Reset the pane sizes") returns to automatic, and `Ctrl-w >` `Ctrl-w <lt>` `Ctrl-w +` `Ctrl-w -` are the keyboard path. A zoomed pane has no dividers to drag.

Clickable titles and buttons: a click on the title row of the detail or diff pane focuses that pane. The detail title row starts with the three tab labels (`Details`, `Changes`, `Files`), drawn as buttons: the selected one is the accent chip (quieter when the pane has no focus), the others sit on the bar background in muted text (underlined where the terminal tier has no background colours, `[Name]` in the ASCII tier from 29 columns), one column of line between them; below 29 columns the padding around the labels goes. The content of the detail pane sits on a panel background, the bar colour (24-bit schemes only; the 16-colour and `NO_COLOR` tiers rely on the frame line and the buttons), so the pane reads as a separate area. A click on a label selects the tab. The diff title row ends in buttons (see the table) when the pane is at least 30 columns wider than the buttons need; narrower panes show only the rightmost ones (`[x]`, `[z]`, `[w]` first), the keys stay available. The highlighted picker row shows `[pin]`/`[unpin]` and, for a recent repository, `[remove]` at its right edge (rows of 60 columns or more inside the frame, so screens of 62 columns or more). Clicking the commands button at the right end of the tab row opens the command palette, which lists the actions of the focused pane and the global ones, so every action without a button (for example `L` load anyway, the search keys, `r` refresh) can be run with the mouse; typing a search or a filter text needs the keyboard, as nothing else can enter text.

Terminal.Gui turns on mouse reporting (SGR, mode 1006) at startup and turns it off on exit; there is no switch to disable it yet. Verified by writing SGR mouse sequences into the pane of a tmux 3.7c session running the Linux build (#64 and #100): clicks, double-clicks, the wheel, press-drag-release (reported as a press, position reports with the button held, a release and then a click at the release position, which the drag logic swallows), divider and title drags, header, palette and button clicks all arrive; a double-click is delivered as a click followed by a double-click event (so a double-click on a sidebar section toggles it once), and a sideways wheel (Ctrl or Shift plus wheel) is ignored (unit-tested only). Not yet verified with a physical mouse, over ssh, or in kitty, Windows Terminal and macOS terminals (tracked in #49). Terminals or ssh paths that drop mouse sequences leave the keyboard path unaffected.

## Design notes

Details moved out of `decisions.md` (#253), roughly in the order it was decided. Notes are historical: where a later note contradicts an earlier one, the later one wins.

- M1 key design (#8, first iteration, owner adjusts after use): both `Tab` cycling and `Ctrl-w` + direction move pane focus; frequent actions are per-view single keys with a `<space>` leader for global ones; chords show a which-key popup after 500 ms and never time out; Insert mode swallows printable keys so chords cannot fire while typing. Patterns followed: vim (motions, counts, `gt`/`gT`, `]c`/`[c`, `Ctrl-w`), lazygit (per-pane focus, `/` filter, `Enter` drills in), yazi (`h`/`l` collapse/enter, `Alt-` combos in inputs). Closes the pane focus and key style open questions.

- Terminal key facts (Terminal.Gui 2.5.0, tmux): `Ctrl-j` arrives as `Ctrl+Enter`, `Ctrl-^` as `Ctrl+6`, `Ctrl-h` as `Ctrl+Backspace`; `KeyTranslator` maps the first two to `Ctrl-j` and `Ctrl-^` so the documented bindings work.

- Diff viewer (#25): the pure part is `Gitunia.Core.Diff` (`DiffDocumentBuilder` flattens the parser's `DiffFile`s into `DiffRow`s plus hunk and file anchors, `DiffNavigator` does `]c`/`[c`/`]f`/`[f`, `DiffSearch`/`DiffSearchState` the search, `PaneZoom` the zoom rule). `DiffStore` (Tui/Loading, one per tab inside `DiffSession`) streams the diff of the commit against its first parent (`diff <first-parent> <commit>`, or `show --format= <commit>` for a root commit) through `DiffReader` off the UI thread, cancels the load of a previous commit and caps the rows at 400,000. It always loads the whole commit, not one file, because `]f`/`[f` walk the files of the commit and a rename needs both paths to be detected; `Enter` on a file just puts the cursor at its header. `DiffPaneController` (Tui/App) is the diff's action handler and search prompt; `ActionRouter` hands it actions after the sidebar and before the graph/detail lists (`ActionRouter.Diff`, and `ViewName` knows the `Diff` view). Layout is data: `PaneLayout.Compute(width, height, isDiffOpen, zoomed)` returns every pane's rectangle and `MainView` binds its views to it, so the layout is unit-tested without a terminal. The diff sits beside a compact detail pane (file list, a third of the width, 24-60 columns) from 70 columns up and replaces it only below that (#108: SourceGit shows that a narrow file list next to the diff works; at 70 columns the diff still has 45). `Ctrl-w j`/`Ctrl-w k` move focus between the top row (sidebar, graph) and the bottom row (detail, diff) via `PaneNavigator.StepVertically` (#105). `<space>z` on the sidebar stays a no-op with a notice: the sidebar is a narrow strip, zooming it has no use (#105, dropped). Focus `Diff` is saved as `Detail` in the session file because the pane is not open after a restart. `ScreenComposer` takes an optional `DiffPaneModel` and `PaneArrangement` and draws its panes from `PaneLayout.Compute`, so side-by-side, replaced and zoomed layouts are frame-tested (`DiffFrameTests`); `--print-frame WxH --diff` opens the diff of the newest commit and `--zoom graph|detail|diff` zooms a pane (#118; `--zoom diff` implies `--diff`), so every layout can be inspected from the command line.

- Diff viewer extras (#106): word wrap is real wrapping, not horizontal scroll. `DiffListSource` maps diff rows to screen lines through `DiffWrapMap` (rebuilt when the document changes, only while wrap is on, so the cost is paid on demand; a width change calls `DiffWrapMap.Resize` (#162): row text widths are measured once per document (+4 bytes per row), and a resize is arithmetic for rows whose characters are all one column wide after tab expansion (#174: ASCII, tab-indented, accented text; the measured width is stored, the bitwise complement marks rows with wide or zero-width characters), and also for those marked rows while they fit one line; only wider-than-the-pane rows with wide characters still use `SegmentCount`; 400k rows: ~300-400 ms full build, 4-8 ms resize, Debug; tab-indented or accented rows 3.6-4.2 ms against 220-540 ms per-row `SegmentCount`); `ListView` items are then screen lines and the controller converts to and from diff rows for search, hunk/file jumps and the remembered cursor. Highlight is applied per screen line, so a search match that spans a wrap point is only highlighted on the part inside each line. The frame composer (`--print-frame`, `DiffFrameTests`) draws unwrapped. "Load anyway" (`L`) lifts the 400,000-row cap and a new 100,000-lines-per-file cap (`DiffParser` keeps the first lines of a longer file and sets `DiffFile.IsTruncated`, so one huge file no longer needs memory for all of it). Dropped: progressive display while the diff streams (the commit is read in one go and the pane shows "Loading..."; closing the pane cancels git; `L` on a huge commit is the only case where it can be slow) and loading binary content (nothing readable to show in a terminal). The diff follows the graph selection (decided over a "stale" marker): once the selected commit's details have arrived (the same settle delay as the detail pane, so fast `j`/`k` does not start git per row) `DiffPaneController.FollowSelection` loads that commit and keeps the cursor on the same file path. A live refresh needs nothing more: a commit's diff never changes, and when a refresh moves the selection to another commit the same follow rule applies. The diff arguments moved to `DiffReader.ReadCommitAsync` in `Gitunia.Git`. Status bar hints come from `PaneHints.For(focusedPane)`.

- Mouse (#64 part a): the mouse follows the key path. `Gitunia.Core.Mouse` holds `MouseGesture` (click, double-click, wheel up/down), `MouseMap` and `DefaultMouseMap` (view, gesture -> action id and count, same view inheritance as the keymap); `docs/ux.md` has the matching table, checked by a test. In the Tui, `PaneListView` (the four list panes) and the picker view translate Terminal.Gui flags (`MouseFlagTranslator`) into gestures; `MouseController` resolves them and calls the same `RouteAction` as keys, so a wheel notch is `list.down` with count 3, a graph double-click is `graph.open-details`, a tab click is `tab.next` with the tab number (`3gt`). Decisions: the toolkit's own wheel scrolling is replaced (it moved only the viewport and left the selection behind, and bypassed the keymap path); a gesture first focuses the pane under the pointer; the toolkit still selects the clicked row (a position, not an action); a sidebar single click is `Enter` (it toggles sections, so double-click is deliberately unbound there: Terminal.Gui reports click then double-click); while an overlay is open, pane gestures are ignored; a sideways wheel is ignored. Terminal.Gui 2.5.0 names: `MouseFlags.WheeledUp/WheeledDown/LeftButtonClicked/LeftButtonDoubleClicked`, a sideways wheel is vertical wheel plus Ctrl.

- Mouse (#100 part b): drag, resize, buttons and overlays follow the same rule (mouse map to action ids, then the key handlers). Drag in Terminal.Gui 2.5.0 arrives as `LeftButtonPressed`, then position reports with `LeftButtonPressed | PositionReport` while the button is held, then `LeftButtonReleased` and a `LeftButtonClicked` at the release position, even after a drag and routed to the view under the pointer. `DragTracker` (pure) tells click from drag and marks that trailing click for swallowing; `DragGrab` grabs the mouse on the press (`View.App.Mouse.GrabMouse`) so a drag goes on outside the view and keeps the grab until the trailing click has reached the dragging view (300 ms fallback timeout), otherwise the click would land on the pane under the pointer and end the selection. Drag-select: the first move off the pressed row focuses the pane, selects the pressed row and raises `DragStart` (`visual.toggle`), then each move raises `DragUp`/`DragDown` with the row distance (`list.up`/`list.down` with that count), so the range is the existing Visual mode (`VisualRangeController`: graph, detail and diff, drawn as selected rows through `IRangeSource.Range`, ended by `v`, `Esc`, `q`, a click, or focus moving). Decisions: `v` is implemented for keys too (it was bound but did nothing); `y` in Visual mode copies the range (#140: `visual.copy`, text builders in `RangeTextBuilder`, diff rows not screen lines, notes skipped), staging will act on it too (#31); auto-scroll while the pointer rests outside the pane (#137): `PaneListView` runs an 80 ms UI-loop timer, step `1 + (distance-1)/2` rows capped at 6 (pure `DragAutoScroll.Step`), stopped when the pointer is back inside, at the list end, on release or when an overlay opens. Resize: `PaneSizes` (sidebar width, bottom strip height, detail width; null is automatic) live in the tab's `RepoViewState` (saved with the session per tab as `sidebarWidth`, `bottomHeight`, `detailWidth`, absent or negative means automatic, no version bump: #138; set through `SetPaneSizesCommand`), are clamped by `PaneLayout` on every layout (`PaneResizer` is the pure rule shared by the drag and the keys `Ctrl-w > < + - =`, because nothing may be mouse-only). A zoomed pane has nothing to resize. Buttons: the diff title row (`[<f] [f>] [<h] [h>] [w] [z] [x]`) and the highlighted picker row (`[pin]`/`[unpin]`, `[remove]`) are drawn by the pure renderers (`DiffTitleButtons`, `PickerRowButtons`) and each button is a mouse-map view of its own, so a click runs the action of its key; buttons are dropped on narrow rows, the keys stay. The "menu" is the command palette: a click on the header bar opens it (the header row was removed later: see the owner review items of #198 below, #221) and a click on an entry runs it. While an overlay is open the wheel scrolls it (or moves the palette highlight) wherever the pointer is, and a click outside closes it (view `Backdrop`, action `cancel`); panes ignore everything else, including the toolkit's own focus-on-click. Clicking a pane title row focuses the pane; dividers and the detail/diff title rows are the resize handles.

- Bottom pane tabs (#169): the detail pane has three tabs, `BottomTab` (`Details`, `Changes`, `Files`, in `Gitunia.Core.Workspaces`), stored in `RepoViewState.BottomTab` (changed by `SetBottomTabCommand`, saved in the session file as the name `BottomTab`; a missing or unknown value, as in older files, is `Changes`). `DetailContentBuilder.Build(entry, state, tab)` builds the rows of one tab (`DetailContent.Tab`; `Files` is filled on every tab so the title can count them, `FirstFileRow` only points at file rows on Changes, so the copy-path and open-diff code needs no tab special case beyond a notice). The title row starts with `DetailTabStrip`, whose layout also resolves clicks (views `DetailTab.Details|Changes|Files`, like the diff buttons). `DetailTabController` handles `detail.next-tab`, `detail.previous-tab` and `detail.tab-*`; `TuiApplication` rebuilds the rows when the tab in the state differs from the shown one and keeps one cursor row per tab while the commit stays selected (`TabSession.DetailSelections`). Keys `]` `[` `gd` `gc` `gf` live in both the Graph and Detail views (the bottom pane follows the graph selection); digits are counts and `gt` belongs to repo tabs, so they were not used. `--print-frame` takes `--tab details|changes|files`. Defaults taken without asking the owner (change them here if wrong): a fresh tab opens on Changes (keeps `Enter`, `j`, `Enter` as the way to a diff; Details is one key away), a diff opens only from Changes (so "opening a diff switches to Changes" holds trivially), Details or Files can be selected while a diff is open (the compact pane beside the diff shows that tab), and the Files tab is a placeholder until its own issue.

- Graph columns (#168): a graph row is a table, `GraphColumnLayout.Compute(width, laneColumns)` (pure, returns `GraphColumns`, like `PaneLayout`) and `GraphRowRenderer` draws it: lanes, message (ref decorations and subject), author, date, short hash, each after one space. The message flexes up to 100 columns (`MaximumMessageWidth`), so on wide terminals the other columns stay beside it and the rest of the row is blank. Author is 16 columns (longer names end with an ellipsis, wide characters are never split), date is `yyyy-MM-dd` as the author's local date (#183: the log uses `--date=raw` (`%ad`, "seconds offset") and the parser keeps the author's UTC offset in `AuthorTime`, so a late-evening commit shows the day the author saw; a bare number without offset counts as UTC; compact absolute, not relative: it needs no clock, so rows and snapshots are deterministic and the date does not change while the list is on screen; the commit details pane has the full time), the hash is the 7-digit short hash in the dim hash colour (the date is faint too). Columns are added in the order author, date, hash only while the message keeps at least 30 columns, so a narrowing terminal drops hash, then date, then author, and they come back on widening. Below about 50 columns only lanes and message remain. A search match on `author:` or `hash:` marks the whole column text; when that column is dropped nothing is marked. The widths are fixed constants rather than content-based so the columns do not shift while commits stream in. The 100k-commit key latency is unchanged (`measure.sh`: `j` median 7.4 ms).

- Look and feel (#171, owner review pending): the default look is decided by `PaletteTable` (colours of a scheme: accents, muted, selection tints, bars, lanes) and `Palette` (role to colour), documented in `docs/ux.md` ("Look and colours"). Open design questions settled with the recommended default: (1) framing keeps the existing layout (one-column dividers and title rows, no boxes around panes: a box costs two rows and columns per pane and the issue excludes layout changes); focus is shown by the filled accent chip on the focused bottom pane's title, the accent divider beside the focused sidebar or bottom pane, and the selection tint; (2) the selected row is a background tint (focused: blue; unfocused: grey) instead of reverse video, and the unfocused detail and diff panes now show their cursor row too (before, nothing marked it); (3) the palette is a GitHub-like set (dark and light variants) in 24-bit colour, with `NO_COLOR`/`TERM=dumb` falling back to styles only; the 256-colour terminal gets the 24-bit scheme because Terminal.Gui writes either 24-bit or 16-colour sequences, and the 16-colour scheme (used when `TERM` has no `256color`, or the driver reports no 24-bit support, in which case we also force the driver to 16 colours) uses only the 16 named colours so the terminal's theme decides; (4) the background is dark unless `COLORFGBG` says light (`ConsoleCapabilities.IsLightBackground`; querying the terminal with OSC 11 would cost start-up time and is not done); (5) overlays use the accent frame, the status mode, active tab and overlay title are one accent chip. `Palette` holds the configured table in a static (set once at start-up, UI thread only; the pure overload `Palette.For(segment, isSelected, isFocused, table)` is what tests use). The contrast of every role on a typical dark and light background (and on the selection tints) is a test (`PaletteTests`, ratio 4.5, dividers 3.0); 16-colour readability depends on the terminal's own theme and was not measured. `--print-frame ... --colors truecolor|16|none [--light]` prints a frame with ANSI colours (`AnsiFrameWriter`; `StyledSegment.Selection` lets a frame made of several panes mark each pane's selection, focused or dim, on its own). The start-up time is unchanged (200x60 on the 100k repository, median of 10 cold starts: ~78 ms before and after).

- Framing (#197, part of the #198 look and feel PR, owner review pending): every pane is a titled box with shared edges and one column of inner padding (`FrameGrid`, `PanePadding`, `docs/ux.md` "Frame (#197)"). Research (ideas only, no code copied): lazygit draws every panel as a bordered box, rounded by default, with the title in the top border, tabs of one panel listed in its title with the active one highlighted, the focused panel's border in a bright colour (https://github.com/jesseduffield/lazygit/blob/master/docs/Config.md, https://github.com/jesseduffield/lazygit/issues/2982); btop++ draws every area as a box with rounded corners as an option and titles in the border (https://github.com/aristocratos/btop); zellij draws a frame with a title around each pane and has an option for rounded corners, and since 0.45 a lighter single title line (https://zellij.dev/documentation/options.html); a design issue for another TUI recommends thin single-line borders applied consistently, one border per logical group instead of nested boxes, short titles, and a focus indication that does not rely on colour alone (https://github.com/tomaskub/yt-smzr/issues/26); gitui, k9s and yazi use titled blocks or no borders (yazi plugins add them); their screenshots were not reviewed in detail, only the descriptions above. Decision: boxes with shared edges (the zellij/tmux way) rather than a box per pane with a gap, because a separate box costs two rows and two columns per pane and the bottom strip already has a title row that can be the shared line; rounded outer corners (lazygit default) with plain junctions; titles as chips in the top edge (lazygit, btop) which doubles as the focus cue; focus is the accent colour on the whole box of the focused pane plus the filled title chip (no number-jump labels: `Tab`/`Ctrl-w` already exist). One column of padding on both sides of every pane, so text does not hug the lines; selection tints cover the padding. The frame is drawn from one grid of cells (per cell: which sides a line leaves through, plus a focus flag), so corners and junctions follow from the rule and the text frame and the UI cannot disagree; the ASCII tier replaces every line, corner and junction with `-`, `|` and `+`. Costs: two columns and one row more than before at the same terminal size (the header row was removed in the same change, #221), the side-by-side threshold of the detail and diff panes went from 70 to 72 columns. Not done: per-pane frame styles (square or heavy) belong with the theme setting (#47).

- Ref label glyphs and bottom pane (owner review of #198, 2026-10-13): the tree and cloud emoji on merged ref labels looked odd, so the current branch is marked `◆ ` (U+25C6, one cell, in the geometric shapes block that common monospace fonts cover; ASCII keeps `HEAD -> `) and a branch that also stands for its remote-tracking branch gets ` ↔` (U+2194, one cell, in the WGL4 set so practically every terminal font has it; ASCII keeps ` (r)`). Both were chosen over a star or a checkmark because they stay one cell wide in most terminals and fonts and do not compete with the commit node `●`. The bottom pane's tabs are buttons (`SegmentRole.TabButton`: muted text on the bar background, underlined without colours, `[Name]` in ASCII, a column of line between them), and its content has its own panel background (`StyledSegment.OnPanel`, `PaletteTable.PanelBackground`; 24-bit only, the cell is still the line's when no background colour exists). Options considered for the separation and not taken: a heavier or double line for the pane edge (the frame grid derives every junction from one rule, a second line style would double the junction table) and a tint in the 16-colour tier (no subtle background exists there).

- Diff inside the Changes tab (owner review of #198, 2026-10-13): "all panes are independent, i.e. file diffs are part of the Changes tab; Changes opens with the diff for the first file; navigating through Changes with h/j/k/l opens diffs for that file instantly, no need to press Enter." Interpretation: (1) the diff is no longer a mode opened by `Enter`; while Changes is the selected tab and the screen is at least 72 columns wide with a bottom strip (`PaneLayout.ShowsDiffWithChanges`), the diff pane is shown beside the file list. On narrow or short screens the on-demand open stays (the diff replaces the file list, zoomed under 14 rows) because the two cannot share the strip. (2) The whole commit's diff is loaded once (as before, against the first parent); the file cursor of the list only scrolls it to that file's header, so `j`/`k` in the list show the next file at once with no git call. Selecting another commit loads its diff (the in-flight load is cancelled by `DiffStore.Start`) at its first file; the file list cursor lands on the first file when the files arrive. (3) h/j/k/l: `j`/`k` move the file cursor and the diff follows; `l` (like `Enter`) moves focus from the list into the diff, `h` (like `q`/`Esc`) back to the list and, from the list, to the graph, so the existing meaning of `h` as "back" holds and `l` is the natural "forward"; the Detail view had no `l` binding, so there is no conflict. In the diff `]f`/`[f` also move the file list cursor. (4) Leaving Changes while the diff has focus returns focus to the list pane. The diff load starts once the commit details have arrived (as in #215), so the diff of a moved-to commit appears after details plus one `git diff` run; the diff prefetch/measure question stays with #225.
