# UX: workflows

*Internal design note for maintainers and agents. Not needed to use or contribute to Gitunia.*

Part of the UX spec; start at [ux.md](ux.md).

## Workflows

### 0. Open a repository, switch tabs, reopen the session

1. **Start.** `gitunia` restores the last session (tabs, active tab and focus; the graph of each tab opens on HEAD, see workflow 2); with no session it opens the picker. `gitunia <path>` opens that path as a tab (a repository already open just gets focused) and keeps the other restored tabs.
2. **Picker.** `Ctrl-t` or `<space>oo` opens it (Insert mode, input focused). It lists open, pinned, recent and discovered repositories, fuzzy-filtered as you type, as a framed overlay with group headers and a tag per row (`open`, `pinned`, `recent`, `found`, `missing` for a tab whose directory is gone); look in `ux-look.md`.
   - `Up`/`Down` and `Ctrl-j`/`Ctrl-k` move; `Enter` or `Ctrl-l` opens in a new tab (or focuses the existing one); `Backspace` deletes a character; `Esc` cancels (with no tab open it quits, since there is nothing to go back to).
   - `Tab` or `Right` accepts the suggestion: the highlighted repository's path is filled in and its subfolders are listed; in a typed path it completes the folder name.
   - Typing and matching ignore case: every segment of a typed path is resolved against the real folder names (`~/projects/x` lists `~/Projects/x` on Linux) and the inserted text keeps the real case.
   - Discovered repositories come from a scan of the conventional source folders below the home directory (`Projects`, `src`, `code`, ... up to three levels deep, hidden and dependency folders skipped); the `scanRoots` config option replaces them. A typed path is listed off the UI thread (the previous rows stay until the new listing arrives, a newer keystroke cancels the older one, a listing slower than 5 s ends with a "timed out" notice). A click highlights a row, a double-click opens it.
   - **Clone and init.** `Alt-c` (or the `Alt-c clone` chip in the picker footer, when it fits) asks for a URL or path in a prompt popup, then for the target directory in a second one (default: the typed folder, else the first scan root, plus the repository name; `Esc` closes only the popup). A local path is taken from the active repository or home, never from the process working directory. The target must be missing or empty (otherwise a status bar message, nothing touched). The clone runs off the UI thread, belongs to no tab and shows `Cloning: Receiving objects 45%` with the cancel chip; `Esc` or the chip stops it and removes git's half-made folder. On success the repository opens in a new tab and the picker closes; on failure the status bar says why and the picker stays. A clone never prompts: a failure that needs credentials says to set up a credential helper or an ssh-agent key. `Alt-i` (or the `Alt-i init` chip) asks for a directory, creates it when missing, runs `git init` (existing files are kept, nothing staged) and opens it; a folder that already is a repository root is just opened. One clone or init at a time, and neither while locating a missing repository.
3. **Typed paths.** Text starting with `/`, `~/`, `./`, `../` or a drive (`C:\` or `C:/`) is a path; anything else is a fuzzy query.
   For a path the list shows the matching directories (repositories marked), `Tab` completes to the common prefix and then to the highlighted directory, and `Enter` opens the resolved path.
   On Windows paths are shown native (`C:\Users\name\repos`, no `~` abbreviation, the hint names `C:\ .\ ..\`); typing `~` or `/` still works, and Tab after a bare `~` continues with `\`.
   Relative paths are taken from the active repository, or the home directory, never from the process working directory.
   A non-repository path shows an inline "not a git repository" message and the picker stays open.
4. **Pin and remove.** In the picker `Alt-p` (or the `Alt-p pin`/`Alt-p unpin` chip in the picker footer, for the highlighted row) pins or unpins the entry; `Alt-d` removes it from recents (never deletes anything on disk). `<space>op` pins the repository of the active tab.
5. **Switch tabs** with `gt`/`gT` (or `3gt`), `Alt-1`..`Alt-9`, or `Ctrl-^` / `<space><Tab>` for the previously active tab. Mouse: click a tab; a click on a tab's `*` also opens its Changes view. `Ctrl-w c` closes the tab; closing the last tab shows the picker.
6. **Tab bar.** One row on the status bar's background, then every tab as a chip ` N name markers `, and a ` + ` button after the last tab that opens the picker. The active tab is the filled accent chip; the others are buttons on a subtle tinted background (underlined without background colours, bracketed `[ 2 name ]` in ASCII; reverse video with `NO_COLOR`).
   - The name is the repository name, or the one given with `Ctrl-w r` (a prompt popup starting with the current name: `Enter` saves it in the session file, an empty name restores the repository name). The branch is not part of the tab.
   - Markers: `!` an operation is in progress (workflow 4), `*` dirty working tree, `↑n` ahead, `↓n` behind (`+n`/`-n` without Unicode), an ellipsis while the tab loads. The active tab follows external git activity by polling (refs every 2 s, working tree every 5 s; `watchFiles` turns on live file watching instead), background tabs update every 30 s and when shown; `<space>or` refreshes manually.
   - Remote chips, right of the tabs: fetch, pull and push show their key from the keymap before the label (`<space>f fetch  <space>p pull  <space>P push`, generated, never hand-written). Rows under about 127 columns drop the key text, under 100 columns the chips. While one runs a single `<space>rc cancel` chip replaces them.
   - Two tabs with the same name show their parent directory; names are cut at 40 characters; when the tabs do not fit, the row scrolls to keep the active one visible and `<` marks hidden tabs on the left.
7. **Missing repository.** A tab whose repository was moved or deleted stays in the bar as `! name (missing)`. `Enter` on it opens the picker (Locate repository, starting in the folder that held it) and the chosen repository replaces the tab; `Ctrl-w c` closes it.
8. **Unsent message.** Closing a tab that holds an unsent commit message (typed or edited, not committed) does not close it at once: the status bar names the tab, and a second `Ctrl-w c` right after (nothing else pressed in between) closes it and drops the message.
9. **Terminal key caveats** (Terminal.Gui 2.5.0 under tmux). `Ctrl-j` arrives as `Ctrl+Enter` and is mapped back to `Ctrl-j` (a picker alias for `Down`); `Ctrl-^` arrives as `Ctrl+6` and is mapped back, with `<space><Tab>` as the fallback; `Ctrl-h` arrives as `Ctrl-Backspace`, which deletes a word like in every single-line prompt.

### 1. Browse the graph, jump, search

1. **Open.** A repository tab opens with focus on the graph and the cursor on HEAD (the checked-out branch's tip or the detached commit; the newest commit when there is none), scrolled into view, whatever the last session had selected. Only the first time a tab is shown: switching back to a tab, or switching its worktree, keeps its own selection. After a refresh (own commit, external git activity) a cursor that was on HEAD or on the newest commit follows HEAD to its new row and the list scrolls to show it; a cursor anywhere else stays on its commit and screen row. Commits stream in; the list is usable immediately and the status bar shows loading progress.
2. **Graph row.** A table: branch lanes, message (ref decorations then subject), author, date and time (`yyyy-MM-dd HH:mm`, the author's local time) and short hash (dimmed).
   - The message starts two columns after the last line of the row's own lanes and is the flexible column; author, date (`yyyy-MM-dd HH:mm`, local time) and hash are fixed-width. Narrow terminals drop columns instead of squeezing the message below 30 columns: hash first, then the time, then the date, then author. `gitunia <repository> --print-frame WxH` shows any width.
3. **Ref labels.** The symbolic `origin/HEAD` is hidden.
   A local branch and its remote-tracking branch of the same name on the same commit are one label, `main ` (ASCII: `main (r)`).
   Every local branch gets a `⎇` before its name, checked out or not: it says the branch exists locally (#826); a remote branch without a local twin has none. The branch HEAD is on has a `◉` directly in front of it (`◉ main`; ASCII: `HEAD -> main`, other local names stay unmarked, so ASCII shows "local" only by the missing `origin/`).
   A remote branch with no local branch of that name, or on another commit, keeps its own `origin/x` label.
   A local branch whose upstream is gone carries the same dimmed mark after its label (`topic ✗`, ASCII `topic (x)`; see the sidebar, #570).
4. **Lanes.** Branches are laid out by tip date: the branch with the newest tip runs in the leftmost lane, the next newest to its right; the checked-out branch gets no lane of its own (it keeps the `◉` mark). Columns never move while scrolling or loading, and a lane freed by an ended branch is reused from the left by the next tip. A detached HEAD is laid out the same way.
   **Own lane per branch:** every branch keeps one lane, and one colour, from its tip down to the commit it forked from, where its lane joins the parent's (`●─┴─┴─╯`); it does not bend in earlier. Where several lanes meet at a commit the leftmost keeps it and the others bend into it. Usually main is the leftmost lane and one straight line from the root, with `release`, `develop` and similar as labels on its commits. A merge opens a lane for the merged branch at the merge row. With more lanes than fit (at most 40% of the pane), the lanes past the limit are drawn in the last column.
   **Colours:** every branch gets one colour, a hash of its name, moved on to the next free one when another open lane or a branch tip within the last 50 rows has it (so a branch's colour can change when a colliding branch appears, never while scrolling or loading); a local branch and its remote-tracking branch share it. A lane that no branch name starts takes a colour derived from its first commit. The colours are the theme's `lanes` list (at most 12, 6 at 16-colour depth, one without colour).
   **Chips:** a label is a box in the colour of its branch name, without parentheses, the local glyph (`⎇ `; `◉ ` on the checked-out branch, ASCII `HEAD -> `) or remote glyph (cloud, ASCII ` (r)`) inside it, one space of padding on each side unless the box has Powerline caps (`labelCaps`, on by default except in the classic Windows console). The chip of the branch that starts the lane has the lane's colour (line, node and chip match); every other chip takes its name's colour, so `test` stacked on `main` on one lane shows two differently coloured chips over one line. A commit with several branch names shows one chip per name; the lane follows its checked-out branch, else the smallest local name, else the smallest remote one. Tags are yellow everywhere.
5. **Straight lines.** A commit with one child and one parent on its own lane is drawn as part of the line (`│`, ASCII `|`), not as a node.
   Node dots (`●`, merge `○`; ASCII `*`, `o`) appear only where a lane starts, ends, forks or merges, and on every commit that carries a ref (branch, tag, remote, HEAD), so labels never hang on a bare line.
6. **Move** with `j`/`k`, `Ctrl-d`/`Ctrl-u`, `gg`/`G`, counts and the mouse wheel.
   While the log is still streaming, `G` goes to the last loaded commit and stays there (it does not follow the stream); the status bar says `Still loading: at the last loaded commit` until the load finishes (a plain `G` only, not `5G`).
   A log longer than 100,000 commits loads its newest 100,000 first (status bar `12/100000+ of 1204331`); a plain `G` there goes to the last loaded commit and loads the rest, with the same hint (#515).
   A faint row `⋮ more commits below, G loads the rest` follows the last loaded commit while the log is cut and idle; the cursor can rest on it, it has no details and no commit (#555).
7. **Jump.** `<space>h` jumps to HEAD.
   `<space>J` opens a status bar prompt (Insert mode) that fuzzy-filters refs (branches, tags, remotes) and also accepts a hash prefix of at least 4 hex digits; the best candidate is shown, `Up`/`Down`/`Tab` cycle through the others, `Enter` selects that commit, `Esc` cancels.
8. **Details.** `Enter` on a commit moves focus to the detail pane; `Esc` or `Ctrl-k` returns.
   The pane follows the graph selection while the graph is focused.
   It sits below the graph (hidden on screens under 14 rows, where `Enter` only shows a notice) and has three tabs, shown as buttons on its title row:
   - **Details:** hash, author, committer (only when different), parents, refs and the full message.
   - **Issue links.** The `[issuetracker "name"]` sections of the git config (repository, global or system) and of a `.issuetracker` file in the repository root (git-config syntax; the file wins on the same name) turn references in the message into links: `regex` (group 1 is the reference; without a group the whole match) and `url` (`$1` is the reference, percent-encoded). Quote values that contain `#` or `;`: `regex = "#(\d+)"`. Only `http` and `https` addresses become links, shown underlined in the accent colour; on overlap the earlier match wins. `gx` (or `Enter`, or a double-click) opens the first link on the line under the cursor in the default browser, `2gx` the second; when no opener starts, the address is copied through OSC 52. A missing or malformed file, section or regex means no links and no error. Both are read when the tab loads and on a manual refresh (`r`).
   - **Changes:** the changed files with status `A` `M` `D` `T`, `R old -> new`, `C old -> new` (the similarity score is not shown); merges show changes against the first parent by default, and the heading names the parent (`(merge: against first parent <hash>)`).
     `<space>vp` (detail and diff panes) switches a merge commit to its next parent, wrapping from the last back to the first (`(merge: against parent 2 <hash>)`, status line `Switching to parent 2 of 2...`): the file list is read again against that parent (`diff-tree` with it) and the diff viewer shows the files of that list against it.
     The choice belongs to the selected commit and is not remembered: selecting another commit, or coming back to this one, starts at the first parent.
     Not a merge commit says so.
     Combined diffs (`--cc`) are not offered, and the difftool (`<space>ed`) always uses the first parent (#95, #497).
   - **Files:** the file tree of the commit (`ls-tree -r -z --long`): directories first, then files, each ordinal by name; a directory whose only child is a directory folds into one row (`src/Gitunia.Core`).
     Every directory starts closed (the open ones are remembered per repository tab while the selection moves to other commits); a closed directory shows its file count, a file its size, and executables, symbolic links and submodules say so (`(executable, 1.2 KB)`, `(symlink, 12 B)`, `(submodule)`).
     `Enter` and a double-click open or close the directory under the cursor, `l` opens a closed one; `h` closes an open directory, else moves to the parent row, and at the top does nothing (`Esc` goes back to the graph).
     `/` filters by path (case-insensitive substring, typed in the status bar, Insert mode): the rows narrow as you type and every directory that holds a match is open (and cannot be closed) until the filter is cleared; `Enter` keeps the filter, `Esc` in the box clears it, and `Esc` in Normal mode clears an active filter before it goes back to the graph.
     The filter stays when the selection moves to another commit.
     The pane beside the tree shows the content of the file under the cursor at once and follows the cursor (see 1c, "File content"); `Enter` and a double-click on a file move focus into it.
     `y` copies the path of the row.
     The tree is listed off the UI thread when the tab is shown (not while another tab is selected), cancelled when the selection moves on, and the last four trees are kept; the title shows the number of files in the tree.
     Timing of large trees: `docs/architecture.md`.
   - A fresh tab opens on Changes.
     `]`/`[` switch to the next/previous tab (wrapping), `gd` `gc` `gf` jump to Details, Changes, Files from the graph or the detail pane; a click on a label does the same.
     The selected tab is part of the repository tab's view: kept while the graph selection moves, saved with the session, and each tab remembers its own cursor row for the selected commit.
   - **File paths.** A file row of the Changes tab and of the working-tree Unstaged and Staged lists shows its path in one of three styles, a per-tab view option (not saved with the session, name first on a fresh tab): `name first` (default; the name, then the directory dimmed), `full path` from the repository root, and `tree`: folders as a tree like the Files tab, a folder row (`src/`) with its files indented below it showing the change mark and the name only (a rename `R old.cs -> new.cs`, the old path in full when it sits in another folder); folders come before files.
     Folders open and close: `za` or a click toggles the folder under the cursor (a double-click leaves the fold as it was and acts), `h` closes an open folder, else moves to the parent folder, `l` opens a closed one (`Enter` goes to the folder diff). A closed folder hides its rows and shows its file count (`src/  3 files`); its diff is still the whole folder. Closed folders are remembered per repository tab (not saved with the session); every folder starts open. A folder row is selectable: the diff pane shows all changes below it, `Enter` focuses the diff and `y` copies the folder path. Commit details, comparisons and merge commits all list this way; the Changes view lists have the same tree (workflow 2, "Tree style in the lists").
     When the row is too narrow the directory is cut from the left (`…Core/Git`) and dropped when not even that fits, so the file name keeps its columns; a status mark keeps its place. A rename shows its old name dimmed after the directory when it fits. `<space>vn` cycles the three styles; the `view ▾` dropdown (`<space>vv`) picks one directly. The dropdown chip sits in the title row of the Changes tab (while Changes or Files is selected) and of both Changes view lists, shows its key when the row is wide enough and is left out when the title leaves no room. The status bar says which style is on; the quick jump labels what is drawn; `y` still copies the whole path.
   - `j`/`k` scroll the rows of the tab.
     On Changes, focus lands on the first file row, that file's diff is already shown beside the list and `j`/`k` show the diff of each file as the cursor reaches it, no `Enter` (see 1c).
     `Enter` moves focus into the diff (on Details it only says to open Changes; on Files it focuses the content beside the tree); `Ctrl-l` does the same by direction.
   - When the details fail to load the pane says so and `<space>or` in the detail pane (or the palette) retries. The title row shows the file count (`.. files` until the details have arrived). The rows of all tabs start at the same left edge; only the commit message is indented.
9. **Search.** `/` opens the search box (Insert mode).
   Plain text matches the commit subject, `author:` matches the author name, `hash:` the start of the hash and `body:` the whole commit message (subject and body).
   `body:` is answered by `log --grep` on demand, so bodies cost no memory and no graph load time; the status bar shows `searching messages` until the answer is in, and a failure shows `Message search failed: ...`.
   All are case-insensitive.
   Matches are highlighted while typing and the status bar shows the count (`/fix_  3/17`).
   `Enter` jumps to the first match at or after the selection and returns to Normal mode, `n`/`N` step through matches (counts work, the search wraps), `Esc` in the box cancels, `Esc` in Normal mode clears the highlight.
   In the box the single-line editing keys below apply.

   **Single-line prompts** (search, filters including the sidebar and help filters, the pickers including the repository picker, reflog and file-history search, settings text fields, quick jump, new-name prompts; #1166, #1171) have a caret, one editor (`PromptTextEditor`). Typed text inserts at the caret. `Left`/`Right` and `Home`/`End` (also `Ctrl-a`/`Ctrl-e`) move it; `Ctrl-Left`/`Ctrl-Right`, `Alt-Left`/`Alt-Right` and `Alt-b`/`Alt-f` move by a word; `Backspace`/`Delete` remove a character; `Ctrl-w`, `Ctrl-Backspace` and `Alt-Backspace` the word before the caret, `Ctrl-Delete` and `Alt-d` the word after it; `Ctrl-u` deletes to the start and `Ctrl-k` to the end (in the type-to-filter pickers `Ctrl-j`/`Ctrl-k` move the highlight, so `Ctrl-k` does not delete there; in the repository picker `Right` completes the path and `Alt-d` removes the recent entry, so the caret moves right with `End`/`Ctrl-e` or word keys only). Words and text elements follow the message box rules (`WordBoundaries`). The caret is drawn as `_` after the last character and as `|` between two characters; a long text is cut around the caret. No selection or clipboard in prompts yet.
   The search scans the loaded commits in small slices between key presses and keeps scanning as the log streams in (on a log cut at the soft row limit, reaching the loaded end loads the rest, about 10 s and ~300 MB on a 1M-commit log, and the scan goes on); the status bar shows `searching N%` meanwhile.
10. **Copy and refresh.** `y` copies the selected commit hash (OSC 52); `<space>or` refreshes the repository now.
11. **Quick jump** (`<space>j`, flash/easymotion style). A prompt in Insert mode (`jump _` in the status bar): every row in view that contains the typed text (case-insensitive; in the graph a row's text is its ref labels and its subject) gets a one-letter label in a chip drawn over the character after the match. A label selects that row and closes the prompt; `Enter` selects the nearest match; `Esc` cancels.
    - Only rows in view are looked at, so the cost does not depend on the log size. Labels go to the matches nearest the cursor first, home-row letters first; a letter that would continue a match in view is never a label; with more matches than letters the farthest stay unlabelled (type more to narrow). A match whose label would fall past the right edge takes no letter.
    - It works in the graph, the diffs (row text, not line numbers or markers; both sides in the side-by-side diff), the Unstaged and Staged lists (file paths) and the detail pane (rows in view, file paths on Changes); not the sidebar. The prompt closes when focus moves to another pane or tab.

12. **Comparing two commits.** Mark one commit; from then on the commit under the cursor is compared with it, as `git diff <older> <newer>`. One mark is enough, there is no second key press.
    - **Keys.** `<space>=` in the graph marks the commit under the cursor (its row starts with `[mark]`); on a different commit it moves the mark, on the marked commit it clears it. `Esc` in the graph clears the mark and the comparison (after the usual claims on `Esc`). While a mark is set the status bar hints read `<space>= move mark  Esc end compare`. A Visual range keeps its meaning (cherry-pick and revert of the range); the mark is separate.
    - **Order.** The older commit is the one lower in the graph, whichever was marked first, so the diff always runs older to newer. Commits on different branches are compared the same way (a plain `git diff A B`, no merge base); a merge commit at either end is compared as a tree (no parent choice).
    - **What shows.** Moving the cursor to any other commit shows the comparison with the mark. The first comparison after marking selects the Changes tab. The Changes tab lists the files of `git diff <older> <newer>` with the heading `N files changed (<older>..<newer>)`, the diff pane beside it shows the file under the cursor from the same command; the Details tab names the comparison (`compare  abc1234..def5678`). With the cursor on the marked commit itself its own changes show. Diff options work as in the commit view. The comparison is not cached; it starts after the same debounce as the commit view and one `git diff` (async, cancellable) runs per resting position, while the Changes tab meanwhile shows the commit's own files.
    - **State.** The mark is part of the tab's view state (`RepositoryViewState.CompareMark`): per tab, kept across tab switches and refreshes, not saved with the session. When the marked commit is no longer in the graph nothing is compared and `Esc` clears the mark or `<space>=` moves it. The actions menu of a graph row (`<space>.` or a double-click) lists "Mark or compare a commit".

### 1b. Sidebar navigation

1. `Ctrl-w h` (or `Tab` cycling) focuses the sidebar (sections: branches, remotes, tags, worktrees, stashes). `j`/`k` move, `l`/`Enter` expand a section or folder, `h` collapses it (or moves to the parent); bare `h`/`l` never leave the sidebar.
2. `Enter` on a branch, remote branch or tag selects its commit in the graph and keeps focus in the sidebar; `Ctrl-l` moves focus to the graph, and `l` on a leaf does nothing.
   A stash is not a graph node, so `Enter` on it shows the stash's files and diff in the detail pane (workflow 7, item 4) and keeps focus in the sidebar; `Ctrl-j` moves on to the detail pane.
3. `/` filters the entries by name (Insert mode: type, `Backspace` erases, `Enter` keeps the filter and returns to Normal mode, `Esc` drops it).
   The filter also matches the worktree shown beside a branch and unfolds every section with a match.
   In Normal mode `Esc` clears an active filter, and otherwise returns focus to the graph.
4. **Prefix folders.** Local and remote branches are grouped by their `/`-separated prefix (nested to any depth; a remote's branches fold under the remote's own folder first); a folder whose only content is one more folder folds into one row (`feature/ui/`). A folder row shows `▸`/`▾` (ASCII `>`/`v`), its name with a trailing `/` and its entry count dimmed; the branch row shows the short name, while checkout and every other branch action use the full name. `l`/`Enter` open a folder, `h` closes it (on a closed folder or a branch it moves to the enclosing folder or section); `Enter` and a click toggle it; it has no actions menu. Folders are closed by default except the ones holding the current branch and a remote's own folder; what the user opened or closed is kept per tab (not saved with the session). The `/` filter matches the full branch name and opens every folder above a match. The `*`, `wt:<directory>`, `↑n↓m` and `✗` markers stay on the branch row.
5. **Tight tree layout.** Section headers start at column 0, their entries one column in, each further level one more column (the Files tab tree uses the same indent and row renderer). A name that must be cut is cut in the middle (`feature/6…-diff`) so its tail stays; the right-hand markers keep their columns and the last one (`wt:<directory>`) gives way first. While the sidebar has focus the status bar shows the full name of the selected row after the position (cut in the middle to a third of the line at most; a worktree shows its path, a section or folder nothing).
6. A section header shows its entry count.
   Remotes and Tags are folded by default.
   A branch shows `wt:<directory>` for the worktree that has it checked out (`*` marks the current branch and the current worktree) and `↑n↓m` against its upstream.
   A local branch whose upstream was deleted on the remote (`gone` after a fetch with `--prune`) gets a dimmed `✗` after its name (ASCII `(x)`), so the branches a local prune could clean up stand out; on a narrow sidebar the name is never cut for the marker below 8 columns or half of the width left after the prefix. The help overlay of the graph and the sidebar ends with a `Markers` section that explains the markers.
   The sidebar is hidden below 60 columns.

### 1c. Diff viewing

1. **Where it is.** The diff is part of the Changes tab, not a mode of its own: while Changes is selected, the diff pane is shown beside the file list. It shows one file at a time: the file under the file list's cursor, from the commit's diff against its first parent, or the parent a merge commit was switched to with `<space>vp` (or the comparison's two commits), so the diff always matches the file list. The pane never shows another file; the next one is chosen in the file list.
   The one exception is the folder view: in the tree style of the file list, a folder row shows the files below it, in commit-diff order, as a single document (title `folder, N files`). `]f` and `[f` step from file to file inside it (and stop at the first and last), the options keep the folder, and moving the list's cursor to a file or another folder switches the pane. Selecting a folder costs no extra read.
   - It is there as soon as the tab is, for the first file. Moving the file cursor with `j`/`k` (or a click on a row) shows that file's diff at once. Selecting another commit in the graph loads that commit's diff at its first file (a load in flight is cancelled when another commit is asked for).
   - `Enter` or `Ctrl-l` on the file list moves focus into the diff to scroll, search and copy; `Esc` or `Ctrl-h` comes back and the diff stays. On the Details tab the pane is not shown; on the Files tab it shows the content of the file under the tree's cursor (item 11).
   - The diff sits beside the compact file list (a third of the width, 24-60 columns) on screens of 72 columns or more. Narrow or short screens (under 72 columns, or without the bottom strip) keep the on-demand behaviour: the diff opens with `Enter` on a file row, takes focus and replaces the detail pane (screens under 14 rows zoom it), and `Esc` closes it. An on-demand diff on a screen that is then widened stays open and also keeps showing a Details or Files tab beside it.
   - `<space>z` zooms the focused graph, detail or diff pane to the full area between the tab row and the status bar and back (the sidebar does not zoom; moving focus to another pane ends the zoom; `Tab` only reaches panes that are shown). Where the Changes or Files tab sits beside the diff / file content the two zoom as one view, side by side, whichever has focus: moving focus between them keeps the zoom. `Ctrl-w >` / `Ctrl-w <` in the paired zoom move the divider (the same width as the normal split, remembered with it); in a single-pane zoom every resize key leaves the sizes alone and the status bar says `Unzoom the pane to resize`; `Ctrl-w =` resets all sizes as usual.
2. **Navigate.** `j`/`k`, `Ctrl-d`/`Ctrl-u`, `gg`/`G` scroll (from the file list beside the diff, `J`/`K` scroll by a line and `D`/`U` by half a page without taking focus; `Ctrl-d`/`Ctrl-u` keep paging the list, #755); `]c`/`[c` jump to the next/previous hunk of the file (counts work; at the first or last one the pane stops and the status bar says `No next hunk` / `No previous hunk`, it never moves on to another file).
   `]f`/`[f` pick the next/previous file of the commit (counts work): the pane then shows that file only and the file list's cursor follows; at the first or last file nothing moves and the status bar says `No next file` / `No previous file`.
   The diff of the Changes view does the same within the list of the file it shows.
   The title shows the file under the cursor, `file n/m` among the commit's files and `hunk n/m` of that file.
3. **Search.** `/` opens a search box (Insert mode, case-insensitive substring over every row of the shown file including headers (other files of the commit are not searched), highlighted while typing); `Enter` jumps to the first match at or after the cursor, `n`/`N` step through matches and wrap, `Esc` in the box cancels.
4. **Buttons.** The right end of the title row has chips (`‹ file`, `file ›`, `‹ hunk`, `hunk ›` and `view ▾`, which is always the rightmost; a file's content has `wrap` and `zoom` instead); each is the mouse path of a key ([Mouse table](ux-mouse.md)) and shows that key from the keymap of the diff's view before its label (`[c ‹ hunk`), so rebinding follows. A pane too narrow for the keys drops them first, then drops buttons (see Mouse). The Changes view diff also puts its staging chips on the first line of the current change group, with their keys (`<space>a stage  <space>d discard`). Quick repeated clicks on a button each count; a drag selects a range of rows.
5. **Rows.** Hunks are told apart by a blank row and a separator row at the start of each: a short rule, the hunk header and a rule to the right edge (plain dashes in the ASCII set), in the quiet colour, spanning both sides in the side-by-side view. Then `old new` line numbers, a `+`/`-`/space marker and the text. Text is cut with an ellipsis while word wrap is off (the default); `<space>vw` turns wrap on (a long row continues on following screen lines, `j`/`k` move by screen line, title `[wrap]`, no horizontal scroll). Tabs expand to 4-column stops and wide characters are never split.
   `<space>vc` (or the `view ▾` dropdown; per tab, not saved; title `[ws]`) draws whitespace as quiet marks: a tab as `→`, each leading or inner space as `·`, each trailing space as `•`, a carriage return as `¶` (ASCII: `>`, `.`, `<`), in their own subtle colour. A mark takes the column of what it replaces, so wrapping, search, quick jump and copy see the real text.
   **Changed words** (always on): inside a changed line the exact words that differ from the paired line are drawn on a tinted background (bold as well, underlined where there is no background colour: 16 colours and `NO_COLOR`). A run of removed lines is paired line by line with the added lines right after it, as in the side-by-side view, in the unified, side-by-side and Changes view diffs; a line without a partner is not marked. Lines are compared as words, runs of whitespace and single symbols; lines that share no word or symbol (rewritten, not edited) get no marks; very large lines or runs are not compared (the part is marked whole), so a huge diff costs only its visible rows. Whitespace marks inside a changed word sit on the same tint; a search match and the selected row keep their own look over it. Under a Visual range or a character selection the word's tint is blended 75% toward the range tint (#1176), and at 16 colours and `NO_COLOR` the reverse video of the range comes on top of bold and underline.
   The conflict editor marks words the same way in every layout (#740, #764).
   Where the base is shown (three panes, or below the sides on a narrow screen) and the hunk has one, the words of the ours (removed tint) and theirs (added tint) lines that differ from the base line of the same row are marked, and the base words either side changed are marked on the removed tint (the union of its differences against both); only on rows where ours and theirs differ.
   Without a shown base the ours and theirs lines are compared with each other.
   A side line without a base line in its row is not marked.
   Binary files, renames without edits, mode changes and "no newline" markers get a note row; parser warnings (such as invalid UTF-8 in the patch) show as a red `!` row above the first file.
6. **Options** (per tab, not saved with the session): `+`/`-` show 3 more/fewer unchanged lines around each change (title `[ctx N]`, and they start the repeat mode, see Modes), `<space>vf` shows whole files (`[file]`), `<space>vi` ignores whitespace-only changes (`[-w]`; whitespace-only files stay in the list without a diff). Each reloads the commit with git's `-U<n>` / `-w` (the cache is dropped, the cursor returns to the same file). In whole-file mode `]c`/`[c` still visit each group of changes as git's hunks would group them for the context set with `+`/`-` (3 by default, not a `diff.context` from the config). The options reset when the tab's repository is reloaded; a user's `diff.context` applies until the first change.
7. **Side by side** (`<space>vs` or the `view ▾` dropdown; per tab, not saved; title `[split]`). The old side on the left with its line numbers, the new side on the right, a vertical rule between; a run of removed lines is paired line by line with the added lines after it (the shorter side stays blank); file and hunk headers and notes span both sides.
   - It needs a pane of 80 text columns; on a narrower pane the unified rows stay and the title says `[split 80+]`.
   - The cursor is one line of the pair: the old side's row (the new side's for an added-only line). `y` copies that row, `Y` the file's rows in diff order, and a Visual range copies in diff order. Wrap wraps each side inside its half. Search, `]c`, `]f` and the options work as in the unified view.
8. **Back.** `Esc` (or `Ctrl-h`) first clears an active search, then returns focus to the file list (beside the file list the diff stays; an on-demand diff closes). If the tab is changed away from Changes while the diff has focus, focus returns to the detail pane.
9. **Limits.** A diff is capped at 400,000 rows and 100,000 lines per file (the last row, or the file's note row, says it was cut short).
   `<space>vl` loads the same commit again without the caps (the cursor stays on the same file; with nothing cut it only says so; binary files have no content to load and stay a note).
10. **Following the graph.** While the pane is shown, moving the graph (or a refresh that moves the selection) loads the newly selected commit once its details have arrived; the old diff stays until then.
    Beside the file list it shows the file under the file cursor (the first one for a new commit); an on-demand diff keeps showing the same file if the new commit touches it, else the first one.
    A resize that makes room for the diff loads it at once; one that takes the room away returns focus from the diff to the file list.
    The status bar shows the keys of the focused pane.
11. **File content** (Files tab). Like the diff of the Changes tab, the pane sits beside the tree from the start (72 columns or more with the bottom strip) and shows the blob of the selected commit read-only for the file under the tree's cursor, so no key is needed. With no file under the cursor (a folder, a submodule, a tree still loading) it shows `Select a file to view its contents`. The read is off the UI thread, starts 40 ms after the cursor rests and is cancelled when it moves on; the old content stays until the new one arrives.
    `J`/`K` scroll the content by a line and `D`/`U` by half a page from the tree (`Ctrl-d`/`Ctrl-u` page the tree). `Enter` or a double-click on a file moves focus into the pane; `Esc` returns to the tree; `Tab`/`Ctrl-w` and the zoom work as for Changes. Where the diff is not shown beside the list the content opens on demand, as the diff does. The title reads `File  <n> lines  <path>`; rows have one line number column and no change marker.
    The 1 MiB blob limit is the only cap (a file of blank lines is about 1M rows, shown in full). Over 1 MiB (judged from the tree listing, so nothing is read) the pane says `File too large to show (<size>, the limit is 1.0 MB)`; a NUL byte in the first 8000 bytes says `Binary file (<size>): its content is not shown`; an empty file says `Empty file`; a submodule has no content; a symbolic link shows its target path. CRLF is shown without the CR; invalid UTF-8 shows as replacement characters; filters and `.gitattributes` conversions are not applied.
    Scrolling, `/` search, quick jump, `<space>vw` wrap and the mouse work as in a diff; `y` copies the line, `Y` the whole file. In the pane `]f`/`[f` move the tree's cursor to the next / previous file row (`No next file` / `No previous file` at the ends), while `]c`/`[c` and the diff options say the content has none. The content belongs to the commit and the Files tab: selecting another commit shows the placeholder until its tree has loaded.

### 2. Changes view: stage, commit, amend, discard

The Changes view is a separate view of the tab, not a graph pane or pseudo-row. Its keymap views are `WorkingUnstaged`, `WorkingStaged`, `WorkingUnstagedDiff`, `WorkingStagedDiff`, `WorkingMessage`; they inherit `Lists` and `Global`, and the diffs the `Diff` navigation rows.

**Layout.** Left column: the `Unstaged` list on top (conflicted files first in their own group, then modified, deleted, renamed and untracked files, each with its status letter and path) and the `Staged` list below it, each titled with its count.
Right: the diff of the file under the cursor and, below it, the message box with an option row `[ ] SignOff  [ ] No-Verify  [ ] Amend` and a `Commit` button (it shows its key, `Ctrl-g`, and drops it on a narrow row).
The sidebar is hidden (the view gets the whole width); the tab bar stays.
- Status letters: `M` `A` `D` `R` `C` `T`, `?` untracked, `!` conflicted. A rename or copy shows as `old -> new` in Staged. Ignored files are in no list. List order follows git's, except that conflicted files come first.
- Terminals under 80 columns show one pane at a time (the focused list shows, `Tab` switches; the focused diff replaces the list). Under 7 rows of content the two lists do not stack; under 12 rows the message box shows only while it has focus, in place of the diff area.

**Open and leave.** `<space>s` toggles the view for the active tab; so do a click on the tab's dirty marker and the palette entry `Open or leave the Changes view`. The history status bar hints `<space>s Changes view` right after `j/k move` in the graph, sidebar and detail panes.
- The view is per tab: a tab keeps its view mode, cursors, draft message and option checkboxes while another tab or the history is shown. The view mode is not saved with the session (a restart opens on the history); the draft is.
- Leave with `Esc` from a list (back to the history with the same graph selection) or `<space>s` again. `Esc` in the diff and the message box steps back to the lists first. `q` quits from every pane.
- Opening focuses the first non-empty list (Unstaged, else Staged). A clean tree shows "Nothing to commit, working tree clean"; the message box stays usable for Amend.

**Focus.** `Tab`/`Shift-Tab` cycle Unstaged, Staged, Diff, Message.
`Ctrl-w h/j/k/l` move by direction (lists left, diff top right, message below it); `Ctrl-w j`/`k` move between the stacked lists, `Ctrl-w l` from either goes to the diff.
`Enter` (or `Ctrl-l`) on a file or folder moves into its diff, `Esc` (or `Ctrl-h`) back.
`y` copies the file's or folder's path.
`<space>1`..`<space>4` jump straight to Unstaged, Staged, Diff (of the file under the cursor) and Message from any pane, including the message box in Normal mode; not in Insert mode, where space is text (`Esc` first).

**Tree style in the lists.** `<space>vn` cycles name first, full path and tree for both lists, as on the Changes tab (an untracked directory stays one file row, `dir/`). Everything that acts on rows goes through the row-to-file map of the state (`WorkingRows`), never through the row number as a file number.
- **Cursor.** `j`/`k`, `gg`/`G`, ranges and clicks move over folder and file rows; `za` or a click opens and closes a folder (a double-click leaves the fold as it was and stages or unstages the folder; each list keeps its own closed folders per tab, not saved with the session); `h` closes an open folder, else moves to the parent folder; `l` opens a closed folder. The cursor stays on the same file or folder when the style or a fold changes; after a stage or unstage it stays at the same row.
- **Folder diff.** A folder row selects the combined diff of every file under it, hidden ones included (at most 200 files, one git call each; a longer folder ends with "Showing the first 200 of N files; M more files left out (<space>vl loads all of them)"). Hunks and lines cannot be staged or discarded from it (the status bar says to pick a file); `Enter` focuses it, `y` copies the folder path, `]f`/`[f` go to the next / previous file row.
- **Stage, unstage, discard.** `<space>a` / `<space>u` (and a double-click) on a folder row act on every file under it in one index call (conflicted files skipped and counted; no confirm). In a Visual range a folder row stands for all its files, each counted once. `<space>d` on a folder row opens one Confirm, "Discard changes to N files in src/?", counting every file under it (hidden ones too), naming the untracked ones (deleted from disk) and saying it cannot be undone; conflicted files, submodules and unreadable names are left out and counted. The same holds for a range with folder rows.

**Side-specific keys.** Each list and each diff side is its own view for the keymap, so help and hints show only what applies: `<space>a`, `<space>A`, `<space>d` exist only on the Unstaged side, `<space>u`, `<space>U` only on the Staged side; the other key there is unbound, not a no-op.

**The diff.** The right box shows the diff of the file under the cursor of the focused list, read off the UI thread with the history diff's limits: the Changes view diff for Unstaged, the index diff for Staged (both paths of a rename), an untracked file as additions, a binary file as a note, and a conflicted file as the combined diff (one file, each line added, removed or context as in the result). It is the same widget as the history diff (hunk jumps, wrap, context, whole file, ignore whitespace, split, search, `y`/`Y`, load anyway); the title reads `Diff  unstaged|staged  change n/m  <path>`; `<space>z` (or `zoom` in the `view ▾` dropdown) gives it the whole view.
Here a unit is a change group, not a hunk of the patch: every run of consecutive added/removed lines is its own unit, even when the patch merged several into one hunk. The group under the cursor (on unchanged lines, the group above) is highlighted by a bar in the left margin (`│`, `|` in ASCII) and, in 24-bit schemes, a quiet tint (`GroupBackground`); the mark is off while a Visual range is open. The staging buttons in the title row and on the group's first line, `]c`/`[c`, the title count and the stage, unstage and discard keys all use these groups (the history diff keeps the patch's own hunks). The diff follows the cursor and reloads after every status read, keeping the cursor row.

**Stage and unstage.** All run off the UI thread, one operation per tab at a time (a key pressed meanwhile says "busy"). When one is done the tab re-reads its status and the cursor lands on the same index, so the keys repeat. Failures show git's message in the status bar. Paths are always passed literally.
1. **Files.** `<space>a` in Unstaged stages the file under the cursor; `<space>u` in Staged unstages it (a rename unstages both paths). `<space>A` stages all (conflicted files skipped, the count reported), `<space>U` unstages all. No confirm, since nothing is lost. A double-click on a row does the same as the key.
2. **Ranges of files.** `v` or a mouse drag in a list starts a Visual range; the motions move its far end, `<space>a`/`<space>u` act on every file of the range in one git call (conflicted files skipped and counted), and `y` copies the paths one per line. The range ends when the operation starts, or on a click, `Esc`, `q`, `v`, a change of focus, or a refresh that changes the list (the status bar says "Selection ended: the rows changed"). The title rows have `stage all` / `unstage all` buttons showing their key when the row is wide enough.
3. **Hunks and lines.** In the diff of an Unstaged file `<space>a` stages the change group under the cursor; in the diff of a Staged file `<space>u` unstages it; the other groups of the same hunk stay as they were. `v` (or a drag) starts a Visual range in the diff and the keys then act on the added and removed lines inside it only (a range with no change is refused). After staging, unstaging or discarding a range the cursor goes to the next remaining change after the range (the last remaining one when none follows) and the view scrolls only if that row is off screen; staging a group without a range moves to the next group. The range survives a refresh that brings the same diff rows; if the rows really changed, or on a wrap, side-by-side or width change, it ends and the status bar says so. A double-click on a diff row acts on its change group.
   - The patch is never taken from the rows on screen: the file's diff is read again with git's default context, the picked lines are found in it by line number and text, and the resulting patch is applied to the index. Git refuses a patch that does not apply and leaves the index alone; if a picked line is no longer in the file the operation stops with "changed since the diff was read" and the diff reloads.
   - Lines of an untracked text file are staged like any other lines (recorded as intent-to-add first). A mode change is never part of a partial patch. Files that cannot be split (binary, staged-added, deleted, renamed without edits, untracked binary or symlink, a name that is not valid UTF-8) go whole when the key acts on the change group, and the status bar says so; lines picked in a Visual range are never widened to the whole file: the status bar warns "cannot be split into lines" and nothing changes.
   - The keys are refused while the diff is loading, for a conflicted file, and while the diff is cut short (`<space>vl` loads all of it first). Afterwards, for a group without a range, the cursor goes to the change group now at the same position (the next group when it was staged), or to the next file when the file is done.
4. **Conflicted files** show `!`.
   `<space>a` (or a double-click) on one opens a Confirm, "Mark X as resolved?" (only here and on a double-click: the conflict editor stages on save without it, workflow 4), saying that conflict markers still in the file are not removed or checked and that the message history will show how to bring the conflict back (the status message after staging carries `git checkout --merge -- <file>` as `Detail`; it overwrites the file's current content). The conflict editor cannot reopen a staged file, so the dialog does not point at `Ctrl-x`.
   `y` runs `git add` on it (status: "Marked X resolved").
   Stage all and a Visual range skip conflicted files and count them; a range of only conflicted files is refused.
   The banner with continue, abort and skip and the mergetool key are built (workflow 4); `Enter` on a conflicted file of the Unstaged list, or `<space>gr` from any pane, opens the built-in conflict editor (workflow 4, item 2a); its mouse path is the `resolve` chip in the Unstaged title row, shown while the cursor is on a conflicted file (a double-click keeps asking "Mark X as resolved?").
5. Every action is also a palette entry. The lists refresh from the tab's status after each operation and by polling; `<space>or` forces a refresh.

**Discard.** Nothing discarded can be undone: git keeps no copy, so there is no reflog hint; the Confirm dialog is the safety. `<space>d` on a file in Unstaged, or on a change group or Visual lines in the Unstaged diff, opens a Confirm that names what is lost; `y` runs it. There is no key for discarding staged changes (unstage first) and no "discard all".
- **Dialog texts:** "Discard all unstaged changes to X?" (plus a note when a deleted file is restored from the index or its staged changes are kept), "Discard this change (N lines) of X?", "Discard the N selected lines of X?", "Delete the untracked file X?" (an untracked directory: "...and everything in it"); for a range, "Discard changes to N files?" naming the untracked files, which are deleted (the first five, then a count). `n`/`Esc` keep the range.
- **What happens:** a tracked file is put back as the index has it (staged changes stay). An untracked file is deleted from disk, but never a tracked or an ignored path. Change groups and lines are cut from the file's unstaged diff, read again with git's default context, and applied backwards to the working tree only; the index is never touched. A line no longer in the file stops with "changed since the diff was read". Files go in batches (one restore for the tracked files, then one clean for the untracked, in chunks of 64 paths); if one fails the status bar says so and that the tracked files may already be restored.
- **Whole file behind a hunk key:** a file with no hunks to pick from (binary, deleted on disk, untracked) is discarded whole when the key acts on the hunk, and the dialog says so. A file that shows hunks but cannot be cut (text that is not valid UTF-8, a renamed file with a quoted path) is refused with "cannot be split into hunks or lines ... nothing was discarded"; lines picked in a Visual range are never widened to the whole file.
- **Refused before the dialog:** a conflicted file, a submodule, and an untracked name that is not valid UTF-8 on an OS without a byte-exact delete (Windows, macOS; Linux deletes it by its exact bytes). Same busy rule as staging.

**Message and commit.**
1. **Writing.** `<space>c` (from a list or the diff) focuses the message box and enters Insert mode.
   The built-in editor: the first line is the subject, a blank line then the body; the title counts the subject width as `12/72` and the part past column 72 is an error-coloured hint, never enforced.
   `Esc` leaves Insert mode but stays in the box (#748): the box has its own Normal mode, the status bar says NORMAL and the cursor stays visible.
   Normal-mode keys, a vim subset (counts are ignored): `h` `j` `k` `l` move the cursor inside the text, `w`/`b` word motions, `0`/`$` line start or end; `i` and `Enter` insert at the cursor, `a` after it, `I` at the line start, `A` at the line end, `o` opens a line below; `x` deletes the character under the cursor, `dd` the line, `u` undoes the last change (an Insert session counts as one change; the history is kept while the tab lives, not in the session file), `Ctrl-r` redoes it (until the text changes again). `viw` selects the word under the cursor (in Normal mode a selection only shows; `i` and typing replaces it, copy and cut need Insert mode) and `Ctrl-d`/`Ctrl-u` move the cursor 3 lines down/up (the keyboard side of the double-click and the wheel). Vim differences on purpose: `I` goes to column 0; `l` can rest past the last character.
   Leaving the box (Normal mode; in Insert mode these are editing keys) is `Ctrl-h`/`Ctrl-j`/`Ctrl-k`/`Ctrl-l`, `Ctrl-w` plus a direction, `Tab`, `<space>1`..`<space>3`, or `Esc` in Normal mode; bare `h`/`j`/`k`/`l` never leave it. The status bar names the pane-move keys on every pane (`Ctrl-h/j/k/l pane`), since `Ctrl-w h/j/k/l` and `Tab` are the fallbacks for terminals that deliver `Ctrl-h` as Backspace. A click in the box places the cursor before it starts Insert mode.
   - Editor keys (Insert mode; not rebindable rows in the [keymap reference](../keymap.md)): typed text and pastes insert at the cursor; `Enter` is a new line; `Backspace`/`Delete` join lines at their ends; `Left`/`Right` wrap across lines; `Up`/`Down` keep the display column; `Tab` inserts spaces up to the next multiple of four (`Shift-Tab` does nothing); `Home`/`End` and `Ctrl-a`/`Ctrl-e` go to the line edges and `Ctrl-Home`/`Ctrl-End` to the start and end of the text; `Ctrl-u` deletes to line start, `Ctrl-k` to line end. Words (one definition in `WordBoundaries`): a run of letters, digits, underscores and combining marks, a run of other symbols, and whitespace between; `foo.bar` is three steps, Unicode letters count. `Ctrl-Left`/`Ctrl-Right`, `Alt-Left`/`Alt-Right` and `Alt-b`/`Alt-f` move by a word, wrapping to the neighbouring line at a line edge; `Ctrl-w`, `Ctrl-Backspace` and `Alt-Backspace` delete the word before the cursor, `Ctrl-Delete` and `Alt-d` the word after it (at a line edge they join the lines like `Backspace`/`Delete`). Under tmux Terminal.Gui delivers `Ctrl-Left/Right/Home/End/Delete` and `Alt-Left/Right` (xterm `CSI 1;5D`, `CSI 1;3D`) and `Alt-b/f/d` (Esc then letter) as such, so both arrow spellings work; `Ctrl-Backspace` and the byte `Ctrl-h` (0x08) both arrive as `Ctrl-Backspace` (decisions.md; the pane-focus `Ctrl-h` is Normal mode only), so Insert mode deletes a word. Selection (#1165): `Shift` with `Left`/`Right`/`Up`/`Down`/`Home`/`End`, and with `Ctrl-`/`Alt-` word and text steps (`Ctrl-Shift-Left`, `Alt-Shift-Right`, `Ctrl-Shift-Home`), extends a selection from where it started; it is drawn with the range tint (a selected line break shows as one tinted cell). Typing, `Enter`, `Tab` or a paste replaces it; `Backspace`, `Delete` and the word and line deletes (`Ctrl-w`, `Ctrl-u`, `Ctrl-k`, `Alt-d` ...) delete just the selection; `Left`/`Right` collapse it to its start/end and any other move drops it. `Alt-w` copies the selection and `Ctrl-x` cuts it through the clipboard (OSC 52, decisions: Clipboard #52; `Ctrl-c` stays quit, `Ctrl-v` is not bound: paste with the terminal's own paste, which sends a bracketed paste). A paste keeps newlines and turns each tab into the box's `Tab` (spaces to the next multiple of four), and it replaces a selection. `Ctrl-z` undoes and `Ctrl-y` redoes in Insert mode (the unit is an Insert session, as for `u`); a redo only applies while the text is as the undo left it. The mouse: a click places the cursor, a drag selects, a double-click selects the word, the wheel moves the cursor 3 lines ([mouse table](ux-mouse.md)). Normal-mode `w`/`b` stay vim-like (whitespace separated). Not checked yet: a plain terminal session and Windows Terminal (follow-up issue). `Alt-Backspace` (Esc then 0x7f) is not delivered to the key handler at all under tmux (checked with a smoke run), so use `Ctrl-w` or `Ctrl-Backspace` there; terminals that send Ctrl-arrows as Alt-arrows are covered by the Alt rows. Windows Terminal (checked by the owner on a fresh build, #1168): every word and text key above works; the same sequences sent through a Windows pseudo-console to the real binary also work, except `Alt-Backspace`, which is not delivered there either. The cursor never splits a wide character, emoji sequence or combining mark. Lines are not wrapped on screen: the cursor's line scrolls sideways.
2. **Draft.** The message, SignOff and No-Verify (not Amend) are kept per tab until a commit succeeds, and saved in the session file (debounced after each edit and on exit) so they survive restarts.
   Quitting never loses a message: `q` quits at once; only when the final save fails while a message is unsent does the first `q` warn and the next one leave.
   Locating a missing tab moves its draft to the replacing tab (when that tab holds a message of its own, both stay and a notice says so).
   Closing a tab with an unsent message needs a second `Ctrl-w c` (workflow 0).
3. **Options.** `Alt-s` (SignOff, `-s`), `Alt-n` (No-Verify, `--no-verify`) and `Alt-a` (Amend) toggle from anywhere in the view including Insert mode, or by clicking the checkboxes. All start off; hooks run unless No-Verify is on.
4. **Commit.** `Ctrl-g` in Insert mode, `<space>c` in the box's Normal mode, or the `Commit` button.
   There is no `Alt-Enter` (Windows Terminal turns it into fullscreen); the other options fall back to the checkboxes and the palette. `Alt-s`/`-n`/`-a` arrive as Alt plus the letter (verified in tmux on Linux with Terminal.Gui 2.5.0; Windows and macOS terminals are not verified).
   - The message goes to `git commit -F -` on stdin, so comment lines (`#`) are kept, unlike a commit through `$EDITOR`.
     Hooks, signing and the author come from the user's git config.
     The commit runs off the UI thread with a 10 minute timeout so hooks can run; the box is read-only meanwhile, and `Esc` cancels it (git is killed, the draft stays; the notice says to check the history, because git may have finished first).
   - `<space>ec` (also in the lists and the diff) commits through `$EDITOR` instead: the TUI suspends and git's own `commit` runs on the staged index. The draft is kept; git uses its own template.
   - **Nothing staged.** With nothing staged but unstaged or untracked changes present (Amend off, no merge, cherry-pick or revert in progress), the commit action opens a Confirm, `Nothing is staged. Stage all changes and commit?`.
     `y` stages everything as `<space>A` does (untracked included, conflicted skipped), waits for the status re-read and commits; `n`/`Esc` leaves the draft and the index untouched.
     The message and options are fixed when `y` is pressed.
5. **Refusals,** without running git, with the reason in the status bar and focus kept in the box: an empty message, and nothing staged with Amend off and nothing to stage ("Nothing staged").
   An amend with nothing staged is allowed and rewrites only the message.
   While a merge, cherry-pick or revert is in progress (`MERGE_HEAD`, `CHERRY_PICK_HEAD`, `REVERT_HEAD`) the nothing-staged check is skipped, because finishing such an operation with an empty tree is valid; the operations themselves are built (workflows 3 and 4).
   Amend is refused when there is no commit yet and during a merge.
6. **Amend.** Toggling it on fills the box with HEAD's message when the draft is empty (the draft is kept aside and restored when Amend is toggled off), shows `Amending <short hash> <subject>` in the box title and runs `git commit --amend`; staged changes are added to the amended commit.
   If HEAD is already on the upstream branch, the status bar warns that a force push will be needed.
   Undo path: the status message after the commit says "Amended to abc1234 (was 9f8e7d6)"; the message history (`<space>m`) holds `git reset --soft <full old hash>` under that entry and the reflog keeps the old commit reachable.
7. **Finishing a merge.** The box starts with git's `MERGE_MSG` (comment lines dropped); untouched, it does not count as an unsent message.
8. **After a commit.** The draft and Amend are cleared, SignOff and No-Verify keep their state, the lists refresh, the status bar says `Committed abc1234` and focus returns to the lists. The history view picks up the commit through the normal refresh.
9. **Failure.** A failing hook (non-zero exit), a prompt, or a signing program that needs a passphrase fails the commit, keeps the draft and the staged state, and shows git's and the hooks' output (stderr, then stdout such as `nothing to commit`) in a scrollable overlay (title `Commit failed`, `Esc` closes it; the status bar carries the first line).
   Under the output a hint says that no keyboard input reaches git and its hooks (stdin is closed) and that `<space>ec` runs `git commit` in the real terminal where it can prompt.
   Files a hook rewrites show as new unstaged changes after the refresh.
   A commit that fails on a tab that is not active leaves the status bar notice and keeps its output; the overlay opens once that tab is shown.

**Key labels and ligatures.** Key labels in help, the palette, context menus, which-key and the status bar get a thin space (U+2009) between a `>` and a following `=`, `-` or `>`, so ligature fonts do not draw `<space>=` as `>=`; the config file and the Settings key reference keep the plain text.

**Key rule.** Standard vim/neovim keys keep their vim meaning (`j` `k` `h` `l` `gg` `G` `/` `n` `N` `v` `y` `i` `Ctrl-d` `Ctrl-u` ...): `h` `j` `k` `l` move inside a pane and never between panes, which is `Ctrl-h` `Ctrl-j` `Ctrl-k` `Ctrl-l` (#834; supersedes the `h` `l` navigation exception of #338 and the `l`/`h` focus moves of #198).
The modal screens that replace the panes (reflog, rebase todo, conflict editor, settings, help) are not panes: there `h` still closes or steps back.
A Gitunia-specific action never takes a bare vim command (`s` substitute, `u` undo, `c` change, `a` append, `x` delete, `r` replace, `D` `M` `E` motions and so on) but a leader chord (`<space>` then a key) or a `Ctrl-`/`Alt-` combination.
Check this before adding a binding.
In an Insert-mode picker or prompt printable keys are text (they filter or are typed), so pickers move with `Up`/`Down`/`Tab` or `Ctrl-j`/`Ctrl-k`, the same in all of them (the delete-branch list has no field and also takes `j`/`k`/`h`/`l`).
- **Leader keys in use:** `<space>o` + `o` `c` `n` `p` `l` `r` `d` (repositories and tabs, refresh, detail retry), `<space>x` `m` `s` `z` `*` `<Tab>` (global); `<space>a` `A` `u` `U` `d` `c` (Changes view; `<space>c` is a single key in each of the lists, the diff and the box, each its own view); `<space>e` + `d` `m` `c` (external tools), `<space>g` + `c` `a` `s` `r` (operation in progress; `r` opens the conflict editor from any pane), `<space>b` (branches: `m` merge, `p` pick, `br` rebase, `x` reset), `<space>t` (tags), `<space>r` (remotes), `<space>k` (stash), `<space>w` (worktrees); `<space>,` (settings, #523); `<space>h` (jump to HEAD) and `<space>J` (find a ref) in the graph; `<space>f` `p` `P` (fetch, pull, push, #918); `<space>v` + `w` `i` `f` `s` `l` (diff view options) and `p` (merge parent); `<space>j` (quick jump); `<space>1`..`<space>4` (Changes view pane jumps).
- **`Alt-`:** `Alt-p` and `Alt-d` are Picker-only, `Alt-1`..`Alt-9` jump tabs, `Alt-s` `Alt-n` `Alt-a` act only in the Changes view.
- **Documented exceptions:** a few bare keys keep a non-vim meaning on purpose, because the panes are read-only or the key is navigation: `q` (quit; vim records a macro), `]` `[` (navigation), `?` (help; vim searches backwards, same as `less`), `Y` (copy the file's rows; close to vim's yank line), `+` `-` (diff context), `J` `K` `D` `U` in the Changes, Files and Changes view lists (scroll the diff or content beside them by a line or half a page, #755) and `gd` `gc` `gf` (bottom-pane tabs, paired with the `]`/`[` cycling).
  The conflict editor (#689, #742) binds bare `n` `N` `o` `t` `b` `m` `O` `T` `e` `u` for the same reason: it is a modal like the rebase todo editor (its search keys are the conflict jumps), and its result pane is the commit box's Normal mode on the whole file.
  The settings screen (#523) is a modal list, not a buffer, so its view keys `x` `a` `d` `J` `K` `+` `-` are bare on purpose (owner to confirm, asked in the PR of #523).

**Mouse.** Same action path as keys. A click on a file row selects it and a double-click stages or unstages it (a deliberate deviation from "double-click opens": the diff already follows the selection). The diff's title row gets `stage`/`unstage` and `discard` buttons next to the hunk buttons, the list titles `stage all`/`unstage all`; the checkboxes toggle and `Commit` commits; a drag over diff rows or file rows starts a Visual range; a click on the tab's dirty marker opens the view. Narrow screens use the `diff ›` chip of the list's title row. Details: [Mouse table](ux-mouse.md).

### 3. Branches, tags, merge, cherry-pick, reset and the reflog (M3)

Planned keys, written here and not yet in the [keymap](../keymap.md): each implementing issue adds its rows to `keymap.default.json` with its bindings.
`<space>t` is the tools prefix (`td` `tm` `te`), so these use other prefixes: `<space>b` branches, `<space>g` operations on the selected commit, `<space>T` tags, `<space>w` worktrees, `<space>S` stashes.
Every action is also a palette entry and has a mouse path (a button in the sidebar section header, or a click on the row and then the same key).

**Common rules.**
- **Target.** The graph acts on the selected commit, the sidebar on the selected row. The status bar names the target while a prompt is open.
- **Prompts.** A name is typed in a prompt popup (see Prompt popups in the Modes section; Insert mode: `Enter` runs, `Esc` cancels), prefilled where a default exists. A choice of a branch or ref uses the fuzzy picker of `<space>J`.
- **Confirm.** Every destructive step (delete, force, hard reset, drop, remove, discard) opens the Confirm dialog of the Modes section.
  It names the exact target, says what is lost and says in one plain line how to get it back (see "Undo hints" below); `y` runs it, `n` or `Esc` drops it.
- **Undo hints** (#1194). Dialogs and the status line use plain words and the short hash, never a git command or a full hash. Where an undo exists, the Confirm has one plain line: either "Afterwards the message history (`<space>m`) shows how to bring it back" (branch, tag, remote branch and remote deletes, remote removal, stash drop, force push) or, for moves of HEAD (reset, rebase, merge), that the reflog (`<space>l`) can go back. The status message after the action is short (`Deleted branch X (was dde61a9)`) and carries the exact restore command and the full hash as its `Detail`, which the message history (`<space>m`) shows under the entry. Where no undo exists the dialog says so, as for discard and re-create. A message that names a key keeps naming it whatever the command level ([ux-keymap.md](ux-keymap.md), "Messages keep their keys"); the keys in these lines are the defaults.
- **Refusals** run no git and say why in the status bar: a branch checked out in another worktree, a dirty tree where git would refuse, a detached HEAD where a branch is needed.
- **No editor, no prompts.** Every call that could open an editor passes `--no-edit` or `-c core.editor=true`; stdin is closed, so a hook that prompts fails with git's output shown in an overlay like a failed commit. Messages are edited in the commit box or with `<space>ec`.
- **Result.** Success posts a status message with the new state; a failure shows git's message.
  An operation that stops on conflicts is not a failure: it becomes an in-progress operation (workflow 4).
  All lists refresh from the tab's status afterwards and the cursor follows the new HEAD or the created ref.

**Branches** (`<space>b` + key; implemented in #35 and #36):
1. `bc` create: prompt for the name, start point the selected commit (graph) or branch (sidebar); the new branch is checked out. `bC` creates without checking out. A name in use is refused before git runs; an invalid name is refused by `git check-ref-format` and shown as an error.
2. `bs` switch (checkout), context based (#571): the branch under the cursor is checked out at once, no prompt.
   A sidebar local branch row checks that branch out; a remote branch row creates the tracking branch and checks it out (a remote branch that has a local twin checks the twin out).
   In the graph, a commit with exactly one branch label (a local branch, or a remote branch without a local twin) checks that branch out; with several labels a filter picker (candidates listed, `Ctrl-j`/`Ctrl-k`/`Up`/`Down`/`Tab` choose, `Enter` runs the highlighted one, remote branches shown as `origin/foo -> local foo`) lists only those plus a detached checkout of the commit; with none, or on any other row (tag, stash), the prompt lists all local branches, remote branches that have no local twin and, from a graph commit, a detached checkout there.
   In the sidebar `Enter` still only selects.
   The current branch and one held by another worktree are refused with no prompt (the message names the worktree path).
   A dirty tree that conflicts with the target fails with git's message; nothing is stashed behind the user's back.
3. `br` rename the selected branch (prompt prefilled with its name).
   `bd` delete (on a folder row or a graph commit with several local branches a list opens first: `j`/`k`/`h`/`l` or the arrows move, `Enter` picks, `Esc` cancels; #727): Confirm naming the branch and its short tip hash; when the branch has commits that neither HEAD nor its upstream reach, a second, explicit Confirm says its commits become unreachable. The restore command (`git branch <name> <hash>`) is in the message history after the delete.
   The current branch and one held by another worktree are refused.
   On a section header or a Remotes or Tags folder row they refuse with "Select a local branch first" and never act on the graph branch (#729); create from them still starts at the graph commit.
   From the graph, `br` and `bd` act on the one local branch at the selected commit (several: `br` asks to pick one in the sidebar, `bd` opens the list).
4. `bu` set the upstream of the selected local branch (type-to-filter picker of remote branches, nothing is fetched), `bU` unset it (the status line prints the `git branch --set-upstream-to=` command that restores it).
   Ahead/behind (`↑n↓m`) already shows in the sidebar and the tab bar; it is not new work.
   `bf` (#572) fast-forwards the selected local branch (sidebar row, or the local branch at the graph commit) to its upstream as last fetched, without checking it out and without a Confirm (nothing is lost): fetch first with `<space>rf`.
   Only a real fast-forward runs; the status line names the old and new short tip; the message history holds the undo (`git update-ref refs/heads/<b> <old>`).
   Refused with nothing changed: up to date, diverged (it has commits the upstream lacks), no upstream or a gone one, the branch checked out here (points to `<space>rl` pull) or in another worktree.
   Fast-forwarding to the commit under the graph cursor instead is not part of this.
5. Mouse: the actions menu of a branch row (`<space>.`, or the `...` marker of the selected sidebar row) lists create, switch, rename, delete, fast-forward and the upstream actions, and the Branches header menu offers create and create-only; there are no header chips (dropped in #469).
   After create, switch, rename or delete the graph cursor moves to the created or checked-out branch's commit (after a delete, to the commit of the current branch).
6. No single-letter sidebar shortcuts (`d`, `r`): they are vim operator and replace keys (vim-clash rule), so the sidebar uses the same `<space>b` chords on the selected row. Every action is in the command palette.

**Integrating** (`<space>g` + key, on the selected commit or branch; the target is the current branch):

The which-key popup of `<space>g` lists the everyday keys only: `m` `M` `p` `r` `i` `x` `v`.
`gs` (squash), `gf` `gw` `gd` (quick rebase) and `gI` (rebase from the root) stay bound and are in the actions menu, the palette and `?` help, but are left out of the popup.
`ga` `gc` `gk` are listed only while an operation is in progress (the banner shows them too).

1. `gm` merge the selection into the current branch.
   Fast-forward when possible; `gM` forces a merge commit (`--no-ff`), `gs` squashes (`--squash`, leaves the changes staged for the commit box; no operation is in progress afterwards).
   The message is git's default (`--no-edit`).
   It runs at once, no Confirm (nothing is lost); the status line names the old short tip; the message history holds the undo (`git reset --hard <old>`, also `ORIG_HEAD`).
   A stop on conflicts becomes the in-progress merge (banner, `<space>gc`, `<space>ga`); a conflicting squash leaves the files marked `!` but no operation and says to resolve and commit.
   A branch row merges that branch, a tag row or a graph commit that commit.
   Refused during any in-progress operation and on a detached or unborn HEAD.
2. `gr` rebase the current branch onto the selection (implemented in #39; non-interactive with `-c core.editor=true`; the interactive variant is `gi` below).
   The Confirm names both sides, says the reflog (`<space>l`) can bring the old state back (the exact `git reset --keep <old tip>` is in the message history afterwards) and warns when the branch has an upstream (history rewrite, force push needed; the text is stronger when every commit is already on it).
   Refused with no git run when an operation is in progress ("finish or abort the <operation> first"), HEAD is detached or unborn, the target is the current commit, or tracked files have uncommitted changes (untracked files are fine; not when the user's `rebase.autoStash` is on: then the Confirm adds a line saying git stashes and restores them, and the undo, `git reset --keep`, never drops local changes).
   A rebase that stops on conflicts is the in-progress rebase of workflow 4 (banner, `<space>gc`, `<space>ga`, `<space>gs`); the status line warns and names the keys.
   When the commits being replayed (the target does not have them) contain merge commits, the Confirm says so ("N merge commits in that range will be flattened"): a plain rebase drops the merge and replays its side's commits as one line; the Confirm adds that `<space>bri` keeps the merges (interactive rebase with `--rebase-merges`, #461).
   The count is one `git rev-list --merges` call, so the Confirm opens when it answers.
   Mouse: the actions menu of a graph row (`<space>.` or a double-click) or sidebar row (`<space>.` or the `...` marker).
   While the Confirm is being prepared a second `<space>brr` says "Already asking", and the Confirm is dropped with a warning if an overlay was opened or HEAD moved meanwhile.
3. `gp` cherry-pick the selection onto the current branch (implemented in #40): the commit under the graph cursor, the commits of a Visual range in the graph (applied oldest first, whatever lanes they sit on) or the tip of the selected sidebar branch or tag.
   `gv` reverts it the same way (`--no-edit`); a range is reverted newest first, git's own order.
   Both run at once, no Confirm (nothing is lost); the status line names the old short tip; the message history holds the undo (`git reset --hard <old>`, also in the reflog).
   A commit whose changes HEAD already has is dropped (`--empty=drop`), and when that is every commit the status says "Nothing to cherry-pick".
   A stop on conflicts becomes the in-progress cherry-pick or revert (banner, `<space>gc` continue, `<space>ga` abort, `<space>gs` skip the commit).
   A detached HEAD is allowed (git allows it); refused during any in-progress operation and on an unborn HEAD.
   The Visual range ends when the action starts.
   Mouse: the actions menu of a row; a Visual range is picked with `<space>bp`/`<space>bv`.
3a.
**Quick rebase** (#459; `gf` fixup, `gw` reword, `gd` drop, graph only, on the commit under the cursor; the interactive engine of #399 with a todo built by the app, no editor).
`gf` melds the commit into the one before it (that commit keeps its message and the fixed-up commit disappears), `gw` opens a prompt popup prefilled with the subject (the body of the message is kept; an empty or unchanged subject stays in the prompt with a reason), `gd` removes the commit.
A Confirm follows each: it names the commit (short hash and subject), how many later commits are replayed and get new hashes, the force-push warning for a branch with an upstream (as `gr`) and one plain undo line (the reflog key; the exact `git reset --keep <old tip>` is in the message history afterwards).
Same refusals as `gr` (operation in progress, detached or unborn HEAD, tracked changes) plus: the commit is a merge commit, it is not in the history of the current branch, it is the only commit of the branch (drop), or (fixup) it is the first commit or the one before it is a merge.
These show as the status error with git's or the engine's reason.
A stop on conflicts is the in-progress rebase of workflow 4. The Confirm is dropped, with a warning, when HEAD moved, an overlay opened or the tab changed while the plan was read.
Mouse: the actions menu of a graph row lists the three.
The todo-list editor (#458) is the full interactive route.
4. A merge commit among the commits opens a one-key prompt, once for the whole range (the overlay below; the status bar carries it only when the screen is too small for the overlay): `1`, `2` pick the mainline parent (parent hashes and subjects shown), `Esc` cancels; a small overlay lists the same parents as rows, a click on a row answers like its digit and a click outside cancels.
   The answer is passed as `-m` to every commit of the call.
   Git accepts `-m 1` on a plain commit but fails the whole call on `-m 2`, so with a plain commit in the range only `1` is accepted and the `[2]` row of the overlay is dimmed and marked unavailable.
   The overlay is placed again when the terminal is resized.
5. A dirty tree is refused for rebase; for the others git decides and its message is shown.

**Interactive rebase** (`<space>bri`, graph and sidebar; engine #399, editor #458): rebases the current branch onto the selection with a todo edited in a modal list, no external editor.
The refusals are those of `gr` (operation in progress, detached or unborn HEAD, target is the current commit, tracked changes), no commits to rebase says so.
A range with merge commits is rebased with `--rebase-merges` (#461): the list then also shows git's `label`, `reset` and `merge` lines (dim, in git's order), which keep the merges and the branches they join.
They cannot be changed: `p`, `s`, `f`, `d` and `r` ignore them, but they move like any row (`K`/`J`), so the commits of a merged branch can be reordered or reworded and the merge is recreated on top.
The footer refuses (and `Enter` is refused) an order git cannot replay: a merge or reset before the label it names, or a squash or fixup right after a reset.
Quick rebase (`gf` `gw` `gd`) of a commit below or inside a merged branch keeps the merges the same way; a conflict stops as in workflow 4 and `<space>gc` continues, `<space>ga` aborts to the original merged history.
Cousin branches (not based on the target) keep their original base, as git's default does.
The commits are read off the UI thread; the editor opens when they arrive.
`<space>brI` (#561) opens the same editor for the whole history (`--root`): the list starts at the root commit, the selection is ignored, the title and the Confirm say "onto the root", and the refusals, Start, Confirm and undo are the same.
The graph actions menu of the root commit (no parents) lists it as "Interactive rebase of the whole history" after "Interactive rebase"; other rows do not.
Any parentless commit shows it (orphan branches, shallow boundaries), but the action always rewrites the current branch from its own root and ignores the selection.
- **The list** shows the commits in replay order, the first row replayed first (git's own todo order, the reverse of the graph), each as `action hash subject`; dropped rows are dim.
  Every row starts as `pick`.
  `j`/`k`/`gg`/`G`/`Ctrl-d`/`Ctrl-u` move; `p` pick, `s` squash, `f` fixup, `d` drop set the action of the highlighted commit; `K`/`J` (or `Alt-k`/`Alt-j`, with a count) move it up or down.
  Squash and fixup meld into the row above, so the first kept commit cannot be one: the footer says so and `Enter` is refused until it is fixed.
  The single letters are git's todo words and keys of this modal list, like the settings screen's, not buffer commands (vim-clash rule).
- **Reword** (`r`) opens the message editor in the same box with the commit's full message (read from git, not only the subject), the multi-line editor of the commit box (workflow 2): `Enter` new line, `Ctrl-g` keeps the message and makes the commit a `reword` (the row then shows the new subject), `Esc` cancels the edit.
  A blank message is refused.
  Choosing `p`, `s`, `f` or `d` afterwards keeps the text, so `r` brings it back.
- **Start** (`Enter`): a Confirm names the branch, the target, how many commits are kept, reworded, squashed, fixed up and dropped, lists the dropped commits (hash and subject, five at most), warns about a branch with an upstream (history rewrite, force push needed) and has one plain undo line (the reflog key; the exact `git reset --keep <old tip>` is in the message history afterwards).
  The Confirm opens over the editor, so `n` keeps the todo.
  On `y` the editor closes and the rebase runs in the background under the tab's operation gate; the state is checked again first (tab, HEAD and refusals), because it can change while the todo is open.
  A stop on conflicts is the in-progress rebase of workflow 4 (banner, `<space>gc`, `<space>ga`, `<space>gs`).
  If git refuses before anything ran (the range changed, `GIT_SEQUENCE_EDITOR` is set), the status says why and the todo comes back.
- **Closing.** `Esc`, `h` or `q` closes; with an edited todo the first press says "Esc again discards the changes to the todo" and the next closes. Nothing was changed in the repository until `y`.
- **Mouse.** The wheel scrolls, a click highlights a commit, and chips under the list (`p pick  r reword  s squash  f fixup  d drop  K move up  J move down  Enter start  Esc cancel`, drawn as key hints like the conflict editor's, flowing onto more rows on a narrow terminal so none is cut off) run the same actions.
  The actions menu of a graph or sidebar row lists "Interactive rebase" next to "Rebase".
  When the box does not fit (under about 9 rows, fewer with a wide terminal) it is not drawn and the keys still answer, blind.

**Reset** (`<space>bx`, not a single letter, so it cannot clash with vim motions or `g` chords): the current branch moves to the selected commit.
A small dialog offers `s` soft (keeps index and files), `m` mixed (keeps files, clears the index), `h` hard.
Soft runs at once and shows the old tip in the status ("Reset to abc1234, was def5678").
Mixed runs at once when the index equals HEAD; otherwise it opens a Confirm saying the staged state (including partially staged hunks) is dropped and cannot be recovered from the reflog.
Hard opens a Confirm that lists the tracked files and the count of changes that will be lost (untracked files stay unless the target commit tracks a file at the same path, and it says so) and says the commits can be brought back from the reflog (`<space>l`), never uncommitted changes.
Refused during an in-progress operation and on a detached or unborn HEAD.
The status after a reset names the old short tip; the message history holds the undo (`reset [--hard] <old hash>`, also `ORIG_HEAD` and the reflog).
Implemented in #392 (`ResetActions.Begin(tab, commit)`, now a thin view class over `ResetRequested`, is the entry the reflog view calls).
The reflog view offers the same key on an entry.
Mouse: the actions menu of a graph or sidebar row.

**Tags** (`<space>T` + key; implemented in #397): `Tc` create at the selected commit, or the commit of the selected sidebar row: a name prompt, then a message prompt (empty makes a lightweight tag, text an annotated one, so no editor is needed; the call also passes `-c core.editor=true`).
A name in use is refused before git runs, an invalid one by `git check-ref-format`.
`Td` delete the local tag: Confirm with the tag's short hash and one plain undo line; the message history holds `git tag <name> <hash>` afterwards (for an annotated tag the hash is the tag object, so the message survives); a copy on a remote is not touched.
`Tp` push the selected tag to a remote: a type-to-filter remote prompt, then one ref (`git push --no-progress <remote> refs/tags/<name>`), no progress, no prompts, git's first error line shown; the push of workflow 5 generalises it.
`TD` deletes the tag on a remote (`git push <remote> --delete refs/tags/<name>`): remote prompt, then a Confirm naming the remote and the tag and saying the local tag stays; no undo besides re-pushing the tag.
From the graph the tag actions act on the one tag at the selected commit (several: pick one in the sidebar).
Mouse: the actions menu of a sidebar or graph row (#428, #471) lists all tag and merge actions; they act on the selected row.
No sidebar `d` shortcut: it is a vim operator (vim-clash rule), so the sidebar uses the same `<space>T` chords on the selected row.

**Reflog** (`<space>l`, graph and sidebar; implemented in #398): a modal list of the reflog of `HEAD`, or, from a local branch row under the sidebar cursor, of that branch (`refs/heads/<name>`).
Newest first (the last 1000 entries): short hash, `HEAD@{n}`, action and message, relative time.
`j`/`k`/`gg`/`G`/`Ctrl-d`/`Ctrl-u` move; `Enter` selects the entry's commit in the graph and keeps the list open (a commit outside the loaded graph says so in the status bar); `<space>bx` resets the current branch to the entry (the reset rules above, via `ResetActions.Begin`); `<space>bc` opens the new-branch prompt at the entry; `<space>bs` checks the entry out with a detached HEAD (git refuses a conflicting dirty tree, nothing is stashed).
The last three close the list first, because their prompt popup and Confirm are overlays of their own.
`Esc` or `h` returns.
The list is read from git on open and on `<space>or`.
`<space>l` inside the list opens the ref picker (implemented in #424): `HEAD` and the local branches, type to filter, `Tab`/`Down`/`Up` move, `Enter` opens that reflog, `Esc` returns to the list.
`/` searches the entries (hash, `HEAD@{n}`, action and message, case-insensitive): the box and the match count (`/fix_  2/5 matches`) are in the list's footer, `Enter` keeps the search and leaves the box, `n`/`N` step through the matches (counts work, wraps), `Esc` in the box cancels and `Esc` in the list clears the search before it closes the list.
Mouse: below the entries four action rows (`Enter` select, `<space>bx` reset, `<space>bc` branch, `<space>bs` checkout) run on the highlighted entry when clicked, so a click on an entry then a click on an action replaces the keys; in the picker a click on a row opens that reflog.
The graph `<space>l` still opens HEAD's reflog directly; the picker is one key away.

**File history** (`<space>H`, #1115): a modal screen with the commits that touched one file (`git log --follow`, renames followed) on the left and that commit's diff of the file on the right.
It opens from the file under the cursor of the detail pane (Changes tab or Files tab, a folder row is no file; the history starts at the shown commit) and from either file list of the Changes view (it starts at `HEAD`); anywhere else, or on a folder or heading row, the status says "Select a file to see its history".
Newest first (the last 1000 commits): short hash, date and subject; the diff shows the file in the highlighted commit only (against the first parent for a merge, with both names of a rename so git pairs them, at most 5000 lines).
A commit before a rename is listed under the name the file had then.
`git log --follow` omits merge commits, so a merge appears only through the commits of its branches.
`j`/`k`/`gg`/`G`/`Ctrl-d`/`Ctrl-u` move the highlight (the diff follows; a newer read cancels the one still running), `J`/`K`/`D`/`U` scroll the diff, `Enter` selects the commit in the graph and closes the screen (a commit outside the loaded graph says so in the status bar and the screen stays), `<space>or` reads the list again keeping the highlight on the same commit, `Esc`, `h` or `q` return to where the screen came from.
A file with no commits (untracked, never committed) opens an empty screen that says so.
Mouse: a click on a commit row highlights it, the wheel moves the highlight, the action row `Enter` below the list selects the commit in the graph; opening is the palette entry (the `: commands` button in the tab row lists it) or the key, like the other file actions (a row menu for the file lists is #1132).
Limits: the list is read in one go (up to 1000 commits), not streamed; a staged rename in the Changes view opens at `HEAD` under its new name, so it shows no history until the rename is committed; a path that is not valid UTF-8 cannot be matched; in a repository with no commit yet the screen is empty.
**Line history** (`<space>L`, #1116): the file history screen for a range of lines (`git log -L<start>,<end>:<path>`): the commits that changed those lines on the left, each commit's patch limited to the range on the right (title `Line history: <path>:<start>-<end>`).
It opens from a diff: the Visual range of the commit diff pane (`v`, move, `<space>L`; without a range the cursor line) or of the Changes view diff box. The commit diff numbers lines as the commit has the file (added and unchanged rows count, removed rows do not: a selection of only removed rows says "Removed lines are not in the file any more"); the Changes view numbers them as `HEAD` has them (unchanged and removed rows count). Added (uncommitted) rows have no history: a selection of only those says "Uncommitted lines have no history yet", a mixed one follows the committed lines and says how many were left out. The Visual range ends when the screen opens.
Not available (the status bar says why): the diff of a folder, an untracked or conflicted file, an unstaged diff of a file that also has staged changes (its old side is the index, not `HEAD`; use its Staged diff), a file content view of the Files tab, a range beyond the file ("file X has only N lines", git's own message) and a path missing at the starting commit. A selection that reaches into a second file follows the first file only and says so.
Lines that shift position (inserted or removed above them) and renames are followed by git; a block cut and pasted elsewhere is not traced and shows as added by the commit that moved it; a range that no commit changed shows "No commit changed these lines". `git log -L` lists merges only through their branches. A line that contains the byte 0x1E (record separator) cuts its commit's patch short (a warning is dropped); not handled. Keys, mouse and the graph jump are those of the file history. Not done: opening it from the blame view (registered as #1139) and from the file content view.
**Blame** (`<space>gb`; #1117): a full-screen view of one file with a gutter per line: short hash (`^` before a boundary commit), author, age (`3d ago`), line number, then the line.
`<space>gb` acts on the file row under the cursor of the details pane (Changes or Files tab: the file is read at the commit shown in the graph; a file the commit deletes, a folder or a heading is refused with a status message) and on the file under the cursor of the Changes view's Unstaged or Staged list (the working tree file; uncommitted lines show `uncommitted`).
The lines appear at once and the gutter fills in while the blame runs (`blaming 40%` in the footer); `j`/`k`/`gg`/`G`/`Ctrl-d`/`Ctrl-u` and a counted motion move, the wheel scrolls, a click highlights a line.
`Enter` (or the action row under the lines) selects the highlighted line's commit in the graph, which also shows it in the details, and closes the view; a line not blamed yet or an uncommitted line says so and the view stays.
`/` searches the lines, the authors and the subjects (case-insensitive; `Enter` runs it and moves to the first match from the cursor line (included), `n`/`N` step with counts and wrap around, `Esc` in the box cancels and `Esc` in the view clears the search before it closes the view).
`Alt-p` (or its action row) blames the file again at the parent of the highlighted line's commit (`<id>^`), using the path git reports for the parent (`previous`), so a rename in that commit is followed; the cursor goes to the line's number in that commit (approximate: lines added or removed above it in that commit shift it) and the title reads `path @ 1234567^`. The blames stack: `Esc` or `h` steps back to the previous one (cursor restored, footer hint `Esc back`) and closes the view only from the first. A line not blamed yet, an uncommitted line and a line of the first commit of the history (no parent) say so and nothing changes; when the file cannot be shown at the parent (it is created in that commit under another path), the view returns to the previous blame and says why.
`<space>H` (or its action row) closes the view and opens the file history (#1130) of the blamed path at the blamed revision (`HEAD` for the working tree file; after `Alt-p` it is `<id>^` and the path git reports there); the whole file, no line range. It does nothing while the search box is open.
`<space>L` (or its action row, #1139) does the same for the highlighted line: the line history starts at the commit that owns the line, with that commit's own path and line number (`BlameChunk.OriginalFirstLine`), so it also works in working-tree blame for committed lines; an uncommitted line says it has no history and the view stays. With a Visual range in the blame view (below) it takes the selected lines: when they all come from one commit and follow each other in it, the walk starts at that commit with that line range; lines of several commits are numbered by the file as shown, which only a blame at a commit (opened from a commit, or after `Alt-p`) fixes, so there the history of the whole range opens at the blamed revision, while in the working tree file it says the lines come from several commits and the view stays (#1175).
Selecting (#1175): `v` starts a Visual range of whole lines at the highlighted line (the key mode is Visual and the footer reads `VISUAL 3 lines`), `j`/`k`/`gg`/`G`/`Ctrl-d`/`Ctrl-u` move its end, `y` copies the lines' code text (no gutter, joined with line feeds) and ends it, `Esc`, `q` or `v` end it without copying, a click on a line ends it. `Alt-v` selects characters of the code column instead (`h` `l` `w` `b` `0` `$` move the end inside the line, `iw` and `il` select the word and the text of the line; `v` turns it into whole lines); `y` copies exactly those characters. The mouse: a drag from the code column selects characters, a drag from the gutter whole lines (the end follows the pointer, also above or below the shown lines, but the view does not scroll by itself), a double-click on the code selects the word and a triple-click the text of the line. Tabs in the code are drawn to tab stops of 4 columns, as in the diff. The selection ends when the view reads the file again (`Alt-p`, a toggle, `Esc` back) or closes. The other read-only text overlays (file history, reflog, status history) keep no selection: they show commit rows and messages, not file text, so the clipboard path of those rows stays the copy actions they have (decision in #1175).
`Alt-w`, `Alt-m` and `Alt-c` toggle git blame's `-w` (ignore whitespace), `-M` (lines moved inside the file) and `-C` (lines copied from other files); each runs the blame again, keeps the cursor and the back stack, and the switches in force show in the footer (`1/3  -w -M`). Git itself honors `blame.ignoreRevsFile` from the user's config (lines of the listed commits go to the commit before them); the footer says `ignore-revs` when it is set. Each toggle also has a clickable `-w`, `-M` or `-C` chip in a row under the action rows.
`Esc` or `h` closes. A binary file, a file missing from the working tree or a failure close the view with a status message; bytes that are not UTF-8 show as Latin-1, CRLF endings are not shown. Renamed files are followed.

### 4. In-progress operations: banner, continue, abort, skip (M3; banner, continue, abort and skip done, the blocking of item 5 comes with each blocked feature)

One flow serves merge, rebase, cherry-pick and revert, and the interactive rebase (#399, editor #458) reuses it. `RepositoryOperationDetector` names the operation from the git directory.

1. **Banner.** While an operation is in progress the tab shows a banner on the frame's bottom edge (the line under the panes, in the status bar's colours;
   the title is a warning-coloured chip starting at column 0 like the `NORMAL` badge): `MERGING feature/x  3 conflicts  <space>gc continue  <space>ga abort  <space>gr open conflict editor` (while conflicts remain the line ends with the key that opens the conflict editor from any pane (item 2a, #742); where the chips leave no room for that, a short form `<space>gr conflict editor` is tried, and where the chips do not fit beside the step and conflict counts the counts go first. The line is never relied on alone: while a conflict remains, the status bar's own hints carry `<space>gr conflict editor` right after help, commands and quit in every pane (in the Unstaged list, while the cursor is on a conflicted file, `Enter conflict editor` leads instead), and the which-key popup docks above the banner instead of covering it;
   a rebase adds `step 2/5` and `<space>gs skip`;
   a cherry-pick or revert of a range shows how many commits are left, `3 commits left`).
   The title names the merged branch (read from git's default merge message, so a custom message gives just `MERGING`), the rebased branch, or the short hash of the picked or reverted commit.
   Each key group is also a clickable chip (mouse views `BannerButton.*`).
   `<space>gc`, `<space>ga` and `<space>gs` work in the graph, the sidebar and the Changes view (where conflicts are resolved).
   On a terminal under 10 rows the banner is dropped and an empty status message shows the same text.
   It is read from the repository's state files (`MERGE_MSG`, `rebase-merge/`, `sequencer/`), so it survives a restart of the app, and the tab bar shows a `!` marker.
2. **Conflicts.** The Changes view lists conflicted files with `!`. `<space>a` marks one resolved (workflow 2, item 4); `<space>em` (from any pane) opens the configured mergetool; `Enter` on a conflicted file opens the conflict editor (next item); `<space>gr` opens it from any pane.
2a.
**Conflict editor** (#689, redesigned in #742 after KDiff3; `Enter` on a `!` row of the Unstaged list, or `<space>gr` from any pane while a file is conflicted: the file under the Unstaged cursor if it is conflicted, else the first conflicted file, so the editor opens from the graph, the sidebar, the diff and the Staged list too, in a rebase, cherry-pick or revert as in a merge; with no conflicted file the status bar says so).
A full-screen view of the whole file: the frame fills the terminal edge to edge except the status bar, which keeps the key hints of the pane the cursor is in. The tab row and the operation banner are covered; the top border carries the file and the position instead (`Conflict: src/a.cs  conflict 2 of 5  3 resolved  2 unresolved  taken from ours`: the position strip ends with the state of the current conflict, which a narrow terminal cuts first, in the error colour `Esc again discards your changes` while that question is open).
```
╭─ Conflict: a.cs  conflict 2 of 5  3 resolved  2 unresolved  taken from o… ╮
│ base  common ancestor │ ours  HEAD          │ theirs  feature             │
│  12 context           │   12 context        │   12 context                │   <- three versions side by side
│ │· 13 old text        │ │✓ 13 our text      │ │· 13 their text            │   <- ✓ = the version taken, · = not
├───────────────────────┴─────────────────────┴─────────────────────────────┤
│ result  line 13 of 340  NORMAL  i types                                   │
│     12 context                                                            │   <- the whole result, an editor
│ │✓ 13 our text                                                            │
│ n next  N previous  <space>a take  <space>u untake  o ours  t theirs  Ctrl-s save │   <- clickable hints
╰───────────────────────────────────────────────────────────────────────────╯
```
- **Panes.** Base, ours and theirs (the labels git wrote after the markers, `HEAD` and the branch) are the whole file in three versions, read-only, side by side on top; the result is the whole file full width below, with a rule between. Rows of the three versions are aligned: common text is the same row in all of them, a conflict takes as many rows as its longest version and the shorter versions are padded with blank filler rows, so the panes scroll together and related lines stay side by side. When the cursor is in one pane the others scroll to the lines beside it (the result follows by the conflict regions: inside a conflict by offset, in common text by the offset after the region before it). Every pane has line numbers of its own file (the result's are the lines of the file as it will be saved); words that differ are marked as in the diff (ours and theirs against the base when the conflict has one, else against each other; the base shows the words either side changed), and a conflict without a base says how to get one (`diff3`, then `R`; an add/add file has an empty base).
- **Marks.** The two columns at the left of every pane row belong to the conflicts: a bar on the rows of the current conflict (with the quiet group tint behind them, as the diff's current change group) and the state of the conflict: `?` (error colour) while it is unresolved; once settled, in a version pane a check mark (`v` in the ASCII set; added colour) on the version the result took (both ours and theirs for "both") and a dot (`.`) on the others, `~` on all three when the result holds picked lines or typed text, and in the result a check mark. That is the only place the state sits: the pane headers carry no marker, they only say which pane has the cursor, and the position strip (top border) spells the state of the current conflict out (`unresolved, still holds its markers`, `taken from ours`, `taken from theirs`, `taken from the base`, `both sides, ours first`, `lines you picked`, `edited by you`). In the result an unresolved conflict still shows its markers in the error colour, a settled one its lines in the added colour, so a half-resolved file reads at a glance. The cursor row is tinted in every pane (stronger in the active one, whose header is the highlighted chip), and a Visual selection has the range tint.
- **Terminal sizes.** From 100 columns the three versions are drawn; from 66 two (ours and theirs, or base and ours when the cursor is in the base); below that one. `Tab` / `Shift-Tab` (and `Ctrl-h` / `Ctrl-l`) move through the panes and so change which versions are shown; the result is always full width. The top panes take about 45% of the rows, the result the rest; the hint chips take one to three rows by height. Under 40 columns or 11 rows nothing is drawn and the keys still work.
- **One focus.** The pane with the cursor is the focus, shown by its highlighted header chip and the stronger cursor tint; nothing else competes with it (no `[taken]` on a header).
- **Mouse.** A click on a pane header, a row of a version pane or a line of the result moves the cursor there and makes that pane the active one (a Visual selection ends; the result is in Normal mode with the cursor at the clicked column, or at the line end past the text; while typing, a click on a result line only moves the typing cursor there and a click on a header or a version row does nothing, `Esc` first). Like a click in the staging diff it only selects: a double-click on a row that lies in a conflict also takes that pane's version for the conflict (`<space>a` on a click-selected row; a base pane without a base says so as the key does), and on common text it only moves the cursor. The wheel scrolls the pane under it and every chip runs its key's action. A drag from a row of a version pane starts a Visual selection there like `v` and the far end follows the pointer (a pointer above or below the panes sticks to the first or last row shown); `<space>a` or the `take lines` chip then takes only those lines. A drag from a header, the result or while typing selects nothing. Clicks on the borders, the dividers and the rules do nothing.
- **Long lines.** Text wider than a version pane is cut at the right edge. `zh` / `zl` (vim's meaning; a count multiplies the 8-column step; in Normal and Visual mode), Shift or Ctrl with the wheel, or the `zh scroll left` / `zl scroll right` chips scroll the base, ours and theirs text sideways together, up to the widest line; the margin, the line numbers and the cursor row tint stay, the word marks move with the text, a wide character cut by the edge leaves a blank column, and the headers show `col N` while scrolled (#862). The scroll stays when the cursor jumps to another conflict (lines shorter than it show blank panes until `zh`). The result pane scrolls its cursor line on its own.
- **Moving.** `j` / `k` (and the arrows, the wheel, a count), `gg` / `G` and `Ctrl-d` / `Ctrl-u` move the cursor in the active pane; `n` / `N` (or `]c` / `[c`) jump to the next or previous conflict, wrapping. `Ctrl-h` / `Ctrl-l` move between the version panes, `Ctrl-j` goes down into the result and `Ctrl-k` back up to the version pane it came from; `Tab` cycles base, ours, theirs, result. The current conflict is the one the cursor is in or last was in; the picks act on it.
- **Picking, like staging in the diff.** In a version pane `<space>a` takes that pane's version for the current conflict (ours, theirs or the base); `o`, `t`, `b` take ours, theirs or the base (in a version pane; the chips do it from any pane), `m` both (ours first), `O` / `T` ours / theirs for every conflict still unresolved. `v` starts a Visual selection of lines in the pane (j/k extend, `Esc` or `v` ends it), `<space>a` then takes only the selected lines that belong to the current conflict: they replace the conflict's markers, or are appended after the lines it already has, so ours and theirs can be mixed line by line (undo takes the last step back). The result changes at once, the settled conflict shows its mark. `<space>u` is the inverse, **untake**: the current conflict is unresolved again (its markers come back, picked lines and typed text go; one `u` brings them back), and with a Visual selection in a version pane only the selected lines leave the result (each from its last matching line; none left: the markers come back; none found: the status bar says so). Both keys are in the hint chips and the status bar (`<space>a take pane` / `<space>u untake`; `take lines` / `untake lines` in Visual); an unresolved conflict answers "nothing to untake". The old `r` is gone. A pick on a base that does not exist is refused with the reason in the status bar.
- **The result is an editor.** `Ctrl-j` (or `Tab`) moves into the result; there the commit box's Normal mode keys work (`h` `l` `w` `b` `0` `$`, `j` `k`, `x`, `dd`, `o`, and `i` `a` `A` `I` to type; Insert mode: text, `Enter`, `Backspace`, `Esc` or `Ctrl-g` to stop, `Ctrl-s` to stop and save; `Tab` inserts a tab character); `e` in a version pane ("edit in result") moves into the result at the first line of the current conflict and starts typing there in Insert mode, with the result header saying `INSERT  typing in the result, Esc keeps the text` and the status bar `Typing in the result at conflict 2: Esc or Ctrl-g keeps the text`; on an unresolved conflict that line is its `<<<<<<<` marker, so take a side first or delete the marker lines. The editor holds the whole file, so text outside conflicts can be edited too.
  - **How typing and picks interact.** Each region of the result is tracked while you type: lines inserted or deleted above it move it; a change that touches a region's lines makes the conflict `edited` (an edited conflict counts as resolved once none of its lines is a conflict marker, so deleting the `<<<<<<<`, `=======` and `>>>>>>>` lines by hand resolves it); lines opened just before or after a region stay outside it. A later pick or untake on a conflict replaces its region's lines wholesale, typed text included (`u` brings it back). Picks on other conflicts, and everything typed outside a region, are never touched. Deleting every line of a region resolves the conflict to nothing.
  - **Undo.** `u` and `Ctrl-r` work in every pane on one stack of the session (the latest 100 changes): a pick, an untake, a Normal mode `x` or `dd`, a pick of all, and a whole typing session (Insert mode until `Esc`) are one step each; motions are none. Closing drops the stack.
- **Line endings.** The result is written with the file's line ending (CRLF when the file used it more than LF) and a final line break only when the file had one. A file that mixes CRLF and LF is written in the common style everywhere, and the status bar says so when it opens.
- **Re-create.** `Ctrl-x` asks "Re-create the conflict of X?" (the file goes back to its conflict markers, also after a save or when it was marked resolved; what the editor holds is discarded; no undo for the file's current content; the Confirm says so without a git command) and on `y` runs `git checkout --merge -- <file>`, then reads the file again into a fresh editor.
  Git's own refusal (no recorded conflict) is shown in the status bar and the editor stays as it was.
- **Base.** The base comes from the file's `|||||||` section (`merge.conflictStyle` `diff3` or `zdiff3`); for the default `merge` style it is found by merging stages 1 to 3 in memory and matching each conflict by its two sides (the file on disk is not touched). A conflict edited by hand, or one that merge does not reproduce, shows "no base" in the base pane and names the setting; `R` then gives the base once `diff3` is on.
- **Save.** `Ctrl-s` (also while typing in the result, no `Esc` first; `Enter` no longer saves) with every conflict settled writes the result to the working tree file and stages it (`git add`) in the same step, with no second Confirm; the editor closes and the file moves from the Unstaged to the Staged list. The status bar says `Resolved and staged X (Staged list), 2 conflicts left` and the cursor goes to the first conflicted file left in the Unstaged list; when none is left it says `Resolved and staged X (Staged list): all conflicts resolved, <space>gc continue` (`commit it` when no operation is in progress, as after a squash merge) and the cursor and focus land on X in the Staged list. Nothing continues by itself: the operation banner keeps its step (`REBASING 1/3  2 conflicts`) with the count lowered by one, and `<space>gc` continues (a merge commits, a rebase continues), see "Continue" below. A staged file during a rebase is not a finished commit.
  With conflicts left it asks first ("Save X with 2 unresolved conflicts out of 5?"; the unresolved ones keep their markers; the Confirm says `Ctrl-x` re-creates the whole conflict), writes, and does not stage the file. The undo after staging is `Ctrl-x` (re-create), which also works on a staged file.
  Nothing picked or typed: refused.
  `Esc` (or `h` in a version pane, `q`) closes; a changed file asks for a second `Esc` first.
  The file is read again right before the write; if it changed on disk since the editor opened, nothing is written and the changes stay.
  The git index is only touched by the Confirm's `git add`.
- **What opens.** Text files that both sides changed (`UU`) and add/add files (`AA`, edited against an empty base since there is no common ancestor), including a merge, rebase, cherry-pick and revert stop, with `merge`, `diff3` and `zdiff3` markers.
  Delete/modify, binary, non-UTF-8 and over-1-MiB files, a symlink or submodule, a file whose markers are unbalanced or gone, and a name that is not valid UTF-8 are refused with the reason and a pointer to the mergetool (`<space>em`).
  `Enter` on a `!` row goes to the editor (or to that refusal); the file's combined diff is still shown beside the list while the row is selected, and the pane keys move focus into it.
- **Not done yet.** Long lines in the version panes are cut with an ellipsis instead of scrolling sideways (#862), and a file longer than 1 MiB is refused as before.
3. **Continue** (`<space>gc`, or the banner chip): refused while conflicted files remain ("2 files still conflicted"); otherwise runs `<op> --continue` with no editor (`-c core.editor=true`, so git's prepared message is used).
   A rebase may stop again at the next commit: the status line warns and the banner updates.
   A continue that fails without a new conflict (a dirty tree, a hook) shows git's reason and leaves the operation as it was.
4. **Abort** (`<space>ga`): Confirm that says the work of the operation is undone and resolutions are lost, with the old tip. **Skip** (`<space>gs`; rebase, cherry-pick and revert only): Confirm naming the commit that is dropped.
5. **Other actions are blocked** (each blocked feature adds its own refusal: #38 merge (done), #39 rebase, #40 cherry-pick and revert (done), #392 reset, #419 branch switch (done)).
   While an operation is in progress branch switch, merge, rebase (interactive too), reset and new cherry-picks are refused with "finish or abort the <operation> first".
   Staging, committing (as the continue step) and viewing keep working.
6. **Completion.** A continue that finishes the operation posts "Merged feature/x into main (abc1234)" or the equivalent and removes the banner.

### 5. Fetch, pull and push

`<space>f` (or `<space>rf`) fetches the current branch's remote with `--prune` (all remotes: `remote.fetch-all` from the palette or the Remotes header menu), `<space>p` (or `<space>rl`) pulls the current branch (fast-forward only; a diverged branch says so instead of creating a merge commit), `<space>rp` pushes it. The tab bar chips and the actions menu of the sidebar's Remotes header carry the same actions; the chips are hidden while the repository picker is open. A pull is refused while another operation of the tab runs; only one fetch, pull, push or remote branch delete runs per tab and the tab is read again afterwards. Each runs in the background with git's progress line in the status bar; `Esc` in the graph (when nothing else claims it) or the cancel chip cancels ("Fetch cancelled"), and the tab stays usable. `<space>x` stays the status message dismiss.

- **Remote branch delete.** `<space>bD`: remote picker (skipped when only one remote has branches), branch picker of the cached remote-tracking branches, then a Confirm naming both; the Confirm names the short tip and the message history holds the undo after the delete (`git push <remote> <old tip>:refs/heads/<branch>`); the local branch stays. With the cursor on a remote branch row, or on a graph commit with exactly one remote branch, the pickers are skipped (`<space>bd` does the same when that commit has no local branch).
- **First push.** `<space>P` (or `<space>rp`) on a branch without an upstream runs `push --set-upstream <remote> <branch>`: with one remote at once, with several a type-to-filter remote prompt (`origin` first). If it is rejected as a non-fast-forward (the remote already has a diverged branch of that name, known locally), the force push Confirm opens as for a plain push and also sets the upstream, unless the local tip is an ancestor of the remote one (just behind: a status line says to pull or rebase and no force is offered); when the remote branch is not known locally the status says to fetch first.
- **Force push.** `<space>rP`, only ever as `--force-with-lease=<branch>:<our remote-tracking tip>`, behind a Confirm naming the remote branch it overwrites and its tip (and that commits only on the remote are lost); if the remote moved since the last fetch git rejects it and nothing is overwritten. A branch without an upstream cannot be force pushed. A plain `<space>rp` that git rejects as a non-fast-forward while the branch is ahead of its upstream opens the same Confirm by itself (not for a "fetch first" rejection, not while another overlay is open).
- The `F` `L` `P` `S` `T` capitals are not "all" variants of the lowercase keys; the lowercase leader keys are taken. The remote chords sit in the `<space>R` group (not `<space>Pd`, since a key cannot be both complete and a chord prefix); all are also in the Remotes header menu. When the graph or sidebar has no suitable row selected for a stash or tag key, a picker opens.

**Credentials and ssh prompts.** The background run never prompts (`GIT_TERMINAL_PROMPT=0`, ssh in `BatchMode`). When a fetch, pull, push, remote branch delete, tag push or remote tag delete fails because it needs a passphrase, a username and password or a host key confirmation, the error stays in the status bar and a Confirm "Credentials needed" opens (only on the active tab and when no other overlay is open; otherwise the status names the command to run by hand). It names the repository and the command (`Runs: git fetch --prune`); `y` ("Retry in terminal") suspends the TUI like `<space>ec` and runs the same command with the terminal handed to git, then the status bar reports `fetch finished` or the exit code (with a pause for Enter on failure) and the tab is read again; `n` or `Esc` leaves it at the failure. A pull retries as `git pull --no-rebase --ff-only`. A failure that is not about credentials (missing repository, rejected push, network) and a cancel offer nothing. Not available on an OS without external-tool support (the status says so).

**Managing remotes** (`<space>R` + key; config only, nothing is fetched; refused while a fetch, pull or push runs on the tab): `Ra` add (name prompt, then URL prompt; a name in use is refused; the status line suggests a fetch). `Rd` remove: a type-to-filter remote picker (none when a remote branch row is selected in the sidebar), then a Confirm naming the remote, its URL and the remote-tracking branches that disappear (the first five, then a count), saying that branches tracking it lose their upstream and the remote itself is untouched; the Confirm has one plain undo line and the message history holds `git remote add <name> <url>` and a fetch after the removal. `Rn` rename: picker, then a name prompt (git renames the remote-tracking branches and upstream settings, so no Confirm). `Ru` set URL: picker, then a URL prompt filled with the current URL. The keys work from every pane; the Remotes header menu lists the four actions.

### 6. Worktrees

`<space>w` + key.
`<space>w` + key. The sidebar's Worktrees section shows each worktree with branch, dirty counts (`S2 M3 U1`: staged, changed incl. untracked, conflicted; a zero is left out), `↑n↓m` against its upstream and `locked`/`prunable` flags, from `git status` run in that worktree. The tab's own worktree follows its live status; the others are read when the tab or its worktree list changes and then every 30 s.
1. `wa` add: prompt for a branch name, then for the path (default a sibling directory named after the branch).
   An existing branch is checked out (one held by another worktree is refused); a new name (also one that exists only as a remote branch: no tracking branch is made) creates the branch at the selected sidebar row's or graph commit, else HEAD.
   The tab stays where it is.
2. `ws` switch (on a worktree row): the tab's active worktree changes in place and keeps its view state (selected commit, scroll, pane layout, filters, sidebar); HEAD, status and graph are read again for the new worktree, and the tab bar title and the sidebar `*` follow.
   `<space>wt` opens it as its own tab instead (or focuses the tab that already shows it).
   On a local branch row `<space>wt` does the same for the worktree that has the branch checked out; a branch without one asks for the path only (the default sibling directory), adds the worktree and opens it in its own tab.
   Refused without running git: no worktree row selected, the bare entry, a prunable one (its directory is gone), the worktree the tab is on, a worktree another tab shows (the message points to `wt`), and while an operation of the tab is still running.
   Switching never changes the process working directory.
3. `wd` remove: Confirm naming the path; a dirty worktree needs a second Confirm that lists what is lost and says there is no undo (`--force`); a locked one is refused until unlocked; the main worktree and the one the tab is on are refused.
4. `wl` lock (prompt for an optional reason), `wu` unlock, `wp` prune: lists the prunable entries in a Confirm and runs `git worktree prune` on `y`.
5. Mouse: the actions menu of a worktree row lists switch, open, add, remove, lock, unlock and prune; the Worktrees header menu offers add and prune.

### 7. Stashes

Keys are `<space>S` chords, not bare sidebar keys (`a` `p` `d` are vim keys, see the key rule). `Ss` `Su` work from every view; `Sa` `Sp` `Sd` act on the stash row under the sidebar cursor and say "Select a stash in the sidebar first" elsewhere (no picker: a destructive key never guesses a target).
1. `Ss` push the tracked changes, `Su` push them plus the untracked files (ignored ones never): a prompt popup for an optional message (`Enter` runs, `Esc` cancels). "Nothing to stash" is a warning and points at `Su`.
2. `Sa` apply, `Sp` pop: no Confirm (nothing is lost; git refuses when local changes would be overwritten and the status bar shows why).
   A conflict made by the call keeps the stash, starts no operation, marks the files `!` and says so in the status bar; if files were already conflicted (a stopped merge) git refuses and its message is shown.
   A pop that succeeds drops the entry and the message carries the restore command.
3. `Sd` drop: Confirm with the stash name and subject; the Confirm says in one plain line that the message history will show how to bring it back, and the history entry after the drop holds `git stash store -m "<subject>" <hash>` with the full hash (the status line shows the short one).
   The target travels as its commit hash and is looked up again right before the call, so a stack that changed meanwhile does not redirect it ("no longer in the stash list", nothing happens).
   The restore command is written for a POSIX shell.
4. `Enter` (or a click) on a stash row shows what is inside it in the detail pane, read-only; focus stays in the sidebar, `Ctrl-j` moves to the detail pane. The Changes tab lists the stash's files (tracked changes with their status letters, then the untracked files saved by `Su` marked `?`) under a heading naming the stash (`Stash stash@{0}: 2 files changed, 1 untracked`), the title shows its name instead of a hash, the Details tab shows the stash commit's message with a `stash` row, and the Files tab says a stash has no tree. The file under the cursor opens in the diff pane as for a commit (tracked changes as `git stash show -p`, untracked files as additions; the diff options apply). There is no stage or unstage inside a stash; single files come out with `<space>kr` (item 5).
   The stash is known by its commit hash: moving the sidebar cursor to another stash row shows that one; selecting a commit in the graph (the user's own move; a reload, restore or tab switch that moves the selection keeps the view), or `Enter` on a branch or tag row, ends the view. While a stash is shown the commit actions that read the graph selection (branch, merge, rebase, reset, pick, compare, tag and external-tool actions) refuse with a notice instead of acting on the graph row, so select a commit first; the graph row menu still opens. A stash that leaves the stack (dropped, popped, in another client) ends the view with a warning; one that only moves down the stack keeps showing under its new name.
5. `<space>kr` (detail pane, Changes tab, #710) restores the file under the cursor from the shown stash into the working tree: `git restore --source=<stash> -- <file>` (a saved untracked file is read from the stash's third parent). Only that file's working-tree content changes; the index, other files and the stash stay. A file that does not exist in the working tree is created without asking. One whose content differs asks first (Confirm naming the file and the stash; `y` runs it); the replaced content is written to the object database before it is overwritten, and the message history carries `git cat-file blob <id> > "<file>"` as the undo (the Confirm says so in plain words). A file that already matches says so and writes nothing; a file the stash deletes ("holds no copy") or a stash that left the stack is refused with a message. Refused with a notice unless a stash is shown and the cursor is on a file row. Sameness is decided by content, so a file that differs only in its executable bit counts as matching. There is no hunk-level restore.
6. Mouse: the actions menu of a stash row lists apply, pop, drop, push and push-all (`drop` keeps its Confirm); the Stashes header menu offers push and push-all. File restore is reached by the command palette (`:` button) with the detail pane focused (it lists the actions bound to that pane); the Changes tab's `...` menu stays the path-style options.
