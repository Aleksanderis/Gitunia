# Testing: design history

How and why the decisions behind `docs/testing.md` were made, roughly in the order they were decided, with the measurements taken. Not required reading for ordinary work: the rules are in `.claude/rules/` and the current spec is in `docs/testing.md`. Where a later note contradicts an earlier one, the later one wins. Details of a fact in `docs/testing.md` that look out of date: check here and in the issue before changing code.

- CI minutes (#211): the free plan allows 2,000 Actions minutes a month for private repos (690 were used in the first days of M1). `ci.yml` therefore skips draft PRs (it runs when one is marked ready), PRs whose base branch is `review/**` (owner review-only PRs, never merged) and docs-only PRs (`docs/**`, `**/*.md`, `.claude/**`, the same list as pushes to `main`). Agents open PRs as drafts, build and test locally, and run `gh pr ready` once the reviewer has no blockers; a docs-only PR is merged on the reviewer verdict alone. Considered and not done: paid minutes (about $0.006-0.008 per Linux minute) and a self-hosted runner; revisit if the OS matrix in M4 (Windows 2x, macOS 10x) needs more.

- Screenshots of the real UI (#227): ANSI frame to PNG with `tmux capture-pane -p -e` of the live binary, `tools/AnsiToSvg` (a small C# tool, one `<text>` run per style with an explicit x per character so the grid never drifts) and `rsvg-convert`. Chosen over `freeze`/`aha` (not installed, extra dependency), chromium (heavy, ~1 s startup per image) and a `--print-frame --colors` mode (does not exist; the issue allowed the tmux capture, and it needs no change to rendering code, so it also shows the real key-driven states such as the open diff). Local only, never in CI. Hosting: first an orphan `screenshots` branch (superseded, see the screenshots repository note below); `pr-<n>/<sha>/`, links pinned to the commit because the repo is private; `clean` removes merged PRs' directories from the tip (history keeps them). Light theme means a light terminal background until the app gets a theme.

- Screenshots repository (#229, owner decision 2026-10-13): the orphan `screenshots` branch moved to the separate private repository `Aleksanderis/Gitunia-screenshots` (`main`), same `pr-<n>/<sha>/` layout. Why: a branch of the code repository is fetched by every clone and its history keeps every image forever, `clean` cannot reclaim space and agents pushed a branch of the main repository; in a separate repository the history can be reset by the owner without touching the code repository. Considered and not taken: release assets (really deletable, but untested for inline rendering in private-repo comments, and the issue asked for git hosting), the wiki repository (same growth, needs the wiki enabled and a first page made in the web UI), drag-and-drop uploads (no API), external image hosts (public). The images of PRs #198, #228 and #236 were copied over (same paths), the links in their PR comments rewritten, and the `screenshots` branch deleted. Agents may push to the screenshots repository without asking (plain pushes only, never forced), like their `feature/`/`fix/` branches; CLAUDE.md "Pushing" says so.

- Accepted intrinsic timer waits (moved from the principles; the rule itself is in the `testing` skill) (the wait is the thing under test): in `GitRunnerTests`, the timeout-kill test (2 s runner timeout on Unix, which also covers the fake start-up; 300 ms on Windows, where the fake marks after 2 s), the slow-consumer test (consumer sleeps 600 ms against a 200 ms runner timeout) and the stalled-stream test (the fake prints once, then sleeps; the idle timeout is 2 s, not 500 ms, because the timer also covers process start-up, which can exceed 500 ms under CPU load so the first chunk never arrives) and, on Windows only, `AssertNeverMarkedAsync` outwaiting 3 s because the cmd fake cannot record its pid. On Linux/macOS that helper waits for the process to exit. Measured under load (#182): 100 runs of the stalled-stream test with one busy loop per core (14 cores) all passed on that 14-core dev machine (`dotnet test --no-build --filter ThenTimeoutAfterFirstChunk` in a loop, one `while :; do :; done` per core). A 2-4 core CI runner is untested; if it flakes, widen the timeout first.

- Moved from `docs/decisions.md` (full wording of entries shortened there):

  - 2026-10-16: **Process:** CI cost (free plan ~1100 of 2000 min used mid-month): CI runs once per ready PR, weekly on main and by dispatch, not on push to main; AOT publish only on PRs touching project/dependency files; agents verify locally, open PRs ready and push once; screenshots only for visual changes, one capture per PR. Revisit at v1.0. Supersedes the draft-PR flow.

## Numbers moved from testing.md (2026-10-30)

Verbatim principle bullets with their one-off counts and timings; the rules stay in `docs/testing.md`.

- Process spawns dominate test time on Windows (#624): the suite starts ~6,200 git processes in `Git.Tests` and ~11,700 in `Tui.Tests` (counted once on one Windows 11 machine, not a budget). Test runners therefore get `TestGitSpeed`: the real `mingw64\bin\git.exe` instead of the `cmd\git.exe` shim (which starts it as a second process), and `gc.auto=0`, `maintenance.auto=false` and `core.fsync=none` (without them every commit starts a `git maintenance run --auto` child). New fixtures that build a runner use it; keep the number of git calls per fixture low.
- Parallelism: `tests/xunit.runner.json` (copied into every test project by `tests/Directory.Build.props`) caps xUnit at 8 threads per assembly, parallel across test classes (collections). xUnit has no method-level parallelism: split a slow class instead. `dotnet test` on the root solution also runs the test assemblies concurrently; on a single csproj or dll it cannot. On a CPU-bound machine that concurrency buys no wall time and only lengthens every git call: with the CPU limited to 2 logical CPUs (`start /affinity 3`), the suite took 402 s concurrent and 432 s one project at a time, but `Git.Tests` alone dropped from 6 m 27 s to 2 m 43 s (#634). The Windows CI leg therefore runs the projects one after another and stops at the first failing one. Capping xUnit threads (2 instead of 8) changed nothing measurable. Test git runners get a 2-minute default timeout (`TestGitSpeed.Timeout`; production keeps 30 s) and waits for background events are generous (30-60 s: a passing test never waits that long); do not write a test whose pass depends on a timeout below ~1 s.
- Windows CI timing (#630), unconfirmed on the runner: `Core.Tests` took 118 s on the first `windows-latest` run. On a Windows 11 developer machine (counted once, not a budget) it takes 3-6 s alone and 8-19 s while `Git.Tests` runs beside it, so contention explains about 3x, not 25x; runner CPU count and Defender are unmeasured. Read the post-#634 (one project at a time) `Core.Tests` time off the next manual CI run before treating the cause as settled. `IgnoreAwareWatchingTests` passed 8 of 8 runs alone and 3 of 3 full-solution runs here; its one known flake was the nested-directory product race (#604, a directory created between the first listing and the watcher being enabled), fixed by listing the new directory again once its watchers are live. The race could not be reproduced on Linux (also not under CPU load), so the regression tests only guard the end state, and the Windows effect is unverified.
- Audit outcome (#676, Linux, theory rows counted; 5,033 cases before, 5,023 after): Platform 49 to 48, Core 1,555 to 1,550, Git 809 to 805 (#681), Tui 2,620 to 2,620 with 14 fewer test methods (the parser rows moved into the existing theory, one more row added). The suite was sound: the saving is in methods, maintenance and one 12 s Tui test (now under 0.5 s: file watching is off by default, so the tab is polled; inject `PollOptions` with short intervals), not in case count. The "unrelated action is not handled" tests stay per handler (router tests cannot see a handler that claims too much); `CommitDetailsCache` and `DiffCache` have separate LRU implementations, so both keep their tests.
Windows runs only the OS-sensitive tests (#637): every test class marked `[Trait("Os", "Independent")]` (pure logic on in-memory data, proven by Linux) is excluded there with `--filter "Os!=Independent"`, and Linux runs all. The default is the safe side: an unmarked test runs on Windows, so a forgotten mark costs minutes, never coverage. `OsTraitGuardTests` (Core.Tests) fails if a marked file itself uses real git, paths, the file system, processes, the environment or the known path-building fakes (`FakeStatusReader` and similar; it cannot see other helpers), and if Git.Tests or Platform.Tests carry the mark. Counted with `--list-tests` (theory rows counted), Windows selects 4,097 of 5,024 tests (Core 1,102 of 1,552, Platform 49 of 49, Git 805 of 805, Tui 2,141 of 2,618). The 82 marked classes were picked by a conservative source scan, so more can be marked later; the saving is mostly in test count, the slow real-git tests stay. The count drifts as tests are added: recount with `dotnet test <project> --no-build --list-tests --filter "Os!=Independent"`. Author rules: `testing` skill, "Mark OS-independent tests".
