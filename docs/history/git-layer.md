# Git layer: design history

How and why the decisions behind `docs/git-layer.md` were made, roughly in the order they were decided, with the measurements taken. Not required reading for ordinary work: the rules are in `.claude/rules/` and the current spec is in `docs/git-layer.md`. Where a later note contradicts an earlier one, the later one wins. Details of a fact in `docs/git-layer.md` that look out of date: check here and in the issue before changing code.

- Standalone launch (spike #3) findings for M1: resolve paths with `git -C <path> rev-parse`; check `--is-bare-repository` before `--show-toplevel`; a linked worktree has `--git-dir` != `--git-common-dir`; dedupe tabs by the resolved toplevel; a path inside a `.git` directory needs its own case. Resolving costs 0-2 ms.

- Commit ids are a fixed 40-byte `ObjectId` struct (SHA-1 or SHA-256) instead of interned hash strings (#13). Why: no intern table or string per parent link, equality and hashing without allocation. Cost: 40 bytes per id even for SHA-1 (about 12 bytes padding); per-commit memory is still dominated by `CommitInfo`, its subject string and decorations. Author names and emails are interned. The default log excludes `refs/stash` so stash commits do not appear as graph nodes; callers that pass revisions get exactly those.

- Diff parser (#15): `DiffParser` is incremental (feed byte chunks; a file is emitted when the next `diff --git` starts, so memory is bounded by the largest single file) and keeps every header and `@@` line verbatim, so `DiffPatchWriter.WriteFile` reproduces git's text exactly. `DiffReader` fixes the options that make output predictable (`--no-color --no-ext-diff --no-textconv --src-prefix=a/ --dst-prefix=b/ --find-renames --find-copies`); callers add the rest (`--cached`, `--binary`, `-U<n>`, `--format=` for `show`). Partial staging uses `DiffPatchWriter.WriteSelection` (hunk and line index addressing, counts and offsets recomputed; `Forward` to stage, `Reverse` to unstage or discard with `apply -R`). Known limits: combined diffs (`diff --cc`, merge commits) are skipped with a warning; invalid UTF-8 is replaced and a warning says the text is no longer exact, so such patches must not be applied; partial patches are not meaningful for binary, added or deleted files (stage whole) and hunks with zero context are not re-anchored; `GitRunner` has no stdin support, so applying a patch needs a temp file or a runner extension (follow-up for the staging issue).

- File watching (#27) lives in `Gitunia.Git` (no Core types): one `RepositoryWatcher` per tab, one shared `WatchBudget`, `RepositoryRefresher` for incremental refresh; details in the Refresh section above. The Platform abstraction is not involved: `FileSystemWatcher` is cross-platform and its failures (inotify limit, buffer overflow, unsupported file systems) fall back to polling, which is the per-OS escape hatch. Wiring into tab state and effects (calling `SetActive` on tab switch, running the refresh effect, applying the changed sections) is left to the UI work. Known limit: the recursive working tree watcher also sees `.git/objects`; the classifier filters those events but they still cost inotify watches.

- Commit details (#24; the debounce on every move and the FIFO cache described here were changed in #215, see "Faster commit details" in architecture.md): `CommitDetailsReader` (`Gitunia.Git`) runs `git log -1 -z` (parsed by `CommitDetailsParser`: full raw message, author and committer with their UTC offsets via `%aI`/`%cI`, parents) and then `git diff-tree --raw -z -M -C` against the explicitly named first parent (or `--root`), because `diff-tree` shows merges against every parent and ignores `--first-parent` (parsed by `CommitFileChangeParser`, statuses reuse `FileChangeKind`). In the Tui, `CommitDetailsStore` (one per tab, owned by `TabSession`) is fed by every graph selection change: it shows the loading state at once, debounces 80 ms, cancels the load of the previous selection (its git processes are killed), ignores stale results and caches the last 64 commits. Pane rows are width-independent (`DetailContentBuilder`; long lines are cut with an ellipsis, not wrapped) and drawn by `DetailPaneRenderer`, shared by the Terminal.Gui list source and `ScreenComposer`, so `--print-frame` shows the pane for the newest commit. Pane focus is `FocusedPane` of the tab's view state; `ActionRouter.ViewName` picks the keymap view (`Graph` or `Detail`) from it.

- Background status polling (#135): `StatusReader` takes an `UntrackedFilesMode`; `BackgroundStatusPoller` uses `Normal` (`--untracked-files=normal`: an untracked directory is one entry), because the tab bar only needs to know the tree is dirty. Measured on a throwaway repo with 20,000 untracked files in 100 directories: `all` 9 ms and 288 KB of output, `normal` 1 ms and 80 bytes (cold, large real trees will show a bigger gap). The active tab keeps `All`. `RepoStatusSummary.From(StatusSnapshot)` replaces the hand-built summaries (`TabRefresher` still builds its own, #144).

- Moved from `docs/decisions.md` (full wording of entries shortened there):

  - 2026-10-15: **Git layer:** Non-UTF-8 paths (#94): status output is decoded surrogate-escaped (`GitPathText`) and paths reach git on stdin (`--pathspec-from-file=-`), never as arguments. Line and hunk patches of files with invalid UTF-8 are refused (`InexactPatchException`); such files are staged whole. Affects #30, #31, #33.

  - 2026-10-15: **Git layer:** Hunk and line staging (#31): the patch is never built from the rows on screen; the file's diff is re-read with default context, the picked lines are found by number and text and applied with `git apply --cached` (`-R` to unstage). Binary, new, deleted and copied files go whole for a hunk and refuse a line range; mode lines stay out of partial patches; a renamed file with edits is cut as an edit of its new path.

  - 2026-10-16: **Git layer:** The working-tree diff of a name that is not valid UTF-8 (#344) streams the unfiltered diff and picks the file by its lossy path; an untracked one is read in-process through a small `open(2)` P/Invoke in `Gitunia.Platform` (bounded read, Linux/macOS only). Why: `git diff` has no pathspec file and the runtime cannot spell such a path.

  - 2026-10-16: **Git layer:** Lines of an untracked text file (#351, supersedes the "new files go whole" part of #31): `git add -N` (intent-to-add) first, then the usual patch; the empty entry is removed again on every outcome that stages nothing, best effort (a kill -9 in between leaves it, visible as an unstaged addition). An untracked symlink is staged whole, never by lines (#379): the no-index view follows the link, the index records its target.

- Implementation notes moved out of `docs/git-layer.md` on 2026-10-16 (the contract now states rules only; these were its long per-feature bullets, kept verbatim). Runner details:

- Runner API (`GitRunner`): `RunAsync` collects output, `StreamAsync` yields stdout chunks (its timeout is an idle timeout that does not run while the consumer handles a chunk; errors surface after the last chunk; disposing early kills git). Errors are `GitCommandFailedException` (exit code not in `GitRunOptions.AcceptedExitCodes`), `GitTimeoutException`, `GitNotFoundException`, `GitVersionTooOldException`; cancellation raises `OperationCanceledException`. On timeout or cancel the whole process tree is killed. Read-only polling must pass `ReadOnly: true` (sets `GIT_OPTIONAL_LOCKS=0`); stdin is closed at once so git never waits for input, unless the call sets `GitRunOptions.StandardInput` (bytes written to stdin, then closed; `RunAsync` only), which is how patches (`apply --cached -`, built with `DiffPatchWriter`) and paths reach mutating calls; mutating calls never pass `ReadOnly: true`. Paths: status output is decoded with `GitPathText.Decode` (valid UTF-8 as is, every invalid byte becomes the lone surrogate `U+DC00 + byte`), so `StatusEntry.Path` of a non-UTF-8 name round-trips byte-exactly through `GitPathText.Encode`. Such a string cannot be a process argument (the runtime would replace the surrogates): stage, unstage and discard pass paths on stdin with `GitOptions.PathspecFromStandardInput` + `PathspecFileNul` and `GitPathText.EncodePathspecFile` (git 2.25+ for `add`/`restore`/`reset`). Diffs are decoded lossily; `DiffFile.HasInvalidText` marks a file with invalid UTF-8 in a path or line, and `DiffPatchWriter` throws `InexactPatchException` for it, so line and hunk staging is refused and the file is staged whole by path. Display code must treat lone surrogates as replacement characters. `GitRunnerOptions.EnvironmentOverrides` exists for test isolation; production code must not use it.

- Commit (#32, `ICommitWriter`/`CommitWriter` in `Commits/`): `CommitAsync(location, CommitRequest(Message, SignOff, NoVerify, Amend))` runs `git commit -F - [-s] [--no-verify] [--amend]` with the message on stdin (kept as typed: the default cleanup of `-F` is `whitespace`, so `#` lines stay), a 10 minute timeout for hooks, and returns the new HEAD plus the previous hash for an amend (read with `rev-parse --verify --quiet HEAD` before and after). `ReadHeadMessageAsync` reads `log -1 --format=%B` for Amend. Hooks, signing and identity come from the user's config; stdin is closed, so a hook or a signing program that prompts fails, and git's and the hooks' stderr come back in `GitCommandFailedException.StandardError` (pre-commit and commit-msg hook output goes to stderr) and git's own stdout (e.g. `nothing to commit`) in `StandardOutput` (filled by `RunAsync`, empty for `StreamAsync` failures). Commits through `$EDITOR` are not a runner call (`ExternalToolRunner`, architecture.md).

- Diffs: `DiffReader.ReadAsync(location, ["diff", ...])` streams `DiffFile` > `DiffHunk` > `DiffLine` (addressed by file, hunk and line index, with old/new line numbers). `IDiffReader.ReadWorkingFileAsync` reads one file of the working-tree view (unstaged, staged, untracked via `--no-index` with the `/dev/null` literal, conflicted via `DiffParser(readsCombined: true)`); paths go as `:(literal)` pathspecs after `--`, and a path with escaped (non-UTF-8) bytes cannot be an argument and the diff command has no `--pathspec-from-file`, so the unfiltered `diff` (or `diff --cached`) is streamed and the file picked by its lossily decoded path, stopping after it (two names that differ only in invalid bytes decode alike: the first wins); an untracked such file is read through `RawPathFileReader` (`open(2)` with the raw bytes, Linux and macOS; Windows names cannot hold such bytes) and written as additions by `NewFilePatch` (mode shown as 100644, a symlink is followed). `DiffPatchWriter` writes files and hunks back verbatim, and `WriteSelection` builds a patch of chosen lines for `git apply --cached` (`-R` for `PatchDirection.Reverse`). Binary files carry no hunks, only header lines. Details and limits: `docs/history/git-layer.md` (#15).

- Partial staging (#31): `IIndexWriter.ApplyPatchAsync(location, patch, direction)` runs `git apply --cached [-R] --whitespace=nowarn -` with the UTF-8 patch on stdin (a mutating call, so not `ReadOnly`; git rejects a patch that does not apply and leaves the index alone). `PatchStager.StageAsync` is the one entry point for hunks and lines: it re-reads the file's diff with git's default context (never the context the user views), finds the chosen `ChangedLine`s (kind, line number and text, so a diff shown with other options still matches; `DiffLineMatcher`), writes the patch with `WriteSelection` (`Forward` for stage, `Reverse` for unstage) and applies it. It stages or unstages the whole file by path instead for what `WriteSelection` does not guard: binary, added, deleted and copied files, an untracked file that is binary or whose name is not valid UTF-8, a truncated diff, `HasInvalidText` (the `InexactPatchException` case) and a name that is not valid UTF-8 (skipped without reading the diff). The patch never uses `-U0`, so no re-anchoring (`--unidiff-zero`) is needed. Lines of an untracked text file (#351): `IIndexWriter.IntentToAddAsync` runs `add --intent-to-add`, the diff is then read as an unstaged new file (`PickableDiffReader.ReadAsync(allowAdded: true)`, never for discarding) and the chosen lines go through the same patch path (`git apply --cached` accepts an intent-to-add entry as absent), so the rest stays an unstaged addition. The empty entry is removed again (`UnstageAsync`, own 30 s timeout, not the caller's token, best effort so it never hides the outcome) on every outcome that does not stage something (stale lines, not splittable, git refusing the patch, cancel, error); an untracked symlink (the `--no-index` view follows it, the index records the link target) is never split: it goes whole when the caller allows it, else `NotSplittable` (#379); a CRLF file under `autocrlf` stages its lines correctly (tested). Results are typed (`PatchStagingResult`: `Applied`, `WholeFile`, `FileChanged`, `NothingSelected`).

- Discard (#33; `IWorkingTreeDiscarder`, `PatchDiscarder`, in `Gitunia.Git/Discard`): nothing here can be undone, callers confirm first. `RestoreAsync` runs `--literal-pathspecs restore --worktree` with the paths on stdin (a file goes back to the index version; staged changes stay, a deleted file returns). `DeleteUntrackedAsync` runs `--literal-pathspecs clean -f -d -q -- <paths>` (batches of 64 arguments): `clean` never touches a tracked or an ignored path, and a path with bytes that are not UTF-8 cannot be an argument: it is found with `ls-files -o --exclude-standard -z` (exact bytes, `GitPathText`) and deleted through `IByteExactFileSystem` (`Gitunia.Platform/FileSystem`: libc `unlink`/`rmdir` on Linux, explicit unsupported on Windows, macOS and other OSes, where `CanDeleteInvalidNames` is false, the call throws `NotSupportedException` and the UI refuses it earlier); directories left empty are removed, ignored files stay. `ApplyReversePatchAsync` runs `apply -R --whitespace=nowarn -` (no `--cached`: the index is never touched). `PatchDiscarder.DiscardAsync` reads the file's unstaged diff through `PickableDiffReader` (shared with `PatchStager`: default context, mode lines dropped, a rename cut as an edit of the new path, null for binary, added, deleted, untracked, truncated or invalid-text files), matches the chosen lines, writes the patch with `WriteSelection(..., Reverse)` (the working tree is the new side) and applies it backwards; files without pickable hunks are restored or deleted whole when the caller allows it, and the result type is `PatchStagingResult`.

- Commit graph: hash, parents, author, date, subject, refs; lane assignment computed incrementally from `rev-list --parents` order. Lane 0 is reserved for the first-parent chain of the checked-out branch's tip (`GraphLayoutBuilder(headCommit)`, tip found by `ICommitLogReader.ReadCurrentBranchTipAsync`, read concurrently with the log): no other commit takes lane 0 until that chain ends (one exception: the commits above HEAD whose first-parent chain reaches it, a branch ahead of HEAD such as `origin/main`, continue the shaft upwards and take lane 0 while it is free, so it stays straight however many commits ahead the branch is; the streamed layout cannot tell these from the log, so `ICommitLogReader.ReadHeadLayoutAsync` returns them as a set next to the tip: one extra `rev-list --parents --topo-order --reverse --ancestry-path --all ^HEAD` run, started together with the tip read and parsed by `FirstParentDescendantsParser`, which keeps the commits whose first parent is the tip or already kept; the walk follows all parents so the set depends only on the history and the tip, never on which refs reach a commit; with several ahead branches the first listed takes lane 0 and the others bend in; a failed read gives no set and the layout keeps the older rule that a tip directly above HEAD takes lane 0), a chain commit whose parent is already waited for in another lane still puts it in lane 0 (the other lane joins with an incoming edge), and the reservation is part of `GraphRow.LaneFingerprint` (the set of commits above HEAD is not: it is a pure function of the history and HEAD, so an incremental reload with the same HEAD cannot join rows laid out with another set; a regression test deletes a merged branch to check this), so an incremental reload after HEAD moved cannot join rows laid out for another HEAD and falls back to reading further or fully. A detached or unborn HEAD, or a failed tip read, gives no head commit and the leftmost free lane is used; the tip is read by a separate git process, so a commit made between the two reads can leave lane 0 reserved but empty until the next refresh. Graph layout is a pure function so it can be tested and cached.

- Implementation (`Gitunia.Git`): `RepositoryWatcher` is the watcher set of one tab. It watches the git directory, the common directory (linked worktrees), `refs/`, `worktrees/` (each linked worktree's gitdir, added when the directory appears later) and the working tree with `FileSystemWatcher`. `RepositoryChangeClassifier` maps a path to `RepositoryChangeKinds` (head, refs, index, working tree, worktrees, operation; lock files, objects and logs are ignored). Events are merged and debounced (200 ms quiet, at most 2 s under a continuous stream); the callback gets the merged kinds on a thread pool thread.

- `SetActive(false)` marks a background tab: it keeps the pending kinds, reports nothing and `IsStale` is true and `BecameStale` is raised once (thread pool) when the first change arrives or when a tab with unreported changes is hidden; `SetActive(true)` reports them at once and re-arms `BecameStale`. The notification goes through an optional `queueNotification` constructor parameter (thread pool by default) and `ReportChange(kinds)` feeds a change in without a file event, so tests assert once/re-arm without sleeps (#170).

- `WatchBudget` caps watchers across all tabs (64 by default; a tab needs 3 to 6). A tab that cannot get its slots, or whose watcher fails to start or raises an error (for example the inotify limit), polls every 5 s instead: a cheap fingerprint of the git directory, refs and worktrees files, plus a working-tree status refresh on every tick. The working tree watcher is recursive, which on Linux costs one inotify watch per directory.

- `RepositoryRefresher.RefreshAsync(location, previous, kinds)` re-reads only the sections the kinds can affect (head and refs together, worktrees, status; operation files are always checked) and returns the new `RepositorySnapshot` plus the `RepositorySections` that actually differ. Unchanged sections keep the previous object, so views can compare by reference and leave scroll and selection alone.

- Background tabs: `BackgroundStatusPoller` (`Gitunia.Tui/App`) runs `git status` for every non-active, non-missing tab, sequentially, at start and every 30 s, and dispatches `StatusLoadedCommand` only when the summary changed. It loads nothing else, so unvisited tabs stay cheap while the tab bar markers stay right (#129). Limit: markers lag by up to the interval.

- Working-tree state (#313): every loaded tab keeps the full `StatusSnapshot` (session restore loads all tabs) in `RepositoryState.WorkingTree` (`WorkingTreeState`: snapshot plus selected file by section and path). `WorkingTreeLoadedCommand` (initial load and every refresh whose status section changed) replaces it, refreshes the tab bar summary and re-finds the selection (same path and list, else the same path in the other list after a stage or unstage, else the row near the old index); a snapshot with the same content returns the same state, so a refresh never repaints or loops. The background poller updates only the summary (`StatusLoadedCommand`, which leaves the snapshot alone), so a background tab's snapshot may be older than its markers until the tab is activated and refreshed. After stage or unstage the cursor stays at the same index of its list (ux.md, workflow 2). List order is git's order; the display order of #29 must be applied in the state layer so indexes stay the row indexes. The Unstaged list holds worktree changes, untracked and conflicted paths; ignored entries are in no list.

- Wiring (`Gitunia.Tui/App/TabRefresher`): `EffectRunner` creates one `TabRefresher` per tab when the tab's load starts; it owns the tab's `RepositoryWatcher` (`SetActive` follows the active tab, so background tabs refresh on activation). After the initial load it records a baseline snapshot (and reloads the graph when a change was seen meanwhile or when `GraphRefCheck` finds the loaded graph's branch, tag and detached-HEAD decorations differ from the baseline refs, which covers a change made between the load and the baseline read), then each change runs `RefreshAsync` off the UI thread (one at a time, changes arriving meanwhile are merged) and dispatches commands only for the sections that differ (HEAD, refs, worktrees, status; stashes are re-read when HEAD or refs changed). The graph is swapped in (`TabSession.ReplaceGraph`) only when HEAD or refs changed or on manual refresh (`<space>r`); an automatic reload is incremental (`IncrementalGraphLoader`, #126): it streams the new log from the top and stops at the first row that equals the old graph (same commit, lane, edges and open lanes below it, `GraphRow.LaneFingerprint`, found by `GraphSplicer`), checks the total with `rev-list --count`, re-reads the refs of the few ref-carrying commits (`--no-walk`) and reuses the old rows below; any mismatch or no join falls back to the full read, and a manual refresh always reads everything; `GraphTabBinder` keeps the selected commit selected and on the same screen row, and the graph search restarts its scan. Failures are reported once through `StatusChannel`; a manual refresh always reports its outcome ("<repo>: refreshed" or the failure). Limits: a selected commit that disappeared keeps the old row position; an incremental reload trusts the old rows below the join, so history rewritten below it without changing the commit count is only picked up by a manual refresh (`r`).


## Detail moved from git-layer.md (2026-10-30)

Verbatim bullets that described classes one by one; the contract stays in `docs/git-layer.md`, the rest is in the code and its XML docs.

- **Commit trees** (`ICommitTreeReader`, `CommitTreeReader`, `CommitTreeParser`; #173): `ls-tree -r -z --long <commit> --` lists every file of a commit in one read-only call, parsed into `TreeEntry(Path, Kind, Id, Size)` (`TreeEntryKind`: file, executable, symlink, submodule from the mode `100755`/`120000`/`160000`; a submodule has no size). Directories are not listed by git; the Core `FileTreeModel` derives them from the paths. Paths that are not UTF-8 survive through `GitPathText`. The whole tree is read at once (not per directory): see the measured timings in `architecture.md`.
- **Blobs** (`IBlobReader`, `BlobReader`; #511): `cat-file blob <id>` reads the content of one file for the Files tab's content view, by the blob id from the tree listing (so odd paths and non-UTF-8 names need no quoting). The cap is `BlobReader.MaximumBytes` (1 MiB): a blob whose size is known to be larger is not read at all, an unknown size is checked on the output; a NUL byte in the first 8000 bytes (git's own check) makes it binary. Result: `BlobContent(Kind: Text | Binary | TooLarge, Text, Size)`; no text conversion or filters.
### Remote calls (`RemoteRunner`, `IRemoteWriter`; #44)

- `RemoteWriter` runs `fetch --progress [--prune] [--all | -- <remote>]`, `pull` as `fetch --progress` then `merge --ff-only @{upstream}` (so the user's `pull.rebase` never applies) and `push --progress [--set-upstream] [--force-with-lease=refs/heads/<b>:<expected>] [-- <remote> [<local>[:refs/heads/<b>]]]` (a plain force never exists: `PushRequest.Lease` is the only way to overwrite, and it expects the tip of our remote-tracking branch; `--set-upstream` is the first push) and `DeleteRemoteBranchAsync` as `push --no-progress --delete -- <remote> refs/heads/<b>` through `RemoteRunner`, with `IProgress<RemoteProgress>` (`Stage`, `Percent` or null for count-only stages, parsed by `RemoteProgressParser` from stderr, `remote: ` prefix stripped). The idle timeout is 2 minutes of silence on stderr (a quiet hook or credential helper counts against it); a cancel kills the process tree, and refs are updated by git only after the objects arrived, so a cancelled fetch leaves the repository consistent (tested with fsck and a lock-file check). The merge step of a pull rewrites the index and working tree, so it is never killed: a cancel is honoured between the fetch and the merge only. A diverged pull throws `PullDivergedException` after the fetch, with no merge or checkout done; `PullOutcome` is `UpToDate` or `FastForwarded`.
- `BranchWriter.FastForwardAsync` (#572) runs `fetch --no-tags --no-write-fetch-head --no-recurse-submodules . <upstream>:refs/heads/<b>` (no leading `+`): a fetch from the repository itself, so no network; git accepts only a fast-forward and refuses a branch checked out in any worktree, and writes the reflog entry. Chosen over `merge-base --is-ancestor` plus `update-ref` because git does both checks atomically.
- `TagWriter` push and remote delete use the same runner (still `--no-progress`, no progress callback).
- `RemoteManager` (`IRemoteManager`; #400) lists remotes (`remote` for names, `config --get-regexp` for the raw URLs, so `insteadOf` aliases survive) and runs `remote add|remove|rename|set-url -- <args>` as plain config writes (no runner, no network, `--` before the names). Git itself removes or renames the remote-tracking branches and moves `branch.*.remote` and `merge` settings; the caller reads the refs again afterwards. Remove is destructive and always behind a Confirm in the UI.
- **No prompts.** stdin is closed and `GIT_TERMINAL_PROMPT=0`, but ssh asks on the controlling terminal. `SshCommandPolicy` sets `GIT_SSH_COMMAND` to the effective command (`GIT_SSH_COMMAND`, else `core.sshCommand`, else a `GIT_SSH` program (left alone), else `ssh`) plus `-o BatchMode=yes`, only when that command is plain `ssh`; a `GIT_SSH` program or another client (plink) is left alone. A call that needs a passphrase fails with git's message (ssh answers `Permission denied (publickey...)`; checked against a real sshd: without `BatchMode` ssh opens `/dev/tty` and prompts even with stdin closed). `RemoteAuthFailure.Matches(stderr)` recognises these failures (`Permission denied (publickey`/`password`/`keyboard-interactive`, `could not read Username`/`Password`, `terminal prompts disabled`, `Authentication failed`, `Host key verification failed`, HTTP 401), and not a missing repository, a refused push or a network error. The UI then offers the same command in the terminal (#45): `RemoteCommands` builds the arguments for both the background writer (with `--progress`; the remote branch delete and the tag push and delete (#512) are built there too, with `--no-progress` in the background only) and the terminal retry (without; a pull is the single process `pull --no-rebase --ff-only`, so `pull.rebase` never applies, and a diverged branch fails as in the background). The retry sets no environment, so ssh, askpass and the credential helper behave as in the user's shell.
- Status bar: `RemoteProgressText.Format` (Core) renders the single progress line (`Fetching: Receiving objects 45%`); the keys, chips and `Esc` cancel are #456, which also wires `GitServices.Remote` to it.
## Mutating operations

All take the repository location, are never `ReadOnly`, and run one at a time per tab (the caller enforces it).

- **Index** (`IIndexWriter`): add, `restore --staged` (`rm --cached` on an unborn branch), `--intent-to-add`, and `ApplyPatchAsync` (`git apply --cached [-R] --whitespace=nowarn -`). Paths on stdin with `--literal-pathspecs`.
- **Partial staging** (`PatchStager`): never builds a patch from the rows on screen. It re-reads the file's diff with git's default context, finds the chosen lines by kind, line number and text (`DiffLineMatcher`), writes a patch with `DiffPatchWriter.WriteSelection` (`Forward` to stage, `Reverse` to unstage) and applies it. Git rejects a patch that does not apply and leaves the index alone. Whole-file fallback for what a partial patch cannot represent: binary, added, deleted and copied files, untracked binary files and symlinks, truncated diffs, `HasInvalidText`, names that are not valid UTF-8. Results are typed (`PatchStagingResult`: `Applied`, `WholeFile`, `FileChanged`, `NothingSelected`). Lines of an untracked text file go through `add --intent-to-add` first; the empty entry is removed again on every outcome that stages nothing.
- **Reflog** (`IReflogReader`, `ReflogReader`, `ReflogParser`): `reflog show --format=<hash, %gd, %gs> --date=relative -n <limit> <ref> --`; the selector carries the relative time, the position is the `n` of `ref@{n}`, the subject splits at the first `: ` into action and message. Read-only.
- **Message search** (`ICommitMessageSearcher`, `CommitMessageSearcher`, #97): `log -z --format=%H --regexp-ignore-case --fixed-strings --grep=<text> --exclude=refs/stash --all --`; returns the set of matching commit ids (subject and body). Run only when the graph search gets a `body:` query; read-only, 60 s timeout.
- **Reset** (`IResetWriter`, `ResetWriter`): `reset --soft|--mixed|--hard <commit>^{commit} --`; returns the HEAD hash read right before, which the status and the Confirm print as the undo. It checks nothing else: the UI refuses a detached HEAD or a running operation and names the lost files from a status read.
- **Ancestry** (`IAncestryReader`, `AncestryReader`, #829): `merge-base --is-ancestor <a> <b>` (read-only; exit 0 yes, exit 1 no, anything else throws). The first-push force offer uses it: a local branch that is an ancestor of `<remote>/<branch>` is only behind it and is not offered a force.
- **Worktrees** (`IWorktreeWriter`, `WorktreeWriter`): `worktree add [-b <new> --] <path> [<start>]`, `remove [--force] -- <path>` (a locked worktree is refused even with force; the branch is kept), `lock [--reason]`, `unlock` and `prune --verbose` (the removed entries come from stderr). `ListChangesAsync` runs `status --porcelain -z --no-renames` inside the worktree so the UI can name what a forced remove would lose (untracked count, ignored do not). Reads stay in `RefReader.ReadWorktreesAsync`.
- **Discard** (`IWorkingTreeDiscarder`, `PatchDiscarder`): nothing here can be undone, so callers confirm first. `--literal-pathspecs restore --worktree` for tracked files (staged changes stay), `clean -f -d -q --` for untracked ones (never touches a tracked or an ignored path; batches of 64 arguments), and `apply -R` for hunks and lines (working tree only, the index is never touched), cut from the same pickable diff staging uses (`PickableDiffReader`).
- **Stash** (`IStashWriter`): `PushAsync(location, message, includeUntracked)` runs `git stash push --quiet [--include-untracked] [-m msg]` and compares `refs/stash` before and after, because git exits 0 on "No local changes to save" (`NothingToStash`). Apply, pop and drop take a `StashEntry` and find its current `stash@{n}` by commit hash first (`Missing` when gone), so a changed stack hardly ever redirects them (a push by another process between the lookup and the call still could); pop needs the `stash@{n}` form anyway. An apply or pop that fails and changed the `git ls-files --unmerged` set is `Conflicted` (the stash is kept); other failures, including a refusal while files were already unmerged, throw. The undo of a drop is `git stash store -m "<subject>" <hash>`.
- **Stash details** (`IStashDetailsReader`, `StashDetailsReader`, #709): looks inside a stash found by commit hash. `ReadFilesAsync(location, entry)` returns `StashFiles` (null when the hash is no longer in `git stash list`): one `rev-list --parents -n 1` gives the parents (base, index and, for `--include-untracked`, the untracked commit), then the tracked changes are `diff-tree --raw -z` of `base..stash` through `CommitFileChangeParser` (renames only, no `--find-copies`, so the list and statuses equal `git stash show --name-status`) and the untracked files are the same read of the third parent against the empty tree (all `Added`), each file a `StashFileChange` with `StashFileOrigin.Tracked` or `Untracked`, tracked first. `ReadDiffAsync(location, entry, origin)` streams `DiffReader.ReadAsync` for the chosen part (`base..stash` with a trailing `--find-renames` that overrides the reader's `--find-copies`, the text of `git stash show -p`; or the third parent as additions), nothing for `Untracked` when the stash has none. The files read checks the stack first and then reads in separate git calls, so a stash dropped and pruned in between throws a git error instead of returning null. The diff is addressed by hash and does not check the stack, so it works while the commit exists and otherwise fails with a git error. Read-only (`GitRunOptions.ReadOnlyRun`, so the runner's default timeout applies).
- **Config** (`IGitConfigReader`, `GitConfigReader`): `config --type=bool --get rebase.autoStash` (exit 1 = not set = off), read with the refs of a tab refresh (the watcher reports a repository `config` change as refs; a manual refresh also reads it, for a global change) into `RepositoryState.RebaseAutoStash`. `RebaseGuard` then skips the uncommitted-changes refusal, because git stashes and restores them itself; a conflicting pop is git's and shows as the usual operation banner.
- **Rebase** (`IRebaseWriter`, `RebaseWriter`): `git -c core.editor=true rebase <onto>^{commit}` through `OperationRunner.RunAsync`, so a stop on conflicts is `OperationOutcome.Conflicted`; non-interactive only. A target starting with `-` is refused.
- **Quick rebase** (`IQuickRebaseWriter`, `QuickRebaseWriter`; #459): fixup, reword and drop of one commit on top of the interactive engine. `PlanAsync(location, kind, commit)` reads the parents (`rev-list --parents -n 1`, twice for a fixup), picks the base (the parent, two back for a fixup, `RebaseBase.Root` at the root), reads the range through the engine and the full message (`log -n 1 --format=%B`); it throws `RebaseRangeException` for a merge commit, a commit outside the history of HEAD, or a fixup with nothing before it. `RunAsync(location, plan, newSubject)` re-reads the range (a different one throws, nothing is rebased) and starts the engine with every other commit picked; a reword replaces only the first line of the message.
- **Interactive rebase** (`IInteractiveRebaseWriter`, `InteractiveRebaseWriter`; #399 the engine, #458 the todo editor on top of it, ux.md workflow 3): `ReadRangeAsync(location, RebaseBase)` lists the commits of `<onto>..HEAD` (or all of HEAD for `RebaseBase.Root`) oldest first with `log --topo-order --reverse -z`; an empty range throws `RebaseRangeException`, and so does a merge commit in the range unless `RebaseBase.KeepMerges` is set (`RebaseBase.WithMerges()`, #461). Keeping merges: when the range has a merge, `ReadRangeAsync` lets git prepare the `--rebase-merges` todo and reads it (`-c core.editor=true -c core.abbrev=no -c rebase.abbreviateCommands=false -c rebase.instructionFormat=%s -c sequence.editor='echo <marker>; cat "$1"; false' rebase -i --rebase-merges --no-update-refs --no-verify`; the editor prints the todo and fails, so git stops before changing anything, restores an autostash and exits 1) into lines with `Action` `Pick`, `Merge` (hash of the merge, `Argument` = labels and `# oneline`), `Label` or `Reset` (name in `Hash`). `RebaseTodoParser` refuses any other command word rather than dropping it. A range without merges is the plain commit list even with `KeepMerges`. `RebaseAsync` takes the same lines as `RebaseTodoEntry` (`Argument` for a merge) and adds `--rebase-merges` when the range has structure lines. The validator also requires every label, reset and merge line to stay and a merge to stay a merge, every label to come before the reset or merge that names it, and no squash or fixup at the start of a line (the start or right after a reset); names no label defines (original commits git resets to for cousins) are left to git. The dump skips the `pre-rebase` hook (`--no-verify`) and `rebase.autoSquash` (`--no-autosquash`); the real start runs the hook. It is the one read that starts a rebase (it creates and removes `.git/rebase-merge` and, with `rebase.autoStash`, stashes and re-applies local changes), so it is refused while an operation is in progress, and a cancel or timeout runs `rebase --abort` on what it left; a refresh in that moment can see a rebase in progress for a few milliseconds. `RebaseAsync` takes one `RebaseTodoEntry(Commit, Action, Message)` per commit in replay order (`Pick`, `Reword`, `Squash`, `Fixup`, `Drop`), validates it against the range (every commit exactly once by full hash, nothing omitted, the first kept entry is not a squash or fixup, a reword has text; `RebaseTodoValidator`) and runs `git -c core.editor=true -c sequence.editor=<cmd> rebase --interactive --no-update-refs --empty=drop <onto>^{commit}|--root` through `OperationRunner`, so a stop on conflicts is `OperationOutcome.Conflicted` and the banner and continue, skip and abort of the operation flow take over. The sequence editor is the `SequenceEditorCommand` (in production `gitunia --sequence-editor`, handled first in `Program.Main`, no UI and no repository discovery) followed by the prepared todo; it copies that file over git's todo (`SequenceEditor.Copy`), so no new environment variable is set. A set `GIT_SEQUENCE_EDITOR` would win over the config and is refused with `RebaseEnvironmentException` (not a range error). The command must be the published binary: under `dotnet run` the process path is the `dotnet` host, which is not supported as an editor. A reword is `pick` plus `exec git commit --amend --allow-empty -F '<file>'`; the message and todo files live in `<git dir>/gitunia-rebase/` (per worktree) and are deleted once no operation is in progress after the call (completed, or git refused to start), and kept while any rebase is stopped (a conflict, a hook rejecting an exec line, a cancel: the later exec lines run on continue), and a stale directory is removed by the next start when no operation is in progress. A squash keeps git's combined message (`core.editor=true`). `InteractiveRebaseResult.OriginalHead` is the undo hint (`git reset --hard <OriginalHead>`; `ORIG_HEAD` and the reflog hold it too); abort returns there. Redundant commits that become empty are dropped (`--empty=drop`, as the plain rebase does).
- **Commit** (`ICommitWriter`): `CommitAsync(location, CommitRequest(Message, SignOff, NoVerify, Amend))` runs `git commit -F - [-s] [--no-verify] [--amend]` with the message on stdin kept as typed (the `-F` default cleanup is `whitespace`, so `#` lines stay) and a 10 minute timeout for hooks. It returns the new HEAD plus the previous hash for an amend. `ReadHeadMessageAsync` reads HEAD's message for Amend. Hook and signing output comes back in `GitCommandFailedException`. Commits through `$EDITOR` are not a runner call.

  - **Lane order (#757).** A commit no lane waits for (a branch tip) takes the leftmost free lane. The log is read newest first, so the branch with the newest tip is leftmost, the next newest right of it, and so on; the checked-out branch gets no lane of its own and the layout never reads HEAD (the lane 0 reservation of #308 was removed, with `ReadHeadLayoutAsync`).
  - **One lane per branch (#759).** A commit's first parent continues the commit's own lane even when another lane already waits for it, so every lane runs down to the commit it forked from, where the lanes join (several `Incoming` edges). Where several lanes wait for one commit its node takes the leftmost of them (the newest tip's) and the others bend into it; branch names on commits of a lane are labels only. Second parents still join an existing lane at the merge row. A new branch off an old commit also keeps its lane open down to its fork, so such a reload joins the old rows only below that fork.
  - **Colours (#761).** `GraphLayoutBuilder` takes the branch name of every tip (`BranchColors.TipsOf` of `ReadTipDecorationsAsync`, null when the read failed: lanes are then coloured by their first commit). A lane gets the colour of its branch name (hash, moved on to a colour no open lane and no branch tip of the last 50 rows uses (#807), out of as many colours as the palette has: `GraphLoader` reads `Palette.LaneColorCount`; local and remote of one name share it; the name of a commit with several is its checked-out branch, else the smallest local name); `GraphEdge.Color` and `GraphRow.NodeColor` carry the slot and the fingerprint includes it, so a reload only joins rows with the same open-lane colours. Limits: the recent tips (#807) are not in the fingerprint, so after an incremental reload a tip within 50 rows below the join may keep a colour that a full read would have moved on (two nearby branches may then share one until the next full read); the tips are read by a separate git process started with the log, so a ref that moves between the two reads gives a lane colour from the other state until the next refresh; when that read fails the lanes are coloured by their first commit and an automatic reload reads the whole log.
    - **Chip colours (#849).** `GraphRow.LabelSlots` holds one `BranchSlot` (short name, slot) per branch name of a commit, from `BranchColors.TipsOf` (first name) and `ExtraNamesOf` (the others); the name that starts the lane has the lane slot, every other name its cached name slot moved on to one that no open lane or recent tip uses, and each is recorded as a recent tip, so stacked branches on one lane differ; `GraphRowRenderer` colours the chip from it (the hash slot of the name when the row has none for that name).
- **Polling (default, #543).** No file watchers are created unless `watchFiles` is set in the config. Each .NET `FileSystemWatcher` takes an inotify instance, a scarce per-user resource (128 on many systems), so other clients poll and so does Gitunia. `TabPoller` (`Gitunia.Tui/App/Tabs`) polls the active tab only: every 2 s `RepositoryFingerprint` (a hash of name, size and time of the files in the git directory, `refs/` and `worktrees/`, off the UI thread) and, when it changed, a refresh of everything (the graph reloads only if HEAD or refs differ); otherwise a working tree status refresh when 5 s have passed. A refresh that took t postpones the next status refresh to at least 5 t (at most 60 s), so a big repository is not kept busy. A tick is skipped while the tab refreshes or runs an action (`IsTabBusy`), never overlaps a running fingerprint read, and a hidden tab does not poll: it checks at once when shown again (background tabs keep `BackgroundStatusPoller`, 30 s). Gitunia's own actions refresh the tab right after they finish (`EffectRunner.Refresh`/`RefreshStatus`). `PollOptions` holds the intervals. When the terminal gains focus the active tab checks at once (`TabPoller.CheckNow`: fingerprint read now and a status refresh due, skipped while busy), as when a tab is shown. Focus reporting (DECSET 1004, `ESC [ I` in / `ESC [ O` out) is not provided by Terminal.Gui v2, so `TerminalFocusReporting` (`Gitunia.Tui/Input`) enables it with `WriteRaw` and registers the two sequences as persistent expected responses on the driver's ANSI parser, which keeps them out of the key handling; it is switched off again before the driver is disposed (also around a suspended external tool). Linux, macOS and Windows (the Windows driver enables Virtual Terminal Input mode and has the same ANSI parser; a focus-in sequence injected into a running Windows 11 build refreshed the tab, #651; classic conhost may not report focus, then only the poll runs); other OSes are an explicit unsupported path: focus just does not refresh there. Limit: a process killed by a signal cannot switch the mode off, so the shell may echo `^[[I`/`^[[O` on focus changes until `reset`. `<space>r` is the manual refresh.
- **Watching (opt-in).** `"watchFiles": true` (read at startup) gives each open tab a `RepositoryWatcher` instead of the poller: it watches the git directory, the common directory (linked worktrees), `refs/`, `worktrees/` and the working tree with `FileSystemWatcher`. `RepositoryChangeClassifier` maps a path to `RepositoryChangeKinds` (head, refs, index, working tree, worktrees, operation; lock files, objects and logs are ignored). Events are merged and debounced (200 ms quiet, at most 2 s under a continuous stream); the callback gets the merged kinds on a thread pool thread.
- **Background tabs.** `SetActive(false)` marks a tab as background: it keeps pending kinds, reports nothing, and `IsStale` is true (`BecameStale` fires once). `SetActive(true)` reports them at once. Background tabs refresh on activation.
- **Budget and fallback (opt-in watching).** `WatchBudget` caps watchers across all tabs (64 by default; a tab needs 3 to 6). A tab that cannot get its slots, or whose watcher fails to start or errors (for example the inotify limit), polls every 5 s instead: a cheap fingerprint of the git directory, refs and worktrees files, plus a working-tree status refresh on every tick. Working-tree watching is ignore-aware (#83): a recursive `FileSystemWatcher` costs one inotify watch per directory on Linux, ignored ones (`node_modules`, `bin/obj`) included, so the root gets a non-recursive watcher plus one per directory that `WorkingTreeDirectoryLister` finds with a single `ls-files -z --cached --others --exclude-standard` (directories holding tracked or non-ignored files, and their parents). These directory watchers do not use `WatchBudget` slots; they are capped per tab (`MaximumWorkingTreeDirectories`, 2048) and a larger tree polls; the cap is not the binding limit, see the instance limit below. The listing runs off-thread after `Start`. A created directory (with its subdirectories) is watched at once (and listed again twice once the watchers are live, so a `mkdir -p` race loses nothing), because it may be empty and unknown to git, and triggers a rescan (serialised, coalesced) that adds listed directories and drops watched ones that git does not list and that are gone or hold files (ignored); an empty one stays. Changes to ignored files inside a watched directory still report `WorkingTree` (the status refresh finds nothing). If the listing fails, the working tree is watched recursively as before. Only Linux uses this mode (`EffectRunner` passes the lister there); Windows and macOS keep one cheap recursive watcher. A new directory is watched with at most 64 subdirectories before the rescan, and a rescan that fails after the first one keeps the current set. Limits: files written between `Start` and the first listing (~330 ms measured on a 10k-directory tree, off-thread) are missed; directories that hold only ignored files or are empty at start (for example `logs/` with `*.log` ignored) are not watched, so a new non-ignored file there is noticed at the next refresh or any other event, not at once; submodule contents are not watched. Per-directory watchers (up to thousands) are created outside the watcher's lock (plan under the lock, create, install under the lock); `Start`, the recursive root fallback and the `worktrees` directory still create their one to six watchers under it. Measured numbers are in `docs/performance.md` ("Working tree watching"). Each .NET `FileSystemWatcher` takes one inotify instance, so the per-user `max_user_instances` limit (128 on many systems, 1024 here) binds before the 2048 cap: with watching on, the per-tab cap is a quarter of that limit read from `/proc/sys/fs/inotify/max_user_instances` (`InotifyLimit.DirectoryCap`, at least 16, at most 2048); hitting a limit falls back to the watcher's own polling (#543).
- **Incremental refresh.** `RepositoryRefresher.RefreshAsync(location, previous, kinds)` re-reads only the sections the kinds can affect (head and refs together, worktrees, status; operation files are always checked) and returns the new `RepositorySnapshot` plus the `RepositorySections` that actually differ. Unchanged sections keep the previous object, so views compare by reference and a refresh never resets scroll or selection.
- **Background status.** `BackgroundStatusPoller` runs `git status` for every non-active, non-missing tab, sequentially, at start and every 30 s, and dispatches only when the summary changed. It loads nothing else, so unvisited tabs stay cheap; tab bar markers lag by up to the interval. Status polling uses `--untracked-files=normal` (the tab bar only needs to know the tree is dirty).
- **Worktree overview.** `WorktreeOverviewPoller` runs `git status` (untracked files listed individually, like the tab's own read) in every other worktree of the active tab, one at a time, when the tab or its worktree list changes and every 30 s, because changes there raise no event for this tab. Bare and prunable entries are skipped, an unreadable worktree keeps its last value. The tab's own worktree is counted from its live `WorkingTree` snapshot. Switching a tab to another worktree (`SwitchWorktreeCommand`) replaces its location and runs the load effect again (new session, refresher and watcher); the view state, refs and sidebar stay.
- **Working-tree state.** Every loaded tab keeps the full `StatusSnapshot` in `RepositoryState.WorkingTree` (snapshot plus the selected file by section and path). A new snapshot replaces it and re-finds the selection (same path and list, else the same path in the other list after a stage or unstage, else the row near the old index); a snapshot with the same content returns the same state, so a refresh never repaints or loops. The background poller updates only the summary, so a background tab's snapshot may be older than its markers until the tab is activated. After stage or unstage the cursor stays at the same index of its list. List order is git's order; any display ordering is applied in the state layer so indexes stay the row indexes.
- **Wiring.** `TabRefresher` (`Gitunia.Tui/App`) is created by the effect runner when a tab's load starts and owns that tab's `TabPoller` (or, with `watchFiles`, its watcher). After the initial load it records a baseline snapshot (and reloads the graph when a change was seen meanwhile or the loaded graph's decorations differ from the baseline refs). Each change then runs `RefreshAsync` off the UI thread (one at a time; changes arriving meanwhile are merged) and dispatches commands only for the sections that differ (stashes are re-read when HEAD or refs changed). Failures are reported once through `StatusChannel`; a manual refresh (`<space>r`) always reports its outcome.
- **Graph reload.** The graph is swapped in only when HEAD or refs changed, or on manual refresh. An automatic reload is incremental (`IncrementalGraphLoader`): it streams the new log from the top and stops at the first row equal to the old graph (same commit, lane, edges and open lanes below it, found by `GraphSplicer` via `GraphRow.LaneFingerprint`), checks the total with `rev-list --count`, re-reads the refs of the few ref-carrying commits (`--no-walk`, started with the log: the layout needs the branch names for the lane colours, #761) and reuses the old rows below. A branch added, deleted or moved onto a reused commit keeps the old rows (only their refs are replaced), because a branch name only picks a lane colour where a lane starts (its chip colour is not redone, see Limits): `GraphRow.ColorChosenByName` marks the branch tips and the second parents that started a lane. The full read is the fallback only when the primary branch name (`BranchColors.PrimaryName`) of such a marked commit changed (a branch moved onto the tip of another branch, or deleted from it); tags never matter. Measured on the 100k-commit repository (#795): ~90-140 ms for a branch created, moved or deleted on an old commit or a checkout, against ~1 s before. Any mismatch falls back to the full read; a manual refresh always reads everything. The selected commit stays selected and on the same screen row.
- **Soft row limit (#515).** A log longer than `GraphLoader.SoftRowLimit` (100,000) loads only its newest rows (`StreamCappedAsync` reads one row more to know, then `rev-list --count` for the total). `RepositoryLoader.ExpandAsync` streams the whole log again later and appends the rows below the cut (skipping the shown ones, checking the last shown id); a replaced graph (refresh) makes a running expansion stale. A refresh of a cut tab reads the newest rows again instead of splicing. Numbers: `performance.md`.
- **Limits.** A branch name added or renamed by an incremental reload on a reused commit (one that did not choose a lane colour) has no `LabelSlots` entry, so its chip takes the hash colour of its name (12 slots, the palette applies its modulo), which may equal a neighbour's, and its chip colour is not seen by the lanes that start within 50 rows below it, like the recent tips of #807 (#849); the next full read corrects both. A selected commit that disappeared keeps the old row position. A branch name that starts two lanes (a local and a remote branch of one name on different commits) shares one colour slot, cached graph-wide while laying out; when a new top row takes that slot first, the lower lane start keeps its old colour until the next full read (cosmetic; also true before #795). An incremental reload trusts the old rows below the join, so history rewritten below it without changing the commit count (for example a `git replace` ref) is only picked up by a manual refresh.
