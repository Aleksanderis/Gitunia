# Architecture

## Overview

```
Terminal (keys, mouse, resize)
   |  raw input / VT sequences
   v
Rendering layer  <----  View model (what to draw)
   ^                         ^
   | commands                | state
   v                         |
State layer (pure: (State, Command) -> (State, Effects))
   |  effects
   v
Git layer (async, cancellable) ---- spawns `git` ---- repo on disk
```

- standalone workspace model. `AppState` holds a `Workspace` (ordered repo tabs, active tab, recent/pinned repos) and each tab owns an independent `RepositoryState` (graph, selection, scroll, status, worktrees). Commands are routed to a tab by id; effects carry the repo path they run against. The app starts without any repo (empty workspace shows the repo picker) and restores the previous session when there is one.
- persistence (open tabs, recents, pins, per-tab view state, config) lives in the user config/state dir, written atomically; a corrupt or missing file must never prevent startup.
- three layers, strictly one-way dependencies: Rendering -> State -> Git. Git knows nothing about state or UI; State knows nothing about the console.
- State is pure and testable without a terminal. Effects (run a git command, open an editor, copy to clipboard) are returned as data and executed by a runner that feeds results back as commands.
- all git calls are async, cancellable and time-bounded; the UI never blocks on them.
- Terminal.Gui v2 is the UI toolkit; the rendering layer wraps it and the state layer never sees it. Custom drawing (commit graph, diff) goes in custom views; modal keys and chords are handled at the application level by our keymap engine. Settings and pitfalls (iteration rate, streaming list source, key handling) and the measured numbers are in "Design notes" below. The custom-renderer spikes were rejected on readability and maintenance cost, not speed. A custom renderer may be added later as a separate project, so keep Terminal.Gui types out of Core and keep view models and key events renderer-agnostic (no abstraction interface until a second renderer exists; see `docs/decisions.md`).

## Solution layout

```
src/
  Gitunia.Platform/   the only OS-specific code: config/state dirs, console capability detection
  Gitunia.Git/        process runner, parsers, readers (instance classes with an interface where the Tui consumes them), repo/worktree/branch/graph models; folders by domain: Commits, Diff, Execution (runner, version, exceptions), Refs, Repositories, Status, Stash, Watching, Worktrees; each has a `Models/` subfolder where records and enums are many; shared `ObjectId` and `ParseResult` stay in the root
  Gitunia.Core/       state, commands, effects, keymap, mouse map, config (no console, no process); folders by domain (Keymap and Search with a `Models/` subfolder, Workspaces with Panes, Repositories and Tabs subfolders, ...)
  Gitunia.Tui/        renderer, input, views, app entry point (AOT publish target); folders: Rendering (no Terminal.Gui types; subfolders Details, Diff, Graph, Panes, Screen, Sidebar, Styling, Tabs, Overlays), Views (Terminal.Gui views; subfolders Lists, Theme), Input (key and mouse translation, keymap and mouse controllers; Drag subfolder), Loading (streaming from git; subfolders Commits, Diff, Graph), Search (graph search and jump-to-ref prompts), App (wiring: workspace host, effect runner, action router; subfolders Clipboard, CommandLine, Details, Overlays, Panes, Sidebar, Tabs)
  Gitunia.CustomRenderTui/  parked alternative renderer (cell buffer, VT input, raw terminal); not referenced by the app, not actively maintained
samples/              runnable demos and reference spikes (not referenced by the app, not maintained)
tests/
  Gitunia.Git.Tests/  against real temp repos
  Gitunia.Core.Tests/ pure state/keymap tests
  Gitunia.Tui.Tests/  snapshot tests of rendered frames
  Gitunia.Platform.Tests/
  Gitunia.CustomRenderTui.Tests/  cell buffer diff and input parser tests
tools/
  ConPtyHarness/      Windows pseudoconsole smoke harness (standalone, used by the custom renderer workflow)
scripts/              helper scripts (bash and PowerShell): fixture and big-repo generators, measurement harness
```

Folder rule: domain first, technical kind second (`Models/` for records and enums), namespaces follow folders, and every test project mirrors the folder and file names of the code it tests (`Commits/CommitLogParserTests.cs`); shared test helpers sit in the folder of their domain or in `Fixtures/`. Unused usings fail the build (IDE0005; it needs `GenerateDocumentationFile`, so the missing-doc, partial-param-doc and broken-cref warnings that brings are silenced in `Directory.Build.props`). Small `Models/` folders (Refs, Watching, Execution) stay for consistency.

Dependencies: Tui -> Core -> Git -> Platform (Tui also -> Platform). Build config is in `Directory.Build.props` / `Directory.Packages.props` (central package management); `IL*` (AOT/trim) warnings fail the build through the global `TreatWarningsAsErrors`. Adjust here when the layout changes.

## Native AOT constraints

- No runtime reflection: use source generators (`System.Text.Json` source gen, `LoggerMessage`, etc.). No Newtonsoft, no Castle-style proxies, no DI container needing runtime codegen (plain constructor wiring is enough).
- `PublishAot=true` and trim/AOT analyzers on from the first commit, warnings as errors for `IL*` codes.
- CI (and every dependency addition) runs the AOT publish and a smoke test of the produced binary.
- Targets: linux-x64 first, then linux-arm64, osx-arm64, win-x64.

## Static or instance, and the composition root

- Static: pure parsers, formatters and layout (`CommitLogParser`, `RefParser`, `DiffParser`, `GraphLayoutBuilder`, ...). Same input, same output, no I/O, no clock, no cache, no state.
- Instance: anything that spawns a process, touches the file system, reads a clock or keeps a cache. These are small sealed classes that take what they use in the constructor (`GitRunner`, `TimeProvider`, `IPlatform`, other readers) and have no static state. The git readers (`CommitLogReader`, `CommitDetailsReader`, `StatusReader`, `DiffReader`, `RefReader`, `StashReader`, `RepositoryRefresher`, `RepositoryDiscovery`, `GitVersionDetector`) take a `GitRunner` and get the repository as a `RepositoryLocation` argument on every call, so one reader serves every tab. `RepositoryOperationDetector` (reads the state files) and `FramePrinter` (reads through `GitServices`, writes to a `TextWriter`) are instances too: a class with I/O is an instance even when it has no dependency yet, so it can be injected and faked (#269). The analyzer's CA1822 does not fire on an interface implementation.
- Interface: only where another layer consumes the class and tests need a fake. The Tui's effects and loaders depend on `ICommitLogReader`, `ICommitDetailsReader`, `IDiffReader`, `IRefReader`, `IStatusReader`, `IStashReader`, `IRepositoryRefresher` (each has a fake in `tests/Gitunia.Tui.Tests/Fakes`) and `IRepositoryOperationDetector` (stubbed inline in the refresher test); classes nobody fakes (`RepositoryDiscovery`, the loaders) have none.
- Composition root: `Program.Main` creates the `GitRunner` and calls `GitServices.Create`, which wires every reader and loader by hand (no DI container: it needs reflection or codegen, and costs startup) and passes the `GitServices` record to the application. Tests build the same record (`TestGit.Services`) or swap one part with `with` and a fake (`tests/Gitunia.Tui.Tests/Fakes`).

## Performance targets

- Cold start to first frame: < 100 ms with a warm git cache.
- Commit graph: open a 100k-commit repo and scroll without dropping frames. Load incrementally (`git log` streamed, paged); never materialize the whole graph eagerly in the UI.
- Many tabs: background tabs hold only compact state and are refreshed lazily or on a throttled timer; only the active tab does continuous work. Tab switch is instant (no reload).
- Memory: compact commit model (struct-of-arrays or interned hashes), virtualized lists.
- Render: diff against the previous frame, write one buffered flush per frame.

### Verified numbers (many restored tabs, #111)

`scripts/measure-tabs.sh <binary> --tabs 12 --runs 7` builds throwaway repos (300 commits each) and a session file in a temp state directory, then restores them under tmux (120x40, Native AOT linux-x64, medians, 1-3 ms polling floor included):

| Metric | Result |
|---|---|
| Cold start to the first frame of the active tab, 12 tabs restored | ~50 ms (max of 7 runs 57; run `--runs 20` for a real p95) |
| RSS after start (only the active tab loaded) | ~36 MB (1 tab restored: ~52 ms, ~36.7 MB) |
| First visit of a background tab (`gt`, includes its load) | ~37 ms (max 48) |
| Switch back to an already loaded tab | ~10-30 ms (single sample, poll-bound) |
| RSS after visiting all 12 tabs | ~46 MB (20 tabs: ~50 MB) |

Restoring many tabs costs no start-up time or memory beyond the active tab (lazy loading, #91); each visited small tab adds roughly 0.5-1 MB. Decision: background tabs do not load when idle; the first-visit cost is well inside the budget and an idle preload would only add memory and git processes. Background tabs get their dirty/ahead/behind markers from `BackgroundStatusPoller` (#129): `git status` only, one tab at a time, once at start and then every 30 s, with no graph, refs or watchers loaded. Larger repos cost more per visited tab (the 100k-commit figure below, ~73 MB, applies per tab of that size).

### Verified numbers (graph view, #22)

Native AOT linux-x64 binary (9.9 MB plus the 564 KB native library), 100k-commit repo from `scripts/gen-big-repo.sh`, `scripts/measure.sh` medians (they include 1-3 ms of tmux polling), Terminal.Gui at 100 iterations per second:

| Terminal | Cold start to first rows | `j` latency | `Ctrl-d` | 200 queued `j` settle | RSS with all 100k loaded |
|---|---|---|---|---|---|
| 80x24 | ~72 ms (p95 106) | ~7.5 ms | ~7 ms | ~15 ms | ~69 MB |
| 120x40 | ~80 ms (p95 101) | ~7.3 ms | ~7.6 ms | ~14 ms | ~73 MB |
| 200x60 | ~89 ms (p95 106) | ~8.8 ms | ~11.7 ms | ~16 ms | ~73 MB |

The first 150 commits are on screen at once; the whole log streams in and is laid out in ~0.8 s without blocking input (the status bar shows `n/total+` while loading). A search over all 100k loaded commits (`/` then a query with no match) takes ~70 ms in 5000-row slices and does not change key latency (`j` ~7.4 ms, cold start ~82 ms, RSS ~73 MB). Idle CPU after loading is ~1%. Memory per loaded commit is ~340 bytes (ad hoc measurement: managed heap growth for 100k synthetic `GraphEntry` values with short subjects, not a repeatable script; a compact `GraphEntry`, not the full `CommitInfo`); an automatic refresh that moves HEAD or refs reloads incrementally (~105 ms for one new commit instead of ~840 ms, #126; the manual `r` always reads everything); frame cost depends on the visible rows only, not on the number of loaded commits. A narrow window cuts the newest subject, so the harness's resize check cannot find its marker there (`resize_ms=nan` at 80x24 is that, not a failure to redraw). RSS re-check (#191): a measurement reported ~107 MB, most likely taken with a restored session of the user (extra tabs, saved scroll position; it could not be reproduced). With state isolated, the build before the graph columns (#168) and the current one both give ~75 MB, so columns and author date cost nothing measurable (a hypothesis for the 107 MB, not a proven cause; per row they add a 16-byte date and a reference to an already interned name, ad hoc estimate ~2.4 MB per 100k rows); `scripts/measure.sh` now isolates state. `jump_to_end_ms=nan` (#192) was a harness fault, not an app bug: default markers are now 20-character prefixes (long subjects are ellipsized, the newest also carries ref decorations) and the jump waits for the log to finish streaming, since `G` goes to the last loaded commit (~25-30 ms afterwards). At 80x24 the newest row is cut inside the marker, so pass an explicit `--marker "Commit #97500"` there. Known limit: the wide-character table in `TextWidth` covers CJK and the main emoji blocks only, so some newer emoji count as one column and can make a row one cell too wide.

Commit details while moving (#215): stepping to the next commit shows its details in ~20 ms (harness floor ~16 ms; was ~118 ms) because `CommitDetailsStore` reads the next 3 and previous 1 commits ahead into an LRU cache (64 entries, 20,000 changed files in total) and starts a selection that follows a pause without the 80 ms debounce. Holding a key still waits for the debounce (~110-130 ms to the last commit's details) and cancels stale reads. Details: `docs/decisions.md`.

Diff while moving (#225): with the diff pane beside the Changes file list, `j`/`k` to the filled diff took ~37 ms (details plus one diff run). `DiffStore` now keeps a bounded LRU `DiffCache` (12 diffs, 16,000 rows in total, a few MB; a diff over the budget alone is not cached) and, once the shown diff has loaded, reads the same neighbours as the details prefetch (3 ahead, 1 behind, one at a time, after an 80 ms pause, cancelled when the selection moves) with at most 4,000 rows each; bigger neighbours load on demand as before. Result ~20 ms (harness floor ~16 ms) on the 100k repo and on a repo of 3,000-row commits; cold start and RSS unchanged on the 100k repo (+~6 MB on the 3,000-row repo). A tab that is switched away from drops its cache. Details: `docs/decisions.md`.

## Cross-platform

- Linux, Windows and macOS are all supported targets; macOS is the lowest priority and may be dropped if it adds significant complexity. Build and test on Linux first, and add Windows/macOS to CI in M4.
- Platform-specific code lives behind a small abstraction in one place (config/state dirs: XDG / `%APPDATA%` / `~/Library`; console setup: raw mode and VT input/output; resize notification: SIGWINCH vs console events; process spawning and signals; file watching quirks). Every abstraction has an implementation or an explicit "unsupported" result for each OS.
- Never hardcode path separators, `/tmp`, `/dev/null` or line endings; handle case-insensitive file systems, long Windows paths and CRLF in diffs.
- Terminal features are capability-detected (truecolor/256/16, Unicode width, mouse, OSC 52), not assumed.

## Design notes

Details moved out of `decisions.md` (#253), roughly in the order it was decided. Notes are historical: where a later note contradicts an earlier one, the later one wins. Dates are those of the original log entries.

- Fourth project `Gitunia.Platform` (config/state dirs, console capability detection) referenced by Git and Tui; Core stays free of OS code. Why: issue #1 requires the platform abstraction in one place and Core must not touch the console or process. SDK pinned to 10.0.400 with `rollForward: latestFeature`; test projects use xUnit v3; test method names may contain underscores (CA1707 off under `tests/`).

- Renderer: Terminal.Gui v2 (2.5.0), not a custom renderer (decision #7, owner chose after reviewing the spikes). Why: the custom renderer code was judged far harder to read and maintain than toolkit widgets, and Terminal.Gui is fast enough. Accepted costs: startup near the 100 ms budget, larger binary and memory, a native library beside the binary, modal keys/chords hand-rolled at the application level (no modal keymap in the toolkit), custom drawing for the commit graph. Spike data (Linux x64, 100k-commit repo, `scripts/measure.sh` medians incl. 1-3 ms tmux polling):
  - List-only spike, Terminal.Gui vs custom: binary 9.47 MB + 564 KB native lib vs 2.56 MB; cold start ~97 ms vs ~28 ms; `j` latency ~34 ms vs ~4.8 ms; RSS ~50 MB vs ~33 MB.
  - Heavier M1-like screen (sidebar, graph, details, status) at 120x40: Terminal.Gui cold start ~107 ms, `j` ~34 ms, RSS ~71 MB; custom 24 ms, 7.4 ms, 35 MB.
  - Both AOT-clean on Linux and Windows (win-x64 smoke under ConPTY in CI passed 8/8 for Terminal.Gui, 10/10 for custom).

- Terminal.Gui settings and pitfalls: set `Application.MaximumIterationsPerSecond` to ~100 (default 25 gave ~34 ms key latency; 100 gives ~13 ms and cold start ~85 ms at ~2.6% idle CPU; higher values busy-spin a core). Use an append-only `IListDataSource` for streamed commits (`SetSource(ObservableCollection)` rescans per add and freezes input). The focused `ListView` swallows keys, so handle keys at the application level (`app.Keyboard.KeyDown`). `TextView` is obsolete in 2.5.0 (a separate package replaces it); check its AOT status before M2 commit-message input.

- The renderer stays swappable, but only Terminal.Gui is built and maintained. The custom renderer lives in `src/Gitunia.CustomRenderTui` (cell buffer with diff flush, VT input parser, raw terminal for Linux/macOS/Windows) with a runnable demo in `samples/Gitunia.CustomRenderTui.Demo`, tests, and a manual-only Windows ConPTY smoke workflow. It is not actively maintained: not referenced by the app, features are not mirrored into it, and it is only kept building and tested in CI as a future option. It may rot; a revival starts with its README's 'missing' list. The spike branches were deleted once this landed; spike numbers stay in the issue comments and the renderer entry in `decisions.md`. What this requires of the main code: Terminal.Gui types stay in the rendering project, the state layer exposes renderer-agnostic view models and key events as data, keymap handling is our own engine, and no renderer abstraction interface is added until a second renderer is revived. If the boundary starts to cost features, tell the owner.

- The Terminal.Gui spike (#4 heavy screen) is preserved as a reference sample in `samples/Gitunia.TerminalGuiSpike` (also tagged `archive/spike-4-terminal-gui-heavy`); not referenced by the app and not maintained. Use it as a starting point for the M1 UI, rewritten against the state layer.

- Terminal.Gui look experiment (merged into that sample): the custom demo's look (header bar, tab row, dimmed hashes, lane colours, status hints) is achievable in Terminal.Gui with ~160 extra lines and no hard limits found. Minor limits: border title glyphs are fixed (workaround: overlay view), `ListView` has no per-row styling (custom `IListDataSource.Render`), colour-depth fallback unverified, wide chars and mouse untested. Measured on the 100k repo at 100 iterations/s: 120x40 cold start ~58 ms, `j` ~8-10 ms, RSS ~75 MB; 200x60 cold start ~98 ms, `j` ~20 ms (custom demo: 16 ms, ~4 ms, ~31-36 MB, flat with screen size). The renderer choice (Terminal.Gui vs CustomRenderTui) is still open for the owner to reconsider; M1 does not start UI work until it is settled.

- Graph lane layout (#16) lives in `Gitunia.Core/Graph`: `GraphLayoutBuilder` appends commits (children before parents) and yields immutable `GraphRow`s (node lane, lane count, `Through`/`Incoming`/`Outgoing` edges); `GraphLayout.Compute` is the batch form and gives the identical result for any chunking. A lane waits for exactly one commit id, so several children of one commit share a single incoming lane (the later children draw an outgoing edge into it); lanes are not shifted left, freed lanes are reused leftmost-first, and a parent missing from the stream keeps its lane open. Why: stable columns while scrolling and loading, O(open lanes) per commit.

- Keymap engine (#19) lives in `Gitunia.Core.Keymap`: bindings are `KeyBinding(mode, view, key sequence, action id)` rows in a `KeyBindingTable` with a view hierarchy (`Graph`/`Detail`/`Sidebar`/`Diff` inherit `Lists`, everything inherits `Global`; a more specific view shadows an equal sequence). `KeymapEngine.Process(state, key, view)` is pure, takes a renderer-agnostic `KeyEvent` and returns the next `KeymapState` plus an outcome; the app switches mode with `state.WithMode`. A binding that is a strict prefix of a longer one in the same view is reported as a conflict (no chord timeout, so it could never fire); when it happens anyway the longer chord wins. Key notation in code and docs is the `docs/ux.md` one (`Ctrl-w c`, `<space>o`); the `docs/ux.md` keymap row for `Ctrl-w h j k l` was split into four explicit chords so the doc test can parse it, and a `v` row (Visual mode toggle) was added. Arrow and PageUp/PageDown keys are bound in lists. Confirm mode deliberately has no `Enter` binding.

- Workspace state (#17) lives in `Gitunia.Core.Workspaces`: immutable records, `WorkspaceReducer.Reduce(Workspace, WorkspaceCommand) -> WorkspaceUpdate(Workspace, Effects)`, tab ids allocated from a counter in the workspace and never reused, commands for a closed tab are dropped (late git results). Tabs are deduped by `RepositoryLocation.RootPath` with a trailing-separator-insensitive comparer that ignores case on Windows and macOS. Closing the active tab activates its right neighbour (left if it was last); recents are capped at 50.

- Graph view (#22) is the first real Tui shell. Everything Terminal.Gui-specific is in `Views` (`GraphListSource`, an append-only `IListDataSource` that draws only the visible rows; `MainView`, `LineView`, `Palette`) and `Input` (`KeyTranslator`, `KeyController`: every key goes through `app.Keyboard.KeyDown` into the keymap engine, and a completed binding becomes an action id handled by `ActionRouter`). `Rendering` has no Terminal.Gui types: a row is a `StyledLine` of `StyledSegment`s with a `SegmentRole`, so `ScreenComposer` renders a whole frame as text for snapshot tests and for `gitunia <repo> --print-frame WxH` (a small diagnostic flag that prints one frame and exits; the CI smoke run uses it). `LoadRepositoryEffect` is executed by `EffectRunner`; results come back as `TabCommand`s on the UI thread through `WorkspaceHost`. A new effect (clipboard, file watching) adds a case to `EffectRunner.Run`, a new action a branch in `ActionRouter.Execute`. The streamed rows of a tab live in a `TabSession` beside the immutable `RepoState`, which still records the selected commit and scroll offset.

- Graph rows keep a compact `GraphEntry` (id, subject, author, time, decorations, lane row) instead of the whole `CommitInfo`. Lanes are laid out on the loader thread; batches (the first 150 commits, then 2000 or 40 ms worth) are appended on the UI thread. The lane area is as wide on every row as the widest row seen so far (at most 40% of the terminal), so columns do not jump while scrolling or loading. Each lane takes two columns, with box-drawing connectors and an ASCII fallback for terminals without Unicode. The slot for the working-tree pseudo-row is `ScreenLayout.ReservedLeadingRows` (0 until the staging view exists). Without a path argument the app still prints the banner and exits (no session restore or repo picker yet); `gitunia <path>` opens one tab. Numbers are in "Verified numbers" above.

- Terminal.Gui findings for #22: a `ListView` over a custom source with `MaxItemLength` 0 and one `Reset` change event per appended batch keeps its selection and viewport while 100k rows stream in; an Esc followed by a key within a few milliseconds arrives as `Alt-<key>` (a terminal limitation, not a bug; people type slower than that, scripts must send them separately).

- Session persistence (#18) lives in `Gitunia.Core.Persistence`: `SessionStore` reads and writes `session.json` in `IPlatform.StateDirectory` (tabs with their repository location and view state, active tab index, recents, pins), schema `version` 1, System.Text.Json source generation (`SessionJsonContext`), saves via `AtomicFileWriter` (temp file in the same directory, flush to disk, rename over the target). Loading never throws: a missing file gives an empty workspace; an unreadable, oversized, malformed or other-version file is renamed to `session.json.corrupt` and an empty workspace is used (the result carries a message for the status line). Bad entries inside a valid file (relative paths, duplicates, unknown pane, bad commit id) are skipped or defaulted. Tabs whose directory vanished are restored flagged `IsMissing`; the others get a `LoadRepositoryEffect`. Per-tab data beyond the view state (head, refs) is not stored; it reloads. The user config file (`ConfigDirectory`: keymap and theme overrides) is not part of this change since no setting exists yet; it gets its own versioned file when the first setting lands. The app wires load at startup and save on change (debounced) when the Tui workspace host exists.

- Graph search and jump to ref (#26): the pure parts live in `Gitunia.Core.Search` (`SearchQueryParser`, `GraphSearchMatcher`, `GraphSearchScanner`, `GraphSearchReducer` with `GraphSearchState`/`Command`/`Effect`, `RefJumpResolver`, `FuzzyMatcher`, `PromptTextEditor`); the Tui side is `SearchController` and `RefJumpController` behind `IPromptHandler` (the router offers every action to them first, Insert-mode keys reach them through `KeyController.TextKeyHandler`). Search state is per tab and lives in `TabSession.Search` (not persisted). Scanning runs on the UI thread in slices of 5000 rows queued one by one (a full 100k scan takes ~70 ms), so no other thread touches the non-thread-safe `CommitGraph`; a newer query bumps a generation counter and the older slices stop; because the whole log streams in anyway, "load on demand" is the scan following the stream (`GraphGrewCommand`) rather than a second process. Plain text matches the subject only: `GraphEntry` keeps no body, and a `--grep` log call would need a second process for little gain (follow-up if wanted). `gr` is a status-bar prompt, not a popup list (no overlay exists yet); the palette/help overlay work may replace it with a shared list overlay. Ref candidates skip symbolic refs such as `origin/HEAD`.

- Clipboard (#52): `Gitunia.Core.Clipboard` has `CopyToClipboardEffect(Text, Description)` (a `WorkspaceEffect`), `Osc52Environment.Detect(lookup)` (injected env lookup, never the process env: `TERM` `dumb`/`linux` -> unsupported, `TMUX` -> tmux passthrough, `STY` -> screen DCS chunks of 76 chars, else direct) and the pure `Osc52Encoder.Encode(text, options)` (UTF-8 base64, ST terminator, refuses empty text and payloads over 100000 base64 bytes, the xterm limit). `Gitunia.Tui.ClipboardWriter` is the only code that writes the sequence to the terminal and returns the status-bar message. OSC 52 gives no acknowledgement, so "supported" is a best guess: the success message says what to enable if the clipboard stays unchanged. Terminals and multiplexers: tmux needs `set -g set-clipboard on` or `set -g allow-passthrough on` (tmux 3.3+); GNU screen may need its own setup; some terminals ask permission or disable OSC 52 by default (e.g. xterm `allowWindowOps`, Alacritty `osc52`, Windows Terminal supports it). Wired in #78: `y` (`graph.copy-hash`) in the graph pane goes through `Gitunia.Tui.App.ClipboardCopier` on the UI thread (so the write cannot interleave with Terminal.Gui output), which posts the message on the `StatusChannel` (warning on failure, the status bar clips it to the screen width); when the console is not interactive no writer exists and the copier only posts a warning.

- Tab bar and repo picker (#21) and session wiring (#81). Core (`Gitunia.Core.Picker`) holds the pure parts: `PickerReducer.Reduce(PickerState, PickerCommand, PickerContext)`, the palette's `FuzzyMatcher` (name matches count double, ties go to the shorter name), `PathQuery`/`PathCompleter` (a typed path starts with `/`, `~`, `./`, `../` or a drive; relative paths resolve against the active repository or the home directory, never the process working directory), `PickerRowBuilder` (open, pinned, recent, discovered; one row per repository with all its tags) and `RepositoryScanner`. The file system reaches the picker only through `PickerContext` (injected functions), so tests use a fake. `PickerController` (Tui) owns the open picker, runs the scan and `RepositoryDiscovery` on the thread pool and posts results to the UI thread. Discovered repositories come from the conventional folders below the home directory (`Projects`, `src`, `code`, `dev`, `repos`, `git`, `work`, ... depth 3, at most 2000, hidden/dependency/symlinked folders skipped, found repositories not descended into), rescanned at most every 30 s when the picker opens; configurable scan roots wait for the config file (M4).

- Lazy tab loading (#91): `EffectRunner` creates every restored tab's `TabSession` (empty, `IsPending`) but starts the load (log, refs, status, sidebar data) only for the active tab; a background tab's load starts the first time it becomes active (it runs off the UI thread, so input is not blocked). Until first activation a background tab also has no HEAD, refs or dirty/ahead/behind markers in the tab bar, and a missing or broken repository is only reported then; a cheap status-only refresh of background tabs is tracked in #129. Decision (#111): background tabs are not loaded when idle (measured: ~37 ms first visit, ~0.5-1 MB per loaded tab, see "Verified numbers" above; a tab opened through the picker is always active, so it loads at once).

- The picker query is plain state edited by the keymap (printable keys arrive as `TextInput`; `Backspace` is handled by the app because the keymap leaves it unbound by design); while it is open the keymap runs in Insert mode with the `Picker` view. A repository that is already open is focused instead of opened twice (the reducer dedupes by root path). A missing tab is located through the picker (`LocatingTabId`): the chosen repository replaces it. Esc with no tab open quits.

- Session wiring (#81): `gitunia` restores the session at startup (`SessionStore.LoadAsync`; a discard shows its detail in the status bar until the first key), `gitunia <path>` opens or focuses that repository on top of the restored tabs, no tabs means the picker opens; `SessionPersistence` saves 500 ms after the last workspace change on a timer thread (skipping unchanged workspaces) and flushes on exit. A start without a path from a non-interactive terminal still prints the banner (the CI smoke run relies on it). Background tabs load lazily (#91, above). Tab bar markers (`RepoStatusSummary`: dirty, ahead, behind) are read when a tab loads and kept current by `TabRefresher` (#90): the first refresh after the load is a baseline that re-applies every section and reloads the graph if a change was seen meanwhile or the loaded graph's ref decorations differ from the baseline refs (`GraphRefCheck`, #161; a commit made between the load and the baseline read leaves no event to diff); later refreshes apply only differing sections and reload the graph only when HEAD or refs changed (or on `r`). Each tab keeps its selection and scroll: `GraphTabBinder` swaps the list source on tab change and restores them once the commit has streamed in.

- Sidebar (#23): the pure part is `Gitunia.Core.Sidebar` (`SidebarBuilder` turns a tab's refs, worktrees and stashes plus `SidebarState` (folded sections, filter, cursor) into `SidebarRow`s; `SidebarReducer` handles `SidebarCommand`s through `RepoReducer`, so cursor, folding and filter live in `RepoState` per tab). `PaneNavigator` (Core) does `Tab`/`Ctrl-w` focus movement over the open panes (sidebar and graph for now; detail and diff plug in by joining the available list). Stashes come from `StashReader` (`stash list --format=%gd%x00%H%x00%gs%x1e`; note `%x00`, the stash list command does not expand `%00`), worktrees from the existing `RefReader`; both load beside the refs in `SidebarDataLoader`. In the Tui, `SidebarActionHandler` takes pane-focus and sidebar actions before the graph router, `SidebarPresenter` keeps the `ListView` selection in step with the state cursor (a click goes back as a command), and `ScreenComposer` takes an optional `SidebarModel`. The sidebar is a quarter of the screen (20-36 columns) and hidden under 60 columns. `KeyController` gained `SetMode` plus `TextTyped`/`Erased` events for Insert-mode text entry (the sidebar filter is the first user). Loader tests post through a serializing `InlineUi` because the workspace host is single-threaded and several loaders now dispatch.

- Help, palette and which-key (#20): overlay state is pure (`Gitunia.Core.Overlays`: `OverlayState`, `PaletteState`, `FuzzyMatcher`, `HelpBuilder`, `PaletteEntryBuilder`, `WhichKeyBuilder`); action titles live in `ActionCatalog` (a test fails when a default action has none) and key text comes from `KeyFormatter`, so nothing is hand-listed. Rendering is renderer-agnostic frames (`Gitunia.Tui.Rendering.Overlays`: `OverlayFrame` of `StyledLine`s, snapshot-tested at several sizes) drawn by one `OverlayView` added last to the window. `OverlayController` (Tui/App) sits in front of the `ActionRouter`: while an overlay is open it consumes actions, in Command mode (palette) typed text reaches it through `KeyController.TextKeyPressed` and every key is swallowed so graph keys never fire. The overlays have their own keymap views, `Palette` (Up/Down, Command mode) and `Help` (inherits `Lists` so scrolling reuses the list motions). The which-key popup appears 500 ms after a chord prefix via `WhichKeyTimer` (a `System.Threading.Timer` that posts to the UI thread; stale callbacks are dropped by a generation counter). Overlays are not part of `--print-frame`: the frames are tested directly. The status-bar key hints gained `? :` with #93.

- Palette scope (#20 review): the palette lists every registered action (the acceptance line), including modal-internal ones; actions without behaviour yet show "<title>: not implemented yet" in the status bar. Hiding modal-only actions is left to the owner.

- Session save failures (read-only or full state directory) post one status error per failing streak (#93): `SessionStore.SaveAsync` returns false, the next change or the exit flush retries silently, and a later success re-arms the message. Replacing a missing tab opens the new repository first and closes the missing tab second, so a failed open never loses the entry.

- Status messages (#93): one global `StatusChannel` per window (not per tab) holds an immutable `StatusLog` of the last 50 messages; messages are single-line (newlines collapse), the newest shows until dismissed or replaced, and background code posts through the UI-thread dispatcher it already uses. Key-action notices (`ActionRouter.Message`) stay transient and are not logged, so the history does not fill with `not implemented yet`. Dismiss is `<space>x` (plus `Esc` in the graph), history `<space>m`, retry of failed commit details `r` in the Detail view.

- Incremental graph reload (#126): measured on the 100k-commit repo (`scripts/gen-big-repo.sh`): a full re-read after a refresh takes ~840 ms, of which ~780 ms is git producing the full log format (C# parse and layout cost ~35 ms; a hashes-only log takes 40 ms thanks to the commit-graph file). That is above the issue's 200 ms limit, so the reload is incremental: after one new commit it takes ~105 ms including the guard commands. The join needs the same commit, lane, edges and an equal `GraphRow.LaneFingerprint` (hash of the commits the open lanes wait for), because lanes depend on the topology above. Guards: `rev-list --count` must equal the spliced length (catches deleted or moved refs whose commits sit below the join), and new rows may not appear in the old graph in a different order. Refs below the join come from a `--no-walk --all` log since refs move without commits changing. Accepted limit: history below the join rewritten with the same commit count is not noticed until a manual refresh (`r` always reads everything). Limit accepted (#148): below the join every commit has the same id, and ids are content hashes, so its ancestors cannot differ; the cases that can still differ (a moved or deleted side-branch tip, a changed count, unshallowing) are caught by the count guard and the lost-tip check in `GraphSplicer.Splice`. What remains unguarded is a `git replace` ref (it changes the parents `git log` reports without changing ids) that keeps the commit count; no extra hash of rows below the join is worth its cost, and `r` resynchronizes. The issue's "retry" path is not a full read: a failed automatic refresh keeps the previous snapshot and reruns incrementally, which is correct since nothing was applied; only a failed manual refresh stays forced. The per-refresh copy of the old rows (`TabRefresher`, ~0.8 MB at 100k rows, needed so the background read does not see the UI list change) and the splicer's result list are accepted too. `TabRefresher` takes an optional `graphReloaded` callback that the wiring tests use to tell incremental from full reloads. Not taken: a topology-only two-pass reload (~120 ms of git alone plus parsing, little gain) and a stored parent list per row (memory).

- Faster commit details (#215): stepping `j`/`k` showed "Loading..." for ~118 ms per commit on both the 100k and a 5k repo (80 ms debounce plus two git processes, ~38 ms). `CommitDetailsStore` now (1) reads a selection that follows a pause of at least the debounce at once and keeps the debounce only for a quick run of moves (holding a key), (2) after the selection settled reads the next 3 and previous 1 commits (`DetailPrefetchPlan`, nearest first, one at a time, best effort) into `CommitDetailsCache`, and (3) cancels the load or prefetch of a stale selection (the git processes are killed). The cache is a true LRU bounded by 64 entries and 20,000 changed files in total (a commit over the file budget alone is not cached), so memory stays small and independent of the graph size and the number of rows (#199 bounds the graph itself, not this). Measured with `scripts/measure.sh` (`details_step_ms`: `j` until the details pane shows another commit and no "Loading...", 300 ms between steps): 118 ms before, ~20 ms after (the harness polling floor is ~16 ms); holding `j` (`details_burst_10j_ms`) stays ~110-130 ms, bounded by the debounce on purpose. Cold start and RSS unchanged (~82 ms, ~75 MB). Not done here (done in #225, see the diff prefetch note): the diff pane still loads when a commit is selected while it is open; one `git` process per commit instead of two was not needed once prefetch hides the cost.

- Diff prefetch (#225): measured `diff_step_ms` (new in `scripts/measure.sh`: `j` until the diff pane shows another commit): ~37 ms median on the 100k repo and on a repo with 3,000-row commits (details are prefetched, so this is one diff run), ~20 ms after. `DiffStore.Load` takes the neighbours (`DetailPrefetchPlan`, the same 3 ahead / 1 behind) and, once the shown diff has loaded or came from the cache, reads them one at a time after an 80 ms pause into `DiffCache`; the first parent of a neighbour comes from `rev-list --parents -n 1` (the details of a neighbour may not be cached yet). Any other `Load` or a tab switch cancels the prefetch (the processes are killed). Bounds (memory, #199): 12 entries and 16,000 rows (~100-200 bytes each) per tab, 4,000 rows per prefetched diff, cut-short diffs never cached, a switched-away tab releases its cache. Bigger commits are not prefetched (their on-demand load is unchanged). Prefetching them as a cached partial document (first rows shown at once, the rest read behind them) was tried and dropped (#235): on a repo of 40 commits with 20,000-row diffs `diff_step_ms` was 39 ms median / 48-71 ms p95 without it (the on-demand read of 20k rows is one fast `git diff`) and 53 ms median / 71-79 ms p95 with it (extra background reads plus the second read after showing), so the 4,000-row limit stays. Fixture: 40 commits, each adding one new 20,001-line file; the prototype was discarded (it only added an `IsPartial` flag to `DiffCacheEntry`, cached cut-short prefetches and re-read the diff in full on selection). "Prefetch only the first files" was not tried: it would show the same first rows and need the same second read, so it is expected to fare no better. Cold start and RSS on the 100k repo unchanged (~78 ms, ~74 MB). The `Details ─ Changes` header match in `measure.sh` was updated to the title layout of #198 (the details metric returned nan since then).
